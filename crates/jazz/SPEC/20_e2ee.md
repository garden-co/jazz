# jazz — Specification · 20. End-to-end encryption

## Overview

This chapter defines optional end-to-end encryption (E2EE) for logical table
values in Jazz-tools. It owns key management, cryptographic transformation and
encrypted-result completeness. Jazz continues to own accounts, transaction
acceptance, row authorisation and sync. Groove continues to own large-value
representation and storage.

The initial delivery targets browser and native Node. React Native is a
follow-up. The large-value cipher interface is part of this design; integration
depends on the separate streaming and replacement work described in
[chapter 19](19_large_values.md). This chapter does not add storage backends.

Invariant digest:

- `INV-E2EE-1`: encryption does not replace ordinary Jazz authorisation.
- `INV-E2EE-2`: recipients are accounts or groups; devices belong to accounts.
- `INV-E2EE-3`: a row's space is derived from a stable scope and reference value.
- `INV-E2EE-4`: scope creation, initial recipients and initial encrypted data
  have one atomic accepted outcome.
- `INV-E2EE-5`: new membership and epoch activation require authoritative
  exclusive acceptance.
- `INV-E2EE-6`: authenticated application readiness is independent of key readiness.
- `INV-E2EE-7`: synchronous write handles include deferred preparation.
- `INV-E2EE-8`: encrypted logical results have explicit completeness and errors.
- `INV-E2EE-9`: encrypted equality indexes are opt-in and scope-constrained.
- `INV-E2EE-10`: cryptographic adapters are replaceable through versioned interfaces.
- `INV-E2EE-11`: encrypted files use the ordinary large-value substrate.
- `INV-E2EE-12`: rotation preserves history and cannot revoke previously held secrets.

## Details

### 20.1 Ownership and authorisation

`INV-E2EE-1`: E2EE MUST preserve ordinary Jazz row authorisation and MUST NOT
treat possession of an encryption key as permission to read or write a row.

[Chapter 7](7_authorization.md) owns policy evaluation. Policies can inspect
plaintext old/new values and authenticated authorship, but cannot inspect
encrypted logical values. Permission-relevant fields remain plaintext.
An authorised writer may lack a key; this prevents preparation of a valid
encrypted write without changing its Jazz permission. Conversely, an authorised
writer can submit opaque invalid data. Encryption authenticates ciphertext,
not arbitrary application-level validity.

The implementation is one logical-operation module in Jazz-tools, beneath
typed operations and above physical Jazz rows. Its interface covers writes,
queries and materialisation, including nested results. React hooks and file
helpers do not implement separate encryption logic. Native Rust and browser
adapters implement cryptography without duplicating the recipient graph or
query semantics.

The transform preserves [representation ownership](18_representation_ownership.md):
Rust remains responsible for physical query execution and maintained results.
The E2EE module compiles logical encrypted operations into ordinary physical
operations and materialises decrypted results. It does not create another peer
sync format or treat remote terminal results as source truth.

Managed account/device relations have package-defined ordinary policies.
Package-defined read policies expose group topology (group IDs, membership
edges and epoch metadata) to every authenticated account in the application.
This does not disclose plaintext keys or grant access to protected data.
Applications retain group/space administration and write policies. The optional
`p.fromEncryptionSpace()` derives ordinary read/write policy from effective
recipients. It and an explicit application policy are alternatives; they do
not merge implicitly. Administration authority is specified separately from
permission on protected application rows.

The administration surface is `db.e2ee.devices`,
`db.e2ee.groups`, `db.e2ee.spaces`, `db.e2ee.recovery` and
`db.e2ee.explain(target)`. It belongs to the authenticated `Db` context, not
the shared `app` schema object. Keys, caches and lifecycle operations must remain
isolated between clients that share a schema. It requires an authenticated Jazz account and
ordinary authorisation for each operation. Group add/remove methods take
`(groupId, recipientId)`; space grant/revoke methods take
`(scope, identifier, recipientId)`. Group-instance convenience methods are
not required for the initial implementation.

### 20.2 Accounts, devices and recovery

`INV-E2EE-2`: An account recipient MUST use its application-scoped Jazz account
ID; acting provider identity and device ID MUST NOT substitute for that ID.

[Account admission](ACCOUNT_HANDLES.md) owns account and principal semantics.
A change between linked acting identities does not change encryption membership.
Groups contain account IDs or other group IDs. Public add/remove operations
take a group ID and a recipient ID; the implementation resolves the recipient
kind without caller-supplied account/group wrappers.

Each device generates an independent recipient keypair. Immutable device-key
records bind the application, verified author account, device, key fingerprint,
mechanism/version and creation transaction. The implementation consumes verified
authorship, not a self-asserted account field.
Each device also generates an independent signing keypair for lifecycle records.
Its signing key is distinct from its recipient key and shared epoch secrets.
Enrolment and approval MUST bind both public keys to the same immutable device
record and prove possession of both private keys. Replacing either key requires
fresh enrolment; an account-owned row alone cannot establish that binding.

All authenticated participants in the application can read public device keys,
their account binding and mechanism/version, without recipient consent or prior
group/space membership. Readability does not prove approval or grant device
administration or data access. The managed `__e2ee_device_keys` relation contains
these explicit public fields; enrolment challenges and account-key deliveries stay
in separate account-private relations. Public entries are immutable and ordinary
Jazz insert policies require their creator-account binding and every key field to match the
referenced private enrolment request. Projection row IDs are not device IDs;
concurrent publication can produce equivalent entries for one device.

All authenticated application participants may also read a key-free device
approval/revocation ledger. This exposes the initial account/device binding,
subsequent device-membership changes and their verification metadata, including
ordinary Jazz provenance. Challenges and encrypted key deliveries remain
account-private. A public key or an unverified ledger proposal MUST NOT confer
membership. Cross-account grants require complete, authority-settled history,
valid device signatures and current eligibility; a stale snapshot or a
caller-supplied active-device list is insufficient.

Ordinary Jazz row provenance remains unchanged: readers can select `$createdBy`
and `$updatedBy`, including the account ID and acting identity's issuer/subject.
A provider subject may contain identifying information. Making public-key records
readable by all application participants also exposes their standard provenance
to that audience. This existing Jazz behaviour is accepted for the initial E2EE
implementation; private provenance is not an E2EE delivery requirement.

New recipient keys must pass the mechanism's seal/open check; signing keys must
pass sign/verify. Both keypairs must pass local storage
format validation before they are saved. Failed generation leaves no retained
record or published request. Corrupt retained keys fail without replacement.

The first device initialises an absent account encryption identity through
authenticated exclusive create-if-absent acceptance. Concurrent initialisers
cannot both establish it. Subsequent devices require exact-key approval by an
active device or a valid recovery path. Approval binds the account, device,
fingerprint, fresh challenge, request revision and approving epoch, and proves
possession of the proposed private key. Missing secrets for an existing identity
never permit silent reinitialisation.

A delivered epoch key must also authenticate the key-confirmation value in its
accepted account identity. Successful decryption of a device envelope alone
does not establish that it contains the correct account key. The confirmation
must come from accepted identity state, not from the delivery being checked.

`devices.list()` separates approval membership from the calling client's ability
to verify key delivery. `state` is `pending`, `active` or `revoked`, based on
verified, authority-settled membership. `keyReadiness` is `verified` only after
this caller authenticates the current account key and the relevant delivery
ancestry; otherwise it is `not-verified`. An approved device may therefore be
`active` with `not-verified` readiness, including when the caller lacks the key
or a delivery fails authentication. `not-verified` does not itself establish
corruption, and `verified` does not prove another device retained its private
key. Revoked devices are never reported with verified readiness. Neither listing
field bypasses the existing cryptographic checks for key use or distribution.

Device approval uses a fresh sealed challenge and a context-bound response before
publishing a key-free approval record. The client waits for that record's global
acceptance before sealing the account key for delivery. Invalid account-owned
records do not establish encryption membership or override valid approvals.
The initial-epoch implementation and durable contexts are specified in
[the account format](E2EE_ACCOUNT_FORMAT.md#device-approval-records-version-1).

Local-first authentication can derive a domain-separated recovery protector
from its existing random secret. Recipient keypairs remain independently
generated. External authentication does not assume a JWT/session is an
exportable recovery secret; it uses device approval or explicit client-only
recovery material. There is no recovery password derivation.

`recovery.status()` reports whether recovery is configured, available devices,
and missing or invalid recovery records that the client can establish. Accepted
registration and the presence of encrypted key material do not prove that the
user retained an externally exported recovery secret or that recovery will
succeed. Distinguish configured recovery from a path validated with available
material; do not report an unchecked registration as proven recoverability.
For local-first protected recovery, the client can retrieve and validate the
protected material. Report only the account/group/space paths and accepted state
actually checked; checking an account path does not prove every group or space path.
Status inspection does not introduce an approval step or enrol a device.

The implementation reports `configured`, accepted `activeDeviceIds`,
`recoveryRootIds` and the checked account `epochId` (null before initialisation).
An active device ID describes an accepted registration, not an online device.
`status(material)` validates explicit recovery material; local-first `status()`
tries the retained protected material when recovery is configured. Account
validation is `validated` only after matching an accepted root, opening the
current epoch delivery and authenticating its key history. `validatedRootId`
identifies that root. The result describes the reported epoch snapshot, not a
guarantee against later membership changes. Other registered roots are not
implicitly validated. External-auth inspection without material reports
`not-checked`; authentication alone cannot prove retention of the exported secret.

Missing/unusable protected material, invalid explicit material and unavailable
history reject inspection rather than producing a successful validation or an
unconfigured result. Recovery inspection shares the recovery-use checks but has
no device handshake responder, does not stage keys and clears temporary private
buffers. With the group schema installed, inspection also replays current
effective group membership, including inherited paths. `groups.validation` is
`checked` and `groups.paths` lists each required group ID and epoch with either
`validated` or `unavailable`. Unavailable paths distinguish
`missing-recovery-delivery`, `unusable-recovery-delivery` and
`maintenance-required`; inspection does not repair them. An unusable delivery
means none could be validated, not proof that the stored ciphertext is corrupt.
Removed memberships are excluded. Without group schema or recovery material,
group coverage is `not-checked`. These results are snapshot evidence for the
selected recovery root, not a promise about later membership changes or other
registered roots. An account epoch change during group inspection requires retry.

Recovery-specific inspection failures expose `E2eeRecoveryError` from
`jazz-tools/e2ee`, with a stable `code` and fixed human-readable text:
`recovery-material-unusable`, `recovery-root-mismatch`,
`recovery-delivery-missing`, `recovery-delivery-unusable`,
`recovery-protector-missing`, `recovery-protector-unusable` and
`recovery-state-changed`. Missing means no applicable record is available in
the client's accepted view, including records hidden by policy. Unusable means
validation did not succeed; it does not establish whether the stored material
or the crypto adapter failed. Private parser/adapter errors are not attached as
causes to these diagnostics. Database, history and lifecycle failures retain
their existing rejection semantics and are never reported as unconfigured
recovery. Shared delivery/protector checks also use these codes during recovery
use; this does not change enrolment or authorisation.

Lifecycle types (`E2eeConfig`, `DeviceInfo`, `RecoveryStatus`) are exported from
`jazz-tools`, alongside the database interfaces they describe. The standalone
`jazz-tools/e2ee` entry point contains the independent crypto interfaces and
`E2eeRecoveryError`; importing it must not pull database-schema dependencies
into an isolated crypto consumer's declarations. Package checks require fresh
`build:runtime` output, not only rebuilt native/WASM artifacts.

A retained recovery root can recover again after a device key is revoked.
Revoking that device key does not revoke the root. If every key holder and
recovery path is lost, ordinary account authentication cannot reconstruct data.

With the space schema installed, recovery creation also backfills and verifies
existing effective space memberships. Explicit and local-first protected use
restore space keys through accepted recovery deliveries, not through account
authentication alone. The current epoch and complete predecessor-key history
are authenticated before private retention. Removed memberships and sealed
spaces are not restored. Space loading revalidates current eligibility before
using a retained key, and Jazz continues to authorise delivery and rotation
writes. Private retention permits reopening a recovered read-only device.
The format and storage contract are defined in
[space recovery](E2EE_SPACE_FORMAT.md#space-recovery-delivery-transcript-version-1).
`recovery.status()` now reports `spaces.validation` as `checked` with `paths`
when material and the space schema are available, or `not-checked` otherwise.
Each path names the portable `scopeId`, scope-row `identifier`, internal
`spaceId` and accepted `epochId`. It reports `validated`, or `unavailable`
with `missing-recovery-delivery`, `unusable-recovery-delivery` or
`maintenance-required`. It discovers required paths from accepted membership,
not just existing recovery envelopes. Removed memberships and sealed spaces
are excluded. Unusable means no candidate passed validation, not proof of
ciphertext corruption. Validation applies to the selected recovery root and
reported epoch; an account epoch change during inspection requires retry.
The reader uses public history without a device or local-store dependency.
It does not enrol, retain keys, publish deliveries or perform maintenance.
Recovery creation, inspection and use share the same discovered-root validation.
A malformed root transcript or a checked root-signature mismatch does not
establish a space and is ignored during recovery discovery. Signature checking
uses the creator's supported verification key and accepted membership before
the root's settlement position. Missing creator history/verification keys,
unsupported mechanisms, operational failures and incomplete membership under
a genuinely signed root still fail closed; they are not treated as absence of
recovery obligations. Direct space operations continue to reject invalid roots.
Native and Chromium space-recovery fixtures accompany the implementation; current-source qualification is recorded in the owning PRs, not inferred from historical stage receipts.

### 20.3 Schema and space identity

`INV-E2EE-3`: Each encrypted row MUST select one immutable space using the stable
target-table scope of a required plaintext reference and that reference's value.

The `.encrypted(...)` table modifier declares encrypted columns, a space-reference column and
optional equality indexes. For example, an encrypted todo whose space reference
is `projectId` uses the referenced projects table as scope and the project row
ID as identifier. Multiple tables referencing that same scope/identifier share
the space. It has its own key history; it is not itself a group.

The logical transform derives a stable internal space address from the
application identity, stable scope ID and canonical identifier. Field framing
is unambiguous. Public grant/revoke operations use scope, identifier and an
account or group ID; they do not expose internal space addresses or epoch keys.

The stable scope ID is the catalogue authority's `GlobalPhysicalTableId` for
the referenced table lineage, carried by `PhysicalIdentityManifest`. It is
not the table's display name, structural schema hash or node-local
`PhysicalTableId`. A compatible table rename retains this identity; a newly
created lineage does not inherit an old space even if its name and row ID
match. The common E2EE layer resolves the supplied scope against the accepted
catalogue descriptor. If that identity is unavailable, preparation waits or
fails explicitly; it MUST NOT invent a name-derived replacement. Resolving
this identity does not itself authorise a grant or initialise a space.

Jazz-managed IDs and references remain plaintext. Omitted encrypted-column
selection means eligible application columns only. Encrypted values use LWW
semantics; encrypted references, server defaults, uniqueness and unsupported
merge strategies are rejected. Values needed by joins or policies remain
plaintext. Ordinary updates cannot move a row to another space.

### 20.4 Creator default and atomic initialisation

`INV-E2EE-4`: Creating a scope, its initial grants and its initial encrypted data
MUST have one atomic accepted outcome; rejection MUST NOT leave accepted
partial state from that operation.

Scope creation establishes explicit initial recipients. When the creation
flow supplies none, the authenticated scope-row creator is the recipient.
The explicit grant materialises the space. Explicit recipient sets replace
this default. A later encrypted writer cannot acquire creator membership
because space metadata is absent from its local replica.

Ordinary `insert` and `upsert` options accept
`{ initialRecipients: [accountIdOrGroupId, ...] }` when creating a registered
scope row. The list is copied before returning, must be non-empty and replaces
the creator default. Upsert rejects this option for an existing scope; use
the space grant/revoke methods to change its recipients. Other tables reject
the option.

For multiple initial recipients, the root and all initial add grants share one
accepted transaction. The root names one required initial grant; additional
initial grants must have the same author account, device, account epoch and
space epoch. Each signature and recipient epoch is verified against covered
history. A same-transaction removal or successor is not an initial grant.

The initialising device necessarily knows the first secret it generates.
Excluding its account from recipients does not erase that knowledge. It may
deliver that first epoch after acceptance, but initial authorship does not
confer recipient membership, successor authorship or replacement keys.
If that delivery is interrupted, the same still-active initial device may
resume it from its author envelope after rechecking accepted state. Its account
epoch must still match the initial author epoch, with no pending rotation or
stale group epoch. An excluded initialiser still reports non-recipient status;
resuming delivery must not make it ready or restore a creator grant.

The schema compiler records registered scopes, including scopes whose own
columns are plaintext. The creation transform includes the grant in the
enclosing operation rather than an after-commit callback. Existing scope rows
may predate the encrypted table declaration and therefore have no space yet.
For such a row, the first authorised encrypted write MUST initialise the absent
space and grant its writer's account access. It MUST NOT implicitly grant the
original scope-row creator access. The app may share with that account or a
group explicitly. Ordinary Jazz policies must authorise both the initialisation
and the data write; write permission alone does not bypass administration policy.

The first write, root and initial grant MUST have one atomic accepted outcome.
Space absence must be established through authoritative exclusive validation,
not inferred from missing local metadata, a refused read or unavailable keys.
The internal root row ID is stable for `(scopeId, identifier)`. It uses the first
16 bytes of SHA-256 over UTF-8 JSON `["jazz.e2ee.space-id.v1", scopeId, identifier]`,
with UUID version 8 and RFC variant bits set. Scope IDs are accepted physical
table lineage IDs, not display names. Epoch and grant IDs remain independent.
Creation checks the exact root ID and records an exact-row absence precondition;
a filtered empty query alone is insufficient. Existing metadata read policies
remain unchanged. This replaces random root IDs in the unreleased design; it
does not provide migration of experimental data created with random root IDs.

The encoding is compact JSON, with no whitespace, BOM or trailing newline.
Both coordinates are lowercase UUID-shaped strings, so escaping and non-ASCII
input are outside this format. These fixed receipts pin the UTF-8 preimage,

Competing first writers cannot establish separate accepted spaces for the same
scope and identifier. A losing operation must not retain accepted partial data
or activate its proposed epoch. Existing, revoked or intentionally emptied/sealed
spaces never reacquire a default grant. Reads do not initialise spaces.

Standalone encrypted inserts and upserts MUST handle first-use initialisation
automatically behind the existing synchronous mutation facade. The returned
wait handle owns the atomic acceptance of the space, grant and data. An explicit
mergeable transaction that needs to initialise a space MUST reject the whole
transaction with guidance to use `beginExclusiveTransaction()` or
`exclusiveTransaction()`. It MUST NOT silently convert an already-open
transaction, replay an application callback or separately commit the space.
Explicit exclusive transactions support initialisation and encrypted data in
one accepted outcome. Writes using existing spaces retain their current
transaction semantics; non-E2EE mutations are unaffected.

First-write initialisation for pre-existing scopes is implemented. Node-hosted
checks cover acceptance, rejection, hidden existing spaces and competing first
writers; Chromium also covers first writes and hidden existing spaces.
See [release qualification](https://github.com/garden-co/jazz/issues/3125) for remaining limits; owning PRs record checks against their exact source revisions.

Transaction-scoped lifecycle preparation is package-internal. Do not add a
public `tx.e2ee` surface or require applications to call transaction-specific
grant methods for ordinary scope creation. The compiler/runtime integration
owns this work behind existing mutation methods and the enclosing wait handle.
Explicit standalone sharing remains available through `db.e2ee.spaces`.

Recipient prerequisites must be loaded before admitting the immutable physical
transaction snapshot. Internal compiler integration can queue opening and writes
while returning provisional rows synchronously. The enclosing wait owns loading,
preparation and acceptance; cancelling before opening must not create a physical
transaction. Loading later must not silently replace an already-observed snapshot.
Supply initial recipients synchronously when staging scope creation, before
yielding, to include them in automatic prerequisite loading. Once the snapshot opens,
recipients supplied afterwards
must already have accepted histories visible in that snapshot. Otherwise the
whole transaction fails without committing the scope, grants or encrypted rows;
the caller must start a new transaction. A recipient enrolled after the snapshot
opened cannot be included by extending or replacing that snapshot.
Public exclusive transactions on an E2EE-enabled Db may wait for encryption
readiness before opening, including transactions that only write plaintext.
This also applies to registered-scope upserts that turn out to update an
existing row. Internal enrolment and maintenance transactions bypass this
preparation step to avoid waiting on themselves; their authorisation and
acceptance checks are unchanged. Dbs without E2EE are unaffected.

One exclusive transaction can prepare the scope row, grants, initial epoch
and encrypted rows. It may use that provisional epoch privately for its own
initial ciphertext and transactional read-your-writes. The epoch becomes
usable by other operations only after acceptance. Competing initialisers
conflict on absence/current-state reads. A retry resolves accepted state and
re-prepares affected ciphertext instead of reusing a losing epoch.

Sequential independently committed transactions, even with compensating
deletion, do not satisfy this requirement. The initialisation wait includes
authoritative acceptance even when the requested durability tier is local.
Offline initialisation may remain pending. Existing transaction-local and
optimistic observations retain their pending/rejected meaning; they cannot
advertise a provisional epoch as accepted.

### 20.5 Membership and epoch acceptance

`INV-E2EE-5`: Membership additions and epoch activation MUST depend on
authoritative exclusive acceptance; pending additions MUST NOT grant keys
or generated permissions.

Use [exclusive transaction semantics](3_transactions.md) to validate the
accepted predecessor and relevant membership revision, including predicate
conflicts. Durability alone, optimistic visibility and column-LWW ordering
cannot establish activation. Readers require accepted outcome and complete
relevant records, not merely an observed head pointer.

Groups form a DAG with at most eight group-to-group edges on a path.
Authoritative validation checks both cycle and depth constraints against
concurrent additions. Local checks are early feedback only. Authoritative
permission reachability is computed for the account and reused across protected
rows, not traversed independently for every row or trusted from a userland cache.

Observed removal/leave requests may retract local access without waiting for
rotation, subject to ordinary Jazz authorisation and reconciliation if rejected.
Alternate effective membership paths continue to grant access. A departing
recipient requests removal; another eligible client creates its replacement
epoch. An empty lineage without a recovery path is sealed.

An eligible client's reconciliation reads current membership and proposes a
successor with fresh secret material. Before acceptance, pending recipients
must not receive wrappers disclosing historical secrets. Use accepted-only
delivery or keep these wrappers privately staged until acceptance; optimistic
replication alone is insufficient. Rotation epochs cannot encrypt ordinary data
until accepted. The private initialisation case in §20.4 is the sole exception.

#### Device-authenticated lifecycle records

Successor proposals MUST carry a device signature covering the complete proposal,
including its application, lineage, predecessor, successor, membership revision
and signing-device identity. Clients verify the signer against accepted device
membership and the exact predecessor/membership state used for the transition.
A removed device retaining account access and predecessor keys MUST NOT be able
to establish a successor or re-enrol itself through those retained keys alone.
Stale or replayed proposals cannot activate against a different accepted state.

Jazz's verified account/acting identity and a shared-key authenticator do not
identify an individual E2EE device. Device signatures supply that cryptographic
authorship, not ordinary row permission or transaction acceptance. Both Jazz
authorisation and authoritative exclusive acceptance remain required. A valid
signature alone does not establish membership or recovery authority; recovery
must use its separately validated recovery path.

Existing-space offline writes use the latest locally known accepted epoch.
A device already proven revoked by a complete accepted account history must
remain refused; an older retained space or group snapshot cannot restore it.
An unfinished transaction or unverified revocation proposal is not such proof.
Pending local updates or deletions must not hide accepted history when deciding
whether retained encryption membership remains usable offline.
Known-stale writes warn by default; an application may request local rejection.
Configure `e2ee.staleWrites: "reject"` to reject these writes locally with
`maintenance-required`; omitting it (or selecting `"warn"`) emits a console
warning before preparing the offline write. The warning explains that removed
recipients may still decrypt data encrypted with the retained epoch. This
choice applies to write preparation, not read readiness or explicit inspection,
and never permits a removed member or a proven revoked device to regain access.
Warning mode still requires complete, coherent accepted membership history.
If locally observed accepted metadata has changed since the retained snapshot,
the client must refresh that history before offline reuse; a partial observation
does not establish continued membership.
An offline operation rejects with `key-unavailable` when the changed history
cannot be coherently verified. If complete accepted history proves that the
account is no longer a recipient, it rejects with `key-not-shared` instead.
Background reconciliation may establish that proof before disconnection;
tests that do not control its completion must allow either rejection, never
successful access. Tests with controlled history still assert the specific code.
This does not alter ordinary server authorisation. Reconnect, membership
changes and affected operations trigger idempotent reconciliation, one lineage
at a time. Child rotation can make parents stale; maintenance is not a
general-purpose job queue.

### 20.6 Readiness, handles and transactions

`INV-E2EE-6`: E2EE key readiness MUST NOT gate authenticated access to the
whole application or unrelated plaintext operations outside the exclusive
transaction preparation boundary described above.

Device approval/status and plaintext data remain accessible under ordinary
policies. Exclusive transactions on E2EE-enabled Dbs have the explicit readiness
dependency above; this is not an application-wide access gate.
Encrypted operations use normal loading/error reporting while keys
are unavailable. No second global sign-in or unlock requirement is introduced.

`INV-E2EE-7`: Synchronous mutation handles MUST register pending preparation
before returning and MUST include its completion or failure in their wait result.

Normal mutation methods remain synchronous. `wait({ tier })` covers key lookup,
cryptographic preparation, physical submission and requested durability.
Control activation and initialisation additionally require authoritative
acceptance. A wait cannot succeed because its physical write is not yet
registered. Unawaited calls promise no completion.

The lifecycle must request `wait({ tier: "global" })` on its exclusive control
transactions before activating an epoch. A no-argument exclusive wait may use
local durability when no upstream is configured; that fallback does not prove
authoritative acceptance. A caller requesting local durability does not weaken
the lifecycle's activation requirement.

Transactions queue preparation in call order. A dependent read drains earlier
preparation and commit drains all preparation before submission. Transaction
operations use the transaction result's wait. Exclusive input may be prepared
locally before submission; the authority does not hold an open transaction
while a client supplies a file or obtains keys. Validate read dependencies at
acceptance. Plaintext-only updates and deletion do not need encrypted-cell keys.

### 20.7 Queries and indexes

`INV-E2EE-8`: Encrypted logical results MUST distinguish incomplete work from
complete data and explicit failure; missing keys MUST NOT produce missing
rows, partial success or a definitive empty result.

Keep the existing `useAll` loading/data/error shape. Encrypted field types
remain their logical types. Structured E2EE errors distinguish transient key
unavailability, no shared key, ordinary permission refusal, unsupported formats
and invalid ciphertext. Device status exposes actionable approval requirements.
Diagnostics reveal no key material or large-value locators.

Materialisation accounts for the physical snapshot frontier, required history,
key dependencies and verified candidates. Point reads, projections, includes,
unions, counts, pagination and subscriptions share this contract. A new
subscription frontier with unresolved dependencies returns loading rather than
unlabelled stale or partial data. Physical access is explicitly raw/opaque and
does not masquerade as a decrypted logical row type.

`INV-E2EE-9`: Encrypted equality indexing MUST be opt-in, scoped to a space,
and followed by client-side verification of candidate plaintext.

Tokens bind space, column and epoch through domain-separated keyed derivation.
Stored ciphertext/index data identifies its epoch. A query generates the
tokens required for every relevant historical epoch and rejects an encrypted
predicate without the plaintext space constraint. Logical limits/counts apply
after candidate verification; unresolved history cannot prove exhaustion.

For a payload enum, the public `match` operator can express whole-value equality
only when it names a known case and explicitly supplies every payload field.
Encrypted queries lower that complete match to the existing whole-cell equality
index. A case-only or partial payload match is unsupported when fields remain
unspecified; it MUST NOT be treated as an equality value with missing fields
defaulted. No per-field payload index is implied.

Equality/frequency and query patterns are disclosed by indexing. There is no
encrypted ordering, range, prefix, fuzzy or full-text search in this version.
Joins use plaintext columns. Unsupported upsert and unknown logical-plan
variants touching encrypted tables fail closed.

The implemented equality path fetches physical candidates without a physical
limit or offset, authenticates and compares their logical values, then applies
logical pagination. It decrypts included children only for selected matching
parents. A nonmatching candidate's unreadable child cannot invalidate a result
that does not include that child. The current public query API has no separate
`count()` method; counts here mean the cardinality of verified logical results.

Subscriptions track the spaces required by their results, plus the caller's
device/account and relevant group history. A changed epoch requires new search
tokens; revocation or unavailable history cannot publish a successful partial
result. Completion or failure from a superseded frontier cannot replace a newer
result. Unsupported encrypted hop, gather, union and partial-value plans reject
through read, transaction and subscription boundaries. Plaintext-only projections
of included encrypted tables do not require encryption configuration or keys.

The independently replaceable `EqualityIndex` adapter supplies deterministic
tokens; the common layer owns context, value encoding and candidate comparison.
[The equality format](E2EE_EQUALITY_FORMAT.md) pins its built-in mechanism,
canonical logical bytes and disclosure limits.

### 20.8 Cryptography and BYOC

`INV-E2EE-10`: The built-in cryptography MUST remain replaceable through
versioned CellCipher, KeyEnvelope, DeviceSigner, EqualityIndex and LargeValueCipher interfaces.

An optional `JazzCrypto` selects each adapter independently; omitted adapters
use their defaults. Interfaces accept key bytes and canonical authenticated
context. Non-exportable key handles are outside this version. Adapters cannot
redefine account identity, scope resolution or routing semantics.

`DeviceSigner` is an independently replaceable adapter for signing-key generation,
signing and verification of canonical lifecycle-record bytes. Its mechanism and
version are explicit; it does not reuse symmetric epoch authentication or turn
recipient sealed boxes into sender authentication. The common layer owns record
framing, key-to-device binding, replay checks and membership validation. Browser
and native Node implementations require shared positive and rejection vectors.
The built-in signature envelope and version-two local key store are pinned in
`E2EE_CRYPTO_FORMAT.md` and `E2EE_ACCOUNT_FORMAT.md`, respectively. Pending-device challenge proofs now use signatures.
Initial-epoch approvals carry approving-device signatures and readers validate
grant chains rooted in the accepted first device. Account-device successor and
revocation readers also verify accepted ordering, membership revisions and
eligible device signatures. These have focused tests; the initial-epoch approval
chain alone does not establish the successor contract or full security qualification.

The built-in suite uses XChaCha20-Poly1305 for cells and symmetric wraps,
libsodium sealed boxes for device envelopes, and secretstream for files.
Native Rust calls pinned libsodium through a narrow adapter; browsers use
the official libsodium.js build. Both use the same library revision and
cryptographic format vectors. The shipped implementation needs documented
independent audit coverage; the audit of a library is not an audit of Jazz's
protocol or its bindings.

The common implementation owns canonical context and derivation conventions.
Context binds application, policy, scope, row, table, column, epoch and mechanism
as applicable to each operation. Derivation separates algorithms and purposes.
Sealed boxes bind context inside their authenticated plaintext because they do
not take a separate associated-data input. Nonces and per-value stream material
must not be reused across replacements.

Every durable envelope has an explicit stable mechanism ID and version.
Authoritative encodings, field order, KDF labels and rejection rules must be
specified and pinned by byte-level vectors before persistent writes are enabled.
Do not adopt an incidental serializer layout. Unknown versions fail closed.
Readers precede writer transitions; changing cryptographic meaning requires a
new version. Custom adapters must be installed on every relevant client.
Conformance checks interoperability and failure behaviour, not cryptographic
strength; custom implementations retain responsibility for their security.

### 20.9 Large values

`INV-E2EE-11`: Encrypted large values MUST use the ordinary large-value
publication and storage contracts with bounded-memory cryptographic streaming.

The physical large-value kind is bytes: Groove receives ciphertext, never
plaintext text/JSON that it must interpret. E2EE record framing is independent
of transport/chunk boundaries. Groove owns chunking, descriptors, locators,
integrity, storage, leases and reclamation. Jazz owns authorised locator
disclosure and owner-row publication as specified in
[chapter 19](19_large_values.md); E2EE adds no per-fetch authorisation registry.

A reader may consume individually authenticated plaintext chunks immediately.
Whole-stream success requires the final authenticated tag; truncation or
corruption terminates with an error even after a prefix has been consumed.
Cipher adapters propagate cancellation/errors and respect backpressure.

Writes replace the whole encrypted value without reading/diffing prior
plaintext or merging its contents. Complete staging and atomic owner-row
publication precede successful wait completion. The same atomic outcome
applies when a new scope and its first file are created together.

The initial work defines/tests this cipher interface. Production file
integration awaits the generic streaming/replacement path and its host
transport; a whole-value fallback cannot claim bounded memory. No S3 or other
storage backend is added by this chapter. Arbitrary plaintext range reads and
incremental encrypted-file edits are outside this version.

Locator disclosure is a capability under chapter 19. Revoking row access does
not claw back a previously disclosed locator. Encryption protects plaintext
from a locator holder without its key; possessing a disclosed locator and an
old key can still permit old-data access. Do not promise a fresh row-policy
check on every chunk fetch.

### 20.10 History, migration and security limits

`INV-E2EE-12`: Rotation MUST preserve legitimate encrypted history and MUST NOT
claim retroactive revocation of plaintext, locators or keys already obtained.

A successor wraps its predecessor secret with authenticated lineage context;
current recipients can walk backwards. Additions share that available history.
A different historical audience requires a different space. Ordinary rotation
does not rewrite old ciphertext.

This version does not add an encryption-migration framework. Ordinary schema
migrations MUST reject unsupported in-place changes to encryption configuration;
they MUST NOT silently reinterpret plaintext as ciphertext or vice versa.
Servers do not hold the keys needed to transform encrypted data.

Converting existing data requires an explicit authorised client workflow:
read the old representation with the required keys and permissions, then write
the new representation through ordinary mutations and await their wait handles.
This applies to encrypting/decrypting existing columns, encrypted index
backfills, changing stable cryptographic identity and moving data between spaces.
Public-boundary tests cover rejected in-place changes, encrypted-column renames,
and explicit copies from plaintext to encrypted data, from encrypted data to
plaintext, and into a new encrypted table and space with an equality index.
These do not establish automatic backfills or a consistent cutover while the
source is being edited concurrently. Display-name changes preserve stable IDs.
Stateful group schemes,
post-quantum envelopes and opportunistic space movement are outside this version.

The threat model includes servers and peers without relevant keys. It does not
hide plaintext schema/references, recipient metadata, ciphertext sizes,
timing or opted-in equality patterns. Authenticated ciphertext cannot prove
that a writer supplied semantically valid application data. Local compromise
can disclose locally held keys and recovery roots.

### 20.11 Implementation status and verification

The implementation is prepared as eleven review layers: versioned crypto adapters; bounded stream ciphers; authority-settled history and portable identities; authenticated devices; independent recovery; groups; spaces; ordinary encrypted operations; equality/nested/live results; offline accepted-history; migrations and legacy-space first writes. This is not merge approval, production readiness, or a security proof.

Declaring encrypted tables MUST compose package-owned managed schemas and policies without granting application-data access or group/space administration implicitly. Explicit lifecycle setup binds to the same application schema and does not mutate the deployed schema at sign-in. Recipient keys, epochs and historical deliveries require the authoritative acceptance and signature checks specified above; internal transaction preparation is not a public `tx.e2ee` interface.

Required executable evidence includes competing initialisers/rotations, accepted-only recipient delivery, verified device authorship, poisoning and replay rejection, independent recovery, all-or-nothing scope/data creation, early waits and transaction error ownership, offline accepted-only observations beneath pending writes, nested permission retraction, query completeness and native/browser byte vectors. Each owning PR records its executed commands and exact revision. Historical implementation-stage receipts are not evidence for an extracted tip.

The [crypto](E2EE_CRYPTO_FORMAT.md), [cell](E2EE_CELL_FORMAT.md), [equality](E2EE_EQUALITY_FORMAT.md), [stream](E2EE_LARGE_VALUE_FORMAT.md) and [accepted-history](E2EE_OFFLINE_HISTORY.md) companions define the named/versioned encodings and pinned corpus. Independent review must cover Jazz framing, context binding, key distribution, authorship assumptions, bindings and exact dependency revisions before general availability. Library assessments and interoperability fixtures are not that review.

Browser/native Node are the target runtimes. RN runtime and encrypted large-value staging/publication/transport are separate qualifications; bounded stream cipher support alone is not encrypted upload support. Membership/history scaling requires measurement independent of protected-row count.
