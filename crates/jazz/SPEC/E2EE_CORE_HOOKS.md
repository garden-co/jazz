# E2EE core hook interface: design note for review

Status: draft for the jazz-core owners, written before any core code changes. It proposes how core provides what the protocol requires; the protocol governs where they differ. A reviewed design is not an implementation qualification: each hook needs its own tests when built. Protocol reference: `crates/jazz/SPEC/E2EE_PROTOCOL.md` (cited as "spec §n"). Paths are relative to `crates/jazz/layers/db/src/` unless they say otherwise. Line numbers are from this branch's tree and are approximate.

Every claim below about core is marked **exists** (present in this tree today) or **to be built**. Nothing E2EE-specific exists in core yet: there is no encryption declaration in the app-file reader, codegen or deploy, no ledger read with accepted positions, no provisional read and no durable transaction fate. Section 4 lists everything to be built.

## 1. Shape of the integration

- **jazz-core stays crypto-free.** jazz-core (`jazz-db`) defines a small _synchronous_ hook trait, `E2eeHooks`, plus the plain data types that cross it. It calls the trait at the write, read and query seams listed below. A new crate, `jazz-e2ee-client`, implements the trait on top of `crates/jazz-e2ee` (formats and primitives) and the protocol state machine. That crate depends on jazz-core; jazz-core never depends on it or on `jazz-e2ee`.
- **The hooks never await.** Everything asynchronous lives in the client runtime _above_ `Db`: key acquisition, deliveries and rotation (spec §3.3–§3.5), preparing a space root (spec §3.2), private-store I/O, and watching member rows, deliveries and chains. That runtime uses ordinary `Db` reads, subscriptions and transactions. The sync hooks only use state already in memory (held keys, prepared roots, replayed chains). When they lack something they return a typed "needs key" outcome, the caller awaits the runtime, and then it retries the single staging call.
  - Exists: the bindings run each operation to completion (binding_host.rs:9, "The database runs every operation to completion synchronously"; `Binding::insert` at :1076 calls `block_on(self.db.insert(..))` at :1085).
  - Exists: `Db::transaction` (db.rs:3603) is `async` and takes an `AsyncFnOnce(&mut MergeableTx<'_>)` callback, so a staging call inside it can await the runtime and retry; the callback itself is not replayed (spec §5.6).
- **The server never runs the trait.** The server-side work is system-table registration (the members table included), derived policies at deploy, the deploy check of each space table's read rule, one new policy node, `InheritsFrom`, one new policy value, `TableIdentity`, a system-table write guard, the scoped relaxation of join validation for system tables, multi-column correlation in sync support, and the pre-state check of deletes (H7; section 4, items 15–17). It is ordinary deploy and policy code, not behind the client feature. There is no E2EE-specific authority request and no native validator.

```rust
// jazz-db, behind cfg(feature = "e2ee-client"). Lives on the Db thread: Rc, !Send. To be built.
pub trait E2eeHooks {
    fn declarations(&self) -> &E2eeDeclarations;                        // H1
    fn seal_write(&self, w: &mut WriteCells<'_>) -> Result<(), SealError>; // H2
    fn open_rows(&self, site: ReadSite, rows: &mut Vec<CurrentRow>)
        -> Result<OpenOutcome, Error>;                                   // H3
    fn plan_query(&self, q: &Query) -> Result<QueryPlan, Error>;          // H4
    fn seal_stream(&self, t: &StreamTarget<'_>)
        -> Result<Box<dyn StreamSealer>, SealError>;                     // H5
    fn open_stream(&self, t: &StreamTarget<'_>, header: &[u8])
        -> Result<Box<dyn StreamOpener>, Error>;                         // H5
}
pub enum SealError { NeedsKey { space: SpaceAddress }, SpacePending { space: SpaceAddress }, Refused(Error) }
pub struct OpenOutcome { pub unreadable: Vec<Unreadable>, pub missing_epochs: Vec<(SpaceAddress, EpochId)> }
```

The hooks are installed with a new `DbConfig::with_e2ee(Rc<dyn E2eeHooks>)` (to be built), next to the existing `with_id_source` and `with_clock` (options.rs:80, :108). An `Option` that is `None` costs one branch per call site.

## 2. Hooks

### H1. Declarations from app files, at open

- **Today (exists).** Nothing: the app-file reader (`crates/jazz/src/tools/deployment/artifact/app_file.rs`, `read` at :166, `read_tables` at :297) has no `encryption` entry, codegen and `jazz-app` know nothing of encrypted columns, and the loaders `load_client(json) -> Result<Migrations>` and `load_client_current(json) -> Result<(Schema, Migrations)>` (`crates/jazz/src/tools/deployment/artifact.rs:773`, :783) return schema and migrations only. `DeployRequest` (`crates/jazz-server/src/server/deployment.rs:16`) carries `target_schema_hash`, `schemas`, `migrations`, `permissions` and `allow_dropping_history`.
- **To be built.**
  - The reader parses each table's `encryption` entry (spec §1.5; with the conversion fields of [migrations](E2EE_MIGRATIONS.md) §3.2) and the top-level `encryption` settings (`allowAccountReset`, mechanisms). It keeps them outside `Schema`, so outside the schema hash, and records them in every schema version (`history`).
  - It refuses a `scope` that is not a table with an `id`, a `space` that is not `id` (with `scope` the table itself) or a `uuid` column referencing `scope`, an in-place encrypt conversion of a nullable plaintext column (migrations §3.2), a merge strategy on an encrypted column (spec §1.5), and any app table or `jazz.permissions.json` entry with the reserved prefix `__e2ee_` (in `read_tables` and `permissions_file::read`, `permissions_file.rs:25`). It also refuses an app relation (a declared reference) to a system table, and an app policy that inherits through one (`Inherits` or `InheritsReferencing` reaching a system table), so no application policy reaches a system table's policies, and with them `InheritsFrom`; an app `exists` over the members table stays allowed (H7). Deploy and codegen share the reader, so both refuse.
  - `load_client_current` (or a sibling) also returns `E2eeDeclarations`: the entries, the settings, the app ID and the environment label. The client runtime builds its hook object from them, and the binding passes it to `DbConfig`.
  - Codegen hides the ciphertext and `__e2ee_eq_*` columns of encrypted tables and exposes the plaintext types.
  - `DeployRequest` gains `encryption` (every version's declarations and the settings).
- **Space row read rule (spec R13; refusal).** After compiling permissions, the deploy checks the select policy of each space table `T` named as `scope` by an entry with at least one encrypted column: it must be `M(T)` or an `And` with `M(T)` as one of its direct conjuncts, where `M(T)` is exactly `Exists { table: "__e2ee_members", condition: And[scopeId = TableIdentity(T), identifier = this.id, accountId = session.user] }` (conjuncts in any order). Anything else (an `Or`, `M(T)` under a `Not`, an `M` naming another table, no `M`) is refused, naming the table. The check is syntactic and exact, so it is decidable.
- **Deploy warnings (spec §1.5).** The deploy compares each encrypted table's select policy with its space table's, syntactically, in both directions: it warns when it can see that the space row is readable more broadly than the encrypted table (for example, the table's policy is the space table's policy conjoined with further conditions), when the encrypted table is readable more broadly than its space row (for example, its policy does not involve the space row), and when a space table's read rule does not yet come from the members table (an entry without encrypted columns, migrations §4.1), when a space table's update policy requires an old-to-new transition (which admits no member change, creation or rotation, spec §1.4), when a space table's update policy is broad (an update clause that is `true`, exactly `M(T)`, or reads no session value and no `$createdBy`: every member, or every reader, then manages members, spec §1.5), and when a space table's insert policy reads `__e2ee_members` for the row being inserted (no member row can ground it, spec §1.5, R12). It never claims more.
- **Catalogue identities.** Cell contexts need Jazz's stable table and column IDs (spec §4.1). Exists: `Db::table_identity(&str) -> Result<Option<GlobalPhysicalTableId>>` and `column_identity` (db.rs:2209, :2219). `GlobalPhysicalTableId` wraps a `uuid::Uuid` (`crates/jazz/layers/types/src/ids.rs:87`): a version 5 UUID of the authority's namespace (a random UUID minted once by the authority, sync.rs ~6407) and the stored name (names.rs:185). They return "not observed" until the client knows the namespace and the version's names are confirmed, so a first-ever offline open cannot encrypt or decrypt. The runtime should cache confirmed identities in private state; see Risks.
  - **To be built: table identity for app code.** `Db::table_identity` is used by core and tests only; no binding and no `JazzClient` method exposes it, so an application could not fill a member row's `scopeId`. The generated members API takes the space table's name and row ID and fills `scopeId` itself through a new binding call (and `JazzClient::table_identity` for Rust apps and trusted backends), failing with the "not observed" error before the identity is known (spec §1.3). The application never handles the identity.
- **Error and fallback.** An invalid declaration is a deploy or load refusal, never a runtime fallback. A client whose declarations do not match the deployed bundle fails at open.
- **Cost.** Paid once at open.

### H2. Write staging: plaintext to ciphertext plus equality tags

- **Call site (exists).** The value must be transformed _before_ `Inner::chunk_large_cells` (db.rs:7213). That function content-hashes and chunks large values, and the same mutated op is what is stored and uploaded. A hook at cell binding would encrypt SQLite but not the wire. Concretely, the hook runs in:
  - `Db::write_op` (db.rs:3454), the private entry for `insert`, `update`, `upsert`, `delete` and `restore`, and for `MergeableTx` (db.rs:4522) and `MergeableTxHandle::commit` (db.rs:9038), which replay through it;
  - staging in `TxRef::insert` (db.rs:10743) and its siblings, for handle transactions (`begin_mergeable` / `begin_serializable`, db.rs:9993/:10001) and `serializable_tx()` (db.rs:11183), at staging time, so that a refusal surfaces on the staging call and not at commit.
- **Data crossing (to be built).**

  ```rust
  pub struct WriteCells<'a> {
      pub table: &'a str, pub row: RowUuid, pub kind: WriteKind,      // Insert|Update|Upsert|Delete|Move { target_space }
      pub cells: &'a mut BTreeMap<String, Value>,                      // plaintext in, ciphertext out; includes conversion source cells
      pub stored_space: Option<&'a Value>,                             // current row's space cell (updates, moves)
      pub companion_rows: &'a mut Vec<(String, RowUuid, BTreeMap<String, Value>)>, // internal rows staged in the same transaction
  }
  ```

  - The hook replaces each encrypted column's value with `Value::Bytes(cell record)` and adds `__e2ee_eq_<col>` cells.
  - It refuses a change of the space coordinate (spec §5.1) except for `WriteKind::Move`, which re-encrypts every encrypted column under the target space ([migrations](E2EE_MIGRATIONS.md) §4.4), and refuses partial edits of encrypted columns.
  - During a conversion it writes the target and sets the source to null (plaintext) or the cleared marker (encrypted), in the same `WriteCells` (migrations §3.4); a tag backfill writes only the token.
  - Deletes, restores and updates that touch no encrypted column return `Ok` without a key.
  - For updates and upserts, core supplies `stored_space`, the space cell of the current row, which is plaintext; core already loads that row for updates and upserts.
  - `companion_rows` lets the hook stage internal rows (a space root) into the write's own transaction; core inserts them in the same transaction, as the same session (R2), before the write. This is how creation stays atomic with the write without a separate transaction kind.

- **No key (`NeedsKey`).** Core has not applied anything, so the caller awaits `runtime.acquire(space)` (key acquisition, a missing root and a pending rotation, as `db.encryption.acquire`, spec §5.6) and re-issues the same call. In an open transaction only that staging call is retried; the callback is never replayed (spec §5.6).
- **Space creation (spec §3.2, §5.4).** The client never evaluates write policies (exists: a replica runs no write-policy check, `Inner::checked` at db.rs:8140 returns `None` on a client; the only client-side answer is the asynchronous `JazzClient::permission_advice`, `crates/jazz/src/tools/client.rs:1701`, which asks the authority and is `Unknown` offline). Creation is therefore optimistic and needs no advice:
  - an encrypted write to a space with no known valid root and no prepared root returns `NeedsKey`; the runtime prepares the root (online it first reads the address's roots; it generates `K₀`, builds and signs the root, and persists `K₀` as an `unpublished` held key) and the caller retries;
  - on the retry the hook stages the prepared root as a companion row of the write, and seals the write under `K₀`;
  - the authority's R15 decides; a refusal fails that transaction only. The runtime tells a refusal of the root itself from a transaction that failed otherwise, a cancellation before submission and an unknown outcome (spec §3.2). Only a refusal of the root stops automatic creation of the space on this device (in the running client's memory only, lost on restart, spec §3.2); after it, the hook returns `SpacePending` for the space and the caller fails the write `space-pending`, until a valid root exists or an explicit `createSpace` succeeds (spec §3.2). An unknown outcome is reconciled by the transaction's identity, and no second root is prepared meanwhile;
  - inserting a space row stages nothing.
- **Pending rotation (spec §3.5).** When the runtime has marked a space as needing rotation and this device's rotation of it has not been refused while the client runs, the hook returns `NeedsKey`; `runtime.acquire(space)` makes the rotation in its own serializable transaction (successor plus deliveries to the members), waits for its outcome within the write's deadline, and the caller retries. Refused, offline or undecided, the retry seals under the current version. Rotation is never a companion row of the write, so its refusal never fails the write.
- **Epoch choice.** The deepest held key that is not marked `refused` (spec §5.2). It is in memory, so no I/O happens on the write path. A refused key is kept for good and only ever opens cells (spec §3.2).
- **Cost.** A hash-set lookup per write for unencrypted tables. A member-row insert may seal one delivery. For encrypted columns: one XChaCha20-Poly1305 seal per encrypted cell plus a keyed BLAKE2b per equality column.

### H3. Reads: one-shot, query results, subscription deltas

- **Principle.** Ciphertext stays ciphertext inside core: storage, the SQL compiler, fanout's watch indexes and diffs. Decryption happens once, on each materialised result _before_ it leaves `Inner` toward a reader. A dropped row is then simply absent, and fanout's `diff` (fanout.rs:2411) computes correct indices without remapping.
- **Call sites (exist).**
  - `Inner::run_with_deps` (db.rs:5085), after execution. This covers `Db::all`, `read` and their variants, and `all_serialized_query` (sync.rs:15048), which the bindings use.
  - Fanout's materialisation paths that bypass `run`: `Fanout::group_rows` (fanout.rs:1823), `recheck_rows` (:1495) and `stored_images` (:1422). The hook runs on their output, before `diff` and `deliver` (:2122).
  - `Binding::local_current_row` (`binding_host.rs:1410`) and transaction reads run in _strict_ mode (spec §4.4).
- **Data crossing.**
  - `ReadSite { strict: bool, table, query_shape }` and the rows.
  - The hook rewrites encrypted cells in place to plaintext and removes `__e2ee_eq_*` cells.
  - In lenient mode it removes unreadable rows and returns them in `OpenOutcome.unreadable` as `{table, id, column, code, space}`. In strict mode the first bad cell is an error.
  - Short values (spec §4.1): an empty cell reads as the declared default and, when the empty value is stored in the row rather than supplied by the lens for a row that predates the column, is also reported `empty-cell` (core marks lens-supplied defaults on the rows it hands over; to be built); the cleared marker is absent for a converting column and `superseded` otherwise. During a conversion it applies "source if present, else target" (migrations §3.3), decrypting an encrypted source with its own context. A cell sealed under another space of the row is decrypted by its epoch's space, returned and reported `stale-space` (migrations §3.9).
- **Missing epochs.** The hook lists a row needing an epoch the device lacks in `missing_epochs` and reports it provisionally. The runtime acquires the key asynchronously, at most once per read (spec §4.2), and then settles the report to the protocol's code before it reaches listeners: `key-pending` once per space when the account is a member, `key-unavailable` per row when it is not (spec §3.4, §4.3). The hook knows nothing of membership.
  - One-shot reads: `Binding::all` is already async. The binding wrapper awaits the acquisition and re-runs the read once.
  - Subscriptions: after a key arrives, the runtime calls a new `Db::refresh_reads_of(tables)` (to be built), a public wrapper of the private `Fanout::refresh_where` (fanout.rs:1344). Rows that became readable then arrive as ordinary additions.
- **Bounded wait (spec §4.6).** The 10 s wait-for-delivery episode lives in the binding's stream wrapper around the subscription stream. Core keeps diffing against its own baseline while the wrapper withholds, so the wrapper keeps a full copy of the latest result, applying each withheld delta to it, and ends the wait by emitting that copy as one reset event; afterwards it forwards deltas unchanged. On expiry it emits the copy and reports the space `key-pending`. It discards the copy on stop, sign-out and account change. Bindings need a reset event in their subscription stream type if they lack one; core needs nothing new.
- **Limit and offset.** Unreadable rows are dropped after the SQL window (spec §4.3), which is exactly what post-execution filtering gives.
- **Refused here.** The hook refuses relation reads whose nested rows (array subqueries in cells) contain encrypted tables until nested decryption is designed, and splices on encrypted columns.
- **Cost.** This is the main hot-path cost; see Risks. It is mitigated by a per-client decrypted-cell cache. Its key is the hash of the complete authentication input: the cell cipher's full context bytes (`frame[ctx, cellType]`), the identity of the held key used (space root and epoch) and the ciphertext. A hit never bypasses `stale-space` classification or the AAD checks. The cache is cleared on held-key removal (revision change, spec §6.4), on a change of the active schema view, on a change of the mechanism allow-list (spec §0, which closes the owner), and on sign-out or account change.

### H4. Equality-filter rewriting

- **Call site (exists).** `Db::prepare_query_bound` (db.rs:3092), before query validation, and the remote shape a subscription sends upstream (`remote_shape`, sync.rs:8493). The server must receive the _rewritten_ query, because it only ever sees tags.
- **Data crossing.**
  - Input: `&Query`.
  - Output:

    ```rust
    QueryPlan::Plain
    QueryPlan::Rewritten {
        physical: Query, residual: Residual { preds, limit, offset },
        epochs: EpochSetId, incomplete: Option<SpaceAddress>,
    }
    QueryPlan::NeedsKey { space }
    ```

  - `physical` replaces `Eq(col, v)` (or a full enum `match`) with `In(__e2ee_eq_col, [token per held epoch])`, keeps the required plaintext `Eq(space, s)`, and drops `limit`/`offset` (an unwindowed prepared query exists, db.rs ~136).
  - `residual` is applied after H3 decrypts: compare the authenticated plaintext, then window.
  - `epochs` is folded into the query's shape hash, so a new held epoch makes a new prepared query. The runtime re-prepares live subscriptions when its epoch set changes (retry budget of 3, spec §4.5).
  - **Cold queries.** Online, an encrypted predicate on a space for which no epoch is held returns `NeedsKey` instead of an empty `IN`; the binding acquires within the read budget and plans again (spec §4.5).
  - **Incomplete results.** When the known lineage has unheld epochs, the plan sets `incomplete`, and the runtime reports the space once with the protocol's code for its state: `key-pending` for a member, `key-unavailable` otherwise (spec §4.5), exactly as for H3.
  - **Conversions (migrations §3.3).** The physical query has one tag predicate per column, `__e2ee_eq_<source> IN sourceTokens OR __e2ee_eq_<target> IN targetTokens`, and the residual applies source-present precedence. Source tokens are computed only for an identity conversion (re-home, re-encrypt without `convert`) or a re-encrypt with a declared `reverse` mapping, and only when the source is tagged; otherwise, and for encrypt and tag backfill, the query is refused with `conversion-pending` while the space has rows with a present source (or an empty token). That count is an ordinary indexed `Db` read, so the hook cannot run it: the runtime runs it before planning (once per query and space, cached until the space's rows change) and passes the result in through the hook's in-memory state.

- **Refusals (never a scan).**
  - Ordering by an encrypted column.
  - Joins, `reachable`, unions, `partial` selects, or aggregates over encrypted columns.
  - Encrypted predicates other than `eq`.
  - `eq` on an encrypted column without an equality index or without a space `eq`.
- **Offline.** Offline no tokens are computed: the physical query is just `Eq(space, s)`, and the residual does the filtering.
- **Cost.** A query walk at prepare time, plus one BLAKE2b per held epoch per predicate.

### H5. Large-value streaming

- **Call sites (exist).**
  - Write side: the byte path before the large-value chunker, reached from `Binding::begin_streaming_mutation` (binding_host.rs:1811) and the streaming upload functions in large_ops.rs.
  - At begin, `seal_stream` validates the target (only non-indexed `bytes` columns, spec §5.5), selects the epoch and returns a `StreamSealer`.
    - Each `push(&[u8])` returns ciphertext bytes, which go into the unchanged chunker.
    - `finish()` emits the final tagged record.
    - The routing record and header (spec §4.1) are written first.
  - Read side: the range read and whole-value materialisation in large_ops.rs / large.rs.
    - `open_stream` decrypts sequentially. Range reads, JSON-pointer reads, deltas, appends and splices on encrypted columns are refused in the first release. This is a scope decision, not a format limit: STREAM records authenticate individually, so a later range read can seek to a record boundary.
    - A whole read decrypts from the start.
- **Content addressing.** Chunks are hashed after encryption, so there is no cross-row deduplication of encrypted values. This is acceptable, and required for confidentiality.
- **No key.** `NeedsKey` is returned at begin, before any source bytes are pulled (spec §5.5).
- **Cost.** Streaming XChaCha20; memory is bounded by the chunk size.

### H6. Sync arrivals of internal-table rows (key triggers)

- **Recommendation: no new core hook.** The runtime opens ordinary local subscriptions on the internal tables, as the client's own identity:
  - its own account's `__e2ee_members` rows (by `accountId`), which name the spaces it is a member of, and the deliveries addressed to its account (by `recipientAccountId`);
  - its own account's `__e2ee_device_removal_requests` (by `accountId`), so a pending request of another of its devices is completed (spec §2.8);
  - per space it is a member of: the space's member rows (at most 1,000 in a supported space, spec §3.8), `__e2ee_spaces` and `__e2ee_space_successors` (each by `(scopeId, identifier)`), and `__e2ee_space_deliveries` of the versions concerned only, the current version and skipped versions it holds (by `(scopeId, identifier, keyEpochId)`); all readable to members, spec R12, R14. Deliveries of earlier versions are not watched (spec §3.4, §3.8);
  - the public `__e2ee_account_roots` of the members of those spaces, so a member's reset (a new generation, which makes it lack every version) is seen when no space table changes (spec §2.11, §3.4);
  - while a delivery to a member waits for a valid sealing key, that member's `__e2ee_account_keys` rows (spec §2.12, §3.4);
  - only on a device that may act on the needs-rotation mark (it holds the current version and its rotation of the space has not been refused while the client runs, spec §3.5): the public account successors of the members holding the current version, so the mark is re-evaluated on an account-only change such as a `remove-device` successor, even when no space table changed. The delivery transaction reads the rest of a member's account history when it needs it (spec §3.4).
- **Shared account watches.** The public account watches are one subscription per table over the set of accounts needed across all spaces (`accountId IN …`; exists: `Predicate::In`, also on the wire, `WireRelationPredicate::In`, `crates/jazz/layers/model/src/query/relation_codec.rs:650`; `accountId` is indexed, H7), replaced when the set changes, the new subscription opened before the old one closes. Design figure: 10,000 watched accounts per device (spec §3.8); splitting the set is left until measurement shows a need (Main risks). Each decision is made from the results of a watch opened before it, never from a separate read, so nothing changes unseen between the two. An account leaves the set when it is no longer a member of a watched space, or its waiting delivery is made or abandoned.
- From these the runtime computes, per space and in memory, which members lack a version it holds, from each member's current generation (spec §3.4), whether the space needs rotation (spec §3.5), whether the space has no valid root (spec §3.2), and its member count (spec §3.8). Each is a comparison of two indexed per-space result sets, at a cost proportional to the space's members and the current version's envelopes; no anti-join query is needed.
- A new delivery or version triggers acquisition with backoff (spec §4.2). This needs only that the internal tables are in the client's schema (H7) and readable under their derived policies.
- **Alternative.** A raw arrival callback in `Db::notify` (db.rs:3380). It is cheaper, but it puts protocol awareness into core and bypasses policy-filtered visibility.

### H7. System tables, derived policies and `InheritsFrom`

- **Today (exists).** There is no catalogue table with Jazz-owned policies. Jazz accounts are not Jazz tables: `jazz_types::account_registry` is pure logic, and the server keeps its state in raw host SQLite tables (`crates/jazz-server/src/server/account_store.rs`). `_jazz_*` tables are skipped by `stored_schema` (db.rs:1201). The E2EE tables must sync, be queried by clients and be policy-checked, so they need a new category, **system tables**: catalogue tables whose definitions and policies come from Jazz, not the app (to be built).
- **Registration (to be built).**
  - A fixed, versioned schema fragment `e2ee_system_tables_v1()` (spec §1.2–§1.3 columns, `uuid` for every ID, account and address column) is defined in jazz-core, with the indexes of spec §1.3: `(scopeId, identifier)` on every space table, `(scopeId, identifier, accountId)` and `accountId` on `__e2ee_members`, `(scopeId, identifier, keyEpochId)` and `recipientAccountId` on deliveries, and `accountId` / `deviceId` on the account tables, as `composite_indexes` / `indexed_columns` of the table schema (exists: `TableSchema`, `crates/jazz/layers/model/src/model/public_api/types/schema.rs:439/456`). Every table already has a unique `(id, _branch)` index (values.rs:1749), so the space-row lookup by ID is indexed. No fragment column is a reference, since `identifier` names a row of any of several tables.
  - **The loaders add the fragment, not the server.** `prepare_deployment` (`crates/jazz/src/tools/deployment.rs:222`) recomputes the hash of every submitted schema and refuses a mismatch, so the server cannot append a fragment to a submitted schema. Every loader (`load` and `load_backend`, which also compute the bundle ID, and the client loaders `load_client` and `load_client_current`, `crates/jazz/src/tools/deployment/artifact.rs:341`, :423, :773, :783) appends the fragment to every schema version whose declarations include `encryption`, before hashing, so both sides compute one schema and hash. The server's `deploy` (`crates/jazz-server/src/server/deployment.rs:125`) checks that such a schema contains exactly the fragment and refuses it otherwise.
  - **The members table is visible to the app.** Codegen exposes `__e2ee_members` (read, insert and delete; no update) so the app lists and changes members through the ordinary API, and the permissions reader accepts it as the table of an `exists` (only there: an app permissions entry for it is still refused). The other internal tables stay out of generated code.
  - The fragment enters the app's schema hash (decided, D3). Held keys do not depend on the schema hash (spec §6.2), so an app schema change never invalidates them.
- **Where policies are derived (to be built).** Today policies arrive at the server already compiled from `jazz.permissions.json` (`DeployRequest.permissions`). `derive_e2ee_policies(&schema, &decls) -> BTreeMap<Table, TablePolicies>` is a pure function (new, in `crates/jazz/src/tools/deployment/artifact/`) and runs on both sides:
  - **In the loaders that compute a bundle ID.** Exists: `load` and `load_backend` compute the permissions bundle ID locally (`compute_bundle`, called at `crates/jazz/src/tools/deployment/artifact.rs:368` and :501; :1285: "the bundle id the server computes when this backend publishes"), and a backend pins its sessions to that ID (the socket prelude's `bundle`, `crates/jazz-server/src/server/routes/websocket.rs:507`). If only the server merged the derived policies, every encrypted app's locally computed ID would differ from the server's. So `load` and `load_backend` merge the derived policies into the permissions before computing the bundle ID. The client loaders take no permissions and compute no bundle ID; they append the schema fragment only.
  - **On the server.** The deploy request still carries only the app's own permissions. In `deploy`, the server refuses any `__e2ee_*` entry in them, derives the system-table policies from the submitted schema and declarations with the same function, and merges them before staging, so its bundle ID equals the loaders'. The server's derivation is authoritative; a loader whose derivation differs (an older binary) computes another bundle ID, and its backend's sessions are pinned to a bundle the server did not publish (exists: such sessions are refused at admission, "permissions bundle … is not published on this store", `check_session_pin`, `crates/jazz/layers/db/src/sync.rs` ~11217; `superseded_error` is for a bundle that was replaced).
  - **Only Core evaluates read policies.** Core is the only authority ([topology](9_topology.md)): clients and the browser worker relay evaluate no read policy, so the derived read policies and `TableIdentity` are needed only where Core compiles them, and Core always knows its own names. A database that is not the authority but serves subscribers exists only in tests; there an identity binds only once the database's names are confirmed (until then it grants nothing, below), and a subscription's support leaves an unknown identity out of its key (multi-column correlation, below), so it stays complete. It fails closed, never open.
- **System-table write guard (spec R1; to be built).** Exists: policies do not bind every writer. A `system` session compiles every policy to true (compile.rs:2146, :2184), trusted backends and authorities map to the system author (`crates/jazz-server/src/runtime/mod.rs:1394`), and `Who::Local` / `Who::Attributed` writes are unchecked (db.rs:8140). Core therefore refuses, in the write path for every writer and before policies, updates of `__e2ee_*` rows and deletes of `__e2ee_*` rows other than `__e2ee_members`. Inserts and deletes of member rows by a trusted backend bypass policies like any of its writes. E2EE inserts are written with `WriteIdentity::Session` (options.rs:302) so that `$createdBy` is the session account (R2).

#### The `InheritsFrom` policy node

- **Need.** Every internal space row names its space row by two columns: `scopeId`, the space table's catalogue identity, and `identifier`, the space row's ID (spec §1.3). This is a polymorphic soft reference: not a reference column, and not to one table. Exists: `Inherits { operation, via_column, max_depth }` (compile.rs:2417) follows only a reference column to one table.
- **Node (to be built).** A new variant of `PolicyExpr` (`crates/jazz/layers/model/src/model/public_api/policy.rs:58`):

  ```rust
  /// Inherit `operation` from the row named by a (table identity, row id)
  /// pair: `table_column` holds a catalogue table identity, `id_column` a
  /// row id of that table. Only the tables in `tables` are candidates.
  InheritsFrom { operation: Operation, table_column: String, id_column: String, tables: Vec<String> },
  ```

- **Semantics.** For the row under check, it holds iff for some `T` in `tables`: `table_column` equals `T`'s catalogue identity, and a non-deleted row of `T` whose `id` equals `id_column`, as the checking transaction leaves it, passes `T`'s policy for `operation`:
  - `Select`: `T`'s select policy, exactly as a direct read of that row (spec read(row)).
  - `Update`: **both** clauses of `T`'s update policy, against the same row image as old and new row: `USING` **and** (`WITH CHECK`, or `USING` when there is none), the no-op save of spec update(row). Exists: `OperationPolicy { using, with_check }` (`crates/jazz/layers/model/src/model/public_api/types/policy.rs:14`), and an ordinary update checks the new row with `with_check.or(using)` (db.rs ~6566). The node must **not** use `Table::policy(Update)` (values.rs:1248), which returns `using.or(with_check)`, a single clause, and which the existing `Inherits` path uses (compile.rs ~2437).
  - A row naming any other table, or a missing or deleted row, passes nothing.
  - **Deletes read the pre-state.** In a delete's policy (the member-row delete, `IF(Select) AND IF(Update)`), the node reads the space row, and every table `T`'s policies read, in the unit's pre-state (spec R12), not as the transaction leaves it; see "Pre-state delete check" below.
- **Compilation (compile.rs, beside `Inherits`).** An `OR` over `tables`, each disjunct `alias.table_column = <identity of T> AND semi_join(T AS p, p.id = alias.id_column, not deleted, clause(s) of T as above)`.
  - **Identities are resolved on the authority, when the policy is compiled for evaluation.** The bundle stores table names (`tables`), which are stored names within the bundle's schema; the compiler resolves each to its `GlobalPhysicalTableId` from the authority's namespace and the stored name (the function behind `table_identity`), which the authority always has. Exists: the client-side permission compiler (`expr::compile`, `permissions_file`) has no namespace, which is why resolution is not done there. A rename lens keeps the stored name, so the identity is stable.
  - **Depth.** `InheritsFrom` is not a hop of the application's inheritance chain: it compiles `T`'s policy with the **full** depth bound a direct read of `T` uses (`DEFAULT_INHERITS_DEPTH = 10`, compile.rs:29), not depth − 1, so read(row) is exactly a direct read. This cannot recurse: `InheritsFrom` appears only in system-table policies, and the deploy refuses it in application policies and refuses a candidate that is a system table. Built: the deploy's policy check (`check_deployable_policies`, which `jazz-tools validate` also runs) refuses an `InheritsFrom` whose candidate's policy for its operation reaches another `InheritsFrom`, directly, through an inherited policy or by naming its own table, with the typed `UnsupportedPolicy::NestedInheritsFrom`; the compiler's own refusal of one stays as a guard.
  - **Evidence inside a transaction.** The node uses core's existing grounding unchanged ([authorization](7_authorization.md), "Policy evidence inside a transaction"). Exists: `finish_checks` (db.rs:6432) grounds a unit's writes in rounds (`ground_after`, db.rs:6471): a row the unit writes becomes evidence for other checks only after its own checks pass, and the row under check is never evidence for itself; `post_state_pass` (db.rs:6591) then re-checks passed writes against the unit's post-state so that a later write cannot invalidate them. It admits nothing that grounding refused. So a space row inserted or updated in the same transaction as a root, successor or member row is seen as written once its own write check has passed. A member row never grounds the read(row) of its own insert, because the space row's read rule needs that member row (spec R13); this is why the member insert policy has a creator clause (below). Exists: `ground_after` re-runs every failed check in each round while the previous round grounded something, whatever tables it reads, so a root staged with a new space row and its creator's member row passes in a later round, once both have grounded. The tables the node reads (the candidate tables and every table their select and update policies read, the members table among them) matter for the post-state pass, which records them for each passed check and re-checks it against the unit's post-state.
- **Every place that matches on `PolicyExpr` needs an arm (to be built).** Exhaustive matches (the compiler forces an arm): `walk` (fanout.rs:2666) and `policy_expr` (compile.rs:2221). Matches with a catch-all, which would otherwise silently misclassify the node and must get an explicit arm:
  - unsafe defaults: `policy_pins` (fanout.rs:2603, `_ => true`: must be false, the node reads another row), `policy_reads_other_rows` (db.rs:4474, `_ => false`: must be true), `policy_is_monotone` (db.rs:8715, `_ => true`: must be false, the space row's policy can change);
  - others: `row_local_policy` (db.rs:237), `conjuncts`, `value_pin`, `row_pin` (fanout.rs:2645, :2847, :2862, :2920), `correlation`, `clauses`, `hops` (sync.rs:3814, :3827, :3876), `recursive_base`, `inherits` (compile.rs:4367, :4410), the printer, `outer_row_refusal` and `too_deep` in `crates/jazz/src/tools/deployment/artifact/expr.rs` (:2736, :2765, :3035, :3079), and `policy_json` (permissions_file.rs:403); the server's former permissions validation now runs in the schema compile (`public_schema_convert.rs`), which the lowering arm below covers;
  - the core-schema lowering in `crates/jazz/layers/model/src/model/public_schema_convert.rs`: `append_policy_clause` (:1191) gains an `InheritsFrom` arm beside `Inherits`, and the catch-alls in that file (:180, :227, :1187, :1363, :1542, :1626, :1759) an explicit one (representation below).
- **Correlated `Exists` on the two-column address: to be built.** Exists: positive `Exists`, correlated with the outer row and inside `And` and `Or`, is lowered into a join (`append_exists_policy_clause`, :1502, from `append_policy_clause`, :1277; `policy_requires_branch`, :1179; outer-row references, :155). The lowering makes one outer-row correlation of each `Exists` the join's primary key (the one on `id`, else the first, public_schema_convert.rs ~1559) and keeps the others as correlated filters, which validation checks for comparable types only. Schema validation refuses a primary correlation on a `uuid` that is not a declared reference: `validate_join` (`crates/jazz/layers/model/src/query/validation.rs:1793`) lets an undeclared column equality through only when neither side is `uuid` or an array (the early branch), and otherwise requires a declared reference, in the source column's reference lookup and in the target check. An existing test pins this for app tables (`packages/jazz-tools/src/dev/schema-validation.test.ts:37-54`, `exists boards(id = this.boardId)`). Refused today: `MEMBER` (primary `scopeId = this.scopeId`: "is followed as a reference, but it is not declared as one"), `M(T)` (primary `identifier = this.id`: "is matched against the ids of …, but it is not declared as a reference"), and `CREATOR` and `IF` (primary `id = this.identifier`, a row-id join on an undeclared source column). The address columns cannot be declared references (`identifier` names a row of any of several tables). So today every derived policy, and every space table's read rule, would be refused when the schema compiles, before any E2EE code runs.
  - **The build: a relaxation scoped to system tables.** `validate_join` accepts an undeclared `uuid` primary correlation when the column on one side belongs to an E2EE system table (reserved prefix `__e2ee_`, which only the Jazz fragment may define, H1), at all three places: the early branch, the source column's reference lookup and the target check. Whether the planner or `join_support` in sync also assume declared references is to be checked when this is built. The derived policies and `M(T)` use only such joins. Every other join keeps the declared-reference rule, so the pinned test stays as it is and still passes: it joins two app tables. A sibling test pins the scoped acceptance (`M(T)` on an app space table, and each derived policy) and, in the same schema, the refusal of an undeclared `uuid` equality between two app tables.
  - Not taken: a separate lowering for system tables and `M(T)`. It would duplicate the join planner, validation and sync support for a few fixed shapes, and every later change to them would have to be made twice.
  - `convert_policy_predicate` (:3095) refuses `Exists` only as a plain predicate, which no derived policy needs. No policy needs `Not(Exists)`.
- **Candidates are fixed at deploy.** `derive_e2ee_policies` writes `tables` as the sorted, distinct set of `scope` tables of the declarations. The deploy refuses an empty list, an unknown table, and an `__e2ee_` table. No client chooses the candidates.
- **Write policies only.** No read rule needs `InheritsFrom`: the read rules are `MEMBER` and `M(T)`, `Exists` over the members table (spec R12–R14), and `IF` appears only in insert and delete policies (below). Sync support ships none for it. So the deploy's policy check (`check_deployable_policies`, also run by `jazz-tools validate`) refuses an `InheritsFrom` that a read (`select`) policy reaches, directly or through an inherited policy, with the typed `UnsupportedPolicy::InheritsFromInReadPolicy`.
- **Derived policies** (spec R12–R17; `IF(t)` is `InheritsFrom { operation: t, table_column: "scopeId", id_column: "identifier", tables }`; `MEMBER(c)` is `Exists { table: "__e2ee_members", condition: And[scopeId = this.scopeId, identifier = this.identifier, accountId = c] }`; `CREATOR` is `Or` over each `T` in `tables` of `And[scopeId = TableIdentity(T), Exists { table: T, condition: And[id = this.identifier, $createdBy.account = session.user, InsertedByThisTransaction] }]`, the spec's creator(row)). Updates are `False` on every internal table, and deletes on every one but `__e2ee_members`, and the write guard refuses them (R1); author columns compare to the session (R2). All compared columns are `uuid`, and `session.user` is a `Value::Uuid` (compile.rs:89), so the comparisons match without coercion (exists: a text column compared with `session.user` would never match, since only claims are coerced).

  | Table                     | Select                                        | Insert                                                                                  | Delete                                               |
  | ------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------- |
  | `__e2ee_members`          | `accountId = session OR MEMBER(session.user)` | `(IF(Select) AND IF(Update)) OR (accountId = session AND CREATOR)`                      | `accountId = session OR (IF(Select) AND IF(Update))` |
  | `__e2ee_spaces`           | `MEMBER(session.user)`                        | `MEMBER(session.user) AND IF(Select) AND IF(Update)`, `creatorAccountId` = session      | `False`                                              |
  | `__e2ee_space_successors` | `MEMBER(session.user)`                        | `MEMBER(session.user) AND IF(Select) AND IF(Update)`, `authorAccountId` = session       | `False`                                              |
  | `__e2ee_space_deliveries` | `MEMBER(session.user)`                        | `MEMBER(session.user) AND MEMBER(this.recipientAccountId)`, `senderAccountId` = session | `False`                                              |

  Exists: `Exists` correlates with the row under check through outer-row references (`this.col`, compile.rs:2204), excludes deleted rows, and does not compose the target table's own policy (compile.rs ~2396), which is what `MEMBER` and `CREATOR` need. `$createdBy.account` is an ordinary policy column inside an `Exists` today, as in `exists chats(id = this.chatId, $createdBy.account = session.user)` (`crates/jazz-codegen/tests/apps/chat-react/jazz.permissions.json`). `CREATOR` reads no member row and does not apply `T`'s read policy, so a space row the same transaction inserts grounds it as soon as that row's own insert check passes; it reaches the space row through the same `(scopeId, identifier)` link and candidate list as `IF`. Its `accountId = session` conjunct lets the creator add only itself. `InsertedByThisTransaction` (below) limits the clause to the transaction that inserts the space row, so a removed creator cannot add itself back and existing rows give their creators nothing (spec R12).

  A member-row delete is checked against the transaction's pre-state. Its first disjunct lets any member leave (spec R12), including a member that may not update, or read, the space row; leaving deletes every member row of the account for the space (spec §1.3). The second lets an updater delete any member row, its own included. There is no uniqueness check on roots or member rows (spec R15, §1.3), and no count of member rows (spec §3.8). Nothing else is checked: no signature, chain, marker or envelope (spec §1.4).
  - **Pre-state delete check (exists).** Jazz's authorization rules say `USING` clauses, `delete_using` included, read committed state ([authorization](7_authorization.md), "Policy evidence inside a transaction"), which is the pre-state spec R12 needs. While a unit is decided (at the authority on upload, in a relay's admission, and in a node's own commit), a delete's policy, an update's `USING` and the read-for-write check read the row as it stood before the unit, and the policy's other rows likewise, never the unit's own earlier writes (`Inner::holds_on_acted_row` in db.rs). So the decision does not depend on the order of the unit's writes: an updater that deletes its own member row and another member's in one transaction is accepted in either order. A row the unit created has no committed state to act on; the end-state check of its first write decides it. `InheritsFrom` in a delete's policy reads the space row in the same pre-state. Tested by `an_updater_removes_itself_and_another_member_in_one_unit` and `a_delete_judges_the_row_as_it_stood_before_the_unit` (`crates/jazz/tests/inherits_from_policies.rs`).
  - **Deleted rows stay evidence (exists, unchanged).** A row the unit deletes still counts as evidence for the unit's other writes, in the grounding rounds and in the post-state pass: the unit's deletes are not overlaid (7_authorization.md, "Policy evidence inside a transaction"; pinned by `a_unit_s_earlier_inserts_are_evidence_and_its_deletes_are_not` in `crates/jazz/tests/write_check_evidence.rs`, "a deleted committed band is evidence as committed"). E2EE does not change this core decision. Spec R12 states the consequence: a removal and a delivery to the removed account (or an updater's self-removal and its rotation) in one transaction are accepted, and the removed account then counts as holding the version, which marks the space as needing rotation.

#### The `TableIdentity` policy value

- **Need.** The space table's read rule compares the member row's `scopeId` with the space table's own catalogue identity (spec R13), which the app cannot write as a literal: it is minted by the authority. Without that comparison, an updater of any space table could add a member row naming a row of another table with the same ID.
- **Value (to be built).** A new `PolicyValue` variant `TableIdentity { table }`, written `table_id('projects')` in `jazz.permissions.json`. Like `InheritsFrom`'s `tables`, the bundle stores the stored table name, and the authority resolves it to the `GlobalPhysicalTableId` when it compiles the policy; the deploy refuses an unknown table. Every match on `PolicyValue` gains an arm (the outer-row helpers in public_schema_convert.rs:162 among them).
- **Encoding.** An additive variant of `jazz-bundle-v1`, emitted only into bundles of encrypted apps, with the same compatibility as `InheritsFrom` (below). Serde writes `{"type":"TableIdentity","table":"projects"}`; that string is to be pinned in `policy_expr_json_is_pinned` with the bundle's canonical form and digest, as for `InheritsFrom`.

#### Core representation of `TableIdentity` and `InheritsFrom` (to be built)

A public `PolicyExpr` reaches two places in core: the Db's SQL compiler (`policy_expr`, compile.rs:2221), which evaluates policies for write checks, reads and sync support, and the core-schema lowering (`public_schema_convert.rs`) into the query form that schema validation and the planner use. Both get an explicit representation; neither guesses.

- **`TableIdentity { table }`.**
  - Source: `table_id('T')` in `jazz.permissions.json`. The permissions expression reader (`crates/jazz/src/tools/deployment/artifact/expr.rs`) has no such function today; it gains one that yields `PolicyValue::TableIdentity { table }` with `T`'s stored name, refusing an unknown table.
  - Lowering: a new operand `Operand::TableIdentity(stored_name)` beside the literal and session-path operands (`convert_policy_operand`, public_schema_convert.rs:3233). The lowering stays a pure function of the schema: it carries the name, not the identity. Validation types the operand `uuid`, so it compares with `uuid` columns only.
  - Encoding: `Operand` derives `Serialize`/`Deserialize` (`crates/jazz/layers/model/src/query/policy_and_request_contracts.rs:788`) and is part of `Query`, which the wire carries (`crates/jazz/layers/protocol/src/wire.rs`) and canonical request keys hash (`canonical_operand_key`, `canonical_request.rs:362`). A new variant changes that encoding. It is produced only by the lowering of policies; whether lowered policies are stored or sent is to be established when this is built. If they are, the variant is named, versioned and pinned with a byte-level fixture and a compatibility note like `InheritsFrom`'s. Either way, `canonical_operand_key` gains a distinct tag, pinned by a test, and a query received from a peer carrying the variant is refused.
  - Evaluation: the SQL compiler binds it as a `uuid` parameter from `names::identity(namespace, stored_name, None)` (`crates/jazz/layers/db/src/names.rs:186`) when it compiles the policy; the compiler's context does not carry the namespace, so the store passes it in when it compiles the policy. When the identity is not known, it binds no value: a comparison with it holds for no row, and a `NOT` whose operand compares with an unknown identity is false rather than the negation of that comparison, so the policy grants nothing through the identity either way; it is compiled again once the names are confirmed. Only a store that is not the authority can lack an identity (before its catalogue mirror has confirmed the names), and in the shipped topology only Core, the authority, evaluates policies ([topology](9_topology.md)), and it always knows them. So the fail-closed rule matters only for a non-authority database that evaluates policies, which exists only in tests.
- **`InheritsFrom { operation, table_column, id_column, tables }`.**
  - Lowering: expanded when lowered, since `tables` is fixed in the node, into a policy `Or` with one branch per candidate `T`: `table_column = TableIdentity(T)` and a correlated existence join on `T` (`T.id = this.<id_column>`, not deleted) whose condition is `T`'s select policy for `Select`, or both of `T`'s update clauses for `Update`, each lowered as a direct policy of `T` at full depth. It reuses the inlining of a target table's policy that `append_inherited_policy` does for `Inherits` (from `append_policy_clause`, :1191), with a correlated join on `id_column` in place of a reference column; validation accepts that join under the system-table relaxation above.
  - Evaluation in the SQL compiler: as in "Compilation" above.

#### `InsertedByThisTransaction` (to be built)

- **Need.** The creator clause must hold only in the transaction that inserts the space row (spec R12). Exists: no policy can say this. `$createdAt` is dated by the creating client's clock, and the authority admits stamps up to `SKEW_TOLERANCE_MS` (30 s) ahead (`admit_session_write`, db.rs ~9848), so a time cut-off cannot separate existing rows from new ones.
- **Node.** A new variant of `PolicyExpr`, `InsertedByThisTransaction`, with no arguments. Inside an `Exists` it refers to that `Exists`'s row: it holds iff the unit under check inserts that row (a fresh insert, not a restore or an update). Anywhere else (a read policy, a row the unit did not insert, a `Single` write, which inserts one row only) it is false.
- **Evaluation.** Only write checks use it, and they run where the unit's writes are known: `finish_checks` (db.rs:6432) grounds the unit's writes in rounds, and a row the unit inserted becomes evidence once its own check passes (H7, "Evidence inside a transaction"). The node tests the candidate row's ID and branch key against the unit's grounded inserts into that table, passed to the compiled check as a bound set of (ID, branch) pairs, so the same row ID on another branch is not one of them; outside a write check the set is empty. The same holds on the eager path and on the authority's upload path.
- **Encoding.** Like `InheritsFrom`, it is an additive variant of the stored permissions; it is named, versioned and pinned with a fixture (§4 item 7).
- **Tests.** As in spec R12: the creator's member row in the same transaction as the space row is accepted in both orders and every transaction kind; in any later transaction, including straight after, after removal, and after a restore of the space row, it is refused.

#### Sync support for the two-column address

Multi-column correlation applies to the support of every application's read policies, not only the system tables'. A comparison with a table identity joins it only in a policy that uses `table_id`.

- **Before (existed).** When Core serves a read, the client also receives, for each correlated `Exists` in the read table's select policy, the consulted rows whose correlated column equals the read row's (`Inner::exists_support` in `crates/jazz/layers/db/src/sync.rs`). It correlated on **one** column pair: the first outer-row equality conjunct (its `correlation` helper). For `MEMBER` that is `scopeId`, so serving one internal row would load every member row of every space of that space table. For `M(T)` it is `identifier`, which has no index of its own.
- **Multi-column correlation (exists).** Support takes every outer-row equality conjunct of the condition (`column = this.column`) and every comparison with a table identity (`scopeId = TableIdentity(T)`); other constants, such as literals, are not taken. The first outer-row equality leads, as before, and the support matches on it and the others as one composite key. `MEMBER` and `M(T)` then load the member rows of one space by `(scopeId, identifier)`, served by the prefix of the `(scopeId, identifier, accountId)` index. A policy with one correlated column is unchanged.
  - The composite key compares stored cells, so an equality joins it only when its two sides store equal values as equal cells: the same type, and for enum columns the same stored column (each stored enum column numbers its variants for itself). A table identity joins it only once the store knows it (the names are confirmed). Support is built once per subscription and kept, so an identity still unknown then is left out for that subscription's life. Leaving an equality out only widens the support (for `M(T)`, to the member rows of every space sharing the `identifier`), and the session's policies still filter what ships.
- **Cost accepted.** Per internal row or space row served: the member rows of that one space, at most 1,000 in a supported space (spec §3.8), never member rows of other spaces. Also binding the session conjunct (`accountId = session.user`) would narrow this to the session's own rows; that is a later optimisation, to be measured with the rest (Main risks).
- **Not taken:** fixing the conjunct order so that `identifier` comes first, with an `identifier` index on members. It would work for these shapes but depends on conjunct order, which the deploy check of `M(T)` deliberately ignores (H1).

- **Account tables.** Fixed policies, R3–R11 of the spec. They check access only (spec §1.4). The founder, root-kind and `allowAccountReset` conditions of R5–R6 read Jazz's account registry and the deployed configuration; they are checks beside the policy, next to the existing local-first registry, not part of `InheritsFrom`.

#### Encoding, fixture and compatibility

- **What is stored (exists).** Deployed permissions are stored as a bundle: the canonical JSON (sorted keys, no whitespace) of the per-table policies, with a bundle ID over the schema hash and definition (catalogue.rs ~139). `PolicyExpr` is serde-tagged by `type`, and its JSON is pinned by `policy_expr_json_is_pinned` (policy.rs ~482).
- **Name and version.** The node is the `PolicyExpr` variant `"InheritsFrom"` with fields `operation`, `table_column`, `id_column`, `tables` (table names), an additive extension of the bundle definition encoding `jazz-bundle-v1`. The encoding's version does not change: no existing variant changes, and a bundle without the node is byte-identical to today's, with the same ID. It is emitted only into bundles of apps that declare `encryption`. The `Update` operation of this node means both clauses (above); that meaning is part of the variant.
- **Byte-level fixture.** For `IF(Select)` with `tables = ["projects"]`, serde writes
  `{"type":"InheritsFrom","operation":"Select","table_column":"scopeId","id_column":"identifier","tables":["projects"]}`,
  and the bundle stores its canonical form, 116 bytes of UTF-8,
  `{"id_column":"identifier","operation":"Select","table_column":"scopeId","tables":["projects"],"type":"InheritsFrom"}`,
  with SHA-256 `c2aead25ca360dafc60aed57ce264c42ec8ae17e8f52ee70e5a01dc17c05bd4b`. Both strings are to be added to `policy_expr_json_is_pinned`, whose expected unknown-variant message gains `` `InheritsFrom` ``.
- **Compatibility.**
  - Sync wire: unchanged. Catalogue sync carries schemas without permissions, so clients never decode a bundle definition.
  - Row storage: unchanged. The node is policy, not data.
  - Stored permissions: a server binary that predates the node fails to decode a bundle containing it (`unknown variant`), refusing it rather than dropping a policy, so a downgrade fails closed. Such a server could not run an encrypted app anyway. Bundles of apps without `encryption` are unaffected in bytes and IDs.
  - Clients: `load` and `load_backend` derive the system-table policies to compute the bundle ID (above); a client evaluates no policy at all: Core evaluates both read and write policies.

### H9. Host-supplied private storage and randomness

- **Traits** (in `jazz-e2ee-client`; futures are `LocalBoxFuture` because they are polled on the Db thread; to be built):

  ```rust
  pub trait PrivateStore {           // per Dₐ(account) scope: a device document and one held-key document per space root (spec §6.1)
      fn load(&self, scope: &str, doc: &str) -> LocalBoxFuture<'_, Result<Option<Vec<u8>>, StoreError>>;
      fn save(&self, scope: &str, doc: &str, bytes: &[u8], expected_revision: u64) -> LocalBoxFuture<'_, Result<(), StoreError>>;
      fn list(&self, scope: &str) -> LocalBoxFuture<'_, Result<Vec<String>, StoreError>>;
      fn delete(&self, scope: &str) -> LocalBoxFuture<'_, Result<(), StoreError>>;     // the whole scope
      fn protect(&self, secret: &[u8]) -> LocalBoxFuture<'_, Result<Vec<u8>, StoreError>>;   // at-rest wrap
      fn unprotect(&self, blob: &[u8]) -> LocalBoxFuture<'_, Result<Zeroizing<Vec<u8>>, StoreError>>;
  }
  ```

  - `protect` / `unprotect` back each platform's at-rest protection:
    - browser: non-extractable WebCrypto AES-KW/GCM key in IndexedDB;
    - Apple: Keychain item;
    - Android: Keystore-wrapped key;
    - otherwise: app-supplied.
  - Unwrapped private keys live in Rust memory (zeroized) only while the session holds them, because sealed-box opening runs in Rust.

- **Randomness (exists).** `jazz_e2ee::random::RandomSource` (`crates/jazz-e2ee/src/random.rs:12`), with `OsRandom` (:26) through getrandom. Recommendation: the default everywhere is `OsRandom`; hosts override it only for deterministic tests and simulation. It is not a per-binding obligation.
- **Per binding (to be built).**
  - **napi** (`crates/jazz-napi`): a JS object with promise-returning methods, called through a thread-safe function. A default Node file store is provided.
  - **wasm** (`crates/jazz-wasm`): no awaited JS→Rust callback exists yet. Add one using `js_sys::Function` → `Promise` → `wasm_bindgen_futures::JsFuture`. The store and keys live in the worker that owns the durable store; see Risks.
  - **jazz-native-relay** (C ABI): function-pointer callbacks with completion handles. jazz-rn's C++ implements them over Keychain/Keystore.
  - **jazz-ffi** (Swift/Kotlin/Go): a foreign trait `PrivateKeyStore`, blocking on its own thread and adapted into the async trait.
  - **Rust apps** (`crates/jazz/src/tools/client.rs`): a config field `private_store: Rc<dyn PrivateStore>` (or a `Send` factory constructed on the client thread).
- **Recovery secrets (spec §2.9).** The recovery key derivation lives in `jazz-e2ee` next to the account sealing key derivation (spec §2.12). Bindings pass the secret in, never store it.
- **Error.** A store failure fails the operation loudly (spec §0). It is never reported as `key-unavailable`. An unknown store format is refused and never overwritten (spec §6.1).

### H10. Feature flag and build split

- **Today (exists).** There is no client/server feature in jazz-core. The role is decided at runtime (`Db::set_authority`, db.rs:2140).
- **Proposal (to be built).**
  - Add a feature `e2ee-client` on `jazz-db`, re-exported by `jazz`. It gates the `E2eeHooks` trait, `DbConfig::with_e2ee` and every call site; with it off, each site compiles to nothing.
  - `jazz-e2ee-client` enables it. Client bindings depend on `jazz-e2ee-client`. jazz-server never does.
  - The deploy-side code (system tables, the write guard, `derive_e2ee_policies`, the `InheritsFrom` node) is **not** gated: the server needs it.
- **Feature unification caveat.** A workspace build that compiles a client binding and the server together unifies `e2ee-client` into the server's jazz-core. That is harmless, since there is no crypto dependency and the hooks are only installed by client openers, but it is not a hard exclusion. Add a runtime guard: `Db::set_authority` refuses a `Db` with hooks installed. Add a CI check that `cargo tree -p jazz-server -e features` lacks `e2ee-client` when built alone.

### H11. Deliveries, creation and rotation

- **A client-runtime task, with no new authority request.** It runs above `Db`, on the subscriptions of H6:
  - Acquisition (spec §3.3) on `NeedsKey`, a missing epoch in a read, a new delivery or a new version of a held space. With no key and a member row, the space is `key-pending` until a delivery arrives; without a member row, `key-unavailable`.
  - Delivery (spec §3.4): for each member that lacks a version this device holds after a random delay and only if no delivery has appeared meanwhile, it checks that the version belongs to that space's authenticated chain, seals to the member's current account sealing key (without one, it watches the member's account keys until one appears, H6) and inserts the delivery in a serializable transaction that read the member's account rows and member rows. A conflict re-reads; a refusal ends that delivery. Holders acting at once may each deliver (spec §3.4).
  - Bad deliveries (spec §3.4): a delivery to its account that provably fails to open or authenticate is skipped, and the runtime emits `invalid-delivery` naming the sender; it writes nothing.
  - Space creation: prepared on `NeedsKey` for a rootless space and staged with the write (H2); `db.encryption.createSpace(row)`; and in conversion sweeps ([migrations](E2EE_MIGRATIONS.md) §3.5). It learns that it may not create from a refusal of the root, which stops the automatic paths for that space on this device while the client runs; `createSpace` always attempts (spec §3.2). A transaction that failed for another reason, or was cancelled before submission, stops nothing; an unknown outcome is reconciled, never duplicated.
  - Repair of refused and lost creations (spec §3.2): once the real key is held, serializable transactions of at most 100 rows that each read the rows and exact cells they rewrite, rewrite only cells still under the losing epoch, and re-read on conflict, like the conversion sweep. The losing key is never deleted. A pass runs once the real key is held, after a restart, and when one of the device's own writes under the losing key settles; it reads the replica, the device's own unsettled writes included.
  - Rotation (spec §3.5): before an encrypted write to a space marked as needing rotation (H2), on `db.encryption.rotate(space)`. A bad delivery triggers no rotation by itself: the recipient's application is told (spec §3.4). One serializable transaction holds the successor and deliveries to at most 100 members (previous-version holders first, random order); the rest follow in delivery transactions of up to 100, to every remaining member whether or not a delivery to it exists. A refusal stops automatic rotation of that space on this device while the client runs (in memory only); explicit `rotate` always attempts (spec §3.5). `db.encryption.recoverRotation(space)` is the explicit recovery rotation.
- **Cost.** Proportional to the members of the spaces the session is a member of (at most 1,000 per supported space, spec §3.8), and to the rotations it makes: one delivery per member per version it lacks, and one per current member in each rotation.

## 5. Main risks

- **Key versions and deliveries accumulate.** Every rotation adds a version and one delivery per member. Reads look up the held key per cell version, and H4 computes one equality token per held version per predicate. A rotation carries at most 100 deliveries and the rest follow in batches, so a space with many members costs one HPKE seal and one row per member per rotation, spread over several transactions. Measure reads, equality queries, rotation size and delivery storage in a space with many members and rotations before landing.
- **Hot-path decryption.** Every subscription refresh re-materialises and re-decrypts its rows; fanout re-runs whole groups on invalidation. A 10,000-row live query in a busy project could decrypt 10,000 cells per change.
  - Mitigations: the decrypted-cell cache, and decrypting only the selected columns.
  - Benchmark before landing. The cache holds plaintext in memory; it is cleared on held-key removal, allow-list change and sign-out.
- **Browser thread model.**
  - Durable data lives in the worker, while tabs have in-memory dbs. If decryption happens in the worker, plaintext crosses `postMessage` to tabs; this is acceptable because it stays same-origin, and only one key store is needed.
  - If tabs decrypt, each tab needs the private store, and held-key revisions must be coordinated across tabs (spec §6.4 "last tab out").
  - Decided: keys and decryption in the worker (D5).
- **Blocking versus async key acquisition.**
  - Keeping the hooks sync and returning `NeedsKey` keeps core simple. The costs: every binding entry point must loop on `NeedsKey`; a binding that exposes a synchronous transaction callback refuses a staging call that needs an unheld key or an unprepared space root with `key-pending`, and the application acquires first (spec §5.6). Core's own `Db::transaction` is async and does not have this limit.
  - An acquisition also performs reads through the same `Db`, so it must never run re-entrantly inside a hook. The runtime must never call `Db` from inside a hook.
- **Catalogue identity before confirmation.** A first offline open cannot build cell contexts.
- **Policy cost on the server.** Every read of an internal space row, and every delivery insert, is one or two indexed member lookups; root, successor and member-row writes evaluate the space row's read and both update clauses through `InheritsFrom`; fanout evaluates the member lookup for sync visibility, and sync support loads one space's member rows per row served (H7). Measure it with the app's real space-row policies.
- **Space size.** The first release supports 1,000 members per space, as a documented limit that nothing enforces (spec §3.8). At that size a rotation is about 1,000 seals and 1,000 delivery rows that every holder device receives, and a device removal marks every space whose current version the removed device could open (spec §2.8). Measure these before landing, and before raising the limit.
- **Refused creations cost a scan of the space.** Repairing a refused or lost creation reads the space's rows to find cells under the refused epoch (spec §3.2), then rewrites them in bounded serializable transactions that re-read on conflict. It is proportional to the space, happens only after a refusal or a lost root, and is bounded by the rows the device may update.
- **Unreadable rows and pagination.** Short pages are accepted by the spec, but UI code that treats a short page as the end of the results will misbehave.
- **Feature unification.** See H10.

## 6. Decisions

- **D1. Access model (decided).** Entitlement to a space's keys is a row in Jazz's members table, from which the space row's read rule must come (checked at deploy). Changing members, creating and rotating need read and update permission on the space row (update meaning both update clauses on the current row, as a no-op save), except that the account creating the space row may add itself in the same transaction, and any member may leave. The space row's update rule is therefore the rule for managing members; the deploy warns where it can see that rule is broad. Keys move by delivery from members' clients, derived from member rows and deliveries. Removal is detected from member rows and rotated lazily.
- **D2. Where decryption happens (decided: the recommendation).** Inside core at result materialisation (H3), so pagination, fanout diffs and every binding behave alike. Alternative: above core, in each binding, with the delta indices patched separately.
- **D3. Whether the E2EE system schema enters the app's schema hash and bundle (decided: the recommendation).** Included deterministically, appended by the loaders only when encryption is declared. One bundle identity then covers what clients and the server enforce. Alternative: a separate system namespace outside the hash, which needs a second catalogue track.
- **D4. Reaching the space row from internal rows (decided).** One focused policy node, `InheritsFrom` (table identity plus row ID columns), over candidate tables fixed at deploy (H7), and one set of internal tables for every space table. Not taken: one set of internal tables per space table, and a native server validator.
- **D5. Browser worker model (decided: the recommendation).** Keys and decryption in the worker that owns the durable store, with tabs receiving plaintext. Alternative: per-tab decryption with a shared IndexedDB key store.
- **D6. Key triggers (decided: the recommendation).** Internal subscriptions run by the client runtime (H6). Alternative: a raw arrival callback in `Db::notify`.
- **D7. No-key writes (decided: the recommendation).** `NeedsKey` plus a retry by the caller. Alternative: async hooks inside core, which would break the run-to-completion model.
- **D8. Randomness (decided: the recommendation).** `OsRandom` by default everywhere, with host injection only for tests.
- **D9. Space creation (decided).** Optimistic, in the same transaction as the first encrypted write that needs the space or by explicit `createSpace`; no creation on space-row insert; no local permission evaluation; no server-side root uniqueness. A refusal of the root stops automatic creation of that space on the device while the client runs; an explicit `createSpace` always attempts.
- **D10. Bad deliveries (decided).** A delivery that does not open is reported to the recipient's application (`invalid-delivery`, naming the sender) and nothing is written; the recipient stays `key-pending` until an updater rotates. Insiders delivering badly are a documented limit, handled by removing them (spec §3.4, §8).
- **D11. Supported size (decided).** Up to 1,000 members per space in the first release, documented and not enforced (no policy can count rows); members' runtimes report `space-over-member-limit` beyond it. Devices watch only the deliveries of the current version, of skipped versions they hold and of their own account. A device removal rotates each affected space lazily, like a member removal (spec §2.8, §3.8).
