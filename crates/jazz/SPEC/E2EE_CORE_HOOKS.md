# E2EE core hooks

This note describes the integration between the encrypted client runtime and Jazz core. The protocol requirements are in [E2EE_PROTOCOL.md](E2EE_PROTOCOL.md). Implementation details and tests are linked at each hook.

## 1. Shape of the integration

- **jazz-core stays crypto-free.** jazz-core (`jazz-db`) defines a small _synchronous_ hook trait, `E2eeHooks`, plus the plain data types that cross it. It calls the trait at the write, read and query seams listed below. A new crate, `jazz-e2ee-client`, implements the trait on top of `crates/jazz-e2ee` (formats and primitives) and the protocol state machine. That crate depends on jazz-core; jazz-core never depends on it or on `jazz-e2ee`.
- **The hooks never await.** Everything asynchronous lives in the client runtime _above_ `Db`: key acquisition, deliveries and rotation (spec §3.3–§3.5), preparing a space root (spec §3.2), private-store I/O, and watching member rows, deliveries and chains. That runtime uses ordinary `Db` reads, subscriptions and transactions. The sync hooks only use state already in memory (held keys, prepared roots, replayed chains). When they lack something they return a typed "needs key" outcome, the caller awaits the runtime, and then it retries the single staging call.
  - Exists: the bindings run each operation to completion (binding_host.rs:9, "The database runs every operation to completion synchronously"; `Binding::insert` at :1076 calls `block_on(self.db.insert(..))` at :1085).
  - Exists: `Db::transaction` (db.rs:3603) is `async` and takes an `AsyncFnOnce(&mut MergeableTx<'_>)` callback, so a staging call inside it can await the runtime and retry; the callback itself is not replayed (spec §5.6).
- **The server never runs the trait.** The server-side work is system-table registration (the members table included), derived policies at deploy, the deploy check of each space table's read rule, one new policy node, `InheritsFrom`, one new policy value, `TableIdentity`, a system-table write guard, the scoped relaxation of join validation for system tables, multi-column correlation in sync support, and the pre-state check of deletes (H7; section 4, items 14–16). It is ordinary deploy and policy code, not behind the client feature. There is no E2EE-specific authority request and no native validator.

The hook interface is defined in [`E2eeHooks`](../layers/db/src/e2ee.rs); its write, read, query and stream call sites are linked in sections H1–H5 below.

The hooks are installed when the database opens, with `DbConfig::with_e2ee(Rc<dyn E2eeHooks>)` (exists), next to `with_id_source` and `with_clock`, so a database never runs without them. An `Option` that is `None` costs one branch per call site.

A call the hooks refuse for want of a key (`NeedsKey`, `SpacePending`, here and in H3–H5) applies nothing and fails with reason `key-pending` (code `NotObserved`) or `space-pending` (code `WriteRejected`), the protocol's §7 names (exists: `Reason::KeyPending`, `Reason::SpacePending`, and `Error::space`, all behind the `e2ee-client` feature, so a build without it sees no change). The error carries the space in its `space` field (`Error::space`); `E2eeRefusal::of(&error)` gives both.

## 2. Hooks

### H1. Declarations from app files, at open

- App-file declarations and the system-table fragment are loaded by [`load_client_encrypted`](../src/tools/deployment/artifact.rs#L978-L1010) and validated during deployment in [`artifact/encryption.rs`](../src/tools/deployment/artifact/encryption.rs#L95-L180). Code generation preserves the declarations in generated bindings.
- Client opens obtain those declarations and install the hooks; the schema-only loader refuses encrypted apps. The refusal is covered by [declaration tests](../tests/e2ee_declarations.rs#L998-L1093).
- The deployment derives system-table policies from the declarations. The policies and space-table read-rule check are implemented in [`artifact/encryption.rs`](../src/tools/deployment/artifact/encryption.rs#L1170-L1310).
- **Space row read rule (spec R13; refusal).** After compiling permissions, the deploy checks the select policy of each space table `T` named as `scope` by an entry with at least one encrypted column: it must be `M(T)` or an `And` with `M(T)` as one of its direct conjuncts, where `M(T)` is exactly `Exists { table: "__e2ee_members", condition: And[scopeId = TableIdentity(T), identifier = this.id, accountId = session.user] }` (conjuncts in any order). Anything else (an `Or`, `M(T)` under a `Not`, an `M` naming another table, no `M`) is refused, naming the table. The check is syntactic and exact, so it is decidable.
- **Deploy warnings (spec §1.5).** The deploy compares each encrypted table's select policy with its space table's, syntactically, in both directions: it warns when it can see that the space row is readable more broadly than the encrypted table (for example, the table's policy is the space table's policy conjoined with further conditions), when the encrypted table is readable more broadly than its space row (for example, its policy does not involve the space row), and when a space table's read rule does not yet come from the members table (an entry without encrypted columns, [schema changes](E2EE_SCHEMA_CHANGES.md) §4), when a space table's update policy requires an old-to-new transition (which admits no member change, creation or rotation, spec §1.4), when a space table's update policy is broad (an update clause that is `true`, exactly `M(T)`, or reads no session value and no `$createdBy`: every member, or every reader, then manages members, spec §1.5), and when a space table's insert policy reads `__e2ee_members` for the row being inserted (no member row can ground it, spec §1.5, R12). It never claims more.
- **Catalogue identities.** Cell contexts need Jazz's stable table and column IDs (spec §4.1). Exists: `Db::table_identity(&str) -> Result<Option<GlobalPhysicalTableId>>` and `column_identity` (db.rs:2209, :2219). `GlobalPhysicalTableId` wraps a `uuid::Uuid` (`crates/jazz/layers/types/src/ids.rs:87`): a version 5 UUID of the authority's namespace (a random UUID minted once by the authority, sync.rs ~6407) and the stored name (names.rs:185). They return "not observed" until the client knows the namespace and the version's names are confirmed, so a first-ever offline open cannot encrypt or decrypt. The runtime should cache confirmed identities in private state; see Risks.
  - **Table identity for app code.** Rust apps and trusted backends can resolve the space table's identity with [`JazzClient::table_identity`](../src/tools/client.rs#L2374-L2386). The [binding host](../layers/db/src/binding_host.rs#L1511-L1523) exposes the same lookup as a UUID string, for example through [`tableIdentity` in NAPI](../../jazz-napi/src/lib.rs#L3151-L3154). Use this identity as `scopeId` on a member row. The lookup reports `NotObserved` until the client sees the authority's catalogue for its schema version.
- **Error and fallback.** Deploy and load refuse invalid declarations. At open, the [binding-host guard](../layers/db/src/binding_host.rs#L693-L712) checks the hooks' declaration flag for schemas with Jazz's system tables. The caller must build the hooks from the app's own declarations (H10).
- **Cost.** Paid once at open.

### H2. Write staging: plaintext to ciphertext plus equality tags

- **Call site (exists).** The value must be transformed _before_ `Inner::chunk_large_cells` (db.rs:7213). That function content-hashes and chunks large values, and the same mutated op is what is stored and uploaded. A hook at cell binding would encrypt SQLite but not the wire. Concretely, the hook runs in:
  - `Db::write_op` (db.rs:3454), the private entry for `insert`, `update`, `upsert`, `delete` and `restore`, and for `MergeableTx` (db.rs:4522) and `MergeableTxHandle::commit` (db.rs:9038), which replay through it;
  - staging in `TxRef::insert` (db.rs:10743) and its siblings, for handle transactions (`begin_mergeable` / `begin_serializable`, db.rs:9993/:10001) and `serializable_tx()` (db.rs:11183), at staging time, so that a refusal surfaces on the staging call and not at commit.
- **Built (exists).** `seal_write` runs in `Db::write_op` and, for handle transactions, at staging (`Db::stage_with_edits`, so a refusal surfaces on the staging call). `MergeableTxHandle` replays through `write_op`, so its refusal surfaces at its commit. The current row's space cell is read for updates and upserts. Companion rows are inserted in the write's own commit before it, as the same identity; in a handle transaction they leave the batch if the write then fails. Partial reads and edits of encrypted columns (ranges, JSON pointers, deltas, splices, appends) are refused by core.
- **Data crossing (exists).**

  ```rust
  pub struct WriteCells<'a> {
      pub table: &'a str, pub row: RowUuid, pub kind: WriteKind,      // Insert|Update|Upsert|Delete|Restore
      pub cells: &'a mut BTreeMap<String, Value>,                      // plaintext in, ciphertext out
      pub stored_space: Option<&'a Value>,                             // current row's space cell (updates, upserts)
      pub companion_rows: &'a mut Vec<(String, RowUuid, BTreeMap<String, Value>)>, // internal rows staged in the same transaction
  }
  ```

  - The hook replaces each encrypted column's value with `Value::Bytes(cell record)` and adds `__e2ee_eq_<col>` cells.
  - It refuses a change of the space coordinate (spec §5.1) and partial edits of encrypted columns.
  - Deletes, restores and updates that touch no encrypted column return `Ok` without a key.
  - For updates and upserts, core supplies `stored_space`, the space cell of the current row, which is plaintext; core already loads that row for updates and upserts.
  - `companion_rows` lets the hook stage internal rows (a space root) into the write's own transaction; core inserts them in the same transaction, as the same session (R2), before the write. This is how creation stays atomic with the write without a separate transaction kind.

- **No key (`NeedsKey`).** Core has not applied anything, so the caller awaits `runtime.acquire(space)` (key acquisition, a missing root and a pending rotation, as `db.encryption.acquire`, spec §5.6) and re-issues the same call. In an open core transaction, the retry applies only to that staging call (spec §5.6).
- **Space creation (spec §3.2, §5.4).** The client never evaluates write policies (exists: a replica runs no write-policy check, `Inner::checked` at db.rs:8140 returns `None` on a client; the only client-side answer is the asynchronous `JazzClient::permission_advice`, `crates/jazz/src/tools/client.rs:1701`, which asks the authority and is `Unknown` offline). Creation is therefore optimistic and needs no advice:
  - an encrypted write to a space with no known valid root and no prepared root returns `NeedsKey`; the runtime prepares the root (online it first reads the address's roots; it generates `K₀`, builds and signs the root, and persists `K₀` as an `unpublished` held key) and the caller retries;
  - on the retry the hook stages the prepared root as a companion row of the write, and seals the write under `K₀`;
  - the authority's R15 decides; a refusal fails that transaction only. The runtime tells a refusal of the root itself from a transaction that failed otherwise, a cancellation before submission and an unknown outcome (spec §3.2). Only a refusal of the root stops automatic creation of the space on this device (in the running client's memory only, lost on restart, spec §3.2); after it, the hook returns `SpacePending` for the space and the caller fails the write `space-pending`, until a valid root exists or an explicit `createSpace` succeeds (spec §3.2). An unknown outcome is reconciled by the transaction's identity, and no second root is prepared meanwhile;
  - inserting a space row stages nothing.
- **Dropped companions (`companions_dropped`).** A companion row `seal_write` staged can fail to be stored. Core then calls `companions_dropped(&[(table, row id)])` on the hooks, a default no-op, once nothing borrows the store (the hooks never call the database). It does so when:
  - a write fails after sealing (a direct write, or a handle-transaction staging call that fails after its companions were staged);
  - a handle transaction is abandoned, or fails to commit, with companions staged and not committed;
  - a callback transaction rolls back, for the companions its sealed writes applied.

  A transaction that commits its rows reports nothing. A row staged again later (a retried write) is a new staging. The client's hooks act only on a space root (`__e2ee_spaces`) they had staged: they move its ID from the staged set to a dropped set. While the dropped root's key is still `unpublished`, the write path treats it as absent and returns `NeedsKey`, so nothing seals under a key whose root was never stored. The first step of the next write (`E2eeClient::write` and `prepare_space` share it) abandons each dropped creation: the creation is settled as not accepted, so its key is kept (a refused key only ever opens cells) and is no longer held back. The write then prepares and stages a fresh root as for any rootless space. Other companion rows are ignored.

- **Pending rotation (spec §3.5).** When the runtime has marked a space as needing rotation and this device's rotation of it has not been refused while the client runs, the hook returns `NeedsKey`; `runtime.acquire(space)` makes the rotation in its own serializable transaction (successor plus deliveries to the members), waits for its outcome within the write's deadline, and the caller retries. Refused, offline or undecided, the retry seals under the current version. Rotation is never a companion row of the write, so its refusal never fails the write.
- **Epoch choice.** The deepest held key that is not marked `refused` (spec §5.2). It is in memory, so no I/O happens on the write path. A refused key is kept for good and only ever opens cells (spec §3.2).
- **Cost.** A hash-set lookup per write for unencrypted tables. A member-row insert may seal one delivery. For encrypted columns: one XChaCha20-Poly1305 seal per encrypted cell plus a keyed BLAKE2b per equality column.

### H3. Reads: one-shot, query results, subscription deltas

- **Principle.** Ciphertext stays ciphertext inside core: storage, the SQL compiler, fanout's watch indexes and diffs. Decryption happens once, on each materialised result _before_ it leaves `Inner` toward a reader. A dropped row is then simply absent, and fanout's `diff` (fanout.rs:2411) computes correct indices without remapping.
- **Call sites (exist).**
  - `Inner::run_for_reader`, after execution: `Db::all`, `all_strict`, `read` and their variants, transaction reads, and `all_serialized_query`, which the bindings use. Internal reads (sync serving, read-set validation, eviction) stay sealed.
  - Fanout's materialisation paths: a subscription's opening, `Fanout::group_rows` (full re-runs) and `recheck_rows`. The hook runs on their output, before `diff` and `deliver`. `stored_images` is not opened: it reads stored key cells for invalidation, which compare as stored.
  - `Binding::local_current_row` (through `Db::all_strict`), transaction reads and provisional reads run in _strict_ mode (spec §4.4).
- **Data crossing.**
  - `ReadSite { strict, table, query, shape, splices, lens_defaults }` and the rows: the query as executed, its prepared shape, the columns read as splices, and the value a migration gave rows stored before a column existed (`ReadSite::is_lens_default`).
  - The hook rewrites encrypted cells in place to plaintext and removes `__e2ee_eq_*` cells.
  - In lenient mode it removes unreadable rows and returns them in `OpenOutcome.unreadable` as `{table, id, column, code, space}`. In strict mode the first bad cell is an error.
  - Short values (spec §4.1): an empty cell reads as the declared default and, when the empty value is stored in the row rather than supplied by the lens for a row that predates the column, is also reported `empty-cell` (core hands the hook each lens-added column's value through `ReadSite`, per column; see "Limit" below). A cell that opens under a held key of another space than the row's own is decrypted by its epoch's space, returned and reported `stale-space`.
- **Reports stay with the hooks.** `OpenOutcome` is what core reads to decide a strict read; core does not carry the §4.3 reports (`unreadable`, `missing_epochs`) of a lenient read to the caller or to a subscriber, because every read entry point and every subscription event would need a new channel. The hooks built the reports in `open_rows`, so the runtime that owns them already holds each one, and it delivers them (spec §4.3) and settles the provisional ones as described next. A runtime reads them from its own hooks, never from a result.
- **Missing epochs.** The hook lists a row needing an epoch the device lacks in `missing_epochs` and reports it provisionally. The runtime acquires the key asynchronously, at most once per read (spec §4.2), and then settles the report to the protocol's code before it reaches listeners: `key-pending` once per space when the account is a member, `key-unavailable` per row when it is not (spec §3.4, §4.3). The hook knows nothing of membership.
  - One-shot reads: `Binding::all` is already async. The binding wrapper awaits the acquisition and re-runs the read once.
  - Subscriptions: after a key arrives, the runtime calls `Db::refresh_reads_of(tables)` (exists), a public wrapper of the private `Fanout::refresh_where`. Rows that became readable then arrive as ordinary additions.
- **Bounded wait (spec §4.6).** The 10 s wait-for-delivery episode lives in the binding's stream wrapper around the subscription stream. Core keeps diffing against its own baseline while the wrapper withholds, so the wrapper keeps a full copy of the latest result, applying each withheld delta to it, and ends the wait by emitting that copy as one reset event; afterwards it forwards deltas unchanged. On expiry it emits the copy and reports the space `key-pending`. It discards the copy on stop, sign-out and account change. Bindings need a reset event in their subscription stream type if they lack one; core needs nothing new.
- **Limit and offset.** Unreadable rows are dropped after the SQL window (spec §4.3), which is exactly what post-execution filtering gives.
- **Built (exists).** `open_rows` runs on every read that leaves the store toward a reader (`Inner::run_for_reader`: one-shot reads, serialized reads, transaction reads) and in fanout on a subscription's opening, full re-runs and rechecks. Reads in a transaction, the row a binding builds a write on (`Db::all_strict`) and reads in a callback transaction are strict, and core itself fails a strict read whose outcome leaves a row out. `ReadSite` carries the query, its shape, the splice columns and, per column, the value a migration gave rows stored before the column existed.
  - **Limit: migration values are marked per column, not per row.** A cell equal to a lens-added column's stored default is marked, whether the lens supplied it or a writer stored that same value: the store keeps no record of which. A writer that stores the empty value in a lens-added encrypted column is therefore not reported `empty-cell`.
- **Refused here.** Core refuses, when the query is prepared and naming the table, every read that would return cells of an encrypted table the hook is never given to open: relation reads whose nested rows (array subqueries in cells) are encrypted, includes of encrypted rows, flat joins over an encrypted table (their cells are named by source, the root's included) and the history of an encrypted table ("Reading encrypted table `T` … is not supported yet"; spec §4.5). Conditions of joins, nested joins, correlations, `reachable`, `inherits` and policy branches are refused whenever they name an encrypted column of the table they run on. Core also refuses splices, ranges, JSON pointers, deltas and edits of encrypted columns. And from the declarations the hooks carry, core refuses, naming table and column ("Reading encrypted column `T.c` … is not supported yet"), every read shape on an encrypted column except the one the hook can plan, a top-level equality of an equality-indexed column with a value: aggregates and `group_by`, `ORDER BY`, ranges, `IN`, `Ne`, `Contains`, null tests, a column on the right of an equality, an equality nested in `Any`, `Not` or `All`, and the join source columns and policy-branch filters that name one. It does so before the hook is asked, and again on the query the hook returns, which must not still filter an encrypted column, so a plaintext literal never goes upstream whatever the hook does. An application's query that names a reserved token column (`__e2ee_*`) in a condition, ordering, aggregate or selection is refused, in ordinary and union queries; the token conditions the hook writes into the query it returns are accepted. A union relation query stays whole, so core reads each arm the same way and refuses any condition in an arm that names an encrypted column (the hook is not given an arm to plan), and ordering the union by one. The query a hook returns may differ from the one it was given only in its conditions and the window its residual takes over; anything else (an added include, say) is refused. Opening a database with hooks is refused when the schema gives a declared encrypted column a stored default, which would be stored as plaintext. Filters through other tables (joins, `reachable`, `inherits`) return only the read's own rows, and core refuses those that name an encrypted column (above), so the hook is never asked to plan them.
- **Cost.** This is the main hot-path cost; see Risks. It is mitigated by a per-client decrypted-cell cache. Its key is the hash of the complete authentication input: the cell cipher's full context bytes (`frame[ctx, cellType]`), the identity of the held key used (space root and epoch) and the ciphertext. A hit never bypasses `stale-space` classification or the AAD checks. The cache is cleared on held-key removal (revision change, spec §6.4), on a change of the active schema view, on a change of the mechanism allow-list (spec §0, which closes the owner), and on sign-out or account change.

### H4. Equality-filter rewriting

- **Call site (exists).** `Db::prepare_query_bound`, before query validation. The prepared query is the physical one, so the remote shape and the query a subscription sends upstream are rewritten too: the server only ever sees tags. The epoch set is folded into the shape hash (`PreparedQuery::e2ee_epochs`, `e2ee_incomplete`); the residual applies after `open_rows`, and a live result of a rewritten query always re-runs in full.
- **Data crossing.**
  - Input: `&Query`.
  - Output:

    ```rust
    QueryPlan::Plain
    QueryPlan::Rewritten {
        physical: Query, residual: Residual { preds, limit, offset },
        epochs: EpochSetId, incomplete: Option<SpaceAddress>,
    }
    QueryPlan::NeedsKey { space }
    ```

  - `physical` replaces `Eq(col, v)` (or a full enum `match`) with `In(__e2ee_eq_col, [token per held epoch])`, keeps the required plaintext `Eq(space, s)`, and drops `limit`/`offset` (an unwindowed prepared query exists, db.rs ~136).
  - `residual` is applied after H3 decrypts: compare the authenticated plaintext, then window.
  - `epochs` is folded into the query's shape hash, so a new held epoch makes a new prepared query. The runtime re-prepares live subscriptions when its epoch set changes (retry budget of 3, spec §4.5).
  - **Cold queries.** Online, an encrypted predicate on a space for which no epoch is held returns `NeedsKey` instead of an empty `IN`; the binding acquires within the read budget and plans again (spec §4.5).
  - **Incomplete results.** When the known lineage has unheld epochs, the plan sets `incomplete`, and execution reports the space as unreadable with no row ID or column. It reports `key-unavailable` once acquisition confirms that the account is not a member, and `key-pending` otherwise (spec §4.5). The runtime deduplicates the report until the missing keys arrive. See the [equality query test](../../jazz-e2ee-client/tests/settled_reasons.rs#L211).

- **Refusals (never a scan).**
  - Ordering by an encrypted column.
  - Joins, `reachable`, unions, `partial` selects, or aggregates over encrypted columns.
  - Encrypted predicates other than `eq`.
  - `eq` on an encrypted column without an equality index or without a space `eq`.
- **Offline.** Offline no tokens are computed: the physical query is just `Eq(space, s)`, and the residual does the filtering.
- **Cost.** A query walk at prepare time, plus one BLAKE2b per held epoch per predicate. A rewritten live query is not incremental: on each change to its table it re-reads and decrypts every row in the space that matches the token filter, runs without `LIMIT`, and applies the residual's window afterwards. Its cost grows with the matching rows of the space, not with the window.

### H5. Large-value streaming

- **Row-aware uploads.** The native bindings, Rust reader, and typed Rust bindings (including transactions) call `begin_streaming_value_upload_for(mutation, table, row, cells, column, target)`. On an encrypted table, begin validates every supplied sibling and seals encrypted siblings before the first source read. An existing row supplies its stored space, and begin rejects a conflicting space in the metadata. A new row supplies its space in the metadata or uses its own ID for a self-space table. Publication checks the space again and writes the prepared cells.
- **Stream targets.** A plain target may have encrypted siblings. An encrypted target must be a non-indexed bytes column. Indexed or non-bytes encrypted targets are refused before the source is read. The chunker receives the sealed stream, starting with the header and ending with the final record.
- **Rowless uploads.** `Db::begin_streaming_value_upload` and `JazzClient::begin_streaming_upload` refuse every encrypted target and any named encrypted sibling at begin. Finish checks the mutation kind and metadata before publication. On an encrypted table, it permits a plain-only patch to an existing row and refuses an insert, an upsert, or a patch supplying an encrypted sibling.
  - **Read side: through `open_rows`.** A whole read materialises the stored value before `open_rows`, which opens stream records like any other cell: the large-value format's reader tries the cell record first and the stream record second, a choice per value that only the hook can make. The trait has no `open_stream`: core offers no streaming read of an encrypted value in the first release, and the hook is added with the first one.
- **Call sites.**
  - Write side: the byte path before the large-value chunker, reached from `Binding::begin_streaming_mutation` and the streaming upload functions in large_ops.rs.
  - At begin, `seal_stream` validates the target (only non-indexed `bytes` columns, spec §5.5), selects the epoch and returns a `StreamSealer`.
    - Each `push(&[u8])` returns ciphertext bytes, which go into the unchanged chunker.
    - `finish()` emits the final tagged record.
    - The routing record and header (spec §4.1) are written first.
  - Read side: the whole-value materialisation in large_ops.rs / large.rs, opened by `open_rows`.
    - A later streaming read would decrypt sequentially. Range reads, JSON-pointer reads, deltas, appends and splices on encrypted columns are refused in the first release. This is a scope decision, not a format limit: STREAM records authenticate individually, so a later range read can seek to a record boundary.
    - A whole read decrypts from the start.
- **Content addressing.** Chunks are hashed after encryption, so there is no cross-row deduplication of encrypted values. This is acceptable, and required for confidentiality.
- **No key.** `NeedsKey` is returned at begin, before any source bytes are pulled (spec §5.5).
- **Cost.** Streaming XChaCha20; memory is bounded by the chunk size.

### H6. Sync arrivals of internal-table rows (key triggers)

- **Recommendation: no new core hook.** The runtime opens ordinary local subscriptions on the internal tables, as the client's own identity:
  - its own account's `__e2ee_members` rows (by `accountId`), which name the spaces it is a member of, and the deliveries addressed to its account (by `recipientAccountId`);
  - its own account's `__e2ee_device_removal_requests` (by `accountId`), so a pending request of another of its devices is completed (spec §2.8);
  - built: its own account's public rows that change its state (roots, public approvals, public successors, recovery roots, sealing keys, removal requests, by `accountId`), after which the runtime verifies the account again (`E2eeClient::watch_account`, `E2eeClient::ensure_account`);
  - per space it is a member of: the space's member rows (at most 1,000 in a supported space, spec §3.8), `__e2ee_spaces` and `__e2ee_space_successors` (each by `(scopeId, identifier)`), and `__e2ee_space_deliveries` of the versions concerned only, the current version and skipped versions it holds (by `(scopeId, identifier, keyEpochId)`); all readable to members, spec R12, R14. Deliveries of earlier versions are not watched (spec §3.4, §3.8);
  - the public `__e2ee_account_roots` of the members of those spaces, so a member's reset (a new generation, which makes it lack every version) is seen when no space table changes (spec §2.11, §3.4);
  - while a delivery to a member waits for a valid sealing key, that member's `__e2ee_account_keys` rows (spec §2.12, §3.4);
  - only on a device that may act on the needs-rotation mark (it holds the current version and its rotation of the space has not been refused while the client runs, spec §3.5): the public account successors of the members holding the current version, so the mark is re-evaluated on an account-only change such as a `remove-device` successor, even when no space table changed. The delivery transaction reads the rest of a member's account history when it needs it (spec §3.4).
- **Shared account watches.** The public account watches are one subscription per table over the set of accounts needed across all spaces (`accountId IN …`; exists: `Predicate::In`, also on the wire, `WireRelationPredicate::In`, `crates/jazz/layers/model/src/query/relation_codec.rs:650`; `accountId` is indexed, H7), replaced when the set changes, the new subscription opened before the old one closes. Design figure: 10,000 watched accounts per device (spec §3.8); splitting the set is left until measurement shows a need (Main risks). Each decision is made from the results of a watch opened before it, never from a separate read, so nothing changes unseen between the two. An account leaves the set when it is no longer a member of a watched space, or its waiting delivery is made or abandoned.
- **Built (exists, `E2eeClient::watch_spaces`, `sync_spaces`).** Own member rows by `accountId`, own deliveries by `recipientAccountId`, and per space it holds keys of or has a report waiting for: its roots, successors and member rows. A space joins the watch before it is acquired. The watches of member accounts' rows, of deliveries per held version and of the needs-rotation mark belong to the delivery and rotation parts; a failed acquisition is retried by the caller, with its own backoff.
- From these the runtime computes, per space and in memory, which members lack a version it holds, from each member's current generation (spec §3.4), whether the space needs rotation (spec §3.5), whether the space has no valid root (spec §3.2), and its member count (spec §3.8). Each is a comparison of two indexed per-space result sets, at a cost proportional to the space's members and the current version's envelopes; no anti-join query is needed.
- A new delivery or version triggers acquisition with backoff (spec §4.2). This needs only that the internal tables are in the client's schema (H7) and readable under their derived policies.

### H7. System tables, derived policies and `InheritsFrom`

App loaders append Jazz's versioned system-table fragment; deployment derives its policies from the encrypted app declarations and validates the space-table read rule. The write guard protects internal rows, and policy checks use pre-state for deletes. See [deployment policy handling](../src/tools/deployment/artifact/encryption.rs), [core policy evaluation](../layers/db/src/compile.rs) and [policy tests](../tests/inherits_from_policies.rs).

Policy JSON adds `InheritsFrom`, `InsertedByThisTransaction` and `TableIdentity` to `jazz-bundle-v1`; bundles that do not use them keep their bytes and bundle IDs. `Operand::TableIdentity` is produced by policy lowering only, and a query that supplies it is refused. Equality token additions are named `json.v1` and `array.v1`; their bytes and compatibility rules are in [E2EE_EQUALITY_FORMAT.md](E2EE_EQUALITY_FORMAT.md), with fixtures in `crates/jazz-e2ee/tests/vectors.rs` and the address-policy encoding tests. The full write-ups (variant indexes, fixtures, sync wire, downgrade and activation digest) are [ADDRESS_POLICY_NODES_COMPATIBILITY.md](../../../dev/ADDRESS_POLICY_NODES_COMPATIBILITY.md) and [E2EE_EQUALITY_JSON_ARRAY_COMPATIBILITY.md](../../../dev/E2EE_EQUALITY_JSON_ARRAY_COMPATIBILITY.md).

### H9. Host-supplied private storage and randomness

The host supplies durable private storage and a random source to the client runtime. The runtime passes plaintext key documents to the host's private store, including JavaScript in the browser and Swift or Kotlin through UniFFI. The host store protects the documents at rest. On a UniFFI save, Rust wipes its temporary copy during serialization. UniFFI owns the serialized callback buffer, so the Rust store adapter cannot wipe it. See the [store and random-source interfaces](../../jazz-e2ee-client/src/store.rs) and the [host interface](../../jazz-e2ee-client/src/host/mod.rs).

### H10. Feature flag and build split

- **Today (exists).** There is no client/server feature in jazz-core. The role is decided at runtime (`Db::set_authority`, db.rs:2140).
- **Built (exists).**
  - A feature `e2ee-client` on `jazz-db`, re-exported by `jazz` (jazz-core). It gates the `E2eeHooks` trait, the installation of hooks and every call site; with it off, each site compiles to nothing.
  - `jazz-e2ee-client` enables it. Client bindings depend on `jazz-e2ee-client`. jazz-server never does.
  - The [binding-host open guard](../layers/db/src/binding_host.rs#L685-L715)
    refuses an encrypted schema unless the open installs hooks built from an
    encrypted app's declarations. A build without `e2ee-client` cannot install
    those hooks. The guard checks the hooks' declaration flag. The caller
    must build them from the app's own declarations, which
    [`load_client_encrypted`](../src/tools/deployment/artifact.rs#L937-L960)
    returns with the schema. The flag also covers versions that keep the
    system tables but declare no encrypted columns. The
    [declarations test](../tests/e2ee_declarations.rs#L998-L1093) covers the
    guard. The [React Native relay](../../jazz-native-relay/src/lib.rs#L1690-L1714)
    has an encrypted open path when built with the feature. A backend can open
    with [keyless hooks](../../jazz-napi/src/lib.rs#L2648-L2668): plain tables
    and columns work as usual, encrypted cells are omitted, and encrypted
    writes and equality filters are refused (spec §1.4).
  - The deploy-side code (system tables, the write guard, `derive_e2ee_policies`, the `InheritsFrom` node) is **not** gated: the server needs it.
- **Feature unification caveat.** A workspace build that compiles a client binding and the server together unifies `e2ee-client` into the server's jazz-core. That is harmless, since there is no crypto dependency and the hooks are only installed by client openers, but it is not a hard exclusion. Runtime guard (exists): `Db::set_authority` returns an error for a `Db` with hooks installed, and the authority refuses hooks. CI check (exists): `dev/gates/server-excludes-e2ee-client.mjs`, in the lint partition, fails if `cargo tree -p jazz-server -e features -i jazz-db` lists `e2ee-client`. The workspace test build also gets `e2ee-client` through its binding crates. The [dedicated jazz-core integration run](../../../dev/gates/local-ci-equivalent.mjs#L367-L384) explicitly requests that same feature.

### H11. Deliveries, creation and rotation

- **A client-runtime task, with no new authority request.** It runs above `Db`, on the subscriptions of H6:
  - Acquisition (spec §3.3) on `NeedsKey`, a missing epoch in a read, a new delivery or a new version of a held space. With no key and a member row, the space is `key-pending` until a delivery arrives; without a member row, `key-unavailable`.
  - Delivery (spec §3.4): for each member that lacks a version this device holds, when the pass runs (spec §3.4), it checks that the version belongs to that space's authenticated chain, seals to the member's current account sealing key (without one, it watches the member's account keys until one appears, H6) and inserts the delivery in a serializable transaction that read the member's account rows, the member rows and the space's deliveries. A conflict re-reads; a refusal ends that delivery. The first holder to commit wins (spec §3.4).
  - Bad deliveries (spec §3.4): a delivery to its account that provably fails to open or authenticate is skipped, and the runtime emits `invalid-delivery` naming the sender; it writes nothing.
  - Space creation: prepared on `NeedsKey` for a rootless space and staged with the write (H2); and `db.encryption.createSpace(row)`. It learns that it may not create from a refusal of the root, which stops the automatic paths for that space on this device while the client runs; `createSpace` always attempts (spec §3.2). A transaction that failed for another reason, or was cancelled before submission, stops nothing; an unknown outcome is reconciled, never duplicated.
  - Repair of refused and lost creations (spec §3.2): once the real key is held, serializable transactions of at most 100 rows that each read the rows and exact cells they rewrite, rewrite only cells still under the losing epoch, and re-read on conflict. The losing key is never deleted. A pass runs once the real key is held, after a restart, and when one of the device's own writes under the losing key settles; it reads the replica, the device's own unsettled writes included.
  - Rotation (spec §3.5): before an encrypted write to a space marked as needing rotation (H2), on `db.encryption.rotate(space)`. A bad delivery triggers no rotation by itself: the recipient's application is told (spec §3.4). One serializable transaction holds the successor and deliveries to at most 100 members (previous-version holders first, random order); the rest follow in delivery transactions of up to 100, to every remaining member whether or not a delivery to it exists. A refusal stops automatic rotation of that space on this device while the client runs (in memory only); explicit `rotate` always attempts (spec §3.5). `db.encryption.recoverRotation(space)` is the explicit recovery rotation.
- **Cost.** Proportional to the members of the spaces the session is a member of (at most 1,000 per supported space, spec §3.8), and to the rotations it makes: one delivery per member per version it lacks, and one per current member in each rotation.

## 5. Main risks

- **Key versions and deliveries accumulate.** Every rotation adds a version and one delivery per member. Reads look up the held key per cell version, and H4 computes one equality token per held version per predicate. A rotation carries at most 100 deliveries and the rest follow in batches, so a space with many members costs one HPKE seal and one row per member per rotation, spread over several transactions. Measure reads, equality queries, rotation size and delivery storage in a space with many members and rotations before landing.
- **Hot-path decryption.** Every subscription refresh re-materialises and re-decrypts its rows; fanout re-runs whole groups on invalidation. A 10,000-row live query in a busy project could decrypt 10,000 cells per change.
  - Mitigations: the decrypted-cell cache, and decrypting only the selected columns.
  - Benchmark before landing. The cache holds plaintext in memory; it is cleared on held-key removal, allow-list change and sign-out.
- **Browser thread model.**
  - Durable data lives in the worker, while tabs have in-memory dbs. If decryption happens in the worker, plaintext crosses `postMessage` to tabs; this is acceptable because it stays same-origin, and only one key store is needed.
  - If tabs decrypt, each tab needs the private store, and held-key revisions must be coordinated across tabs (spec §6.4 "last tab out").
  - Decided: tabs decrypt over a shared store (D5); the worker-only design needs a core change to sync.
- **Blocking versus async key acquisition.**
  - Keeping the hooks sync and returning `NeedsKey` keeps core simple. The costs: every binding entry point must loop on `NeedsKey`; a binding that exposes a synchronous transaction callback refuses a staging call that needs an unheld key or an unprepared space root with `key-pending`, and the application acquires first (spec §5.6). Core's own `Db::transaction` is async and does not have this limit.
  - An acquisition also performs reads through the same `Db`, so it must never run re-entrantly inside a hook. The runtime must never call `Db` from inside a hook.
- **Catalogue identity before confirmation.** A first offline open cannot build cell contexts.
- **Policy cost on the server.** Every read of an internal space row, and every delivery insert, is one or two indexed member lookups; root, successor and member-row writes evaluate the space row's read and both update clauses through `InheritsFrom`; fanout evaluates the member lookup for sync visibility, and sync support loads one space's member rows per row served (H7). Measure it with the app's real space-row policies.
- **Space size.** The first release supports 1,000 members per space, as a documented limit that nothing enforces (spec §3.8). At that size a rotation is about 1,000 seals and 1,000 delivery rows that every holder device receives, and a device removal marks every space whose current version the removed device could open (spec §2.8). Measure these before landing, and before raising the limit.
- **Refused creations cost a scan of the space.** Repairing a refused or lost creation reads the space's rows to find cells under the refused epoch (spec §3.2), then rewrites them in bounded serializable transactions that re-read on conflict. It is proportional to the space, happens only after a refusal or a lost root, and is bounded by the rows the device may update.
- **Unreadable rows and pagination.** Short pages are accepted by the spec, but UI code that treats a short page as the end of the results will misbehave.
- **Feature unification.** See H10.

## 6. Decisions

- **D1. Access model (decided).** Entitlement to a space's keys is a row in Jazz's members table, from which the space row's read rule must come (checked at deploy). Changing members, creating and rotating need read and update permission on the space row (update meaning both update clauses on the current row, as a no-op save), except that the account creating the space row may add itself in the same transaction, and any member may leave. The space row's update rule is therefore the rule for managing members; the deploy warns where it can see that rule is broad. Keys move by delivery from members' clients, derived from member rows and deliveries. Removal is detected from member rows and rotated lazily.
- **D2. Where decryption happens.** Inside core at result materialisation (H3), so pagination, fanout diffs and every binding behave alike.
- **D3. Whether the E2EE system schema enters the app's schema hash and bundle.** Included deterministically, appended by the loaders only when encryption is declared.
- **D4. Reaching the space row from internal rows.** One focused policy node, `InheritsFrom` (table identity plus row ID columns), over candidate tables fixed at deploy (H7), and one set of internal tables for every space table.
- **D5. Browser thread model (decided: per-tab decryption over a shared IndexedDB key store).** Each tab runs its own `Db` (an in-memory replica that syncs sealed rows with the worker that owns the durable store), and the hooks run where a `Db` reads or writes its own rows: core serves a downstream peer stored (sealed) images and takes its uploads as they are, with no hook on either path. Decrypting only in the worker would need a core change to sync, so each tab's runtime opens the shared private store and decrypts and seals itself. Keys are held in memory only, zeroized when dropped, and never persisted unwrapped; the store's at-rest key is a non-extractable WebCrypto key. Tabs coordinate through the store's compare-and-swap and a Web Lock (spec §6.4). Known limit, whatever the worker model: any script that runs on the page's origin can use the non-extractable (but usable) WebCrypto key to unprotect this device's stored long-term keys and read the space keys a tab holds from memory, so it can open what later deliveries and rotations give the device, and act as the device, until the device is removed from its account (which rotates the account); rotating a space does not stop it. It cannot reach other devices' keys, and it loses access when the device is removed, except through a device it approved while it had access: that device keeps access until it is removed too, so the account's device list must be checked and every affected or unknown device removed. Replaces the earlier decision (keys and decryption in the worker, tabs receiving plaintext).
- **D6. Key triggers.** Internal subscriptions run by the client runtime (H6).
- **D7. No-key writes.** `NeedsKey` plus a retry by the caller.
- **D8. Randomness (decided: the recommendation).** `OsRandom` by default everywhere, with host injection only for tests.
- **D9. Space creation (decided).** Optimistic, in the same transaction as the first encrypted write that needs the space or by explicit `createSpace`; no creation on space-row insert; no local permission evaluation; no server-side root uniqueness. A refusal of the root stops automatic creation of that space on the device while the client runs; an explicit `createSpace` always attempts.
- **D10. Bad deliveries (decided).** A delivery that does not open is reported to the recipient's application (`invalid-delivery`, naming the sender) and nothing is written; the recipient stays `key-pending` until an updater rotates. Insiders delivering badly are a documented limit, handled by removing them (spec §3.4, §8).
- **D11. Supported size (decided).** Up to 1,000 members per space in the first release, documented and not enforced (no policy can count rows); members' runtimes report `space-over-member-limit` beyond it. Devices watch only the deliveries of the current version, of skipped versions they hold and of their own account. A device removal rotates each affected space lazily, like a member removal (spec §2.8, §3.8).
