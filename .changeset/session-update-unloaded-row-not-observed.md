A backend `update()` inside `forReqUser`/`forSession` no longer needs the row to be loaded first. On a row this backend instance hasn't loaded yet (for example right after a restart, or on another instance), it reads the row through the caller's session (waiting at most 10 seconds for the server) and then stages the update, instead of failing with "read policy denied UPDATE ... requires read permission on the target row". A backend connected to Jazz Cloud never decides a session's write permissions itself, whatever the row's read policy reads: it stages the update or upsert and Jazz Cloud decides, as it already did for upserts. The update shows on that backend until Cloud answers to reads that include pending writes (`local-first` and `local-only`), judged by the session's read policy on the updated row: a session that updates a column its read policy compares, on a row it can't read, can read that row that way until Cloud refuses the update. A backend's default `remote` read shows only rows Cloud accepted, under their own permissions. The update's `wait()` rejects if Cloud refuses it, and a write another session builds on it meanwhile is rejected with it. This also covers a fresh backend under a read policy that depends on other rows (such as a membership table), which used to refuse even an allowed update until it held those rows. When the server sends no row, because it doesn't exist or the session can't read it, the update is refused with "the row does not exist or the session may not read it". A backend with a local-only store has no server to ask and decides itself.
