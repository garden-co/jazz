Write denials are consistent wherever they are decided, and reveal less about whether a row exists. On the server, and on a backend with a local-only store, an update or delete a session may not make is refused with the same message whether the row is hidden from the session, deleted while hidden from it, or doesn't exist. An upsert can't hide this fully: on a row that doesn't exist it inserts, so it is refused only where the row exists. On a backend connected to Jazz Cloud, Cloud decides, and such an update is always refused with the same code, `permission_denied`, though not always with the same message or at the same time: a row the backend holds deleted is refused at once, a row it holds is staged and its `wait()` rejects with Cloud's refusal, and a row it doesn't hold is read from the server first (for up to 10 seconds) and then its `wait()` rejects. A write denied at once, as it is staged (on a local-only store, or a row the backend holds deleted), now throws an error with `code: "permission_denied"`, the code a rejected `wait()` carries, so one check handles both. `TestDb.expectDenied` now counts a write denied at once, and fails with "expected the write to be denied, but it was accepted" when it isn't denied.
