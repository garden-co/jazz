Write denials are consistent wherever they are decided, and reveal less about whether a row exists. An update or delete a session may not make is refused with the same message whether the row is hidden from the session, deleted while hidden from it, or doesn't exist, on the server and on a backend. An upsert can't hide this fully: on a row that doesn't exist it inserts, so it is refused only where the row exists. On a backend connected to Jazz Cloud, Cloud decides: a write to a row the backend holds is staged and its `wait()` rejects, while an update of a row it doesn't hold is refused after asking the server, so the time to the answer and where it surfaces can still differ. A write denied at once, as it is staged (for example on a local-only store, or an update of a row the server didn't send), now throws an error with `code: "permission_denied"`, the code a rejected `wait()` carries, so one check handles both. `TestDb.expectDenied` now counts a write denied at once, and fails with "expected the write to be denied, but it was accepted" when it isn't denied.
