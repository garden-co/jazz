End-to-end encryption (E2EE) keeps selected logical values encrypted on the server. Jazz still checks ordinary row permissions. A recipient needs both permission to receive a row and a verified encryption key to read its protected values.

This is experimental browser and native Node functionality. It is not a claim of independent security audit, production qualification or React Native support. The [encrypted chat example](https://github.com/garden-co/jazz/tree/main/examples/e2ee-chat) demonstrates two-account messaging and encrypted image uploads using the existing chat UI.

## Declare an encryption space

An encryption space belongs to a stable scope row. In this example, each chat has its own space; messages reference it through `chatId`:

<include cwd lang="ts" meta='title="schema.ts"'>
  ../examples/e2ee-chat/schema.ts#e2ee-chat-schema
</include>

The application sees the declared logical types. Jazz stores ciphertext for the protected columns. References, sender IDs, row IDs, timestamps, row provenance, ciphertext sizes and access patterns are not hidden. Keep fields needed for permissions outside the encrypted column list. The server cannot validate encrypted message text or image contents.

Declaring encrypted columns adds the managed schema and package-owned device policies. Applications still define permissions for their rows and space administration. Do not replace the package-owned device policies or use a blanket allow-all space mutation policy. The example constrains chat membership and key grants to the chat owner.

The example creates an immutable `chatOwners` binding in the same exclusive
transaction as the chat. Its declared references let the root-insertion policy
prove that the current account owns the specific chat. The managed space's
`identifier` is not itself a declared chat reference; do not replace this check
with a creator-only root policy, which would let other accounts insert conflicting
roots for an existing chat.

`e2eeAccountRelation()` from `jazz-tools/e2ee` declares the binding's `accountId`
relationship to the SDK-managed account identity table. Pass a different local
column when needed, for example `e2eeAccountRelation("ownerId")`. The application
table name is arbitrary: administration policies explicitly connect its account
and scope references to the space creator and `identifier`.

For creator-owned records, declare an explicit ownership column:

```ts
projects: s.table(
  { name: s.string(), ownerId: s.uuid() },
  { owner: e2eeAccountRelation("ownerId") },
),
```

Populate `ownerId` with the creating account's ID and constrain inserts to that
account, as in the permissions below. Jazz also records `$createdBy.account`
automatically, and it remains the original creator when somebody edits the row.
You can use that metadata in ordinary permission predicates. Declaring an account
relationship through `$createdBy.account` or `$updatedBy.account` is not supported
by the current catalogue encoding; use a stored UUID column for the relationship.

## Authorise space administration

Use `p.messages.space` to authorise the space declared by `.encrypted(...)`.
`allowInsert` controls creation; `allowUpdate` controls membership changes and
key maintenance. These rules are separate from ordinary message permissions.
For example, with a declared account relationship on `chats.ownerId`:

```ts
p.messages.space.allowRead.always();
p.messages.space.allowInsert.where((space) =>
  p.chats.existsIncludingCreated.where({
    ownerId: space.creatorAccountId,
    id: space.identifier,
  }),
);
p.messages.space.allowUpdate.where((space) =>
  p.chats.existsIncludingCreated.where({
    id: space.identifier,
    ownerId: session.user.account,
  }),
);
```

The creation callback exposes `creatorAccountId`, the immutable account that
created this space root. It is a built-in field, independent of its recipients
and of the scope row's creator. The rule above explicitly requires it to match
the chat's owner. Membership callbacks expose `identifier` and check the acting
`session.user.account`.
Jazz binds each rule to the declared scope's accepted catalogue identity and
maintains a private typed administration binding with the signed root. Signed
roots and the binding remain immutable. The SDK generates the history, delivery
and current-membership policies; keep group administration rules separate.
Sibling encrypted tables sharing a scope share its administration rules.
Mixing these helpers with explicit policies on the managed space tables rejects.
Initialise helper-managed spaces for the creator, then add other recipients
with `spaces.grant()`. Explicit initial-recipient lists are unsupported with
this administration helper. Existing applications using explicit managed-table
policies retain that functionality.

## Derive row permissions from space membership

Use `fromEncryptionSpace()` to derive row permissions from current space
membership. With no options, recipients can read, insert, update and delete its
encrypted rows. Encrypted declarations automatically add the membership tables
for their referenced scopes. Choose the helper on each protected table:

```ts title="schema.ts"
import { schema as s } from "jazz-tools";
import { e2eeAccountRelation } from "jazz-tools/e2ee";

export const app = s.defineApp({
  chats: s.table({ ownerId: s.uuid() }, { owner: e2eeAccountRelation("ownerId") }),
  messages: s
    .table({ chatId: s.uuid(), text: s.string() }, { chat: s.rel("chats", "chatId") })
    .encrypted({ space: "chatId", columns: ["text"] }),
});
```

```ts title="permissions.ts (excerpt)"
import { definePermissions } from "jazz-tools";
import { app } from "./schema.js";

export const permissions = definePermissions(app, ({ policy: p, session }) => {
  p.messages.fromEncryptionSpace();
  p.messages.space.allowRead.always();
  p.messages.space.allowInsert.where((space) =>
    p.chats.existsIncludingCreated.where({
      id: space.identifier,
      ownerId: space.creatorAccountId,
    }),
  );
  p.messages.space.allowUpdate.where((space) =>
    p.chats.exists.where({
      id: space.identifier,
      ownerId: session.user.account,
    }),
  );
  // Also define chat permissions, as above.
});
```

The space administration rules also authorise current space membership writes.
For groups, use the group administration helper described below. Data access
does not grant administration authority. Current membership writes are denied
without administration rules. The SDK maintains direct account and nested group edges in the same
exclusive transaction as signed membership history. A denied edge change rejects
the history change too. Group changes use the existing recursive policy support;
the SDK does not copy all effective members into each space.

Import `./permissions.js` in the client before creating the Db, using the same
`app` instance, or define the permissions alongside your schema. A successful
`definePermissions` call records which tables use the helper in memory. This
lets write preparation distinguish helper tables from explicit-policy tables.
Registration contains no secrets and does not replace the deployed policies
enforced by the server. Automatically generated membership tables do not select
data permissions or enable membership maintenance by themselves. Explicit data
permissions retain their first-write behaviour. The older
`encryptionSpacePolicySchema()` declaration remains supported but is unnecessary
for new encrypted schemas.

Wait for the scope creation handle's `wait({ tier: "global" })` before writing
helper-protected rows. A missing or unaccepted space throws
`E2eeDataError("space-not-initialised")`, including before an upload consumes its
source. Creating the scope and its first helper-protected row in one transaction
is not supported. Tables using explicit policies retain their atomic first-write
behaviour, even when they reference the same scope.

Pass optional `read`, `insert`, `update` and `delete` predicates to restrict each
operation further. `write` supplies a common predicate for insert, update and
delete. All supplied predicates are ANDed with membership; when both `write`
and an operation-specific predicate are present, both must pass. Predicates
accept the same where objects, expressions and row callbacks as `.where()`.
Update restrictions apply to both the existing and proposed row.

```ts
p.messages.fromEncryptionSpace({
  write: { "$createdBy.account": session.user.account },
});
```

This lets members read all messages and change only their own. Omitted
operations require membership alone. Keep restrictions inside the helper:
separate explicit allow rules are ORed, so combining them with the helper is
rejected to prevent bypassing membership. A read predicate such as
`{ visibility: "public" }` still requires membership and does not make encrypted
content public outside the space.

Initial membership matches the explicit recipient list, which can
exclude the creator. Revocation retracts ordinary row access but cannot erase
keys or plaintext that a former recipient already retained.

## Keep account and key storage separate

Configure `e2ee: { app }` when creating the authenticated Db in a browser. Jazz
defaults to a persistent IndexedDB key store, separate from account selection
and the Jazz row cache. Its records are scoped by the canonical account registry
URL (which includes the server and application ID), environment and account ID.
Concurrent tabs update keys atomically, and writes wait for strict IndexedDB
transaction durability. Storage failures are reported; Jazz never substitutes
an in-memory store. Clearing the row cache does not delete this key store.

Supply `e2ee: { app, store }` to override the browser default. Native Node and
other non-browser hosts require this explicit store. The store implements
`AccountStore`, but must use a different value from account-selection storage.
Its `update(transform)` operation must be atomic across concurrent callers; the
synchronous transform can run more than once. Custom stores retain their
existing format and location: enabling the browser default does not migrate
keys from a previously configured custom store.

The default IndexedDB storage format is `jazz-e2ee-keys-v1`, IDB schema version
1, object store `accounts`. A record key is the JSON tuple
`[registry, environment, accountId]`; its value is the existing versioned E2EE
key-state string. This is a new namespace and does not modify account-selection
or Jazz row-cache encodings.

Do not use an in-memory closure when keys must survive reload. Do not use a localStorage read/modify/write sequence as an atomic store. Losing key storage is not equivalent to logging in again: another device requires approval or recovery. Protect stored keys against browser-profile theft and cross-site scripting. E2EE cannot protect plaintext from compromised application code running on a recipient device.

The store contains private device decryption and signing keys; the SDK does not
encrypt that store at rest. Native hosts must provide appropriately protected
storage. Browser IndexedDB remains accessible to same-origin code.

## Start automatically, including offline

Creating the Db prepares its local encryption state automatically. Do not gate
the interface on `devices.list()`, an explicit initialisation call or a successful
server connection. Creating a scope also prepares its initial space and grants.

A newly generated local account can initialise offline once this browser profile
has cached an authenticated catalogue for the same server, application and
environment. The catalogue contains schema information, not account keys or
membership. A first visit without that catalogue still needs a connection.
Imported accounts and recipients without accepted public keys cannot be treated
as fresh local founders.

Account-selection storage reserves one original device for each account and
application before publishing an offline founder. Its v3 inventory keeps v1/v2
roots and selection readable, but ordinary legacy provenance does not prove
first-device ownership. A missing bound founder journal cannot regenerate an
epoch; the exact original journal can resume after an account recovery import.
Independent account stores still rely on Global authority to select one winner.

Use `wait({ tier: "local" })` to wait for the persistent local owner before
clearing a draft or reporting “Saved on this device”. This is not server
acceptance, verified membership or delivery to another person. Keep the original
write handle and observe `wait({ tier: "global" })` separately when the interface
needs accepted completion. For initialisation, that wait also covers accepted
history verification and the permitted initial key handoff.

The SDK journals the original device, epoch, transaction and encrypted material
before publication. Persistent restart and reconnect reuse that work; they do
not rerun your callback or consume an upload stream again. Retain both the Jazz
database and private key store. Clearing either is not a recovery mechanism.

## Share with another account

Use application-scoped Jazz account IDs, not provider subjects or device IDs.

The example's sharing helper updates ordinary membership and then grants the key:

<include cwd lang="ts" meta='title="src/chat.ts"'>
  ../examples/e2ee-chat/src/chat.ts#e2ee-chat-share
</include>

The recipient must have usable, accepted device history. A key grant does not add an application membership row, and an application membership row does not grant a key. If an app performs those operations separately, report success only after both finish. Use a stable membership-row identity so retrying does not create duplicate memberships. Show failures and allow explicit retry rather than claiming atomic sharing.

Creating a scope row prepares its initial space and creator grant automatically. Explicit initial recipients can exclude the creator; do not assume the initialiser becomes a member. Use an exclusive transaction when initial scope, membership and encrypted data must share one accepted outcome. Keep `existsIncludingCreated` on the relevant INSERT-policy source occurrences. It does not change read, update or delete policies, or let created rows substitute for accepted history during later administration.

Initial recipient delivery follows in a later accepted transaction. Local completion does not wait for it. An explicit Global wait includes the permitted handoff, but failure cannot roll back data that the server has already accepted. The SDK retries rejected maintenance conflicts at most twice, revalidating accepted eligibility each time, without replaying your original write. Report other failures and inspect the state with `db.e2ee.explain({ scope: app.chats, identifier: chatId })`; do not describe accepted data as rolled back.

For a pre-existing scope without an encryption space and a table using explicit
policies, the first encrypted write
initialises the space for that writer, not automatically for the original scope
row's creator. Explicitly grant other intended recipients.

## Upload an encrypted image

Pass the file's byte stream to the ordinary streaming API. This is the example's
message helper; its `IMAGE_TYPES` and `MAX_IMAGE_BYTES` constants allow PNG, JPEG,
WebP and GIF images up to 10 MiB:

<include cwd lang="ts" meta='title="src/chat.ts"'>
  ../examples/e2ee-chat/src/chat.ts#e2ee-chat-upload
</include>

Image bytes and protected metadata use the same space and are published in one mutation. Do not convert the image to a DataURL or encrypt it in a component. The SDK handles authenticated stream framing and ordinary large-value storage. The example limits accepted image types and size for usability; client validation is not a server-enforced security boundary.

Uploads consume bounded chunks with backpressure. They stage ciphertext before opening the final exclusive transaction. Immediately before publication, Jazz checks the selected epoch, writer/device and effective membership against transaction-backed accepted history. A change during the upload rejects publication, even if ordinary stale writes are configured to warn. Present that failure and require explicit resubmission; the SDK must not replay a one-shot source or weaken the retry's transaction checks.

For a new scope and its first file, `db.streamingTransaction(callback)` collects mutation declarations, stages their streams and publishes them together. Its callback receives a mutation-only plan, not an open database transaction: there are no reads or manual commit. It supports ordinary `insert` and streaming `insertStreaming`, `updateStreaming` and `upsertStreaming`; declaration methods return row IDs. All declarations are validated before any source is pulled. Do not hold an ordinary transaction open while waiting for file input.

### Upload limits

- Encrypted streaming supports logical byte columns in the root view. Explicit branch targets and implicit `branchBy` targets are rejected before source consumption.
- Encrypted text/JSON streams, equality-indexed streamed columns, scope-row streams and partial file edits are unsupported.
- Missing keys or unsupported declarations fail before source consumption. Ordinary row authorisation is checked at final acceptance, so a denied write may already have uploaded ciphertext.
- A source failure releases stages not committed locally. Once a local transaction is committed, rejected-version storage retains its payload for normal retry/discard handling.
- Persistent restart retains the original exclusive transaction and its validation evidence. Missing or incompatible evidence fails closed; it must not become a mergeable write or silently create another transaction. Do not automatically resubmit a source after a lost connection.

## Read and render

Use ordinary typed queries and React hooks. The central decoder returns logical values only after authentication. An image stream must pass final authentication and end-of-stream checks before any complete value is exposed. Encrypted decoding and key failures throw `E2eeDataError`, with codes including `key-unavailable`, `key-not-shared`, `maintenance-required` and `invalid-ciphertext`; ordinary transport, authorisation and query failures retain their own error types. The `refused` state belongs to `db.e2ee.explain`, not the query error-code contract. An active device with usable account keys can still lack membership in the row's space. Never display ciphertext as plaintext or replace an authentication failure with an empty successful result.

The example uses `ReadTier.LocalFirst` for retained messages and separate ID-only `ReadTier.Remote` queries for server availability. `Remote` reads use the Global tier and exclude pending local writes. After a browser restart, “Available from server” means the server query observed the row; it does not recover the original write handle's Global completion or prove recipient delivery. If a server-backed query ends with a connection error, choose **Reload chat** after reconnecting. The example does not automatically retry terminal query errors or install a service worker.

Ordinary queries materialise the entire image in memory. Bounded upload memory is not a bounded-memory download guarantee. Create a Blob/object URL only after successful decryption and revoke the URL when replacing or unmounting it. Download from those authenticated bytes, not from an exposed raw ciphertext locator.

## Devices, groups and recovery

`db.e2ee.devices.list()` distinguishes verified membership (`state`) from this caller's key-delivery readiness (`keyReadiness`). Approve a pending device from an already authorised device with `devices.approve(deviceId).wait()`; revoke through `devices.revoke(deviceId).wait()`. Do not infer remote key possession merely from an active ledger entry.

Groups contain accounts or other groups. Encrypted table declarations add the
managed group schema and the current membership tables automatically. A
group-only application can declare the exported `deviceRequestSchema` and
`groupSchema` explicitly and include `deviceRequestPermissions` in its deployed
policy bundle. The chat example does not include groups.

Declare who may create and administer groups through `e2ee.groups` in the
permissions callback. For groups administered by their creators:

```ts title="permissions.ts (group rules)"
export const permissions = definePermissions(app, ({ policy: p, session, e2ee }) => {
  e2ee.groups.allowInsert.always();
  e2ee.groups.allowUpdate.where({ creatorAccountId: session.user.account });
  // Include your application-data and space-administration rules here too.
});
```

Direct predicates expose the group's `id` and immutable `creatorAccountId`.
Callbacks expose `group.id` for application ownership checks; declare the
corresponding group reference on the application table. `allowInsert` controls root
creation. `allowUpdate` controls membership changes, key rotation, device and
recovery key delivery, and current membership writes. Both rules are needed to
complete group creation under this owner-managed configuration, including the
creator's initial membership and key delivery. Signed roots and history remain
immutable. Omitted rules deny the corresponding operations. Group membership
or possession of a key does not grant administration authority.

Here, `allowInsert.always()` lets any authenticated account create its own
group; Jazz supplies the authentication and creator checks. Membership changes
and later key maintenance use the same `allowUpdate` rule. With the creator-only
rule above, later delivery to additional devices or recovery recipients requires
an available creator device with the relevant keys.

Jazz generates the underlying authenticated author checks and policies. Repair
requests may be authored by the requesting account; they grant no membership
or key access. Topology and encrypted maintenance records are readable by
authenticated accounts. The helper cannot be mixed with explicit policies on
the managed group tables, including current group membership. Existing raw
policy configurations remain supported when the helper is unused. The helper
adds no stored fields, tables or signed formats; `creatorAccountId` is the
public policy name for the existing group creator account.

With those permissions deployed, create and share a group:

```ts
const engineering = await db.e2ee.groups.create().wait();
await db.e2ee.groups.add(engineering.id, aliceAccountId).wait();
await db.e2ee.groups.add(engineering.id, bobAccountId).wait();
await db.e2ee.spaces.grant(app.chats, chatId, engineering.id).wait();
```

Group administrators control who gains access through the group to every space
shared with it. Group administration does not itself authorise sharing a space.
To remove one membership path, call
`groups.remove(engineering.id, aliceAccountId).wait()`; to stop sharing just one
chat, call `spaces.revoke(app.chats, chatId, engineering.id).wait()`. Other direct
and group membership paths still apply.

E2EE lifecycle waits have no tier option: they wait for accepted completion. A
bare recipient ID is resolved against accepted account and group history in the
transaction authorising the change; unknown and ambiguous IDs reject without a
membership write. Explicit `{ kind: "account" | "group", id }` selectors remain
supported. Accepted topology and epoch history determine effective membership.
Keep nesting shallow, because evaluating it requires following the dependent
groups and membership records.

`recovery.create().wait()` returns recovery material. Treat it as a credential: do not put it in logs, normal UI state or ordinary rows. `recovery.status(material?)` reports coverage and validation; `recovery.use(material?).wait()` performs recovery. Account recovery and complete coverage of every group/space are different outcomes. The chat example does not provide a device/recovery administration UI; retain browser storage or implement that flow before depending on another device.

The example deliberately keeps grants, successors and device-key deliveries
owner-controlled. Other recipients can send/read messages and reload retained
keys, but cannot publish their own device deliveries under its ordinary policies.
Later device-key redistribution therefore requires an available owner. This is
not a general multi-device administration example.

## Revocation, offline use and retained history

`spaces.revoke(scope, identifier, recipientId).wait()` changes membership and triggers the required key transition. Remove ordinary application access separately when the app uses its own membership policies. Removal cannot erase plaintext, ciphertext or secrets that a former recipient already retained. A malicious server colluding with an old keyholder may retain staged or historical ciphertext; rotation does not promise retroactive secrecy.

Accepted spaces can read and write offline using retained rows, keys and complete accepted history. Newly generated local founders can use their own provisional spaces before server acceptance, but that state is not verified membership. An explicit initial recipient still needs accepted public keys; possession of an author envelope does not make the author a recipient.

Encrypted uploads into an accepted space validate locally retained acceptance,
signatures, device eligibility and membership before pulling the source. Missing
history may be fetched online before staging. A missing root on an existing
scope is not proof that the scope is unencrypted; if the client is explicitly
offline, that case fails before source consumption. Storage or verification
failures are not cache misses.

The final exclusive transaction rechecks the selected epoch and membership.
An offline Local receipt promises local durability, not eventual authority
acceptance. Reconnect can reject the original write; show that outcome without
replaying the source or inventing a new identity.

Known stale membership warns before writes by default. Set
`e2ee.staleWrites: "reject"` to refuse those writes locally. Warning mode can
expose new content to removed recipients who retain an old key; it never restores
access to a proven revoked device or removed member. A membership change while a
file source is being consumed rejects publication even in warning mode.

## Querying and schema changes

Encrypted predicates require an opt-in equality index and an equality constraint on the plaintext space column. The SDK rejects unindexed encrypted predicates and unsupported operators; it does not silently filter plaintext on the client. `orderBy` on encrypted columns is unsupported, including equality-indexed columns. Deterministic index tokens disclose equality information. Keep permission and routing fields plaintext, and choose searchable protected fields deliberately. File streams cannot target an equality-indexed encrypted column.

Encryption contexts bind stable application, scope, row, table and column identities and logical types. Use supported schema migrations; do not copy ciphertext between rows/columns or relabel logical types as a shortcut. A schema migration does not encrypt existing plaintext values: conversion requires an explicit authorised client read, re-encrypt and write workflow. A rename and a value conversion are different operations. Test migrations with authorised readers and retained history before deployment.
