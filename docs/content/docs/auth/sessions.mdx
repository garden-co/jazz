## Session identity and authorship

Jazz also records authorship and edit times through the edit metadata magic columns `$createdBy`,
`$createdAt`, `$updatedBy`, and `$updatedAt`.

Do not declare `createdAt`, `createdBy`, `updatedAt`, or `updatedBy` merely to model that same
metadata: use these `$...` columns in queries, ordering, and permissions, and let Jazz stamp writes.
`jazz-tools validate` points out those conventional duplicates. If importing an external system whose
field really has one of those names, mark that one field explicitly with
`s.allowExternalProvenanceName(...)`.

See [Queries](/docs/reading/queries#edit-metadata-columns) for how to select and filter on these
columns.

Provider session fields and claims, including `iss`, `sub`, and `user_id`, retain their admitted
values. Jazz separately derives the reserved logical `session.author` from the exact `[iss, sub]`
pair. Its portable value is canonical JSON and is used for transaction authorship, `$createdBy`,
`$updatedBy`, and provenance policies; it is interned only inside a running core. On backends,
`await context.forRequest(...)` and `context.forSession(...)` both run as that user for permissions and
also stamp authorship as that user. Client bindings expose the same derived value as
`session.author`; use it when an application needs to store or compare an author, rather than
reconstructing the encoding from `issuer` and `user_id`.

For trusted invite or membership input where you have an issuer and subject but no active Jazz
session, use the shared constructor:

```ts
import { sessionAuthor } from "jazz-tools";

const invitedAuthor = sessionAuthor(trustedIssuer, trustedSubject);
await db.insert(app.members, { roomId, author: invitedAuthor });
```

`sessionAuthor(...)` only validates and canonically encodes the two components. It does not verify a
JWT, authenticate the subject, or admit that identity to Jazz; only use identity components obtained
from a trusted authentication boundary.

### Attribution without impersonation

Sometimes backend code should keep backend-level permissions but still record a user's identity in
edit metadata. Use the attribution helpers for this:

- `context.withAttribution(issuer, userId)`&hairsp;—&hairsp;stamps writes as the exact issuer/user pair
- `context.withAttributionForSession(session)`&hairsp;—&hairsp;derives authorship from a resolved session
- `await context.withAttributionForRequest(req)`&hairsp;—&hairsp;derives authorship from an authenticated request

<include cwd lang="ts">
  ../examples/docs/todo-server-ts/src/request-context.ts#backend-attribution-ts
</include>

These differ from `forRequest` / `forSession` in one key way:

- `await context.forRequest(...)` / `context.forSession(...)` change both permission evaluation **and** authorship
- `withAttribution*` only changes authorship&hairsp;—&hairsp;permissions stay at the backend level
- `asBackend()` and unscoped `db()` writes default to `jazz:system`

<Callout type="info">
  Client-side filters are useful for UX, but they don't enforce access control on their own. Use
  [Permissions](/docs/auth/permissions) to define row-level policies that control which sessions can
  read or mutate a row.
</Callout>
