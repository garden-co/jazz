## How writes work

Writes are methods on the `Db` handle: `insert`, `upsert`, `update`, `delete` and `restore`. Each
call commits as its own transaction, which the server checks against your
[declarative permissions](/docs/schemas/policies) and accepts or rejects as a whole. To make several
reads and writes commit together, group them in a [transaction](#transactions).

Every write returns a `WriteResult`:

- `value`&hairsp;—&hairsp;The written result. `insert` and `restore` return the row, so a new
  row's id is `db.insert(…).value.id`; `upsert`, `update`, and `delete` return `undefined`. Inside a
  [transaction](#transactions), `tx.insert(…)` returns the staged row itself.
- `txId`&hairsp;—&hairsp;A promise for the committed transaction ID, the durable identity of this
  write.
- `wait(...)`&hairsp;—&hairsp;A method that waits until the write is confirmed at a
  [durability tier](#write-durability-tiers), for example accepted by the server.

Writes made through an open transaction are not individually waitable. Wait on the result returned
by the transaction or its `commit()` call instead.

When a write shows up depends on the client. A thin client shows it after the server answers. A
[local-first client](/docs/setup/web-client/local-first-client) applies it to its local database
first, so it shows at once, before the server has seen it.
[Write durability tiers](#write-durability-tiers) covers what that means when you wait.

### Upsert with a known ID

Use `upsert(...)` when your app already knows the row ID and wants to create that row if it does
not exist, or update it if it does. Like `insert`, `update`, and `delete`, it returns a
`MutationResult<void>` that can be awaited for durability.

### Restore a deleted row

Trying to insert, update or delete an already deleted row will fail. Use `restore(...)` to make a soft-deleted row visible again.
`restore` requires providing new data for the restored row (missing fields will use schema defaults, if they exist).
Deleted rows are omitted from queries by default. Add `includeDeleted()` when you need to find a
row before restoring it.

### Partial updates and nullable fields

`update(...)` only modifies the keys you pass.
Omitted fields are left unchanged; explicitly passing `undefined` also leaves a field unchanged.
To clear a nullable column in TypeScript, pass `null`.
Required fields cannot be set to `null`.

### Editing a page of a large value

Use `update(...)` to replace complete primitives and, with its `applyDiffs`
option, edit a selected page of a `bytes` or `string` column or set an existing
JSON member. Replacements and diffs are one atomic update, but a column must
appear in only one of them. Splice coordinates are relative to `within`, and
multiple splices run in order against the result of the previous splice.

```ts
db.update(
  app.documents,
  documentId,
  { title: "Revised document" },
  {
    applyDiffs: {
      bytes: {
        within: { from: 1_000_000, to: 2_000_000 },
        splices: [{ at: 4, delete: 3, insert: new Uint8Array([1, 2]) }],
      },
      text: {
        within: { from: 4, to: 124 }, // UTF-16 coordinates
        splices: [{ at: 3, delete: 1, insert: "revised" }],
      },
      metadata: {
        edits: [{ op: "set", at: "/chapters/0/title", value: "New title" }],
      },
    },
  },
);
```

For a diff-only update, pass an empty replacement object:

```ts
db.update(
  app.documents,
  documentId,
  {},
  {
    applyDiffs: {
      text: {
        within: { from: 4, to: 124 },
        splices: [{ at: 3, delete: 1, insert: "revised" }],
      },
    },
  },
);
```

For byte-oriented text, use `{ fromUtf8, toUtf8 }` in `within` and
`{ atUtf8, deleteUtf8, insert }` in each splice. Jazz rejects out-of-range
coordinates and text boundaries that split a code point or surrogate pair. This
revision does not add a page-staleness/CAS check; keep page coordinates aligned
with the value your application last read. `update(..., { applyDiffs })` is for
existing rows only; inserts and full replacement continue to use the ordinary
mutation methods.

`applyDiffs` also works inside a transaction. Coordinates are relative to the
value the transaction sees, including its own earlier writes, so an append
after an append in the same transaction lands after both, and every diff
commits together with the transaction's other writes:

```ts
await db.transaction(async (tx) => {
  tx.update(
    app.documents,
    documentId,
    { editedAt: new Date() },
    {
      applyDiffs: {
        text: {
          within: { from: length, to: length }, // an empty page at the end
          splices: [{ at: 0, delete: 0, insert: nextTokens }],
        },
      },
    },
  );
});
```

Only the pages a diff touches are rewritten, so streaming many small appends
into a long value stays cheap however long it grows.

### Uploading and downloading files

Store a file in a `bytes` column next to its metadata:

```ts title="schema.ts"
files: s.table({
  name: s.string(),
  type: s.string(),
  size: s.int(),
  content: s.bytes(),
}),
```

Upload from the browser with `insertStreaming`, which streams the bytes into the row instead of
copying the whole file into memory. It works in the thin and the local-first client, and it goes
through `/jazz`, so the file never passes through a route of your own:

```ts
async function upload(file: File) {
  const inserted = await db.insertStreaming(app.files, {
    name: file.name,
    type: file.type,
    size: file.size,
    content: file.stream(),
  });
  await inserted.wait({ tier: "global" });
  return inserted.value.id;
}
```

`updateStreaming` and `upsertStreaming` replace a file in an existing row the same way.

To download, select the column. For a large file, read it a page at a time with a range (see
[Partial large values](/docs/reading/includes-and-relations#partial-large-values)):

```ts
const row = await db.one(app.files.where({ id }).select("name", "type", "content"));
const url = URL.createObjectURL(new Blob([row!.content], { type: row!.type }));

// Or the first megabyte only:
const head = await db.one(app.files.where({ id }).select({ content: { from: 0, to: 1_048_576 } }));
```

## Transactions

Use a transaction when several reads and writes must share one commit. Use a mergeable transaction
for most work. Use a serializable transaction only when the authority must check the whole
operation against one stable view of the data.

See [Transactions](/docs/writing/transactions) for examples, error handling and the differences
between commit and authority acceptance.

## Write durability tiers

A write can be confirmed at two points: when the client has saved it, and when the server has
accepted it. For ordinary mutations and mergeable transactions, `wait({ tier })` controls which
confirmation the caller waits for:

| Tier     | Resolves when                           |
| -------- | --------------------------------------- |
| `local`  | Saved by the local persistence driver   |
| `global` | Authorized and durably accepted by Core |

<WriteTierDiagram />

Offline, only `local` can resolve. A `global` wait stays pending until the device
reconnects and Core accepts or rejects the queued write, however long the outage
lasts. Both choices apply the initial mutation locally and upload it when connected.

A `global` wait fails early only when the client stops trying to reach Core: a
protocol error, a closed client, or a credential the server refuses that nothing
renews. Only an account context's refresh cycle and a local-first token the Db
mints itself count as renewing a credential, so their waits outlast an expired
token. With a static token or a backend secret, a refused credential ends the
wait. To bound how long you wait, pass `timeoutMs`. The wait then rejects with
a `WriteWaitTimeoutError` (`code: "timeout"`), but the write stays queued and may
still be accepted, so do not retry it:

```ts
try {
  await db.insert(app.todos, { title: "Buy milk" }).wait({ tier: "global", timeoutMs: 5_000 });
} catch (error) {
  if (error instanceof WriteWaitTimeoutError) showPendingBadge();
  else throw error;
}
```

## Showing sync status

To show whether the user's changes have reached the server, read the Db's sync status. It combines
the upstream connection with the number of transactions the server has not accepted or rejected yet:

```ts
const status = db.getSyncStatus();
// {
//   link: { state: "offline", reason: "network", retrying: true },
//   pendingUploads: 3,
//   synced: false,
// }

const unsubscribe = db.onSyncStatusChange((status) => renderBadge(status));
```

`link.state` is one of:

| State        | Meaning                                                                                                                                                                                                                                                                          |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `local-only` | No server is configured, so nothing is uploaded                                                                                                                                                                                                                                  |
| `connecting` | Connecting for the first time, or reconnecting after a short drop                                                                                                                                                                                                                |
| `connected`  | Connected to the server                                                                                                                                                                                                                                                          |
| `offline`    | Not connected. `reason` says why: `disconnected` after `db.disconnect()`, `network` when the server has been unreachable for a while (the client keeps retrying), `auth` when the server refused the credential, or `stopped` after a failure that only `db.reconnect()` retries |

`offline` can also have the reason `authority-changed`: the server serves a different history than
the client's local store, because the server's store was recreated (a deleted dev data directory, a
restarted in-memory server, a new environment behind the same URL) or it is another app's server.
The client stops syncing with it, keeps its local data and unsynced writes, and fails `global` waits
and `db.waitForSync()` with an `AuthorityChangedError` (check with `isAuthorityChangedError`). Nothing
is reset automatically. To sync with the new server, reset the local store: in the browser,
`await db.deleteClientStorage()`; in Node, delete the client's data directory and open
it again. Writes that never reached the old server are lost with the store.

In the browser, tabs that sync through a shared worker may not yet see this: a tab's `global` waits
can keep waiting after the worker's link was refused. Treat `authority-changed` in a multi-tab app as
best effort for now.

In the browser, `offline` can also have the reason `held-by-another-tab`, with `retrying: true`.
When a guest signs up in one tab, another tab may still hold the account's local store as the
guest. The signed-up tab shows `connecting` and joins once that tab follows or closes. If that
hasn't happened after 30 seconds (the other tab may be frozen in the background), the link reports
`held-by-another-tab`, and waits fail with a `StoreHeldByAnotherTabError` (check with
`isStoreHeldByAnotherTabError`), so the app can ask the user to close or reload the other tab. The
tab keeps trying and joins as soon as it can. Writes made meanwhile stay in that tab's memory until
then, so a reload before it joins loses them.

A brief drop shows as `connecting`, not `offline`, so a status badge doesn't flicker. `synced` is
`true` when nothing waits for upload and the link is `connected` (or `local-only`).

In Node and React Native, `pendingUploads` includes transactions recovered from local storage after a
restart. In the browser, each tab counts only the transactions it committed itself. Transactions
recovered after a reload, or written by another tab, are uploaded by the shared worker and are not
counted, and `db.waitForSync()` does not wait for them.

The framework bindings expose the same object: `useSyncStatus()` in React and React Native (from `jazz-tools/react-native`, also in Expo apps; the
object), in Solid (an accessor) and in Vue (a ref), and `syncStatus()` in Svelte (a store, read as
`$status`). The Effect layer has a `syncStatus` stream.

```tsx
function SyncBadge() {
  const { link, pendingUploads, synced } = useSyncStatus();
  if (synced) return <span>Saved</span>;
  if (link.state === "offline") return <span>Offline, {pendingUploads} changes waiting</span>;
  return <span>Saving…</span>;
}
```

To wait until everything written so far has reached the server, for example before letting the user
sign out, use `db.waitForSync()`. Like a `global` write wait, it lasts through outages and
reconnects, and fails only if the server rejects one of those writes or the client stops trying.
Pass `timeoutMs` to bound it; it then rejects with a `WriteWaitTimeoutError` and the writes stay
queued. In the browser it waits only for the current tab's own writes, as described above, so a
write recovered after a reload or made in another tab may still be waiting when it resolves:

```ts
await db.waitForSync({ timeoutMs: 10_000 });
```

## Handling mutation errors

A mutation can fail when you call it or while you wait:

- If Jazz cannot apply the mutation locally, for example because the input is invalid, the mutation
  call throws immediately.
- If a server later rejects the mutation, an active `wait(...)` call rejects: with
  `PersistedWriteRejectedError` on the local-first client, and with a `ThinRemoteError` (code
  `WriteRejected`) on the thin client.

Use `db.onMutationError(...)` as a fallback for rejected mutations without an active `wait(...)`.
Its event is not an `Error`: read `event.code` and `event.reason`, not `.message`.
This includes mutations you did not wait for and mutations whose wait finished before a later
rejection arrived.

An event with code `outcome_unknown` is not a rejection: the thin client's connection ended for
good before the server answered (after `refresh()` signed in someone else, `disconnect()` or
`close()`), and the write may have been applied. Read the row again before you revert or retry it.
An ordinary dropped socket doesn't cause this, since the thin client resends unanswered writes when
it reconnects.

`onMutationError` returns an unsubscribe function. Without a listener, Jazz logs the rejection and
keeps it so that a listener registered later can receive it.

On a server, `jazz.db`, `jazz.forReqUser()` and `jazz.withAttribution()` from one `createJazz`
share one runtime, so `onMutationError` is backend-wide. A listener sees rejections of writes made
through any of them, for every user, so a per-request handler must match events against its own
transaction IDs. Rejections that arrive before any listener exists, such as writes that were still in
flight when the process stopped and are settled on restart, go to whichever `Db` registers a listener
first. Jazz keeps up to 256 of them and reports how many it dropped beyond that. A dropped or
shut-down `Db` releases its listeners, so register long-lived listeners on `jazz.db`: a listener on a
per-request `Db` stops firing once that `Db` is garbage-collected.
