A transaction groups related writes under one commit. Reads made through the transaction can see
its staged writes, while code outside the transaction cannot see them until it commits.

Permission checks follow the same rule. When the authority checks a write, its policy's `exists`
sees the rows the transaction creates or updates, so you can create a row and the rows that depend
on it for permissions in one transaction. A row the transaction deletes is still seen as it was
before the transaction. Each write must also be allowed by the state the whole transaction
leaves behind, whatever order you made the writes in. Writes from other transactions stay
invisible until they are accepted. See [Declarative Permissions](/docs/schemas/policies#share-based-access).

Jazz has two transaction types. The difference is how they handle concurrent changes:

- A mergeable transaction commits locally, even when the device is offline. When it syncs, Jazz
  combines it with concurrent work using the normal conflict rules. Jazz does not reject it just
  because another client changed the same data.
- A serializable transaction uses a stable view of the data. Before accepting it, the authority checks
  whether another write made a conflicting change. If so, it rejects the whole transaction
  and Jazz removes its local changes. Use this when accepting both changes would break a rule.

Most applications should start with a mergeable transaction.

<Accordions type="single">
<Accordion title="What's the authority?">
The authority is the part of Jazz that accepts or rejects writes. It checks permissions and other
rules before accepting them. For a serializable transaction, it also checks that the data read by the
transaction has not changed in a conflicting way.

For most apps, the authority is the server at the `global` durability tier. This is why a serializable
transaction cannot be accepted while the device is offline. For an app without a sync server, the
authority runs locally instead.

</Accordion>
</Accordions>

## Choose a transaction type

| Use                 | Mergeable transaction                     | Serializable transaction                                               |
| ------------------- | ----------------------------------------- | ---------------------------------------------------------------------- |
| Best for            | Grouping normal local-first writes        | Enforcing an invariant across reads and writes                         |
| Concurrent work     | Merges using Jazz's normal conflict rules | The authority validates the transaction as one serialisable unit       |
| TypeScript callback | `db.transaction(...)`                     | `db.serializableTransaction(...)`                                      |
| TypeScript wait     | `wait({ tier: "local" \| "global" })`     | `wait()`                                                               |
| Offline             | Can commit locally and sync later         | Can be staged, but cannot be accepted until the authority is reachable |

You do not need a transaction for every write. `insert`, `update`, `upsert`, `delete` and `restore`
already apply locally first and sync in the background.

<Callout type="info" title="One commit does not mean one UI update">
  Jazz sends every transaction upstream as one unit, and the authority decides that unit as a whole.
  Other clients can still receive rows from a mergeable transaction in separate updates. An
  serializable transaction is shown atomically within each subscription view.
</Callout>

## Use a callback for normal work

The callback form commits automatically when the callback finishes. Jazz rolls the transaction back
if the callback throws or returns a rejected promise.

The TypeScript callback returns the new row ID. Jazz exposes that value as `result.value`, and
`result.wait(...)` resolves to the same value.

Inside a TypeScript transaction:

| Method                                      | Returns                                                   |
| ------------------------------------------- | --------------------------------------------------------- |
| `insert(...)`, `restore(...)`               | The staged row                                            |
| `update(...)`, `upsert(...)`, `delete(...)` | `void`                                                    |
| `all(...)`                                  | A promise for all matching rows, including staged changes |
| `one(...)`                                  | A promise for the first matching row, or `null`           |

To point one new row at another in the same transaction, use the staged row's `id`:

```ts
const project = tx.insert(app.projects, { name: "Launch" });
tx.insert(app.todos, { title: "Write the post", projectId: project.id });
```

`insert` assigns the id itself: an `id` in the values fails with "Unknown column id".

Use the `tx` object for every read and write that belongs to the transaction. A query made through
the outer `db` does not read the transaction's staged changes.

## Know what each await means

In TypeScript, committing and waiting for durability are separate steps:

| Code                                    | What it proves                                                                     |
| --------------------------------------- | ---------------------------------------------------------------------------------- |
| `await db.transaction(...)`             | The callback finished and Jazz created the committed mergeable transaction locally |
| `result.value`                          | The value returned by the callback                                                 |
| `await result.txId`                     | The committed transaction has an ID                                                |
| `await result.wait({ tier })`           | The mergeable transaction reached that durability tier, or was rejected            |
| `await db.serializableTransaction(...)` | Jazz created the committed serializable transaction locally                        |
| `await result.wait()`                   | The authority accepted the serializable transaction, or rejected it                |

If your next action depends on server acceptance, keep the result and call `wait(...)`. Awaiting
`db.transaction(...)` by itself is not enough.

See [Durability Tiers](/docs/reference/durability-tiers) for the meaning of `local` and `global`.

## Handle errors

A transaction can fail at three points:

1. While the callback runs, a write can throw immediately or an awaited read can reject, for
   example because its input is invalid. An update inside a transaction needs its row read first
   in this process (with `tx.one(...)`, say); otherwise it throws a `not_observed` error.
2. The callback or local commit can fail. Jazz rolls back a callback transaction and rejects
   `db.transaction(...)` or `db.serializableTransaction(...)`.
3. The authority can reject a committed transaction later. In TypeScript, `wait(...)` then rejects
   with `PersistedWriteRejectedError` and Jazz removes the rejected local changes.

## Use a serializable transaction to reject conflicts

A serializable transaction reads from a stable transaction snapshot. The authority checks the reads
and writes, then accepts or rejects the transaction as one serialisable unit. This is useful when a
write is valid only if the data you just read has not changed in a conflicting transaction.

In TypeScript, `wait()` takes no durability tier for a serializable transaction. It resolves if the
authority accepts the transaction and rejects if the authority rejects it.

Keep transactions small. Their cost grows faster than their size for now, so split a bulk import
into transactions of 10 to 50 rows.

A conflict rejects with code `serialization_conflict` or `transaction_conflict`; treat both as "read
again and retry". A rejection is different from a transport error, such as "websocket transport
error" during an outage: there the transaction may still reach the authority, so check before you
retry it.

<Callout type="warn">
  The authority checks only the reads the writing client reports. That keeps honest writers from
  acting on stale data, but it is not a security boundary: a client that under-reports its reads can
  commit anyway. Enforce rules that must hold for every writer, such as "a membership needs a live
  invite", in [permission policies](/docs/schemas/policies), or perform the write on your backend,
  as the [invite links](/docs/recipes/access-control/invite-links) recipe does.
</Callout>

## Manage a transaction yourself only when needed

Use `beginTransaction()` when the work cannot fit in one callback. You then own the transaction and
must call `commit()` or `rollback()`.

<include cwd lang="ts" meta='title="app.ts"'>
  ../examples/docs/todo-client-localfirst-ts/src/docs-snippets.ts#writing-manual-transaction-ts
</include>

For a serializable transaction, use `beginSerializableTransaction()` instead. Call `wait()` on the
commit result to wait for the authority to accept or reject the transaction. You do not choose a
durability tier, it is always settled by the authority.

If a mergeable transaction has no writes, `commit()` throws. Call `rollback()` instead.

Await every read you start through a transaction before you commit it. Committing while one of
its reads is still pending throws a `not_observed` error, and the transaction ends without
publishing anything.
