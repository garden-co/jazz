## SQLite underneath

- Each Jazz server stores its data in plain SQLite: tables, rows, indexes
- Works on local disk, in Vercel sandboxes, on Cloudflare Durable Objects and on Turso
- Why SQLite: fast, embeddable, simple to back up and inspect

## What Jazz adds on top

- A typed schema and generated migrations
- Permission policies checked on every read and write
- Live queries: results stay up to date as rows change
- Edit metadata (`$createdBy`, `$updatedAt`, …) and row history
- Merging writes by default, serializable transactions when you need them
- Drafts and branches, mergeable text, files and streams

## How a backend talks to Jazz

- The backend opens one session with the app id, server URL and backend secret
- Backend authority (`client.db`) sees everything, for admin and system work
- `forRequest(req)` gives a user-scoped view: that user's policies and authorship apply
- Queries and subscriptions run on the server; results come back as typed rows
- Writes are confirmed by the server before they count as durable

## How frontends talk to Jazz

- The thin client sends queries and writes to the server over the same API, with the same auth and policies
- No local database in the browser; small bundle

## Sync and local-first

- A local-first client keeps a local SQLite replica of the rows its queries need
- Reads are instant and work offline; writes apply locally and sync later
- The server stays the authority: it checks policies and settles conflicts
- Details: [How Sync Works](/docs/recipes/local-first/how-sync-works)

## Sharding

- One server is enough for many apps; scale out by adding shards
- A stateless gateway routes queries and writes to the right shard
- Cross-shard transactions use two-phase commit
- Per-query consistency: each subscription sees a settled snapshot
