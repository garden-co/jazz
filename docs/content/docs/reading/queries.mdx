## Read durability

Queries and subscriptions return results as soon as they are available locally by default. Local reads are effectively instant, and remote updates stream in as they arrive, which is normally a good default. When you need a stronger guarantee for the first result, pass a `tier` option to fetch data from a different tier before returning.

<DurabilityTiersTable />

For background on how data flows between tiers, see [How Sync Works](/docs/concepts/how-sync-works#infrastructure-tiers).

### Choosing a tier

Pass a read choice when you need to control whether the first result may use local
knowledge&hairsp;—&hairsp;for example, when a user has just navigated to a page and a
stale local snapshot would mislead them.

- `"local-first"` uses cached local data and pending local writes immediately, while continuing to sync.
- `"remote"` waits for Core-authorized query results and excludes pending local edits.

See [Read tiers](/docs/reference/durability-tiers#read-tiers) for pending-write
behavior and how subscriptions change between offline and online operation.
The aliases `"local"` and `"global"` remain accepted for reads; write waits use
`"local"` and `"global"`.

### Waiting briefly for the server

A local-first read can wait a bounded time for the server before its first result. Pass
`firstLoadRemoteWaitMs`:

```ts
const todos = await db.all(app.todos, { tier: "local-first", firstLoadRemoteWaitMs: 500 });
db.subscribe(app.todos, onChange, { tier: "local-first", firstLoadRemoteWaitMs: 500 });
const rows = useAll(app.todos, { tier: "local-first", firstLoadRemoteWaitMs: 500 });
```

In Rust, use `client.query_local_first(query, Duration::from_millis(500))` and
`client.subscribe_local_first(query, Duration::from_millis(500))`.

- Only the initial load waits: a one-shot read, or a subscription's first callback. While the
  client looks online (its connection is live, or its connection attempt started less than 5 s
  ago), Jazz waits up to `firstLoadRemoteWaitMs` for the server's answer and shows that result, together
  with your own pending writes. If the server has not answered in time, it shows the local result.
- It waits even when the local cache already has data, but never longer than the timeout. Use it
  to avoid showing a stale or empty snapshot on a fresh device.
- It never waits offline, without a configured server, after `db.disconnect()`, while the
  connection is retrying, or when the connection drops during the wait: local data shows at once.
- After the first result it behaves exactly like `"local-first"`: your writes show immediately and
  remote changes show when they arrive.
- Queries with an `offset` read the server's page while waiting, because a partly synced cache
  would apply the offset to the wrong rows. On timeout they show the cached page.
- The default, `0`, is plain `"local-first"`. The option applies to local-first reads (including
  the `"local"` alias and the browser default); `"remote"` ignores it.

<Callout type="warn" title="local-first-unless-empty is deprecated">
  `"local-first-unless-empty"` (`ReadTier.LocalFirstUnlessEmpty`) still works as before but warns
  once and will be removed in the next breaking release. Replace it with `"local-first"` plus a
  `firstLoadRemoteWaitMs` of, for example, a few seconds. The old tier waited without a timeout, but
  only when the local result was empty; `firstLoadRemoteWaitMs` also waits when the cache has data,
  bounded by the timeout.
</Callout>

### Own writes

The read tier also determines how a subscription treats your own local writes:

- `"local-first"` shows pending local writes using locally known data.
- `"local-first"` with `firstLoadRemoteWaitMs` shows pending local writes exactly like `"local-first"`, including in a first result that came from the server.
- `"remote"` has no pending overlay: writes appear when reflected in the server's query scope.

See [Durability Tiers](/docs/reference/durability-tiers) for the full reference, including which APIs accept these options and how they compose.

## Magic columns

You can select and filter on Jazz's magic columns just like other columns. They are omitted from
`select("*")`, so opt in explicitly when you want them.

### Edit metadata columns

- `$createdBy`&hairsp;—&hairsp;the Jazz principal that created the row
- `$createdAt`&hairsp;—&hairsp;when the row was first created
- `$updatedBy`&hairsp;—&hairsp;the Jazz principal that last updated the row
- `$updatedAt`&hairsp;—&hairsp;when the row was last updated

These are useful for showing authorship, when a row last changed, or building "my created items"
views without storing duplicate ownership fields.

## Framework hooks

Each framework has a reactive binding that re-renders when query results change. See [Framework Patterns](/docs/reference/framework-patterns#query-subscriptions) for side-by-side examples.

| Framework  | API                            | Notes                                                 |
| ---------- | ------------------------------ | ----------------------------------------------------- |
| React/Expo | `useAll(query)`                | Returns `{ data, isLoading, error }`                  |
| Vue        | `useAll(query)`                | Returns `{ data, isLoading, error }` refs             |
| Svelte     | `new QuerySubscription(query)` | Exposes reactive `.current` / `.isLoading` / `.error` |
| Solid      | `useAll(() => ({ query }))`    | Returns `{ data, isLoading, error }`                  |

### The loading state

`useAll`'s `data` field (or Vue's `data` ref and Svelte's `QuerySubscription.current`) are
`undefined` until the first result arrives from the requested tier. After that, the value is an
array&hairsp;—&hairsp;empty (`[]`) if no rows match, or populated with the requested data.

### Fine-grained updates

Vue's `useAll`, Svelte's `QuerySubscription`, and Solid's `useAll` reconcile new query results into the existing reactive array in place rather than swapping the reference. When an upstream change touches a single row, only that row's affected fields write into the reactive proxy, so `$effect` (Svelte), Solid computations/effects, and `watch` / template bindings (Vue) only re-fire for components that depend on the fields that actually changed.

In practice this means:

- Adding, removing, or reordering rows updates the array structure only — untouched row objects keep their identity, so `{#each items as item (item.id)}` and `<TransitionGroup>` keyed renders are stable.
- Editing a single field on one row writes only that field — sibling rows do not re-render, and per-row components that read other fields stay quiet.
- Vue's `useAll` returns `{ data, isLoading, error }`, where `data` is a deep `Ref` (not a `shallowRef`), so per-field reactivity composes with the rest of your component tree without manual unwrapping.
- React and Solid return `{ data, isLoading, error }`; React returns a fresh `data` array each tick, while Solid's store keeps fine-grained dependency tracking for fields that changed.

React's granularity benefit comes from React's diffing, not from in-place reconciliation.
