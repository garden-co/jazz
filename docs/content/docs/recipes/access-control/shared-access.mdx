After [user-owned data](/docs/recipes/access-control/user-owned-data), the next pattern you're likely to need is sharing. This recipe shows how to let one user grant another access to specific rows using a shares table.

## Schema

Add a `todoShares` table that records which user has access to which todo.

```ts title="schema.ts"
import { schema as s } from "jazz-tools";

export const schema = s.defineSchema({
  todos: s.table(
    { title: s.string(), done: s.boolean() },
    { shares: s.reverse("todoShares", "todo") },
  ),
  todoShares: s.table(
    { todoId: s.uuid(), user_id: s.uuid(), can_edit: s.boolean() },
    { todo: s.rel("todos", "todoId") },
  ),
});
```

## Permissions

The creator can do everything. Share recipients get read access, and optionally edit access via `can_edit`.
A share row is readable by its recipient and by the todo's creator, who needs it to list and revoke
access.

```ts title="schema.ts"
const { definePermissions, exists, session, anyOf } = schema;

const createdByMe = { $createdBy: session.user };

export const permissions = definePermissions({
  todos: {
    read: (todo) =>
      anyOf(createdByMe, exists.todoShares({ todoId: todo.id, user_id: session.user })),
    insert: true,
    update: (todo) =>
      anyOf(
        createdByMe,
        exists.todoShares({ todoId: todo.id, user_id: session.user, can_edit: true }),
      ),
    delete: createdByMe,
  },
  todoShares: {
    // Only the todo creator can manage shares.
    insert: (share) => share.todo.where(createdByMe),
    // The recipient sees their share, and the todo's creator sees every share of it,
    // so they can list who has access and revoke it.
    read: (share) => anyOf({ user_id: session.user }, share.todo.where(createdByMe)),
    delete: (share) => share.todo.where(createdByMe),
  },
});
```

See [Declarative Permissions](/docs/schemas/policies) for more on `exists`, `anyOf`, and `allOf`.

### Finding the recipient's account

A share names the recipient's Jazz account, which the sharer's browser doesn't know. Look it up in
your backend: find the person in your auth library (for example by an email address the sharer
typed), then `await jazz.createAccountFor(user.id)` returns their account ID, creating the account
if they don't have one yet; calling it again returns the same ID. Return that ID to the client.

- Match only on details your auth library has verified, such as a verified email address.
  Otherwise someone could sign up with another person's address and receive their shares.
- Creating the account early has one cost: a guest (device account) can no longer link to that
  user when they sign up later, so their guest data stays separate. See
  [Users without an account](/docs/setup/deployment/own-server#users-without-an-account).

To share with someone without knowing who they are in your app, send them a link instead: see
[Invite links](/docs/recipes/access-control/invite-links).

## Revoking access

Delete the share row to revoke access. The server will stop syncing the todo to the former recipient.
A recipient who is offline keeps their cached copy until they reconnect; see
[What a removed member still sees](/docs/recipes/access-control/group-permissions#what-a-removed-member-still-sees).
