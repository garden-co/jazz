After [user-owned data](/docs/recipes/access-control/user-owned-data), the next pattern you're likely to need is sharing. This recipe shows how to let one user grant another access to specific rows using a shares table.

### Finding the recipient's account

A share names the recipient's Jazz account, which the sharer's browser doesn't know. Look it up in
your backend: find the person in your auth library (for example by an email address the sharer
typed), then `await jazz.createAccountFor(user.id)` returns their account ID, creating the account
if they don't have one yet; calling it again returns the same ID. Return that ID to the client.

- Match only on details your auth library has verified, such as a verified email address.
  Otherwise someone could sign up with another person's address and receive their shares.
- Creating the account early has one cost: a guest (device account) can no longer link to that
  user when they sign up later, so their guest data stays separate. See
  [Users without an account](/docs/setup/deployment/own-server#users-without-an-account).

## Revoking access

Delete the share row to revoke access. The server will stop syncing the todo to the former recipient.
A recipient who is offline keeps their cached copy until they reconnect; see
[What a removed member still sees](/docs/recipes/access-control/group-permissions#what-a-removed-member-still-sees).
