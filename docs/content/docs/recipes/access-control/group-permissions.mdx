This recipe shows how to build a workspace where users have different levels of access depending on their role. The same pattern applies to any group-like concept&hairsp;—&hairsp;teams, projects, channels, organisations.

## Roles at a glance

| Role          | Read | Create | Edit own | Edit any | Manage members |
| ------------- | ---- | ------ | -------- | -------- | -------------- |
| `reader`      | ✓    |        |          |          |                |
| `contributor` | ✓    | ✓      | ✓        |          |                |
| `writer`      | ✓    | ✓      | ✓        | ✓        |                |
| `admin`       | ✓    | ✓      | ✓        | ✓        | ✓              |

## Schema

Three tables: the workspace itself, a members join table that records each user's role, and the documents that belong to the workspace.

## Permissions

<include cwd lang="ts" meta='title="schema.ts"'>
  ../examples/docs/todo-client-localfirst-react/src/recipes/group-permissions/schema.ts#permissions
</include>

`isMember`, `hasRole` and `isAdmin` are plain TypeScript helpers: they take the workspace id to check
(`document.workspaceId` on a document, `workspaceMember.workspaceId` on a membership, `workspace.id`
on a workspace). `createdByMe` and `mine` are plain conditions. `npx jazz-tools generate` inlines
them all into `jazz.permissions.json`.

- **Contributor** edit and delete access requires both `createdByMe` (`{ $createdBy: session.user }`: the row belongs to this author) and a matching contributor membership. Writers and admins can edit and delete any document.
- **Bootstrap insert**: the second branch of the `workspaceMembers` insert policy lets the workspace creator add themselves as the first admin (`workspaceMember.workspace.where(createdByMe)` checks the workspace the new row points to)&hairsp;—&hairsp;otherwise `isAdmin` would block everyone, since there are no members yet.
- **Leave on your own**: members can delete their own membership row (`mine`) regardless of role. Admins can remove anyone.

See [Declarative Permissions](/docs/schemas/policies) for more on `exists`, `anyOf`, `allOf`, relation `.where`, and `$createdBy`.

### What a removed member still sees

- **Online** (thin client, or local-first while connected): the workspace's documents drop out of
  their live queries right away.
- **Offline local-first:** the rows already on their device stay readable, across reloads too,
  until they reconnect. Within about a second of reconnecting they are removed from the device.
  Writes they queued meanwhile are rejected and reverted.
- `clearOnSignOut` doesn't help here: a removed member isn't signed out.

Anything they read before removal they may have copied; removing access stops future reads, not
past ones.
