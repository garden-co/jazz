---
title: How Sync Works
description: Query-driven replication, transaction fate, and the local, edge, and core roles.
---

Jazz applications read and write a local database. Sync is query-driven: an active query tells an
upstream which current rows the application needs, and the upstream sends matching row versions and
later changes. Permissions are enforced by the serving authority before rows are emitted.

## Local-first execution

`Db` is always a client facade. It reads the materialized local state, accepts local writes, and
queues those writes for upstream delivery. A browser persistent client uses OPFS; a browser worker
owns the durable database and coordinates tabs. A client with no server URL remains useful as a
local-only database: its writes settle at `local` and never self-finalize.

Subscriptions keep the local replica fresh. On reconnect, the client re-announces active queries
and retries locally originated transactions by transaction identity, so repeated delivery is safe.

## Roles and topology

```text
client Db  →  edge  →  core
     ↑           ↓
 current rows and query deltas
```

- **Client** — owns a partial local replica and is never a fate authority.
- **Edge** — serves identity-scoped query data and can finally admit mergeable writes for the
  permission scopes it terminates.
- **Core** — the global serialization point. It finalizes exclusive transactions and assigns global
  settlement.

Edges route upstream through core. A relay forwards protocol traffic and does not decide writes.

## Fate and durability

Every committed transaction has a fate and a durability observation. Fate is `pending`, `accepted`,
or `rejected`; it answers whether an authority admitted the transaction. Durability is `local`,
`edge`, or `global`; it answers where the transaction is known to be stored. These are independent:
an edge-accepted transaction is not globally durable until it reaches core.

`WriteHandle.wait({ tier })` waits for the requested durability observation and rejects when the
transaction's fate is rejected. Use `local` for immediate local-first UX, `edge` when the first
server hop must observe the write, and `global` when the application needs global settlement.

## Concurrent writes

Each write creates an immutable row version. Current rows are derived from accepted row history.
Concurrent writes merge deterministically: columns are last-writer-wins by default, and a declared
non-nullable integer counter uses counter merging. Deleted rows are absent from ordinary current
queries; `includeDeleted()` explicitly reads their retained content.

## Query delivery

The first result can wait for `local`, `edge`, or `global` query coverage. After that, a
subscription receives maintained deltas as they reach the local replica. Use `propagation:
"local-only"` when an intentionally offline view must read only the local snapshot.
