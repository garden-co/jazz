title: Kotlin Backend
description: "Open a Jazz app from Kotlin, on the JVM or Android, with the jazz-kotlin library and typed bindings generated from jazz.app.json."
---

A Kotlin/JVM service can be your app's backend. It opens the app from the same `jazz.app.json` and
`jazz.permissions.json` as every other language, with typed bindings generated from them. On start
it publishes the app's permissions bundle, as `createJazz` does. Then it acts as one user of the
app, in a session pinned to that bundle.

The `jazz-kotlin` library wraps Jazz's native core (`jazz-ffi`, through JNA). Its calls are
`suspend` functions, and subscriptions are `Flow`s. It isn't on Maven Central yet, so build it from
the Jazz repository. With a checkout next to your project, include it as a composite build:

```kotlin title="settings.gradle.kts"
includeBuild("../jazz/packages/jazz-kotlin")
```

```kotlin title="build.gradle.kts"
plugins {
    kotlin("jvm") version "2.2.21"
    kotlin("plugin.serialization") version "2.2.21"
    application
}

dependencies {
    implementation("tools.jazz:jazz-kotlin")
}
```

Building `jazz-kotlin` runs `cargo build -p jazz-ffi`, so it needs a Rust toolchain. It loads
`libjazz_ffi` through JNA: set `-Djna.library.path` to the directory that holds it
(`target/debug` in the Jazz checkout). It runs on JDK 17 or later.

On Android, depend on `packages/jazz-kotlin-android` instead: the same API as an AAR, with
`libjazz_ffi` for arm64-v8a, armeabi-v7a and x86_64 (minSdk 24). Building it needs the Android SDK
and NDK, and `cargo-ndk`.

## Generate the bindings

With a `build.gradle.kts` beside `jazz.app.json`, `jazz-tools generate` writes
`src/main/kotlin/JazzApp.kt`, in the package `jazzapp`:

```bash
jazz-tools generate            # checks the files, writes src/main/kotlin/JazzApp.kt
jazz-tools generate --check    # in CI: fails if JazzApp.kt is stale
```

This is the `jazz-tools` binary built from the Jazz repository (`cargo build -p jazz-cli --bin
jazz-tools`); the npm `jazz-tools` CLI doesn't generate Kotlin yet.

Commit `JazzApp.kt`. Per table it gives you:

- a `@Serializable` row data class (`Task`), with the authored column names;
- a new-row data class (`NewTask`), whose optional columns default to `null`;
- a patch builder (`TaskPatch`), used as `jazz.update(Tasks, id) { status(TaskStatus.Done) }`;
- a table object (`Tasks`) with typed columns, for queries:
  `Tasks.where(Tasks.showId eq id).orderBy(Tasks.rank.asc())`;
- an `enum class` per enum column (`TaskStatus`).

Import the generated declarations by name (`import jazzapp.Tasks`, `import jazzapp.NewTask`), or
write them qualified (`jazzapp.Result`), rather than `import jazzapp.*`: a star import outranks
Kotlin's default imports, so a table such as `results` would hide `kotlin.Result` in your code.

Names are the ones `jazz.app.json` uses: a `showId` column is `showId`, and a `due_at` column stays
`due_at` (only names that aren't Kotlin identifiers are camel-cased). Values are plain Kotlin types:
`uuid` is a `String`, `int` an `Int`, `bigint` a `Long`, `float` a `Double`, `timestamp` a `Long`
(milliseconds since the epoch), `bytea` a `ByteArray`, `json` a `JsonElement`, an array a
`List<T>`, an enum its generated `enum class`, and an optional column is nullable. The file names
these fully qualified (`kotlin.String`), so a table may be called `Result` or `Unit`.

`Jazz` is safe to use from any coroutine. Its calls run on `Dispatchers.IO`, and the native core
runs the client on a thread of its own. Call `jazz.close()` (it's `AutoCloseable`) before the
process exits. Closing ends open `watch`es and subscriptions with `JazzException.Closed`, later
calls throw it too, and closing twice is harmless.

`jazz.account()` is the account id of the user the backend acts as. Write it into columns that
policies compare with `session.user`, like StagePlan's `shows.chiefAccount`.

The backend needs the sync server's admin secret, to publish the bundle, and its backend secret, to
vouch for the user it acts as. Like every backend, give it no HTTP surface that callers can reach
without your own authentication.

The [Reading](/docs/reading/queries) and [Writing](/docs/writing/writing-data) pages have a Kotlin
tab for each example. `examples/stage-plan/apps/kotlin-cli` in the repository is a complete
command-line app: it creates a show, lists its tasks by rank, adds tasks and moves them between
stages.

Writes are local-first. A write that the server's permissions refuse doesn't fail the call: it
stays local and never syncs.

## Computed fields and transforms

If `jazz.app.json` declares computed fields or transforms, the bindings declare an
`interface JazzComputed` (e.g. `tasksPriority(score: Int): TaskPriority`,
`isoDateView(stored: Long): String` and `isoDateStored(view: String): Long`), and
`jazzapp.open(config, computed)` takes your implementation, so a missing one doesn't compile. Rows
carry each computed field and each transformed column's view value; inserts and patches take the
view value. Queries compare a transformed column as stored.

## Not supported yet

In Kotlin, Jazz doesn't support these yet:

- reading part of a large value inside an include (root queries only);
- `hopTo`, recursive `gather`, `union` and history queries;
- guest (anonymous) users;
- writing enums with payloads (reading them works: a sealed interface per enum); nested rows and
  catalogue enums in bindings;
- Kotlin Multiplatform targets other than the JVM and Android;
- publishing `jazz-kotlin` and `jazz-kotlin-android` to Maven Central: build them from the
  repository;
- non-finite doubles (`NaN`, infinities): writing or comparing one throws, as JSON has none;
- `limit` and `offset` with `watch`: they apply to the server's result before `watch` re-sorts it
  locally, so a page can be off after changes. Use them with `all`.
