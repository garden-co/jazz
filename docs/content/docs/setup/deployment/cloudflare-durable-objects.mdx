Your whole app runs in one Worker. Your backend serves your routes and signs users in; your app's
core (the part of Jazz that stores and syncs its data) runs in a Durable Object of the same Worker.
Browsers talk only to your Worker. There are no secrets to set.

This page sets up your **main backend**: the backend that runs `createJazz`, serves sync to your
browsers and apps, and decides who each user is. Other trusted machines reach Jazz through it as
[backend clients](/docs/setup/backend-client).

<Callout type="warn" title="Experimental">
  Jazz on Cloudflare is experimental: `jazzWorker` and the bindings it reads may change in any
  release, without a deprecation period. Try it, and tell us what breaks.
</Callout>

## The Worker

```ts title="src/worker.ts"
import { Hono } from "hono";
import { createJazz, durableObjects } from "jazz-tools/backend";
import { r2 } from "jazz-tools/durable-object";
import { jazzWorker } from "jazz-tools/cloudflare";
import { app } from "./jazz.generated";
import permissions from "./jazz.permissions.json" with { type: "json" };

const worker = jazzWorker(
  (env: Env) => {
    const jazz = createJazz({
      app,
      permissions,
      // The core in this Worker, through its binding.
      store: durableObjects({ binding: env.JAZZ }),
      // Read your session; return { userId, expiresAt, claims? } for a signed-in user, or null
      authenticate: async (request) => null,
    });
    // Your own routes. Requests under /jazz (sync and sign-in) are Jazz's.
    const routes = new Hono().get("/api/todos", async (c) => c.json(await jazz.db.all(app.todos)));
    return { jazz, fetch: routes.fetch };
  },
  { blobs: (env) => r2(env.JAZZ_BLOBS) },
);

export const { JazzCore, JazzBackend } = worker;
export default worker;
```

## Wrangler config

Add these entries to your `wrangler.jsonc`, next to what you already have:

```jsonc title="wrangler.jsonc"
{
  "compatibility_flags": ["nodejs_compat"],
  "durable_objects": {
    "bindings": [
      { "name": "JAZZ", "class_name": "JazzCore" },
      { "name": "JAZZ_BACKEND", "class_name": "JazzBackend" },
    ],
  },
  // Append to your migrations if you have some, with a tag you haven't used yet.
  "migrations": [{ "tag": "jazz-v1", "new_sqlite_classes": ["JazzCore", "JazzBackend"] }],
  // Large values (files, long text). Wrangler creates the bucket on deploy.
  "r2_buckets": [{ "binding": "JAZZ_BLOBS" }],
}
```

Then deploy with `npx wrangler deploy`. Browsers connect to the Worker's own origin, with
`serverUrl: "/jazz"`. To serve your built client from the same Worker, use wrangler's `assets` and
send only your API and `/jazz` to the Worker. The BandChat example's `react-hono-betterauth` app
does this, with Better Auth on Jazz (`examples/band-chat/apps/react-hono-betterauth`).

- **Keep the names.** Your app's data lives in the `JazzCore` object. A renamed class, binding or
  Worker starts a new, empty app.
- **R2** has to be enabled on your Cloudflare account once (Dashboard → R2 Object Storage), which
  asks for a payment method even within R2's free tier. To store large values inline, select `{ blobs: "sqlite" }` and omit the R2 binding. The bytes stay in the Durable Object's SQLite, which grows with each of them. Once a core has put
  values in a bucket, keep that binding: it refuses another bucket, and refuses to start without one.
- **Size:** the Worker is about 20 MB, under Workers' 64 MiB limit on every plan, Free included.

## Large values in S3 or Vercel Blob

Select an existing bucket or private Blob store in the **core Worker**. Every
backend connecting to that core uses the same destination. For S3, set
`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` as Worker secrets, plus
`AWS_SESSION_TOKEN` for temporary credentials. For Vercel Blob, set
`BLOB_READ_WRITE_TOKEN`.

For S3, pass `{ blobs: () => s3({ bucket: "app-chunks", region: "us-east-1" }) }` as the second argument to `jazzWorker`. Import `s3` from `jazz-tools/durable-object`.

Set `endpoint` for an S3-compatible service. For private Vercel Blob, import
`vercelBlob` from the same entry and use `blobs: () => vercelBlob()`. The core
can read the store ID from a read-write token or from `storeId`.

For custom secret bindings, return `s3({ bucket, region, credentials: {
accessKeyId, secretAccessKey, sessionToken } })` or `vercelBlob({ credentials:
{ readWriteToken } })` from the callback, using values from its `env` argument.
Both destinations default to the app's own prefix. Give each core a unique
explicit `prefix` if you override it. Vercel Blob does not document atomic
first creation when two cores claim the same custom prefix simultaneously. As with R2, the core claims the prefix,
keeps chunks in SQLite until their uploads succeed, and checks their hashes on read.

## WebSocket hibernation

Every browser's sync socket passes through the backend object, which stays awake (and billed for
duration) while any browser is connected. The core can hibernate even while your backend's socket
to it is open: give the store `lifecycle: "hibernate"`. On wake, the core restores
live query watches, and each subscription sends its full current result on its first matching
change.

```ts
store: durableObjects({ binding: env.JAZZ, lifecycle: "hibernate" }),
```

## What a Durable Object core doesn't do yet

- **Transactions run in your backend**, as with every core: the core never holds one open between
  calls.
- **In a Worker, `durableObjects()` and `remote()` stores** run: `sqlite()` and `memory()` run their core in
  the backend's process, which a Worker can't. The Inspector's query explanations aren't available
  there yet.
