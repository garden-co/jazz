On Vercel, your Next.js app is the whole deployment. The `vercel()` store keeps each namespace's
data (production, a preview branch, …) in a persistent [Vercel Sandbox](https://vercel.com/docs/vercel-sandbox) that your functions
start on demand. There's no separate service to set up and no secrets to copy.

This page sets up your **main backend**: the backend that runs `createJazz`, serves sync to your
browsers and apps, and decides who each user is. Other trusted machines reach Jazz through it as
[backend clients](/docs/setup/backend-client).

## Set it up

Install the Sandbox SDK next to `jazz-tools`:

```bash title="Terminal"
pnpm add @vercel/sandbox
```

Use the `vercel()` store:

```ts title="jazz.server.ts"
import { createJazz, perBranch, vercel } from "jazz-tools/backend";
import { app } from "./schema";
import permissions from "./jazz.permissions.json" with { type: "json" };

export const jazz = createJazz({
  app,
  permissions,
  // Production gets one core, and each preview branch its own.
  store: vercel({
    namespace: ({ environment, branch }) =>
      environment === "production" ? "production" : perBranch(branch),
  }),
  authenticate: async (request) => {
    const session = await getSession(request); // your own auth
    if (!session) return null;
    return {
      userId: session.user.id,
      expiresAt: Math.floor(session.session.expiresAt.getTime() / 1000),
    };
  },
});
```

<include>../../../partials/main-backend-config.mdx</include>

In a Next.js app, install `ws` and `@vercel/functions` (both also needed under `next dev`) and keep
Jazz's native module out of Next's server bundle:

```bash title="Terminal"
npm install ws @vercel/functions
```

```ts title="next.config.ts"
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  // Your backend loads Jazz's native module; Next must not bundle it.
  serverExternalPackages: ["jazz-napi"],
};

export default nextConfig;
```

Mount it with a catch-all route under `/jazz`, where clients connect by default:

```ts title="app/jazz/[...path]/route.ts"
import { jazz } from "@/jazz.server";

export const { GET, POST, DELETE } = jazz.next();
```

Then deploy as usual with `git push` or `vercel deploy`. Your functions authenticate to Vercel with
their own OIDC token, and the core's secrets are generated inside the Sandbox, so Jazz needs no
environment variables of its own. Your auth may: Better Auth, for example, needs
`BETTER_AUTH_SECRET` in each environment.

On Vercel, sync uses a WebSocket (through `upgradeWebSocket` from `@vercel/functions`). Under plain
`next dev`, which can't upgrade sockets, the browser
switches to an HTTP stream on its own.

Install `ws`: for now, Next.js 16's default bundler (Turbopack) can't build Jazz's route without it,
so `next dev` answers every `/jazz` request with a 500 and `next build` fails. With webpack, a backend
without `ws` logs once at startup "jazz: next() on Vercel needs the ws package: npm install ws.
Without it, sync sockets can't open: clients sync over the HTTP stream instead." Clients still sync
then, but the HTTP stream needs a single instance or sticky routing.

Set `publicUrl` to the URLs browsers reach `/jazz` at. Without it, the backend takes its URL from
each request's headers, and logs "createJazz: vouched for a local-first guest of …, taken from the
request's headers. Set publicUrl …" the first time a device account signs in. With `publicUrl` set,
the backend accepts device accounts only for the URLs it lists and refuses others with a warning
("refused a local-first guest whose proof is for …"), so list every URL your users reach `/jazz`
at, a second custom domain included. Device accounts belong to one origin: a guest on your
production domain and one on a deployment URL are different accounts, while signed-in users see the
same data on every URL. Vercel's system environment variables name the production domain and the
current deployment's URLs:

```ts title="jazz.server.ts"
export const jazz = createJazz({
  // …
  publicUrl: [
    process.env.VERCEL_PROJECT_PRODUCTION_URL,
    process.env.VERCEL_BRANCH_URL,
    process.env.VERCEL_URL,
  ]
    .filter(Boolean)
    .map((host) => `https://${host}/jazz`),
});
```

Your auth library needs storage that outlives a function call. Better Auth with a local SQLite
file, as in its quick start, loses its users on Vercel: give it a hosted database, or keep its
tables in Jazz with the [Jazz adapter](/docs/setup/auth/better-auth#use-jazz-as-the-database).

## Large values

Large values, such as files and long streams, are stored in chunks, which can live outside the
core's database. On Vercel, `vercel()` picks where they go:

- **Vercel Blob**, when a Blob store is connected to the project (the Storage tab in the Vercel
  dashboard sets `BLOB_STORE_ID`). A store created through the Vercel API or CLI sets only
  `BLOB_READ_WRITE_TOKEN`, so pass its id as `vercelBlob({ storeId })`. Nothing else to set up: browsers send and fetch large values
  through your `/jazz` route, and the core reads and writes the blobs itself with your function's
  OIDC token. Blobs are private, and each is checked against its SHA-256 when read.
- **The core's SQLite file** on its Drive, when no Blob store is connected. This works, but the
  file grows with every large value, and the backend logs a warning saying how to connect one.

To choose yourself, pass `blobs`:

```ts title="jazz.server.ts"
import { s3, vercel, vercelBlob } from "jazz-tools/backend";

// `namespace` as in "Set it up" above
vercel({ namespace }); // Vercel Blob if a Blob store is connected, otherwise SQLite
vercel({ namespace, blobs: vercelBlob({ storeId: "store_..." }) }); // a specific Blob store
vercel({ namespace, blobs: s3() }); // an S3 bucket connected through the Vercel Marketplace
vercel({ namespace, blobs: "sqlite" }); // always the core's SQLite file
```

`s3()` reads `S3_BUCKET_NAME`, `AWS_REGION` and `AWS_ROLE_ARN`, which the Marketplace's AWS
integration sets, and the core assumes that role with your function's OIDC token. The bucket can be in
any region: on Vercel, `AWS_REGION` is the function's region, so if it doesn't match the bucket, the
backend learns the bucket's region from S3's first reply, signs for it from then on, and logs a
warning suggesting you set `AWS_REGION` to it. Putting the bucket in your Sandbox's region still
keeps latency and transfer costs down. Its options are the same
as for [your own server](/docs/setup/deployment/own-server#large-values).

Each Blob store or bucket serves one Vercel environment. A store you connect spans every
environment unless you limit it, so create one store per environment, connect each to its own
environment only, and enable OIDC for each environment in the project's settings. With the CLI,
name the environment when you create the store, for example
`vercel blob create-store my-app-production --access private --environment production --yes`.
Without `--environment`, a store created through the CLI or the API is connected to production,
preview and development alike, and a second one then fails with `project_env_var_not_unique`. A core given another environment's store refuses to start, for
example "Blob store … serves the production environment, not preview; connect a separate Blob store
to each environment". Both `vercelBlob()` and `s3()` also take a `prefix`, by default
`jazz/<store id>/`.

Where large values go is a one-way choice. A core that started on SQLite can move to Vercel Blob
or S3 later: connect a store and redeploy. The core then moves the chunks already in its SQLite file
to the new store in the background, which uses compute and storage operations until it's done; how
long that takes depends on how much is stored in SQLite. Every other change, including disconnecting or swapping
the Blob store, moving between Vercel Blob and S3, or moving back to SQLite, is not supported yet
and the core refuses to start.

Upload files from the browser with `db.insertStreaming(..., file.stream())`, which goes through
`/jazz` (see [Uploading and downloading files](/docs/writing/writing-data#uploading-and-downloading-files)),
not through a route of your own: Vercel refuses a function request body over 4.5 MB with
`413 FUNCTION_PAYLOAD_TOO_LARGE`, so an upload route that passes `request.body` to
`insertStreaming` works locally and fails on Vercel. Downloads through your own route are fine.

History keeps every version of a row, so deleting rows doesn't free their large values, and there
is no way to erase them yet. Expect blob storage to only grow.

A change to the `vercelBlob()` or `s3()` options doesn't reach a core that is already running the
same `jazz-tools` version. It applies the next time the core starts: after it stops when idle, or
when you deploy a new `jazz-tools` version.

## Production, previews and development

`namespace` decides which core, and so which data, a deployment uses. Each core is a Sandbox named
`jazz-<VERCEL_PROJECT_ID>-<namespace>` with its own Drive. The function gets the deployment's
`environment` (`"production"`, `"preview"`, or a custom environment's slug) and its Git `branch`.
Pick one of these setups:

```ts title="jazz.server.ts"
import { perBranch, vercel } from "jazz-tools/backend";

// Production, and one core per preview branch: each branch starts with its own data.
vercel({
  namespace: ({ environment, branch }) =>
    environment === "production" ? "production" : perBranch(branch),
});

// One core per Vercel environment: every preview shares one core, as a staging environment
// (a custom environment such as "staging" gets its own).
vercel({ namespace: ({ environment }) => environment });
```

- **Per branch** isolates each pull request: a migration or test data on one branch never reaches
  another. `perBranch` gives the same core names as earlier versions, so existing preview cores
  keep their data. A preview deployed with `vercel deploy` or through the API has no
  branch unless the Vercel project is connected to a Git repository, even when you run the CLI
  inside a checkout. Such a preview has no branch to name, and the store throws when it opens; use
  `perBranch(branch) || "cli-previews"` to give such previews a core of their own.
- **Shared** keeps one set of preview data that all branches see. It needs fewer cores, but the
  branches share one schema history too, so a schema change or migration deployed from one branch
  applies to the data every preview uses.
- **Production's core is never shared.** A core trusts the environment whose deployment started it
  first and refuses the others. So a fixed string namespace isn't a setup: whichever environment
  deploys first pins the core, and if a preview starts it first, production's own deploys are
  refused. Name production's core from `environment`, as both setups above do.

To reset a preview's data, delete its Sandbox and the Drive attached to it (the one it mounts at
`/data`) in the Vercel dashboard. This can't be undone. Production's Sandbox and Drive are in the
same list with similar names, and a long preview Drive name is shortened with a hash, so check the
Sandbox's name (`jazz-<project>-<namespace>`) and pick the Drive from the Sandbox itself. The next
request creates both again, with an empty database and a new app ID. Large values already in Vercel Blob or S3 stay there; delete them from the store if you
need to. Nothing deletes the cores of merged or deleted branches yet.

Blob stores follow environments, not namespaces: connect one store to production and one to preview
(see [Large values](#large-values)).

When `vercel()` opens, it logs which core it uses once per process, for example
`jazz: store vercel namespace "production" (core jazz-prj-…-production)`.

## Local development

Outside Vercel, `vercel()` uses a local store instead, by default `sqlite({ path: ".jazz/local" })`.
Only production and preview deployments use the Sandbox: `next dev`, `vercel dev` and an
environment pulled with `vercel env pull` all run against a SQLite file on your machine. Pass `local` to
choose a different one, such as `vercel({ namespace, local: sqlite({ path: ".jazz/dev" }) })` to keep data you
already have.

Add `.jazz/` to `.gitignore`.

Use `vercel()` in development too, rather than switching to `sqlite()` yourself: `sqlite()` refuses
to start on Vercel, which has no lasting disk.

Only one process can open a SQLite directory at a time. If a second one tries, it fails with an
error saying another process holds the directory, usually a second dev server. Stop it, or give
each server its own `path`.

## Options

`namespace` is required; the other options are optional.

| Option           | Default                                                               | What it does                                                                                                                                                         |
| :--------------- | :-------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `namespace`      | required                                                              | Which core a deployment uses: a string, or a function of `{ environment, branch }`; see [Production, previews and development](#production-previews-and-development) |
| `region`         | `iad1`                                                                | Where the Sandbox runs; put it near your functions                                                                                                                   |
| `vcpus`          | `1`                                                                   | Sandbox size, 2 GB of memory per vCPU                                                                                                                                |
| `maxDriveBytes`  | 10 GiB                                                                | The most data the environment's Drive holds                                                                                                                          |
| `idleMs`         | 5 minutes                                                             | How long the Sandbox stays up with no requests or clients                                                                                                            |
| `coreTarballUrl` | the Linux `jazz-napi` package for your installed `jazz-tools` version | Which Jazz core build the Sandbox runs                                                                                                                               |
| `blobs`          | `vercelBlob()` if a Blob store is connected, otherwise `"sqlite"`     | Where large values go; see [Large values](#large-values)                                                                                                             |
| `local`          | `sqlite({ path: ".jazz/local" })`                                     | The store used outside Vercel                                                                                                                                        |

`vercel()` without `namespace` throws when it's called, in `next dev` too, and names the usual
choices. The namespace is lowercased, other characters become `-`, and the whole Sandbox name may be
at most 128 characters (about 90 for the namespace); an empty or longer one throws. `environment`
and `branch` come from Vercel's system environment variables, which are exposed by default. While
`vercel()` throws, the browser stays on its loading state, so check the function logs when a
deployment never finishes loading.

Upgrading from `name`: `vercel({ name })` now throws, and when it can, the error gives the exact
namespace to use. A name of the form `jazz-<project>-<rest>` becomes `namespace: "<rest>"`, where
`<project>` is your Vercel project ID lowercased, with each run of characters other than `a-z` and
`0-9` turned into one `-` (`prj_AbC1` becomes `prj-abc1`). A name of any other form (`myapp-core`,
uppercase letters, the raw `prj_…` ID) can't be reached by a namespace: that core keeps its data,
but this version opens another one, and the error says so. Without `name`, earlier versions used
the per-branch setup above, which keeps those cores. Copy that one when upgrading: the
one-core-per-environment setup (as on the home page) moves previews onto a new, empty core.

The default `coreTarballUrl` covers every published `jazz-tools` version, release candidates
included; set it only for a build you made yourself. If the Sandbox can't download the core, the
function's error says so and the Sandbox is stopped. A Sandbox that already holds another
app's core is refused.

## Limits

- Each namespace gets one persistent Sandbox and its Drive. Two apps in one Vercel project need
  namespaces that differ per environment too, for example
  `` ({ environment }) => `chat-${environment}` ``. The smallest size is 2 GB of memory and 1 vCPU.
- Nothing cleans up the Sandboxes and Drives of merged or deleted branches yet; delete them in the
  Vercel dashboard.
- The first request in an environment takes longer: it creates the Sandbox and downloads the Jazz
  server onto the Drive. Vercel's own checks of a new deployment can make that first request,
  or wake a stopped Sandbox, so the cold start may already be over when you first open the page.
- The Sandbox stops after 5 minutes with no requests and no connected clients; a connected
  client keeps it awake, even when idle. The next request wakes it, which took 0.6 to 1 s in our
  benchmarks and 4.2 s on a real project; requests after the wake took about 0.45 s.
- Vercel ends a function's WebSockets at the route's `maxDuration` (300 s by default). Just before
  that, `jazz.next()` closes each sync socket and clients reconnect at once. To reconnect less
  often, raise the limit in the route file with `export const maxDuration = 800;` (Pro plan).
- A redeploy on the same `jazz-tools` version doesn't disturb connected clients. Deploying a newer
  `jazz-tools` restarts the core on that version, which briefly drops open sockets; clients
  reconnect. An older deployment that is still running never moves the core back.
- A thin client resends unanswered writes after its socket reconnects, and each lands once; a
  transaction in flight at the drop ends with `ThinConnectionLostError`. See
  [Pending writes](/docs/setup/web-client/thin-client#pending-writes).
- `vercel()` needs Next.js 16 for now: under Next 15's webpack build, every request fails with
  "Cannot find module 'jazz-tools/package.json'".
