On your own machine, Jazz is part of your backend's process, with the data in a directory on its
disk.

This page sets up your **main backend**: the backend that runs `createJazz`, serves sync to your
browsers and apps, and decides who each user is. Other trusted machines reach Jazz through it as
[backend clients](/docs/setup/backend-client).

## Create Jazz once

```ts title="jazz.server.ts"
import { createJazz, sqlite } from "jazz-tools/backend";
import { app, permissions } from "./schema";

export const jazz = createJazz({
  app,
  permissions,
  store: sqlite({ path: process.env.JAZZ_DATA_DIR ?? "./data/jazz" }),
  authenticate: async (request) => /* your session */ null,
});
```

### Large values

Large values, such as files and long streams, are stored in chunks. Rows and the chunk index always
stay in SQLite. By default `sqlite()` keeps the chunks as files in `<path>/blobs`. Choose where they
go with `blobs`:

```ts
import { files, s3, sqlite } from "jazz-tools/backend";

sqlite({ path: "./data/jazz" }); // chunks in ./data/jazz/blobs
sqlite({ path: "./data/jazz", blobs: files({ dir: "/mnt/blobs" }) }); // a directory of your choice
sqlite({ path: "./data/jazz", blobs: s3() }); // an S3-compatible bucket
sqlite({ path: "./data/jazz", blobs: "sqlite" }); // inside the SQLite database (not recommended)
```

`"sqlite"` works, but the database file grows with every large value.

`s3()` works with AWS S3, Cloudflare R2 and MinIO. All its options are optional:

| Option     | Default            | What it does                                 |
| :--------- | :----------------- | :------------------------------------------- |
| `bucket`   | `S3_BUCKET_NAME`   | The bucket                                   |
| `region`   | `AWS_REGION`       | The bucket's region; `auto` for R2           |
| `endpoint` | AWS                | Another S3-compatible endpoint, such as R2's |
| `prefix`   | `jazz/<store id>/` | Prepended to every object name               |

```ts
// Cloudflare R2
s3({
  bucket: "my-app",
  region: "auto",
  endpoint: "https://<account>.r2.cloudflarestorage.com",
});
```

The backend reads its credentials from `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, or from
`AWS_ROLE_ARN` with `AWS_WEB_IDENTITY_TOKEN_FILE`. Each chunk is uploaded with its SHA-256, so the
bucket rejects a corrupted upload. One bucket can serve many apps and environments: each data
directory keeps its objects under its own prefix, claims that prefix the first time it uses it, and
deletes the chunks it no longer needs. Another data directory is refused on a prefix that is
already claimed.

The data directory records its choice in `<path>/blob-store`. You can move an existing directory
from `"sqlite"` to `files()` or `s3()` later; any other switch is not supported yet and refuses to
start. A blob directory belongs to exactly one data directory, so two data directories can't share
one. To copy a data directory, give the copy its own blob directory or prefix and delete its
`store-id` and `blob-store` files before it first starts, or it claims the original's.

## Deploy it

That's the whole deployment:

- **No separate process and no port.** Sync is served by your own HTTP server under `/jazz`.
- **No deploy step.** On start, Jazz applies the schema, migrations and permissions your code
  declares. If they can't be applied (a schema with no migration path), the process refuses to start
  instead of serving with the wrong rules.
- **No secrets to manage.** Browsers hold no Jazz credential: your `authenticate` function
  decides who each request is (see [How Auth Works in Jazz](/docs/setup/auth/backend)).

Keep the data directory on a durable disk (a Docker volume, an attached block device), and run one
process per directory: a second process on the same directory is refused (`<path>/jazz.lock`). `sqlite()` refuses to start on serverless hosts with no
lasting disk (Vercel, AWS Lambda, Netlify); on Vercel, use [`vercel()`](/docs/setup/deployment/vercel).

```dockerfile title="Dockerfile"
FROM node:22-slim
WORKDIR /app
COPY . .
RUN npm ci && npm run build
ENV JAZZ_DATA_DIR=/data/jazz
VOLUME /data
CMD ["node", "dist/server.js"]
```

## Data on another machine

When the data should live apart from your app servers (several app instances sharing one database,
serverless functions, an existing Jazz Cloud app), keep it in [Jazz Cloud](/docs/setup/deployment/jazz-cloud)
and point `createJazz` at it with `remote()`:

```ts title="jazz.server.ts"
import { createJazz, remote } from "jazz-tools/backend";
import { app, permissions } from "./schema";

export const jazz = createJazz({
  app,
  permissions,
  store: remote({
    appId: process.env.JAZZ_APP_ID!,
    url: process.env.JAZZ_SERVER_URL!,
    secret: process.env.JAZZ_ADMIN_SECRET!, // the app's admin secret
  }),
  authenticate: async (request) => /* your session */ null,
});
```

Everything else stays the same. Browsers still sync with your backend under `/jazz` and never see
the core's address or secret. Your backend sends its schema, migrations and permissions to the core
on start, and tells the core who each user is; the core does no auth of its own and trusts only the
holder of the app's admin secret. Keep it server-side, like a database password.

Jazz always runs inside a backend like this one. There is no separate Jazz server to install or
run.
