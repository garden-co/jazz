On your own machine, Jazz is part of your backend's process, with the data in a directory on its
disk.

This page sets up your **main backend**: the backend that runs `createJazz`, serves sync to your
browsers and apps, and decides who each user is. Other trusted machines reach Jazz through it as
[backend clients](/docs/setup/backend-client).

## Create Jazz once

```ts title="jazz.server.ts"
import { createJazz, files, sqlite } from "jazz-tools/backend";
import { app } from "./jazz.generated";
import permissions from "./jazz.permissions.json" with { type: "json" };

export const jazz = createJazz({
  app,
  permissions,
  store: sqlite({ path: process.env.JAZZ_DATA_DIR ?? "./data/jazz", blobs: files() }),
  // Read your session; return { userId, expiresAt, claims? } for a signed-in user, or null
  authenticate: async (request) => null,
});
```

The examples on this page are ES modules and use top-level `await`, so the backend package needs
`"type": "module"` (or `.mts` files). `jazz.generated.ts` must be an ES module too. In a CommonJS
package, such as an Expo app's, importing it gives `{ default }`, and `createJazz` fails with
`jazz.generated.ts arrived as { default: … }`. A backend in its own ESM package isn't enough while
the app files stay in the CommonJS package: put `jazz.app.json`, `jazz.permissions.json` and
`jazz.generated.ts` in a folder (for example `jazz/`) with a `package.json` of
`{ "type": "module" }`, run `npx jazz-tools generate` there, and import them from there in both the
app and the backend.

### Large values

Large values, such as files and long streams, are stored in chunks. Rows and the chunk index always
stay in SQLite. Choose a destination with the required `blobs` option. For existing stores
that used the previous default, pass `files()` to keep using `<path>/blobs`.

```ts
import { files, s3, sqlite } from "jazz-tools/backend";

sqlite({ path: "./data/jazz", blobs: files() }); // chunks in ./data/jazz/blobs
sqlite({ path: "./data/jazz", blobs: files({ dir: "/mnt/blobs" }) }); // a directory of your choice
sqlite({ path: "./data/jazz", blobs: s3() }); // an S3-compatible bucket
sqlite({ path: "./data/jazz", blobs: "sqlite" }); // inside the SQLite database (not recommended)
```

`"sqlite"` works, but the database file grows with every large value.

`s3()` works with any S3-compatible service, such as AWS S3 or Cloudflare R2. All its options are optional:

| Option     | Default            | What it does                                 |
| :--------- | :----------------- | :------------------------------------------- |
| `bucket`   | `S3_BUCKET_NAME`   | The bucket                                   |
| `region`   | `AWS_REGION`       | The bucket's region; `auto` for R2           |
| `endpoint` | AWS                | Another S3-compatible endpoint, such as R2's |
| `prefix`   | `jazz/<store id>/` | Prepended to every object name               |

```ts
// Cloudflare R2
s3({
  bucket: "my-app",
  region: "auto",
  endpoint: "https://<account>.r2.cloudflarestorage.com",
});
```

The backend finds its credentials the way the AWS SDKs do, taking the first of:

1. `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (with `AWS_SESSION_TOKEN` for session keys).
2. `AWS_ROLE_ARN` with `AWS_WEB_IDENTITY_TOKEN_FILE`, such as an EKS service account's role.
3. The role the host attaches to the container: on ECS, Fargate, EKS Pod Identity and Lambda, the
   host sets `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` or `AWS_CONTAINER_CREDENTIALS_FULL_URI` (with
   `AWS_CONTAINER_AUTHORIZATION_TOKEN` or `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE`) for you.
4. On EC2, the instance profile's role, read from the instance metadata service with IMDSv2. Set
   `AWS_REGION` yourself there. In a container on EC2, the instance's metadata hop limit must be at
   least 2. `AWS_EC2_METADATA_DISABLED=true` skips this step.

Keys from a role are refreshed before they expire, so a task role or instance profile needs no
static keys. If none of these is found, the backend refuses to start and names every source it
tried. Each chunk is uploaded with its SHA-256, so the
bucket rejects a corrupted upload. One bucket can serve many apps and environments: each data
directory keeps its objects under its own prefix, claims that prefix the first time it uses it, and
deletes the chunks it no longer needs. Another data directory is refused on a prefix that is
already claimed.

The store records its choice in its `jazz.sqlite`. You can move an existing directory
from `"sqlite"` to `files()` or `s3()` later; any other switch is not supported yet and refuses to
start, so treat it as a one-way choice. A blob directory belongs to exactly one data directory, so two data directories can't share
one. To copy a data directory, run `npx jazz-tools store detach <path>` on the stopped copy before it
first starts, or it claims the original's chunks. A `blobs/` directory copied inside it becomes the
copy's own; a blob directory outside it, or a prefix, is the original's, so give the copy its own (a
copied chunk directory without its `owner` file, or a new `s3()` prefix).

A data directory keeps the app id it was first started with and refuses to start with another
`--app-id`. To change it (a wrong first start, or a renamed app), stop the server and run
`npx jazz-tools store set-app-id <path> <app id>`. Guests' device accounts are derived from the
app id, so they no longer match after a change.

History keeps every version of a row, so deleting rows doesn't free their large values, and there
is no way to erase them yet. Expect blob storage to only grow.

### A separate frontend dev server

When the frontend runs on its own dev server (Vite, say) and the backend on another port, proxy
`/jazz` and your auth routes to the backend so the browser stays on one origin, with WebSockets
on:

```ts title="vite.config.ts"
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    proxy: {
      "/jazz": { target: "http://localhost:3000", ws: true },
      "/api/auth": { target: "http://localhost:3000" },
    },
  },
});
```

With Better Auth, add the dev server's origin to `trustedOrigins`, or sign-in answers
`403 INVALID_ORIGIN` (see [Better Auth](/docs/setup/auth/better-auth#behind-a-dev-server-proxy)).

Keep `ws: true` on: a proxy that leaves the WebSocket upgrade hanging costs about 20 seconds on
every page load before the client falls back to an HTTP stream.

In production, serve the built frontend from the same origin as the backend (or put both behind
one proxy that passes WebSocket upgrades through).

## Deploy it

Deploy your backend as usual. Jazz serves sync requests through your HTTP server at `/jazz`. On
startup, Jazz applies the schema, migrations and permissions from your app files. If it can't apply
them, for example because a migration is missing, it won't start.

Keep the data directory on a durable disk (a Docker volume, an attached block device), and run one
process per directory: a second process on the same directory is refused (`<path>/jazz.lock`). `sqlite()` refuses to start on serverless hosts with no
lasting disk (Vercel, AWS Lambda, Netlify); on Vercel, use [`vercel()`](/docs/setup/deployment/vercel).
Jazz creates the directory's files readable by every user on the machine (mode 0644), so on a shared
host restrict the directory itself to the service's user (for example `chmod 700`).

Give each environment its own data directory, and its own blob directory or bucket prefix, so
production, a staging server and your machine never share data: set `JAZZ_DATA_DIR` per
environment, as in the example above. For a staging copy of production's data, copy a backup into a
new directory (see [Operating Jazz](/docs/operating/backups-and-upgrades)); never point two servers
at one directory.

```dockerfile title="Dockerfile"
FROM node:22-slim
WORKDIR /app
COPY . .
RUN npm ci && npm run build
ENV JAZZ_DATA_DIR=/data/jazz
VOLUME /data
CMD ["node", "dist/server.js"]
```

On shutdown, close Jazz so writes still in flight reach the store and open sockets end cleanly:

```ts title="server.ts"
process.on("SIGTERM", () => {
  void jazz.close().then(() => server.close());
});
```

### Proxies, paths and origins

These `createJazz` options cover a backend behind a proxy or on a non-default path:

| Option            | Default            | What it does                                                                                                                                              |
| :---------------- | :----------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `basePath`        | `"/jazz"`          | The path Jazz is served under. Mount your routes with `jazz.basePath`, and pass the same path as `serverUrl` in the browser                               |
| `publicUrl`       | the request's host | The URL (or URLs) browsers reach Jazz at, when a proxy changes the host or path. Recommended in production; list your dev URL too if it uses this backend |
| `allowedOrigins`  | the backend's own  | Other browser origins that may sync and sign in                                                                                                           |
| `upgradesSockets` | `false`            | Set when your host upgrades sockets itself and passes them to `jazz.acceptSocket` (Bun, Deno, your own `ws`); `attach()` and Vercel set it on their own   |

A proxy in front of your backend must pass WebSocket upgrades through to `/jazz`. Pages on another
origin can't sign in with your app's cookie yet, even with `allowedOrigins`; serve the page and
`/jazz` from the same origin for now.

## Data on another machine

An existing app on [Jazz Cloud (deprecated)](/docs/setup/deployment/jazz-cloud) keeps its data
there: point `createJazz` at it with `remote()`:

```ts title="jazz.server.ts"
import { createJazz, remote } from "jazz-tools/backend";
import { app } from "./jazz.generated";
import permissions from "./jazz.permissions.json" with { type: "json" };

export const jazz = createJazz({
  app,
  permissions,
  store: remote({
    appId: process.env.JAZZ_APP_ID!,
    url: process.env.JAZZ_SERVER_URL!,
    secret: process.env.JAZZ_ADMIN_SECRET!, // the app's admin secret
  }),
  // Read your session; return { userId, expiresAt, claims? } for a signed-in user, or null
  authenticate: async (request) => null,
});
```

Set `url` to the core's final URL: your backend never follows a redirect from the core (it would
carry the backend's credential along), so a core that answers with one fails to open.

Everything else stays the same. Browsers still sync with your backend under `/jazz` and never see
the core's address or secret. Your backend sends its schema, migrations and permissions to the core
on start, and tells the core who each user is; the core does no auth of its own and trusts only the
holder of the app's admin secret. Keep it server-side, like a database password.

Jazz always runs inside a backend like this one. There is no separate Jazz server to install or
run.

## Coming from the alpha.59 server

Alpha.59 ran Jazz as its own process (`jazz-tools server`), and clients connected to its port
(`:1625/` by default). In alpha.60 that process is gone:

- **Clients sync with your backend under `/jazz`**, on your app's own origin, instead of with a
  separate Jazz server.
- **`--jwks-url` and the other JWT flags move into `authenticate`.** Pass the same values to
  [`fromJWT()`](/docs/setup/auth/custom#tokens-from-your-identity-provider).
- **`jazz-tools deploy` is gone.** Your backend applies its schema, migrations and permissions
  each time it starts.
- **Move the data directory with alpha.65's import tool** (see
  [Upgrading from alpha.59](/docs/operating/backups-and-upgrades#self-hosted-alpha59-servers)).
  The import keeps large values inside `jazz.sqlite`. On its first start your backend moves them
  to `blobs/`, or wherever `blobs` points, without logging anything. Run the import's `verify`
  before that first start.
