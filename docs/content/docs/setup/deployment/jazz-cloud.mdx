Jazz Cloud stores and syncs your app's data. Your own backend sits in front of it: browsers talk only to your backend, which signs users in with your auth and connects to Jazz Cloud. Jazz Cloud does no user auth of its own.

This page sets up your **main backend**: the backend that runs `createJazz`, serves sync to your
browsers and apps, and decides who each user is. Other trusted machines reach Jazz through it as
[backend clients](/docs/setup/backend-client).

## Get an app ID

Your app ID namespaces your data for storage and sync. Click below to generate one on Jazz Cloud. You also get the secrets your backend needs. Generated apps are unclaimed until you claim them in the dashboard, and unclaimed apps are deleted after 14 days.

## Connect your backend

Put the generated values in your backend's environment. All of them stay server-side; the browser never needs the app ID or the sync URL, and the admin secret is like a database password:

```bash title=".env"
JAZZ_APP_ID="<your app ID>"
JAZZ_SERVER_URL="https://v2.sync.jazz.tools/"
JAZZ_ADMIN_SECRET="<admin secret>"
```

Then open the app in your backend's language. The TypeScript backend points `createJazz` at Jazz
Cloud; a Rust or Go backend connects to the same sync URL with the same admin secret.

<Tabs groupId="jazz-environment" items={["TypeScript", "Rust", "Go"]} persist updateAnchor>
  <Tab value="TypeScript">
    Point `createJazz` at Jazz Cloud with the `remote()` store:

    ```ts title="jazz.server.ts"
    import { createJazz, remote } from "jazz-tools/backend";
    import { app } from "./jazz.generated";
    import permissions from "./jazz.permissions.json" with { type: "json" };

    export const jazz = createJazz({
      app,
      permissions,
      store: remote({
        appId: process.env.JAZZ_APP_ID!,
        url: process.env.JAZZ_SERVER_URL!,
        secret: process.env.JAZZ_ADMIN_SECRET!, // the app's admin secret
      }),
      // Who is signed in, read from your own auth's session.
      authenticate: async (request) => {
        const session = await getSession(request);
        if (!session) return null;
        return {
          userId: session.user.id,
          expiresAt: Math.floor(session.session.expiresAt.getTime() / 1000),
        };
      },
    });
    ```

  <Tab value="Rust">
    The `jazz-app` crate isn't on crates.io yet, so depend on it from the Jazz repository:

    ```toml title="Cargo.toml"
    [dependencies]
    jazz-app = { git = "https://github.com/garden-co/jazz" }
    tokio = { version = "1", features = ["full"] }
    ```

    **Generate the bindings.**
    With a `Cargo.toml` that depends on `jazz-app` beside `jazz.app.json`, `jazz-tools generate` writes
    `src/jazz_app.rs`:

    ```bash
    npx jazz-tools generate            # checks the files, writes src/jazz_app.rs
    npx jazz-tools generate --check    # in CI: fails if src/jazz_app.rs is stale
    ```

    Commit `src/jazz_app.rs` and declare it with `mod jazz_app;`. Per table it gives you:

    - a row struct (`Todo`), with snake_case fields;
    - `NewTodo`, where `NewTodo::new(…)` takes the required columns;
    - `TodoUpdate`;
    - a module (`todos`) with `query()`, typed columns and relations.

    If your app declares computed fields or transforms, the bindings also declare a `Computed` trait,
    and `open` takes your implementation of it.

    To generate the bindings at build time instead, call `jazz_codegen::rust::build()` from `build.rs`
    and `include!` its output.

    **Open the app.**
    <include cwd lang="rust" meta='title="src/main.rs"'>
      ../examples/docs/todo-server-rs/src/main.rs#backend-open-rust
    </include>

    `jazz_app::Jazz` is `Send + Clone`, so it can sit in shared state, such as an Axum router's. The
    client runs on a thread of its own. Before the process exits, call `jazz.shutdown().await`, so that
    the calls already made finish and the local store closes.

    The backend needs the sync server's admin secret, to publish the bundle, and its backend secret, to
    vouch for the user it acts as. Keep both on the server.

    The [Reading](/docs/reading/queries) and [Writing](/docs/writing/writing-data) pages have a Rust tab
    for each example. `examples/todo-server-rs` in the repository is a complete service.

    **Run the core under the app id your clients use.** A TypeScript client names no app: it derives
    the app id from its `serverUrl`, and its account routes are `<serverUrl>/apps/<that id>/…`. The
    id is the UUIDv5, in the DNS namespace, of the endpoint URL as the client resolves it: origin and
    path, `ws(s)` read as `http(s)`, no trailing slash, such as `https://app.example.com/jazz`. If the
    core behind your backend runs under any other id, every account route answers 404. (TypeScript's
    `createJazz` maps between the two for you; Rust and Go don't yet.) So either run the core under
    the derived id, or, when the id is fixed, as an app's on Jazz Cloud is, set your clients'
    `scope` to it: `<JazzProvider config={{ serverUrl: "/jazz", scope: "<app id>" }}>`.

    ```rust
    // The URL your clients sync with, exactly as they resolve it.
    let app_id = AppId::from_name("https://app.example.com/jazz");
    ```

    What Rust's backend doesn't do yet is listed in [Language support](/docs/reference/language-support#rust).

  <Tab value="Go">
    Add the module. Its versions are Jazz's: each release tags it as `packages/jazz-go/v<version>`, so
    its path ends in `/v2`:

    ```bash
    go get github.com/garden-co/jazz/packages/jazz-go/v2@v2.0.0-alpha.65
    ```

    Building needs cgo (a C compiler) and Jazz's core as a static library, `libjazz_ffi.a`, for your
    platform. Download it from the same release (`linux-x86_64`, `linux-aarch64` or `darwin-aarch64`),
    check it, and point `CGO_LDFLAGS` at it:

    ```bash
    release=https://github.com/garden-co/jazz/releases/download/v2.0.0-alpha.65
    archive=libjazz_ffi-linux-x86_64.tar.gz
    mkdir -p ~/.local/lib/jazz && cd ~/.local/lib/jazz
    curl -fsSLO "$release/$archive" && curl -fsSL "$release/SHA256SUMS" | grep " $archive\$" | sha256sum -c -
    tar -xzf "$archive" libjazz_ffi.a LINK_FLAGS   # only the static library: the linker prefers a shared one
    export CGO_LDFLAGS="-L$HOME/.local/lib/jazz $(cat ~/.local/lib/jazz/LINK_FLAGS)"
    cd - && go build ./...
    ```

    (On macOS, `shasum -a 256 -c -` checks the sum.)

    Or build it from source, with Rust:

    ```bash
    git clone --depth 1 --branch v2.0.0-alpha.65 https://github.com/garden-co/jazz
    cargo build --release -p jazz-ffi --manifest-path jazz/Cargo.toml
    export CGO_LDFLAGS="-L$PWD/jazz/target/release"
    ```

    Use the library of the same release as the module. Linux is tested in CI; macOS (Apple silicon)
    builds but is not tested yet; Intel Macs and Windows have no library.

    **Generate the bindings.**
    With a `go.mod` that requires `jazz-go/v2` beside `jazz.app.json`, `jazz-tools generate` writes the
    `jazzapp` package to `jazzapp/jazz_app.go`:

    ```bash
    npx jazz-tools generate            # checks the files, writes jazzapp/jazz_app.go
    npx jazz-tools generate --check    # in CI: fails if jazzapp/jazz_app.go is stale
    ```

    Commit `jazzapp/jazz_app.go` and import it as `<your module>/jazzapp`. Per table it gives you:

    - a row struct (`Task`), with `json` tags of the column names. Nullable columns are pointers;
    - `NewTask`, the row to insert. Nullable and defaulted columns are pointers you may leave nil;
    - `TaskPatch`, whose fields change a column only when you set them with `jazz.Set(…)`;
    - a string type with constants for each enum column (`TaskStatus`, `TaskStatusTodo`, …);
    - the table's relations as optional fields of the row (`Task.Show *Show`, `Task.Comments
    []Comment`), filled when a query includes them: `q.Include(jazzapp.Tasks.Show)`;
    - a table value (`jazzapp.Tasks`) with typed columns (`jazzapp.Tasks.Status.Eq(…)`), relations,
      `Query()`, `Insert`, `Update` and `Delete`. Writes and reads take a `jazz.Querier`: the `*jazz.DB`,
      or a `*jazz.Tx` inside `db.Tx(ctx, func(tx *jazz.Tx) error { … })`.

    If your app declares computed fields or transforms, the bindings also declare a `jazzapp.Computed`
    interface: a method per computed field, and a `View` and `Stored` method per transform.
    `jazzapp.Open(ctx, cfg, computed)` takes your implementation, so a missing method is a compile error.

    **Open the app.**
    <include cwd lang="go" meta='title="main.go"'>
      ../examples/stage-plan/apps/go-cli/docs_snippets_test.go#backend-open-go
    </include>

    Writes are local-first: a write the server's permissions refuse returns no error. It is never
    synced, and other users never see it.

    Mergeable text columns (`merge: "text"`, `"markdown"`, `"html"`) get an edit method:
    `jazzapp.Tasks.EditNotes(ctx, db, id, jazz.Splice(pos, deleteLen, "insert"))`, with positions as
    UTF-8 byte offsets, which merge with concurrent edits. `jazz.InsertStreaming` streams an
    `io.Reader` into a `bytes` column and `jazz.OpenBytes` reads one a page at a time (`jazz.Range` and
    `jazz.JSONAt` select part of a large value), `jazzapp.Tasks.Upsert` and `Restore` upsert and
    restore rows (`jazz.IncludeDeleted(q)` reads deleted ones), `jazz.HopTo`, `jazz.Gather`
    (recursive queries), `jazz.Union` and `jazz.History` cover the graph and history queries, and `jazzapp.Tasks.CanInsert(ctx, db, row)` (and `CanRead`,
    `CanUpdate`, `CanDelete`) advise what the app's permissions allow.

    Errors match their kind with `errors.Is`: `jazz.ErrPermission`, `jazz.ErrRefused`,
    `jazz.ErrNotSupported`, `jazz.ErrConflict`, `jazz.ErrIO` and `jazz.ErrClosed`. Use `errors.As` with a
    `*jazz.Error` for the details.

    A `*jazz.DB` is safe for concurrent use. Every call takes a `context.Context`. A cancelled context
    returns at once, but the call still runs to its end, so a write may still apply. Before the process
    exits, call `db.Close()`.

    A backend that syncs needs the sync server's URL, its admin secret (`AdminSecret`, to publish the
    permissions) and its backend secret (`BackendSecret`, to vouch for its session user and for the end
    users its endpoint signs in). Like every
    backend, give it no HTTP surface that callers can reach without your own authentication.

    The [Reading](/docs/reading/queries) and [Writing](/docs/writing/writing-data) pages have a Go tab
    for each example. `examples/stage-plan/apps/go-cli` in the repository is a complete StagePlan
    command-line app.

    the app id from its `serverUrl`, and its account routes are `<serverUrl>/apps/<that id>/…`. The
    id is the UUIDv5, in the DNS namespace, of the endpoint URL as the client resolves it: origin and
    path, `ws(s)` read as `http(s)`, no trailing slash, such as `https://app.example.com/jazz`. If the
    core behind your backend runs under any other id, every account route answers 404. (TypeScript's
    `createJazz` maps between the two for you; Rust and Go don't yet.) So either run the core under
    the derived id, or, when the id is fixed, as an app's on Jazz Cloud is, set your clients'
    `scope` to it: `<JazzProvider config={{ serverUrl: "/jazz", scope: "<app id>" }}>`.

    ```go

    // The URL your clients sync with, exactly as they resolve it.
    appID := uuid.NewSHA1(uuid.NameSpaceDNS, []byte("https://app.example.com/jazz")).String()
    ```

On start, your backend applies its schema, migrations and permissions to the app on Jazz Cloud. For each request it tells Jazz Cloud who the user is, which is why `authenticate` lives in your backend. Browsers sync with your backend under `/jazz`, never with Jazz Cloud directly.

## Serve your users from Rust or Go

A Rust or Go backend serves the same `/jazz` routes as `createJazz`, and acts as a request's user in
your own routes, like `jazz.forReqUser(request)`:

<Tabs groupId="jazz-environment" items={["TypeScript", "Rust", "Go"]} persist updateAnchor>
  <Tab value="TypeScript">
    See [Mount it](#mount-it) and [User-scoped use](#user-scoped-use) above.
  </Tab>
  <Tab value="Rust">
    `jazz_app::endpoint::Endpoint` is the app's Jazz endpoint: the routes your users' browser and
    native clients connect to, the same ones `createJazz` serves. Build it from the backend's handle and
    your app's sign-in, a closure that reads the request's cookies or bearer token and answers who is
    signed in (see [How Auth Works in Jazz](/docs/setup/auth/backend)). With the `axum` feature,
    `endpoint.router()` serves all of it:

    ```toml title="Cargo.toml"
    [dependencies]
    jazz-app = { git = "https://github.com/garden-co/jazz", features = ["axum"] }
    axum = "0.8"
    ```

    <include cwd lang="rust" meta='title="src/main.rs"'>
      ../examples/docs/endpoint-server-rs/src/lib.rs#backend-serve-rust
    </include>

    `AuthUser::new` takes the user's id and when the answer stops holding (Unix seconds); add claims
    with `.claims(…)`. A sync session asks its client to reconnect shortly before that, or after an hour
    at most (`.session_ttl(…)`), and the endpoint asks your sign-in again then. `.base_path(…)` serves it
    under another path than `/jazz`.

    Without Axum, your HTTP server passes requests under `/jazz` to `endpoint.handle(request)`. It
    upgrades the sync socket (`endpoint.is_socket(path)`) itself and passes the socket's binary
    messages to `endpoint.serve_socket(request, incoming, outgoing)`, then closes it with the code and
    reason that returns.

    **Act as the request's user.**
    In your own routes, `endpoint.for_user(&request)` is the backend's handle acting as the request's
    user (TS `forReqUser`): its reads and writes run as them, under your permissions.
    `endpoint.for_auth_user(&user)` does the same for an `AuthUser` you already have (TS `forSession`).

    <include cwd lang="rust" meta='title="src/main.rs"'>
      ../examples/docs/endpoint-server-rs/src/lib.rs#backend-for-user-rust
    </include>

    A user gets a Jazz account when they first sign in from a client. Until then `for_user` fails with
    `Error::NoAccount`. `endpoint.create_account_for(user_id)` creates one for a user who never opens a
    client, and `endpoint.account_for(&request)` returns the request's user's account, if they have one.

    Users' handles share one client, which the endpoint opens on first use and keeps in memory. Their
    `shutdown` does nothing; `endpoint.shutdown()` stops that client, and the backend's own handle runs
    on.
