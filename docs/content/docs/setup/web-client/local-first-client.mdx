The local-first client keeps a replica of the data each user can read in the browser. Queries
answer from it instantly, writes show up before they sync, and the app keeps working offline. It
loads as its own chunk on top of the [thin client](/docs/setup/web-client/thin-client).

## Connect

Pass a loader for the local-first client. The app starts thin, then upgrades in the background
after the first load:

<Tabs groupId="jazz-framework" items={["React", "TypeScript"]} persist updateAnchor>
  <Tab value="React">
    ```tsx title="App.tsx"
    import { JazzProvider } from "jazz-tools/react";

    function Root() {
      return (
        <JazzProvider client={() => import("jazz-tools/local-first")} signedOut={<SignIn />}>
          <App />
        </JazzProvider>
      );
    }
    ```

  </Tab>
  <Tab value="TypeScript">
    ```ts title="app.ts"
    import { createJazzClient } from "jazz-tools/client";
    import { app } from "./schema";

    const jazz = await createJazzClient({ client: () => import("jazz-tools/local-first") });
    authClient.onSessionChange(() => void jazz.reauthenticate());
    // The client swaps to local-first in the background and closes the old db,
    // so read db from the snapshot each time instead of keeping it.
    const db = () => jazz.getSnapshot().client!.db;

    const todos = await db().all(app.todos);
    ```

  </Tab>
</Tabs>

A browser that has upgraded this account before opens it local-first straight away, so the app
works offline on later visits. If a background upgrade fails, the app stays on the thin client and
logs a warning.

The `import()` stays in your code, so the Wasm engine downloads only when the client upgrades. To
upgrade only on demand, call `useDb().upgradeToLocalFirst(() => import("jazz-tools/local-first"))`
instead; see [Upgrading to local-first](/docs/setup/web-client/thin-client#upgrading-to-local-first).

## Options

<include>../../../partials/web-client-shared-options.mdx</include>

The local-first client also takes:

| Option           | Default                    | What it does                                                                      |
| :--------------- | :------------------------- | :-------------------------------------------------------------------------------- |
| `driver`         | `{ type: "persistent" }`   | Where the replica lives: IndexedDB, or `{ type: "memory" }` for nothing on disk   |
| `dbName`         | derived from your endpoint | Logical base name of the local database; Jazz keeps one per endpoint and account  |
| `runtimeSources` | found automatically        | Where to load the Wasm and worker from; see [Wasm and workers](#wasm-and-workers) |
| `logLevel`       | `"warn"`                   | Wasm log level, for debugging                                                     |

## Local storage

By default the replica lives in IndexedDB, one database per endpoint and account, so two users on
the same browser never share data. `driver: { type: "memory" }` keeps it in memory only, and it is
gone when the tab closes. `await db.deleteClientStorage()` clears the current one; see
[Resetting browser storage](/docs/setup/auth/backend#resetting-browser-storage).

### Eviction

`{ type: "persistent" }` writes to [IndexedDB](https://developer.mozilla.org/docs/Web/API/IndexedDB_API). By default browsers treat this as **best-effort** storage&hairsp;—&hairsp;under disk pressure, or after long inactivity, the browser can clear it without warning. For a local-first app that means a returning user can find their identity (the local-first secret) and any data owned only by that user wiped.

The trade-offs are:

- **Best-effort (default).** No prompt, no friction. Acceptable when the server holds a copy of every row the user cares about, or when the app gracefully reseeds from sync. Anything that exists only on this device is at risk.
- **Persistent.** Storage is only cleared by an explicit user action (clearing site data, uninstalling). Required for true offline-first apps and for any data that doesn't round-trip through a server. Browsers gate this behind [`navigator.storage.persist()`](https://developer.mozilla.org/docs/Web/API/StorageManager/persist), which may show a prompt or grant silently based on engagement heuristics.

To request persistent storage, call it once after the user has signed in or interacted enough that a prompt makes sense:

```ts
if (navigator.storage?.persist) {
  const granted = await navigator.storage.persist();
  if (!granted) {
    // Fall back: rely on sync, warn the user, or retry later.
  }
}
```

Check `navigator.storage.persisted()` on subsequent loads to see whether the grant is still in effect. Pair this with the [backup and restore](/docs/setup/auth/local-first#backing-up-and-restoring-the-secret) flow so the local-first secret can be recovered if storage is ever cleared.

## Offline and guests

Reads and writes keep working offline and sync when the connection returns. A signed-out visitor
can also start as a [local-first guest](/docs/setup/auth/local-first): an account created on the
device, which keeps its data when the visitor signs up later.

## Wasm and workers

### Bundler config

There is no Jazz plugin to add. In development, run your app as usual: `createJazz` in your
[main backend](/docs/how-jazz-works#how-a-backend-talks-to-jazz) is the dev server, and it publishes your schema, permissions
and migrations every time it starts.

The local-first client loads Jazz's Wasm in the browser, and a Next.js backend loads Jazz's native
module (`jazz-napi`) on the server. Tell your bundler to leave them alone:

<Tabs groupId="jazz-bundler" items={["Vite", "Next.js"]} persist updateAnchor>
  <Tab value="Vite">
    ```ts title="vite.config.ts"
    import { defineConfig } from "vite";

    export default defineConfig({
      // plugins: your framework's plugin (React, Vue, Svelte, Solid, SvelteKit) ...
      // Load the Wasm as a real module instead of pre-bundling it.
      optimizeDeps: { exclude: ["jazz-wasm"] },
    });
    ```

    This is the same for React, Vue, Svelte, Solid and SvelteKit. With pnpm, also add `jazz-wasm` as a
    direct dependency of your app so its strict layout resolves it.

  </Tab>
  <Tab value="Next.js">
    ```ts title="next.config.ts"
    import type { NextConfig } from "next";

    const nextConfig: NextConfig = {
      // Your backend loads Jazz's native module; Next must not bundle it.
      serverExternalPackages: ["jazz-napi"],
    };

    export default nextConfig;
    ```

  </Tab>
</Tabs>

The [thin client](/docs/setup/web-client/thin-client) has no Wasm, so it needs no Vite line. A
Next.js app that imports `jazz-tools/backend` still needs `serverExternalPackages`.

### Wasm loading

Use `runtimeSources` when Jazz can't automatically find its internal assets. This usually only happens with non-standard bundler configurations.

| Field                            | Use it when                                                                 |
| -------------------------------- | --------------------------------------------------------------------------- |
| `runtimeSources.baseUrl`         | Jazz runtime assets are served from a shared base path like `/assets/jazz/` |
| `runtimeSources.wasmUrl`         | The Wasm file has an explicit public URL                                    |
| `runtimeSources.brokerWorkerUrl` | The browser broker worker has an explicit public URL                        |
| `runtimeSources.wasmVersion`     | An immutable deployed build version for configured browser asset URLs       |
| `runtimeSources.wasmSource`      | Your runtime gives you Wasm bytes directly                                  |
| `runtimeSources.wasmModule`      | Your runtime gives you a precompiled `WebAssembly.Module`                   |

Jazz resolves these in this order:

1. `runtimeSources.wasmModule`
2. `runtimeSources.wasmSource`
3. `runtimeSources.wasmUrl` / `runtimeSources.brokerWorkerUrl`
4. `runtimeSources.baseUrl`
5. built-in zero-config fallback

Use `baseUrl` when both assets live together under one public directory. Use explicit `wasmUrl` /
`brokerWorkerUrl` when your app serves them from different places.

For browser URL overrides, also set `wasmVersion` to an immutable value that changes whenever
either the Wasm or broker-worker build changes (for example, your deployment's asset manifest
version). Jazz adds that value to both asset URLs, so a rolling deployment cannot reuse a
long-lived SharedWorker with bytes fetched from an older build at the same URL. Your asset host
must serve these URLs with query strings intact.

### Worker failures

After the shared worker acknowledges startup, runtime initialisation has a five-minute grace period. If it does not become ready, startup reports an error instead of leaving the client pending indefinitely. Suspended tabs receive fresh grace when they resume.

While control requests are waiting for worker replies, Jazz probes the connection every 30 seconds and allows 30 seconds for a response. These are connection-health checks, not query or storage-operation timeouts: a responsive worker can continue a long operation, and idle connections are not continuously probed.

An unresponsive-worker error does not prove that an outstanding operation failed. It may already have completed. Jazz does not automatically retry operations with an unknown outcome or clear IndexedDB. Use the existing [client and session lifecycle](/docs/setup/auth/backend#lifecycle) to recover, and establish a mutation's outcome before retrying it. Terminal shutdown reports the causal failure without waiting indefinitely for an unresponsive worker; it does not claim that an unacknowledged durable handoff succeeded.

An intentional storage reset releases the old foreground identity without returning it to the erased store. `deleteClientStorage()` waits for a fresh identity before the same application client can be used again. If shutdown starts during that acquisition, Jazz retires the unused identity instead. Inspector attachments are session-scoped: after a reset, open a new attachment rather than reusing the old one.
