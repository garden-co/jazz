A device account is a Jazz account whose key lives on the device. It needs no sign-in and works
offline. Device accounts are how you do **guests** in Jazz: someone can use your app before they sign
up, and keep everything they made when they do. They are also a **local-first friendly** way to
sign in at all: an app with no sign-in of its own can run on device accounts alone.

Jazz derives a device account's founding identity from a random key. Creating one works offline.
When it connects, the server verifies the key's signing proof and admits the account.

## Client setup

Start the session as a device account with `initial: "device"`:

```ts
import { createJazzClient } from "jazz-tools/client";

const session = await createJazzClient({
  serverUrl: "/jazz",
  initial: "device",
  // Local data, so a guest keeps working offline once its first visit has reached the backend.
  client: () => import("jazz-tools/local-first"),
});
```

In React, React Native, Expo, Vue, Solid and Svelte, pass the same config to the provider:
`<JazzProvider config={{ serverUrl: "/jazz", initial: "device" }}>`.

Your backend lets device accounts sync by returning `acceptDeviceAccounts(request)` from
`authenticate` for signed-out requests (an app with no sign-in passes
`authenticate: acceptDeviceAccounts`). Device accounts are refused otherwise. With
`serverUrl: null`, Jazz stays on the device: no backend, one device account per browser profile.

Your backend still decides who is signed in. A device account is who the session is signed in as
while your backend names no one; once your backend's `authenticate` names a user, `refresh()`
follows it. See [How Auth Works](/docs/setup/auth/backend).

Jazz creates the device account, or reopens the one already on the device. Provided the app has
fully loaded at least once, new device accounts can be created offline. In a browser, the key is
kept in browser storage. On Expo, Jazz stores it using SecureStore. In a bare React Native app,
provide your own atomic `AccountStore` backed by protected device storage. A first visit made while
your backend is unreachable is not safe yet: the client stays thin, and a guest write made then can
be lost on reload.

To start signed out and create the device account only when the user asks (a "Continue as guest"
button), leave out `initial` and call `createDeviceAccount()` on the session, or from
`useJazzSession()` under `<JazzProvider>` (Svelte: `getJazzSession()`).

`snapshot.user.kind` is `"device"` while the session is signed in as a device account, and
`"backend"` for a user your backend signed in.

## Backing up and restoring the key

A device account's key is held by the user's device. It is 32 random bytes. If it is lost, the user
can't get back into their account without a linked sign-in method. You can turn the key into a
recovery phrase that users can back up and use to regain access if the key is deleted from the
device's storage.

The recovery phrase is like a password: anyone who has it can sign in to the account. Keep it out of
logs, and warn the user that it's sensitive. `session.exportDeviceKey()` returns the key as a
`jazz-auth-v1:…` string:

```ts
import { RecoveryPhrase } from "jazz-tools/passphrase";

const phrase = RecoveryPhrase.fromSecret(session.exportDeviceKey());
```

You can only export the key while the session is signed in as the device account. Signing out
doesn't delete the key from the device, so the account can still be restored later.

### Recovery passphrase

To restore a device account from a recovery phrase, turn the phrase back into a key and pass it to
`restoreDeviceAccount`:

```ts
await session.restoreDeviceAccount(RecoveryPhrase.toSecret(userInput));
```

If the phrase is invalid, `RecoveryPhrase.toSecret` throws a `RecoveryPhraseError` whose `code` is
`invalid-word`, `invalid-checksum` or `invalid-length`, so handle it in your sign-in form.

You don't need to sign out first: restoring switches accounts whoever is signed in, a new device
account included, the same way any account change does (see
[Switching accounts](/docs/setup/auth/backend#switching-accounts) for what happens to pending
writes).

### Passkey backup

Browser apps can wrap the same key with a passkey:

```ts
import { BrowserPasskeyBackup } from "jazz-tools/passkey-backup";

const backup = new BrowserPasskeyBackup({
  appName: "My App",
  appHostname: "app.example",
});
await backup.backup(session.exportDeviceKey(), "My account");
```

Pass the value returned by `await backup.restore()` to `await session.restoreDeviceAccount(key)` to
sign in to the account.

Passkey support and sync depend on the user's platform. Passkeys are associated with a domain: if
`appHostname` isn't set correctly, the user may not be offered the passkey when restoring their
account, or may not be able to create it. Without `appHostname`, the passkey belongs to the current
page's hostname, so a passkey made on a preview URL won't work on production. Set it to your
production hostname.

## Signing up later

When a guest signs up with your auth, call `await session.linkDeviceAccount()` after your sign-up
has set its session. The client proves it owns the device account with its key; your backend's
`authenticate` names the new user, and Jazz links that user to the existing account. Jazz performs
graceful shutdown, linking, and client replacement. The account ID stays the same, so account-based
ownership remains valid, and earlier rows keep the identity that authored them.

The session also links on its own when your backend names a user with no Jazz account yet while a
device account is signed in. Turn that off on shared devices with
`linkDeviceAccountOnSignUp: false`.

The user must not have a Jazz account of their own yet. If they do, the app chooses whether to
sign in to that account (`refresh()`) or migrate data explicitly; Jazz never merges accounts. See
[Other / Custom](/docs/setup/auth/custom#guests-who-sign-up) and
[Lifecycle](/docs/setup/auth/backend#lifecycle) for failure and sign-out handling.

## Permissions by auth mode

Use `session.user`, the account, for stable ownership. Use `session.identity`, the exact issuer and
subject, when a policy deliberately distinguishes linked identities. A device account's identity
(issuer `urn:jazz:local-first`) is authenticated by its signing key; it is not an unauthenticated
guest.

You can also use claims returned by your backend's `authenticate` function in your permission policies. For example, you could give users with an admin role access to additional data. See [Declarative Permissions](/docs/schemas/policies).
