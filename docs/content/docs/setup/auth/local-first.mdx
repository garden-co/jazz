A local-first account lets someone start using an app before signing up. Jazz derives its founding identity and account from a random signing root. Creating that account works offline. When it connects, the core verifies the signing proof and admits the deterministic account.

## Client setup

Configure a session once:

```ts
import { createJazzClient } from "jazz-tools/client";

const jazz = await createJazzClient({
  serverUrl: "/jazz",
  initial: "local-first",
  // Local data, so a guest keeps working offline once its first visit has reached the backend.
  client: () => import("jazz-tools/local-first"),
});
```

Your backend lets guests sync by returning `acceptDeviceAccounts(request)` from `authenticate`
for signed-out requests (an app with no sign-in passes `authenticate: acceptDeviceAccounts`).
Guests are refused otherwise. With `serverUrl: null`, Jazz stays on the device: no backend, one
local-first account per browser profile.

Jazz creates the local-first account on the device, or opens an existing one. Provided the app has fully loaded at least once, new local-first accounts can be created offline. In a browser, the account secret is kept in browser storage. On Expo, Jazz stores local-first account secrets using SecureStore. In a bare React Native app, provide your own atomic `AccountStore` backed by protected device storage. A first visit made while your backend is unreachable is not safe yet: the
client stays thin, and a guest write made then can be lost on reload.

If you're using a framework, Jazz provides `JazzSessionProvider` and hooks for working with the current account. See [Lifecycle](/docs/setup/auth/backend#lifecycle) for details.

## Backing up and restoring the secret

Local-first accounts are accessed using a secret, which is held by the account owner. The secret is
32 automatically generated random bytes. If these bytes are lost, the user can't log back into
their account without a linked sign-in method. You can convert the secret into a recovery phrase
that users can back up and use to regain access if the secret is deleted from the device's storage.

The recovery phrase is like a password: anyone who has it can log into the account. Keep it out of
logs, and warn the user that it's sensitive. `exportLocalFirstSecret` returns the secret as a
`jazz-auth-v1:…` string:

```ts
import { exportLocalFirstSecret } from "jazz-tools";
import { RecoveryPhrase } from "jazz-tools/passphrase";

const secret = exportLocalFirstSecret(jazz.getSnapshot().account!);
const phrase = RecoveryPhrase.fromSecret(secret);
```

You can only export the secret while the local-first account is signed in. Logging out doesn't delete the secret from the device, so the account can still be restored later.

### Recovery passphrase

To restore a local-first account from a recovery phrase, convert the phrase back into a secret and
pass it to `restoreLocalFirst`:

```ts
await jazz.restoreLocalFirst(RecoveryPhrase.toSecret(userInput));
```

If the phrase is invalid, `RecoveryPhrase.toSecret` throws a `RecoveryPhraseError` whose `code` is
`invalid-word`, `invalid-checksum` or `invalid-length`, so handle it in your sign-in form. See
[Lifecycle](/docs/setup/auth/backend#lifecycle) for what happens to pending writes when the account
changes.

### Passkey backup

Browser apps can wrap the same exported root with a passkey:

```ts
import { BrowserPasskeyBackup } from "jazz-tools/passkey-backup";

const backup = new BrowserPasskeyBackup({
  appName: "My App",
  appHostname: "app.example",
});
await backup.backup(exportLocalFirstSecret(jazz.getSnapshot().account!), "My account");
```

Pass the value returned by `await backup.restore()` to `await jazz.restoreLocalFirst(secret)` to
log in to the account.

Passkey support and sync depend on the user's platform. Passkeys are associated with a domain: if
`appHostname` isn't set correctly, the user may not be offered the passkey when restoring their
account, or may not be able to create it. Without `appHostname`, the passkey belongs to the current
page's hostname, so a passkey made on a preview URL won't work on production. Set it to your
production hostname.

## Signing up later

When a local-first user signs up with your auth, call `await jazz.linkWithBackend()` after your
sign-up has set its session. The client proves it owns the local-first account with its own key;
your backend's `authenticate` names the new user, and Jazz links that user to the existing account.
Jazz performs graceful shutdown, linking, and client replacement. The account ID stays the same, so
account-based ownership remains valid, and earlier rows keep the identity that authored them.

The user must not have a Jazz account of their own yet. If they do, the app chooses whether to
sign in to that account (`loginWithBackend()`) or migrate data explicitly; Jazz never merges
accounts. See [Other / Custom](/docs/setup/auth/custom#guests-who-sign-up) and
[Lifecycle](/docs/setup/auth/backend#lifecycle) for failure and logout handling.

## Permissions by auth mode

Use `session.user`, the account, for stable ownership. Use `session.identity`, the exact issuer and subject, when a policy deliberately distinguishes linked identities. A local-first identity is authenticated by its signing key; it is not an unauthenticated guest.

You can also use claims returned by your backend's `authenticate` function in your permission policies. For example, you could give users with an admin role access to additional data. See [Declarative Permissions](/docs/schemas/policies).
