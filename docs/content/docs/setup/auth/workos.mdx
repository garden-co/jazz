[WorkOS](https://workos.com/) AuthKit hosts the sign-in pages. Run its server-side flow in the
backend that hosts Jazz: the callback stores a sealed session cookie, and `authenticate` loads it.

```ts title="server.ts"
import { WorkOS } from "@workos-inc/node";
import { createJazz, remote } from "jazz-tools/backend";

const workos = new WorkOS(process.env.WORKOS_API_KEY, {
  clientId: WORKOS_CLIENT_ID,
});
const cookiePassword = process.env.WORKOS_COOKIE_PASSWORD!;

// GET /auth/callback: exchange the code and set the `wos_session` cookie.
const { sealedSession } = await workos.userManagement.authenticateWithCode({
  code,
  clientId: WORKOS_CLIENT_ID,
  session: { sealSession: true, cookiePassword },
});

export const jazz = createJazz({
  app,
  permissions,
  store: remote({ appId, url, secret }),
  authenticate: async (request) => {
    const sessionData = readCookie(request, "wos_session");
    if (!sessionData) return null;
    const session = await workos.userManagement
      .loadSealedSession({ sessionData, cookiePassword })
      .authenticate();
    return session.authenticated
      ? { userId: session.user.id, claims: { role: session.role ?? "" } }
      : null;
  },
});
```

WorkOS access tokens inside the session are short-lived. Refresh an expired session once
(`session.refresh()`) and write the new cookie on your next HTTP response; the example shows one
way to share the refreshed session with sync sockets, which can't set cookies.

If your backend receives WorkOS access tokens instead (for example, from a native app sending
`Authorization: Bearer`), use `fromJWT`. Their `role`, `permissions` and `org_id` claims reach your
policies as `session.claims`:

```ts
authenticate: fromJWT({
  jwksUrl: `https://api.workos.com/sso/jwks/${WORKOS_CLIENT_ID}`,
  issuer: `https://api.workos.com/user_management/${WORKOS_CLIENT_ID}`,
  // WorkOS access tokens carry no `aud`; the issuer already names your client id.
  audience: false,
}),
```
