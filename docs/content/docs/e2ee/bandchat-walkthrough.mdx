This page walks through one real app. It is BandChat with end-to-end encryption, in
`examples/band-chat/apps/react-hono-betterauth-e2ee`.
It is a React app with a Hono server and Better Auth for sign-in.

The code below is the app's own code, trimmed where it says so. Each section links to the reference
page that has the full detail.

## What BandChat hides, and what it does not

A room is an encrypted space. Only the room's members hold its key.

These are encrypted:

- The text of a message.
- The bytes and the name of an attachment.
- Each member's read marker (the time they last read a room).

The server still sees the rest:

- Who is in which room.
- Who wrote a message, and when.
- Room names, reactions and sketches.
- The type and the size of an attachment.
- When each read marker was written. The stored time is encrypted. The moment of the write is not,
  and it shows when that person read the room.

Read markers are hidden from the server, but not from the room's other members. Every member holds
the room's key, so every member could open a marker. The read rule keeps the server from sending
one member another's marker. Reading it takes a member and the server together.

## Declare the encryption in `schema.ts`

Mark each column to seal with `.encrypted()`. Give its table a `space`: the row whose members share
one key. In BandChat a room is its own space, so the messages and the read markers name `"room"`.

This is `schema.ts`, trimmed to the three tables that matter:

```ts title="schema.ts"
import { schema as s } from "jazz-tools";

export const schema = s.defineSchema({
  // The name stays plain, so a room is listed before its key arrives.
  rooms: s.table({ name: s.string() }),
  // One private row per reader and room. The time is sealed with the room's key.
  readMarkers: s.table(
    { roomId: s.uuid(), reader: s.uuid(), lastReadAt: s.timestamp().encrypted() },
    { room: s.rel("rooms", "roomId") },
    { space: "room" },
  ),
  // The text and the attachment are sealed. Who wrote when stays plain.
  messages: s
    .table(
      {
        roomId: s.uuid(),
        senderId: s.uuid(),
        text: s.string().encrypted(),
        attachment: s.bytes().optional().encrypted(),
        attachmentName: s.string().optional().encrypted(),
        attachmentType: s.string().optional(),
        attachmentSize: s.int().optional(),
      },
      { room: s.rel("rooms", "roomId") },
      { space: "room" },
    )
    // A room's newest message is one index entry, so the room list reads it
    // without sorting the room's history.
    .compositeIndex(["roomId", "$createdAt"]),
});
```

Run `npx jazz-tools generate`. It writes the encryption into `jazz.app.json` and the typed
bindings into `jazz.generated.ts`. Your code sees the plain types. `text` is a string, even though
the server stores bytes. [Getting started](/docs/e2ee/getting-started) has the rules for what
`generate` refuses.

## Write the permissions with `isMember`

Membership is one thing: the rows of Jazz's members table. `isMember("rooms", roomId)` is true when
the signed-in account has a member row for that room. Every rule that means "is in this room" says
that, and nothing else.

```ts title="permissions.ts"
import { schema } from "./schema";

const { definePermissions, allOf, session, isMember } = schema;

const isRoomMember = (roomId: Parameters<typeof isMember>[1]) => isMember("rooms", roomId);

export const permissions = definePermissions({
  rooms: {
    read: (room) => isRoomMember(room.id),
    insert: true,
    // Whoever may update a room manages its members, so only the creator may.
    update: { "$createdBy.account": session.user },
    delete: { "$createdBy.account": session.user },
  },
  messages: {
    read: (message) => isRoomMember(message.roomId),
    insert: (message) => isRoomMember(message.roomId),
    update: false,
  },
  // The read rule is narrower than the room's. See "Know the limits" below.
  readMarkers: {
    read: (marker) => allOf({ reader: session.user }, isRoomMember(marker.roomId)),
    insert: (marker) => allOf({ reader: session.user }, isRoomMember(marker.roomId)),
    updateIf: { reader: session.user },
    updateTo: (marker) => allOf({ reader: session.user }, isRoomMember(marker.roomId)),
    delete: { reader: session.user },
  },
});
```

This is trimmed. The real file also has the rules for profiles, reactions, sketches, join requests
and the app's own `roomMembers` table. Its `messages` rules also check the sender, and let only the
sender delete a message.

Two choices matter here.

- **Only the creator updates a room.** The room's update rule is the rule for adding and removing
  members. A member who could update the room could add anyone.
- **A space table's read rule is `isMember` of its own `id`.** `rooms` does that. Deploy refuses the
  app if it does not.

## Give the browser its keys

In a browser, Jazz keeps the device's keys for you, in IndexedDB. You pass `app` so Jazz knows which
columns are encrypted before the first query. You do not write a private store. Apps on Node and the
native platforms do: see [Private store](/docs/e2ee/private-store).

This is BandChat's provider:

```tsx
import { JazzProvider as Jazz } from "jazz-tools/react";
import { app } from "./jazz.generated";

// Start on the thin client. Load the local-first client, which holds the keys,
// in its own chunk once the page has loaded.
const loadLocalFirst = () => import("jazz-tools/local-first");

export function JazzProvider({ children }: React.PropsWithChildren) {
  return (
    <Jazz config={{ serverUrl: "/jazz", client: loadLocalFirst, encryption: { app } }}>
      {children}
    </Jazz>
  );
}
```

The app starts on the thin client, which holds no keys. Rooms and other plain data show at once.
Message text waits for the local-first client. See
[Encryption in the browser](/docs/e2ee/browser#before-the-local-first-client-has-loaded).

The server holds no keys at all. `createJazz` stores and relays the encrypted columns as bytes.
Here is the heart of `server/jazz.ts`:

```ts
import { createJazz, memory } from "jazz-tools/backend";
import { app } from "./jazz.generated";
import permissions from "./jazz.permissions.json" with { type: "json" };

export const jazz = createJazz({
  app,
  permissions,
  store: memory(),
  // Better Auth's session cookie says who the user is.
  authenticate: async (request) => {
    const session = await readBetterAuthSession(request);
    return session
      ? {
          userId: session.user.id,
          expiresAt: Math.floor(session.session.expiresAt.getTime() / 1000),
        }
      : null;
  },
}).ready();

declare function readBetterAuthSession(
  request: Request,
): Promise<{ user: { id: string }; session: { expiresAt: Date } } | null>;
```

The real file uses `sqlite({ path })` outside tests and reads the session with `auth.api.getSession`.

## Create a room and its first member

A room and its creator's member row commit together. Without the member row, the creator could not
read their own room.

`members.row` makes the row to insert. The app chooses the room's ID first, so the row can name it.

```ts
import type { Db } from "jazz-tools";
import { app } from "./jazz.generated";

export async function createRoom(db: Db, author: string, profileId: string, name: string) {
  const roomId = crypto.randomUUID();
  const creatorMember = await db.encryption.members.row({ table: "rooms", id: roomId }, author);
  const written = await db.transaction((tx) => {
    tx.insert(app.rooms, { name }, { id: roomId });
    tx.insert(app.__e2ee_members, creatorMember);
    tx.insert(app.roomMembers, { roomId, memberAuthor: author, memberProfileId: profileId });
  });
  await written.wait({ tier: "global" });
  return roomId;
}
```

`app.roomMembers` is BandChat's own table. It carries each member's profile, so the members list
can show names. Jazz does not read it. The member row is what decides who holds the key.

## Add people

A room link only lets someone ask to join. They add a join request. The creator then admits them.

Admission is one transaction. It inserts the member row, inserts the profile row and deletes the
request. Then the app calls `keys.deliver()`.

```ts
import type { Db } from "jazz-tools";
import { app } from "./jazz.generated";

export async function admitMember({
  db,
  roomId,
  memberAuthor,
  memberProfileId,
  requestIds,
}: {
  db: Db;
  roomId: string;
  memberAuthor: string;
  memberProfileId: string;
  requestIds: string[];
}): Promise<void> {
  const memberRow = await db.encryption.members.row({ table: "rooms", id: roomId }, memberAuthor);
  const written = await db.transaction((tx) => {
    tx.insert(app.__e2ee_members, memberRow);
    tx.insert(app.roomMembers, { roomId, memberAuthor, memberProfileId });
    for (const id of requestIds) tx.delete(app.joinRequests, id);
  });
  await written.wait({ tier: "global" });
}
```

Being admitted does not give the person the key. Their devices get it from a device that already
holds it. That device has to be online. Until then the new member sees the room's messages as
**locked**.

If `deliver()` fails or reports `failed` above zero, BandChat shows "Key not delivered yet".
The member is already admitted. The dialog shows the reason when the call returns one.
The Retry button calls `deliver()` again. Jazz also runs a delivery pass by itself when the app
starts and when the connection comes back. See [Sharing and keys](/docs/e2ee/sharing-and-keys).

## List the members

Ask Jazz for a filter. Then pass it to an ordinary query. If the browser opens offline before
Jazz knows the room table's identity, the filter can fail. BandChat shows the reason and offers
a Retry button.

```tsx
import { useEffect, useState } from "react";
import type { Db } from "jazz-tools";
import { useAll } from "jazz-tools/react";
import { app, type E2eeMember } from "./jazz.generated";

export function useRoomMembers(roomId: string): {
  members: E2eeMember[] | undefined;
  loadFailure: { reason: string; retry: () => void } | undefined;
} {
  const [filter, setFilter] = useState<Awaited<ReturnType<Db["encryption"]["members"]["where"]>>>();
  const [error, setError] = useState<string>();
  const [attempt, setAttempt] = useState(0);
  const { data, db } = useAll(filter ? app.__e2ee_members.where(filter) : undefined);
  useEffect(() => {
    let isLive = true;
    setFilter(undefined);
    setError(undefined);
    db.encryption.members.where({ table: "rooms", id: roomId }).then(
      (found) => isLive && setFilter(found),
      (cause: unknown) =>
        isLive && setError(cause instanceof Error ? cause.message : String(cause)),
    );
    return () => {
      isLive = false;
    };
  }, [attempt, db, roomId]);
  return {
    members: data,
    loadFailure:
      error === undefined ? undefined : { reason: error, retry: () => setAttempt((n) => n + 1) },
  };
}
```

The list comes from the member rows. A person with a member row is listed, even if they have no
`roomMembers` row or no profile. They show as "Unknown".

## Remove a member, then change the key

Removal needs two steps. BandChat does both.

1. **Delete the member rows.** The member rows and the `roomMembers` rows go in one serializable
   transaction. The screen waits until the server accepts it. If another write conflicts, for
   example an admission of the same person, the transaction runs again. It tries three times in all.
2. **Rotate the room's key.** Without this, the room is only marked. The key changes at the next
   encrypted write. With it, the key changes now, so the removed person reads nothing written later.

This is the first step:

```ts
import { PersistedWriteRejectedError, type Db } from "jazz-tools";
import { app } from "./jazz.generated";

const ATTEMPTS = 3;

export async function removeMember({
  db,
  roomId,
  accountId,
}: {
  db: Db;
  roomId: string;
  accountId: string;
}): Promise<number> {
  const filter = await db.encryption.members.where({ table: "rooms", id: roomId }, accountId);
  for (let attempt = 1; ; attempt++) {
    try {
      const written = await db.serializableTransaction(async (tx) => {
        const memberRows = await tx.all(app.__e2ee_members.where(filter), { tier: "remote" });
        const profileRows = await tx.all(
          app.roomMembers.where({ roomId, memberAuthor: accountId }),
          { tier: "remote" },
        );
        for (const row of memberRows) tx.delete(app.__e2ee_members, row.id);
        for (const row of profileRows) tx.delete(app.roomMembers, row.id);
        return memberRows.length;
      });
      return await written.wait();
    } catch (error) {
      if (
        attempt >= ATTEMPTS ||
        !(error instanceof PersistedWriteRejectedError) ||
        (error.code !== "serialization_conflict" && error.code !== "transaction_conflict")
      )
        throw error;
    }
  }
}
```

The real function can also delete a leaver's read markers in the same transaction.

BandChat asks Jazz to rotate the room's key once the server confirms that member rows were
removed. A removal count of zero means the creator may be unable to see that member's rows.
BandChat shows that no member rows were removed. If the room has no key yet, the rotation call
succeeds and returns `0`. A room gets its key from its first encrypted write.

```ts
import type { Db } from "jazz-tools";

export function renewRoomKey(db: Db, roomId: string): Promise<number> {
  return db.encryption.keys.rotate({ table: "rooms", id: roomId });
}
```

If the rotation fails, the dialog says "Removed, but the room's key is not renewed yet" and offers a
retry. The member is already out. The key is not yet new.

Removal is not instant. Between the removal and the rotation, a message can still be sealed under
the old key. And removal cannot take back what the person could already read. They keep every
message they opened before.

Any member can leave a room. Only the creator can remove someone else or renew the key.
Once the creator's browser learns that a member left, Jazz tries to renew the room's key before
the creator's next encrypted write.

## Messages you cannot read yet

A browser that lacks a room's key does not show empty rooms. It says the messages are locked.

Every read result has an `unreadable` list. It names the rows the read left out. BandChat counts it:

```tsx
import { useAll } from "jazz-tools/react";
import { app } from "./jazz.generated";

export function LockedNotice({ roomId }: { roomId: string }) {
  const { data: messages = [], unreadable } = useAll(app.messages.where({ roomId }));
  return unreadable.length > 0 ? (
    <p>
      {unreadable.length} messages are locked on this browser. {messages.length} are shown.
    </p>
  ) : null;
}
```

The messages appear by themselves once the key arrives.

The room list needs no key. For each room it asks for the newest message, using plain columns only:

```ts
import { app } from "./jazz.generated";

export const newestMessage = (roomId: string) =>
  app.messages
    .where({ roomId })
    .select("id", "senderId", "$createdAt")
    .orderBy("$createdAt", "desc")
    .limit(1);
```

The `["roomId", "$createdAt"]` index in the schema makes this one index entry per room. The list
orders rooms by it, and marks a room unread when its newest message is newer than the reader's read
marker. The cost grows with the number of rooms, not with the number of messages. Use it for a
handful of rooms, not hundreds.

## A second browser: approving a device

Each browser is one device. A new browser starts as **waiting for approval**. Its messages stay
locked. A device that is already active approves it.

On the new browser, answer the challenge. It shows a six-digit code:

```ts
import type { Db } from "jazz-tools";

export function showCodeWhenChallenged(db: Db, show: (code: string) => void): () => void {
  return db.encryption.onChallenge(async () => {
    show(await db.encryption.devices.answer());
  });
}
```

On the active browser, start the approval, wait for the new browser's answer, then type its code:

```ts
import type { Db } from "jazz-tools";

export async function approveWaitingDevice(db: Db, confirmCode: () => Promise<string>) {
  const waiting = (await db.encryption.devices.list()).filter(
    (device) => device.status === "waiting",
  );
  const session = await db.encryption.devices.challenge(waiting[0].id);
  // `code()` is null until the new browser has answered.
  while ((await session.code()) === null) await new Promise((resolve) => setTimeout(resolve, 1500));
  await session.approve(await confirmCode());
}
```

In BandChat the person types the code that the new browser shows. A wrong code approves nothing.
The code is how a server that swapped keys gets caught. See
[Devices and recovery](/docs/e2ee/devices-and-recovery).

A browser can also reload halfway through. BandChat handles that. The new browser may answer
again, and the active one may start again.

## Recovery: if every device is gone

If a person loses every device and has no recovery, they lose their encrypted messages for good.
Clearing site data on the only browser does the same. So BandChat has one button: "Set up recovery".

```ts
import type { Db } from "jazz-tools";

export async function setUpRecovery(db: Db, accountName: string) {
  const result = await db.encryption.recovery.enable({ appName: "BandChat", accountName });
  // A passkey holds the secret, or the app shows a phrase once and keeps no copy.
  return result.method === "phrase" ? result.phrase : null;
}
```

`enable` saves the secret in a passkey where the browser offers one. Otherwise it returns a
24-word phrase. BandChat shows the phrase once, keeps it nowhere, and sends it nowhere.

A browser that is waiting for approval offers both ways back:

```ts
import type { Db } from "jazz-tools";

export async function restoreWithPhrase(db: Db, phrase: string) {
  await db.encryption.recovery.restore(phrase.trim());
}

export async function restoreWithPasskey(db: Db) {
  await db.encryption.recovery.restoreFromPasskey({ appName: "BandChat" });
}
```

## Remove a lost device

Say a laptop is stolen. The person goes to another browser and presses "Remove lost device" on the
laptop's row. The button is only on devices that are `active`. Jazz refuses to remove a device that
is waiting.

The laptop may still have an open connection. A removed device must not stay signed in. So the app
ends the person's sign-ins first, and removes the device second.

1. **The server step.** The browser calls a route on BandChat's own server. The route deletes every
   Better Auth session of that user except the caller's. Then it calls `jazz.revokeUser`, which
   closes the user's open connections.
2. **The device step.** When the route answers, the browser calls `devices.remove(id)`.

```ts
import type { Db } from "jazz-tools";

export async function removeLostDevice(db: Db, deviceId: string) {
  const response = await fetch("/api/end-other-sign-ins", {
    method: "POST",
    credentials: "same-origin",
  });
  if (!response.ok) throw new Error(`The server could not sign your other browsers out.`);
  await db.encryption.devices.remove(deviceId);
}
```

The route is in `server/index.ts` and `server/jazz.ts`. It lists the user's sessions page by page,
because Better Auth lists at most 100 at a time, and it deletes them until only the caller's is left.

**This has a cost, and the screen says so before the person confirms.** Every other browser of the
user is signed out and has to sign in again. Those browsers keep their keys and their device
records, so they need no new approval. Changes they had not synced yet may be lost.

The server cannot tell which session belongs to which device. A record like that would be the
device's own claim, and the server holds no keys to check it. So it ends them all.

If the server's answer is lost or it cannot finish, some browsers may already be signed out.
BandChat keeps the device listed until the sign-out step is confirmed. Press the button again to
run both steps.

The removed device keeps the keys it already holds. It receives no new keys.
A device that's connected and watching the room learns of the removal one
sync round trip after it commits. Other devices learn of it when they next
sync the room. Writes can still use the current key before the device learns
of the removal, while offline after learning of it, or when an online
rotation is refused or undecided by the write's deadline. The write goes ahead and the room's key
rotates at the next opportunity.

## Sign out, or leave

These are two different things.

**Signing out keeps the keys.** The browser keeps its keys, its local data and its device record.
The next sign-in on that browser reads at once, with no approval. BandChat does not wipe at
sign-out.

That is a risk on a shared computer. A later user of the same browser profile, or a script on the
app's origin, can ask the browser to use the kept keys. There are two ways to remove the device:

- **Before you sign out,** press "Leave this browser".
- **Afterwards,** press "Remove lost device" on it from another device.

**Leaving** asks another device to remove this browser. It calls `requestRemoval`:

```ts
import type { Db } from "jazz-tools";

export async function leaveThisBrowser(db: Db) {
  await db.encryption.devices.requestRemoval();
}
```

A sole device cannot leave. Nothing would hold the account's keys. The call fails with the code
`no-other-device`, and BandChat says an only device cannot leave.

Otherwise, once Jazz lists the published request, the row shows "Removal pending". The browser stays
usable. When another of the person's devices is online, it completes the removal by itself, sometimes
before "Removal pending" has shown. Then this browser's keys for the account are
erased, and the browser signs itself out.

Before sending the request, BandChat records the account and this browser's device ID in
`localStorage`. That lets it finish leaving even if the tab closes before the answer arrives.
A refusal clears the record. A different ID for the same account means the old keys are gone,
because the browser enrols again under a new ID. Then the page signs out and clears the record.
An ordinary sign-out also clears it.

If erasing the keys fails, Jazz closes its encryption runtime with an error. BandChat says leaving
did not finish and that the keys may still be in this browser. It stays signed in. Reloading checks
again.

There are two known behaviours of leaving:

- **It waits for another device to be online.** Jazz wipes nothing before that, so an account is
  never left without a device that holds its key.
- **It leaves one extra device on the list.** Once the leaving browser has seen its removal while
  signed in, it has enrolled again. The person's other devices now list one more device,
  "waiting for approval". That entry cannot be removed. Ignore it, or approve it to let that
  browser back in.

Leaving wipes the keys, not the browser's local copy of the plain data.

## Know the limits

- **The server sees more than the content.** It sees who is in which room, who wrote when, room
  names, reactions, sketches, attachment types and sizes, and when each read marker was written. A
  marker's write time shows when its reader read.
- **Read markers are not hidden from co-members.** The room's key seals them, so every member could
  open one. A deploy of BandChat prints one warning for this: the read-marker rule is narrower than
  its room's, so every member of a room can decrypt a marker that Jazz does not send them. That is
  expected.
- **A join request guards the profile row only.** A room's creator can give any account a member
  row without a request. So "you only join a room you asked to join" is not enforced by the server.
  Such a member shows as unknown until they have a profile row. They can leave.
- **Removing a lost device signs out the person's other browsers.** They keep their keys and device
  records, and sign in again.
- **Keys stay in the browser after sign-out.** Use "Leave this browser" or "Remove lost device" to
  remove them.
- **Leaving needs another device online.** A sole device cannot leave, and a completed leave adds
  one entry that cannot be removed.
- **Removing a member cannot take back what they read.** A message can be sealed under the old key
  until the key is rotated.
- **The Cloudflare Worker engine refuses encrypted apps.** Run the backend on Node. BandChat's Hono
  server does.
- **The room list is not built for hundreds of rooms.** It runs one live query for each room.

The rest of the limits are on [Encryption limits](/docs/e2ee/limits).
