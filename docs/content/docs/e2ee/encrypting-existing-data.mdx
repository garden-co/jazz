---
title: Encrypting Existing Data
description: "Jazz doesn't convert a plain column that already holds data. Copy the data into a new encrypted table."
languageTabs: backend
---

A column is encrypted from the moment its table is created. Jazz doesn't convert a plain column
that already holds data. To encrypt existing data, copy it into a new encrypted table and switch
your app to that table.

The old plain values stay in the old table's history, on every replica that synced them, and in
backups. Dropping the old table doesn't erase them. Treat the old data as already disclosed.

Nothing may write the old data while you copy and check it. Users can read it throughout. If
your app can't pause those writes, this recipe doesn't fit.

The examples copy `tasks` into `secureTasks`, which has an encrypted `title`. A `comments` table
references tasks through `taskId`.

## 1. Add the new table

The space table's read rule must be `isMember` before a table encrypts columns in its spaces. If
your space table has another read rule, change it in two deploys:

1. Give the space table `{ space: "id" }` in `schema.ts` and deploy. The read rule can stay for
   now, and the deploy warns about it. Then add a member row for each account that should keep
   reading each space row. See [Sharing and keys](/docs/e2ee/sharing-and-keys).
2. Change the read rule to `isMember` and deploy. Accounts without a member row stop reading the
   space row.

Then add the new table with its encrypted columns and its `space`. Set `equality: true` on every
column you will filter by, because it can't be added to an existing table.

In the same migration, give every table that references the old table a new reference column
that points at the new one, such as `secureTaskId` next to `taskId`. An existing reference column
can't be pointed at another table. The copies keep their row IDs, so the new column will hold the
same values as the old one.

## 2. Stop every writer

Deploy permissions that refuse every write to the old table and to each table that references
it. Keep their read rules.

```json title="jazz.permissions.json"
{
  "tables": {
    "tasks": {
      "read": "…the rule it has now…",
      "insert": "false",
      "update": "false",
      "delete": "false"
    },
    "comments": {
      "read": "…the rule it has now…",
      "insert": "false",
      "update": "false",
      "delete": "false"
    }
  }
}
```

Then check two things:

- Shut down every deployment that still serves older permissions, such as an older version, a
  preview or a canary. Its sessions can write until you do. After that, every session is checked
  against the new permissions, including edits a client made offline.
- Stop every backend job that writes these tables. Permissions don't apply to your backend.

## 3. Copy the rows from clients

Only clients hold keys, so clients write the encrypted copies. Upsert each old row into the new
table under the same row ID. Running the copy again then overwrites the copy.

```ts
import type { Db } from "jazz-tools";
import { app } from "./jazz.generated";

// On a client that holds the project's key.
async function copyProject(db: Db, projectId: string) {
  for (const task of await db.all(app.tasks.where({ projectId }), { tier: "remote" })) {
    // The same ID: a second run overwrites this copy.
    await db
      .upsert(app.secureTasks, task.id, { projectId, title: task.title })
      .wait({ tier: "global" });
  }
}
```

A client can copy the rows it can read in spaces whose key it holds. In a space with no key
yet, the first copy must come from a session that can update the space row. A space whose
members are all offline waits until one comes online.

Then fill the new reference columns from your backend. Reference columns are plain, so this
needs no key. `fillReferences` in the next step does it.

## 4. Check the copy from your backend

A client sees only the rows it may read, so it can't prove the copy is complete. Your backend
reads every row, and row IDs, space columns and references are plain. The copy is complete when:

- every old row has a copy with the same ID, and the new table has no other rows
- every copy is in the same space as its old row
- every new reference equals its old one

```ts
import { keyless } from "jazz-tools/backend";
import { app } from "./jazz.generated";
import { jazz } from "./jazz.server";

const backendApp = keyless(app);

// Reads of rows the server has accepted, never pending writes.
const accepted = { tier: "remote" } as const;

// After the stop: each comment's new reference takes its old one.
async function fillReferences() {
  for (const comment of await jazz.db.all(backendApp.comments, accepted)) {
    await jazz.db
      .update(backendApp.comments, comment.id, { secureTaskId: comment.taskId })
      .wait({ tier: "global" });
  }
}

// What is still wrong. Empty lists mean the copy is complete.
async function checkCopy() {
  const copies = new Map(
    (await jazz.db.all(backendApp.secureTasks, accepted)).map((t) => [t.id, t]),
  );
  const old = await jazz.db.all(backendApp.tasks, accepted);
  const oldIds = new Set(old.map((t) => t.id));
  return {
    // Grouped by projectId, these are the spaces whose key holders have not copied yet.
    missing: old.filter((t) => copies.get(t.id)?.projectId !== t.projectId),
    extra: [...copies.values()].filter((t) => !oldIds.has(t.id)),
    references: (await jazz.db.all(backendApp.comments, accepted)).filter(
      (c) => (c.secureTaskId ?? null) !== (c.taskId ?? null),
    ),
  };
}
```

For a large table, check one space at a time. Fix what the check reports and run it again. A
copy with no old row, or in a different space from its old row, means a writer is still running.
Find it and stop it. Switch only when the check passes.

## 5. Switch to the new table

Ship the app version that reads and writes `secureTasks` and follows the new reference columns.
Row IDs you keep elsewhere, such as in URLs, still work.

Keep the old table frozen. Give the referencing tables their write rules back, but keep the old
reference column frozen. Otherwise an older client could change `taskId` and leave `secureTaskId`
pointing elsewhere. An insert must leave `taskId` empty, and an update must keep it as it was
(see [Update policies](/docs/schemas/policies#update-policies-old-row-vs-new-row)):

```json title="jazz.permissions.json"
{
  "tables": {
    "comments": {
      "read": "…the rule it has now…",
      "insert": { "allOf": ["…the rule it has now…", "taskId = null"] },
      "update": {
        "old": "…the rule it has now…",
        "new": {
          "allOf": ["…the rule it has now…", "exists comments(id = this.id, taskId = this.taskId)"]
        }
      },
      "delete": "…the rule it has now…"
    }
  }
}
```

This needs `taskId` to be optional. If it's required, refuse every insert into that table with
`"insert": "false"` until you drop the old column.

## 6. Drop the old table

Once no client uses the old table, drop it and the old reference columns in a later migration.
