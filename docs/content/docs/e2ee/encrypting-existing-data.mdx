title: Encrypting Existing Data
description: "Jazz encrypts columns that are declared encrypted when they are created. To encrypt data you already store in plain columns, copy it into a new encrypted table."
languageTabs: backend
---

Jazz encrypts a column that is declared encrypted when it is created. It does not convert a plain
column that already holds data, and an app file cannot ask it to. To encrypt data you already
store, add a new encrypted table, stop every write to the old data, have your app's clients copy the
rows across, check the copy from your backend, and then switch to the new table.

**The old plaintext stays.** Copying protects the values from then on, not the ones already
stored. The old values remain in the old table's history, on every replica that synced them, and
in backups. Dropping the old column or table does not erase them from any of these. If that
matters, treat the old data as already disclosed.

## The recipe

The recipe rests on one rule: **nothing writes the old data during the final copy and its check.**
Stop the writers, make sure they have stopped, copy, check from your backend, then switch. Your
users can read the old data throughout, but cannot change it from the stop until the switch. If
your app cannot pause those writes, or cannot stop every writer as step 2 describes, this recipe
does not cover it.

The examples use `tasks` as the old table, `secureTasks` as the new one with an encrypted `title`,
and `comments` as a table with a reference `taskId` to `tasks`.

### 1. Prepare the space table, the new table and new references

An encrypted table's rows live in **spaces**, the rows of a space table (a project, a room), and
its members are the rows of `__e2ee_members`. The space table's read rule must come from the
members table before any table encrypts columns in its spaces (see
[Sharing and keys](/docs/e2ee/sharing-and-keys)). If your space table has another read rule, move
it in two deploys first:

1. Declare an `encryption` entry for the space table itself with no encrypted columns
   (`"space": "id", "scope": "<the table>", "columns": {}`). This adds Jazz's encryption tables,
   and the read rule stays as it is for now (the deploy warns). Then write the member rows: for
   each space row, one row per account that should keep reading it, from a client allowed to
   update the space row or from your backend.
2. Change the space table's read rule to the members rule. An account without a member row stops
   reading the space row once its session uses the new permissions. A session pinned to the older
   permissions (see step 2) keeps the old rule until the deployment serving them is shut down.

Then add the new table to your schema, with its encrypted columns and its `encryption` entry
naming the space column, in the same migration that creates the table. Declare `equality` here,
for every column you will filter by. Declare equality when you create the table: it cannot be
added to a table that already exists, because rows older than the column have no equality token.
To filter by a column of an existing table later, copy it into a new table that declares it, with
this same recipe.

In the same migration, give every table that references the old table a new reference column
that points at the new table, such as `secureTaskId` beside `taskId` in `comments`. A reference
column names its table, and the deploy refuses a migration that points an existing one at another
table. The copies keep their row IDs, so the new column will hold the same values as the old one.
A reference inside the old table itself, such as a parent task, needs no new column: the new
table declares its own column referencing the new table, and the copy keeps its values.

### 2. Stop every writer of the old data

The old data is the old table and every old reference column. Deploy a permissions revision that
refuses every write to the old table and to each table that holds an old reference, and keeps
their read rules:

```json title="jazz.permissions.json"
{
  "tables": {
    "tasks": {
      "read": "…the rule it has now…",
      "insert": "false",
      "update": "false",
      "delete": "false"
    },
    "comments": {
      "read": "…the rule it has now…",
      "insert": "false",
      "update": "false",
      "delete": "false"
    }
  }
}
```

Then make sure every writer has stopped:

- **Every client, whatever app version it runs.** Your app's backend pins every session it opens
  to the permissions it was deployed with, and a client cannot choose others. When a backend
  publishes new permissions, Jazz closes the sessions pinned to other permissions, and they
  reconnect through whichever backend serves them now. Shut down every deployment that still
  serves older permissions (an older version still running, a preview, a canary): until then, the
  sessions it pins can still write. Once none is left, every session is checked by this revision,
  including edits a client made offline, which are checked when it reconnects.
- **Your backend.** It is not checked when it acts as the system, so stop every job of its that
  writes these tables.

### 3. Copy every row from the clients, and fill the new references

Copy once every writer has stopped. Only clients hold keys, so only clients can write the encrypted
copies. The server never can. Copy each old row into the new table under **the same row ID**, with
an upsert, so that running the copy again overwrites the copy instead of adding another.

Each client copies what it can:

- the rows it can read, in spaces whose key it holds;
- in a space with no key yet, the first encrypted write creates it, and that needs a session
  allowed to update the space row. Other members get the key from it.

A space whose key holders are all offline waits until one of them comes online. Copying can be
spread across many accounts; step 4 finds the spaces still waiting.

Then fill the new reference columns from your backend: for every row of `comments`, write its
`taskId` into `secureTaskId` (`fillReferences` in step 4). A reference column is plain, so writing
it needs no key, and your backend's writes are not checked against the freeze.

A sketch of the copying client (schematic, not drop-in code):

```ts
import type { Db } from "jazz-tools";
import { app } from "./jazz.generated";

// On a client that holds the project's key.
async function copyProject(db: Db, projectId: string) {
  for (const task of await db.all(app.tasks.where({ projectId }), { tier: "remote" })) {
    // The same ID: a second run overwrites this copy.
    await db
      .upsert(app.secureTasks, task.id, { projectId, title: task.title })
      .wait({ tier: "global" });
  }
}
```

### 4. Check the copy from your backend

Check from your backend, not from a copying client. A client sees only the rows its permissions
let it read, so two lists it reads can match while a row it cannot see has no copy. Your backend's
own database reads every row, whatever your permissions say (see
[How a backend talks to Jazz](/docs/how-jazz-works#how-a-backend-talks-to-jazz)), and it needs no
keys for this check: row IDs, space columns and references are plain.

The check passes when, for every space:

- each old row has a copy with the same ID, and the new table holds no other rows;
- each copy is in the same space as its old row;
- each row's new reference equals its old one, with an empty reference equal to an empty one.

Check settled data: wait for each reference fill to reach the server (`.wait({ tier: "global" })`;
an `await` on the write alone doesn't wait for it), and read with `tier: "remote"`, which returns
only rows the server has accepted.

A sketch of the backend's part (schematic; for a large table, work one space at a time):

```ts
import { keyless } from "jazz-tools/backend";
import { app } from "./jazz.generated";
import { jazz } from "./jazz.server";

const backendApp = keyless(app);

// Reads of rows the server has accepted, never pending writes.
const accepted = { tier: "remote" } as const;

// After the stop: each comment's new reference takes its old one.
async function fillReferences() {
  for (const comment of await jazz.db.all(backendApp.comments, accepted)) {
    await jazz.db
      .update(backendApp.comments, comment.id, { secureTaskId: comment.taskId })
      .wait({ tier: "global" });
  }
}

// What is still wrong. Empty lists mean the copy is complete.
async function checkCopy() {
  const copies = new Map(
    (await jazz.db.all(backendApp.secureTasks, accepted)).map((t) => [t.id, t]),
  );
  const old = await jazz.db.all(backendApp.tasks, accepted);
  const oldIds = new Set(old.map((t) => t.id));
  return {
    // Grouped by projectId, these are the spaces whose key holders have not copied yet.
    missing: old.filter((t) => copies.get(t.id)?.projectId !== t.projectId),
    extra: [...copies.values()].filter((t) => !oldIds.has(t.id)),
    references: (await jazz.db.all(backendApp.comments, accepted)).filter(
      (c) => (c.secureTaskId ?? null) !== (c.taskId ?? null),
    ),
  };
}
```

Fix what it reports, then check again: copy the missing spaces from a client that holds their key,
and fill the references again. With every writer stopped before the copy, a copy without an old
row or in another space than its old row's means a writer was still running: find it and stop it.
Switch only once the check passes with every writer stopped.

### 5. Switch reads and writes to the new table

Ship the app version that reads and writes the new table: its code, relations and permissions point
at `secureTasks` and follow the new reference columns. IDs you keep outside Jazz's relations, such
as in URLs, still work, because the rows keep their IDs.

Its permissions keep the old table frozen, and give the referencing tables their write rules back
for every column but the old reference. That column stays frozen until you drop it: an older
client still running could otherwise change `taskId` alone and leave `secureTaskId` pointing
elsewhere. An insert must leave it empty, and an update must keep it as it was (see
[Update policies](/docs/schemas/policies#update-policies-old-row-vs-new-row)):

```json title="jazz.permissions.json"
{
  "tables": {
    "comments": {
      "read": "…the rule it has now…",
      "insert": { "allOf": ["…the rule it has now…", "taskId = null"] },
      "update": {
        "old": "…the rule it has now…",
        "new": {
          "allOf": ["…the rule it has now…", "exists comments(id = this.id, taskId = this.taskId)"]
        }
      },
      "delete": "…the rule it has now…"
    }
  }
}
```

A row whose `taskId` is empty keeps it empty under this rule, and its other columns stay writable.

### 6. Drop the old table later

Once no client still uses the old table, drop it in a later migration, together with the old
reference columns: a column cannot reference a table that no longer exists. As above, the old
data stays in history, on replicas and in backups.
