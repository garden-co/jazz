title: Sharing and Keys
description: "Add and remove the members of an encrypted space, and when their devices get keys."

A space is a row of the table your encryption declaration names (a project, a room). Its **members**
are the rows of `__e2ee_members` for it, and Jazz's permissions decide who may add them: the space row's
update rule is the rule for managing members, plus one exception: the account that creates the space row
may add itself in the same transaction.

## Create a space and add members

A new space and its creator's own membership are one transaction. `db.encryption.members.row` gives the
values to insert into the generated members table:

```ts
const id = crypto.randomUUID();
const space = { table: "projects", id };
const self = await db.encryption.members.row(space, accountId);
const written = await db.transaction((tx) => {
  tx.insert(app.projects, { name: "plans", ownerId: accountId }, { id });
  tx.insert(app.__e2ee_members, self);
});
await written.wait({ tier: "global" });

// Later, the owner adds a member:
const row = await db.encryption.members.row(space, otherAccountId);
await db.insert(app.__e2ee_members, row).wait({ tier: "global" });
```

The space's key is made by its first encrypted write. A member gets the key from any device that holds it (the
first holder to deliver wins), sealed to the member's account, so the member's devices can all read.

## List members

Pass the filter from `members.where` to the ordinary query API. Pass an account ID as the second argument
to see only that account's rows in the space.

```ts
const filter = await db.encryption.members.where(space);
const members = await db.all(app.__e2ee_members.where(filter));
```

Use the table named by the encryption declaration's `scope`. On a fresh device, these helpers can
return the error code `not-observed` until the device first receives the table's identity from the server.

## When keys arrive

A pass over the spaces a device holds keys of delivers keys to members that lack them. It runs by itself
when the app starts, when the connection comes back, and while the device has a subscription on a space.
Call it when you want new members served now:

```ts
const { delivered } = await db.encryption.keys.deliver();
```

A member's device that reads rows it has no key for yet leaves them out and acquires the key once a
delivery arrives; read again, or keep a subscription on the space.

## Remove a member

An account can leave a space. Anyone the space's update rule allows to manage members can remove
another account. `members.remove` deletes only matching member rows the caller is allowed to see. It
returns the number deleted once the authority accepts the serializable transaction. A result of `0`
means nothing visible was removed. The account may still be a member if the caller cannot read its
rows. Removing an already absent account also returns `0`.

A conflicting admission triggers a retry, up to three attempts in all. A refusal reaches the caller.
To rotate the key immediately after removing a member, call `keys.rotate`.

```ts
const removed = await db.encryption.members.remove(space, otherAccountId);
if (removed > 0) await db.encryption.keys.rotate(space);
```

The new key and up to 100 deliveries commit together. `keys.rotate` returns the number of
deliveries in that transaction. Subsequent writes use the new key while Jazz delivers it to
the remaining members in the background.

If you also need to delete your own app's rows atomically with the membership, use a single
`db.serializableTransaction`. Inside its callback, read the matching rows with
`tx.all(app.__e2ee_members.where(filter))` using the filter from `members.where(space, otherAccountId)`,
then delete them and the related app rows. Await the transaction result's `wait()` before rotating.
Retry the whole transaction on a serialization conflict.

If the space has no key yet, nothing has been sealed. For an active member, `rotate` succeeds and
writes nothing. If the space already has a key, a member whose device is waiting for delivery gets
`rotation-needs-key`. Retry once the device has the current key. The same code can also mean the
device cannot confirm the space's key state. For example, a missing root with a locally held key
or a skipped root row yields the same refusal. If the device sees that its account has no membership,
it gets `not-a-member`. A device waiting for approval gets `no-account`, even in a space with no key yet.
If the server hides the key root and the device has no evidence of it, `rotate` returns `0` for an
active member, just as it does for a space that has never had a key. See the
[rotation tests](https://github.com/garden-co/jazz/blob/5a4121130c/crates/jazz-e2ee-client/tests/spaces.rs#L2239-L2353).

If no online member holds the current key or the key history is broken, ask a person to confirm before calling `db.encryption.keys.recoverRotation(space)` from a device that holds an earlier key.

Without an explicit rotation, the next pass notices that a key is held by an account that is no
longer a member and rotates, once the device has observed the removal. A removed member keeps what
they could already read; Jazz's permissions stop them reading any row after.

Before reusing a space key, Jazz checks whether it needs rotation. If account verification or the
check fails, `onReport` receives `rotation-check-failed` with the space and the original reason.
Jazz marks the space for rotation. The app receives the original failure even if rotation succeeds.

Automatic rotation happens just before a write. If rotation fails, the write can still go ahead
under the current key, which the removed member may hold. The runtime sends `onReport` a
`rotation-failed` report with the space and the `reason`.

`rotate(space)` returns once the new key and its first 100 deliveries are committed. The runtime
then delivers the new key to the remaining members in the background, to each of them even if
another member already sent it one (that delivery may not open). If that fails, it tries again
after 2 seconds, then 4, 8 and so on up to a minute, and gives up after 6 failed attempts in a row;
any member holding the new key then delivers it to those left out on its next pass. Failures
while offline aren't counted.

`onReport` receives a `delivery-failed` report, with the space and the reason, when the runtime
fails to deliver keys to a space's members: for the background deliveries after a rotation (once
per attempt), for the pass it runs when a space's members or keys change, and for the pass over
every held space when the app starts or reconnects. A space is reported at most once per round
of these, so starting offline reports each held space once.

The next write can retry after a transient rotation failure. After a permission denial, this client stops
trying to rotate that space automatically for the rest of the session. A member with permission can
still call `db.encryption.keys.rotate(space)`. See the
[rotation refusal handling](https://github.com/garden-co/jazz/blob/94cd8e1e45/crates/jazz-e2ee-client/src/spaces/delivery.rs#L380-L403).

```ts
db.encryption.onReport((report) => {
  if (report.type === "rotation-check-failed")
    console.warn("rotation check failed", report.space, report.reason);
  if (report.type === "rotation-failed")
    console.warn("key not rotated", report.space, report.reason);
  if (report.type === "delivery-failed")
    console.warn("key delivery failed", report.space, report.reason);
});
```

On Node, the database from `createJazz` can add, list and remove members through `db.encryption.members`.
When Jazz verifies its own account and finds a signed sealing-key record that does not derive
from the account key, it ignores the record. `onReport` emits `conflicting-account-key` with
`recordId`, the signing device’s `signerId` and `epochId`. Jazz remembers the last 10,000 distinct
event identities and suppresses repeats while an identity is in that history. When a new identity
displaces the oldest, Jazz can report the evicted conflict again. See the
[conflicting account key test](https://github.com/garden-co/jazz/blob/5a4121130c/crates/jazz-e2ee-client/tests/accounts.rs#L110).

The backend holds no encryption keys. Use a device client to rotate keys or manage devices and recovery.
