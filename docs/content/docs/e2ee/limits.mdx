The [protocol spec](https://github.com/garden-co/jazz/blob/main/crates/jazz/SPEC/E2EE_PROTOCOL.md#8-security-properties-and-limits)
has the full list and the reasons.

## Queries and schema

- You can filter an encrypted column by equality only, and only if it was declared with
  `equality: true`. Ordering, ranges, text search, grouping and aggregates fail with an error
  that names the pattern.
- `count()` includes rows this device can't decrypt yet, so it can be higher than `all().length`
  for the same filter.
- Jazz doesn't encrypt a plain column that already holds data. See
  [Encrypting existing data](/docs/e2ee/encrypting-existing-data).
- `equality` can't be added to a table that already exists. Copy the column into a new table
  that declares it.
- The deploy restricts schema changes to encrypted tables and names the column it refuses.
  `generate` and `migrations create` can accept a change that the deploy then refuses. The
  [schema change rules](https://github.com/garden-co/jazz/blob/main/crates/jazz/SPEC/E2EE_SCHEMA_CHANGES.md)
  list what is allowed.
- A write can't move an encrypted row to another space, but only the writer's own copy of the
  row enforces this. A client or backend that never loaded the row can upsert it with a
  different space column. Its encrypted values then read as `stale-space` or not at all, until a
  writer that hasn't loaded the row writes the original space back.

## What the server can do

- The server sees everything that isn't an encrypted column: row IDs, plain columns, who is a
  member of which space, and who wrote each row and when.
- Permissions decide who gets keys. Anyone who can update a space row can add any account as a
  member, and so can your backend. Members' devices then send that account the keys.
- The backend can't read or compute on encrypted columns. Do that on a client.
- A Cloudflare Worker backend can serve an encrypted app only through a native Jazz core, with
  `remote()`. A Durable Object core can't host an encrypted schema, and a Worker can't run a
  client that holds keys.

## Members and keys

- A space is designed for up to 1,000 member accounts. Jazz doesn't refuse more.
- A new member can read what was written to the space before they joined.
- A new member waits for the key until a device that holds it is online.
- Removing a member can't take back what they already read.
- After a removal, writes use the old key until the key changes. That includes writes made
  offline and writes from a device that hasn't heard of the removal yet. The server stops
  sending the removed member rows, but the removed member holds the key those rows use.
- A member row written offline before a removal and synced after it makes the account a member
  again. Check the member list after a removal has synced.

## Devices

- Whoever holds a device account's secret controls the account, and removing a device doesn't
  lock them out. See [Devices and recovery](/docs/e2ee/devices-and-recovery#device-accounts).
- A script on your page can use the device's keys. An injected script can read what the device
  reads and act as the device until the device is removed. Changing a space's key doesn't stop
  it. After a suspected injection, use a trusted device to remove the affected device and any
  device you don't recognise.
- Saved keys stay in the browser after sign-out unless you set `clearOnSignOut`. A later user of
  the same browser profile can use them.
- A copy of a private store that comes with its key can act as the device. A restored backup or
  a VM snapshot can be such a copy. Keep the key in the operating system's key store and out of
  backups.
- A new or wiped device can't tell if the server shows it an outdated list of another account's
  devices. A device detects that only for accounts it has seen before.
- Jazz wipes the key material it owns in memory. It can't wipe JavaScript strings, and in React
  Native keys cross the JavaScript bridge as strings. Keep tools that log the bridge or inspect
  the heap away from real accounts.

## Rust, Swift, Kotlin and Go

- Keys are delivered when the app starts, after a read that left rows out, and when you call
  `keysDeliver`. A subscription alone doesn't deliver keys.
- Only `insert`, `update`, `delete`, `upsert` and `restore` wait for a key. Transactions, partial
  edits and branch writes fail with `key-pending` at once. Call `ready` or `keysDeliver`, then
  write again.
- The session APIs don't take a private store, so open an encrypted app with a client. In Rust,
  use `Jazz::open`. `JazzSession::open` returns `Error::EncryptedSessionUnsupported`.
