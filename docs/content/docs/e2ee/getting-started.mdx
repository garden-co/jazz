With end-to-end encryption, the content of some columns is sealed on your users' devices before it
leaves them. Your server and your backend store and relay it but cannot read it. Everything else
about Jazz stays the same: permissions decide who may read and write a row, and encryption keeps the
content unreadable to anyone outside Jazz's permissions.

## Declare the encrypted columns

Encryption is declared in `schema.ts`. Mark each column to seal with `.encrypted()`, and give its table
a **space**: the row whose members share one key. `{ space: "project" }` names the relation that
leads to it; a table whose rows are their own spaces says `{ space: "id" }`.

```ts title="schema.ts"
import { schema as s } from "jazz-tools";

export const schema = s.defineSchema({
  projects: s.table({
    name: s.string(),
    ownerId: s.uuid(),
  }),
  tasks: s.table(
    {
      projectId: s.uuid(),
      title: s.string().encrypted({ equality: true }),
      notes: s.string().optional().encrypted(),
    },
    { project: s.rel("projects", "projectId") },
    { space: "project" },
  ),
});

const { definePermissions, isMember, session } = schema;

export const permissions = definePermissions({
  projects: {
    read: (project) => isMember("projects", project.id),
    insert: { "$createdBy.account": session.user },
    update: { ownerId: session.user },
  },
  tasks: {
    read: (task) => isMember("projects", task.projectId),
    insert: (task) => isMember("projects", task.projectId),
  },
});
```

`npx jazz-tools generate` writes the declaration into `jazz.app.json`, where each encrypted column is
stored as `bytes`. Your code never sees that: the generated types and the values you write and read are
the plaintext type (`title` is a string, `notes` a string or `null`). `equality: true` lets you filter
by a column's exact value, through tokens that show the server which rows share a value; the other
encrypted columns can't be filtered. Apply `.encrypted()` to a whole stored column, such as
`s.array(s.string()).encrypted()`. Encryption applies to the entire array or JSON value.
Computed fields, transformed columns and relation columns cannot be encrypted.

Your permissions decide who is a member of a space: members are the rows of the `__e2ee_members` table,
and `isMember(table, id)` holds when the signed-in account has a member row for that space. A space
table's read rule must be `isMember` of its own `id`, alone (as `projects` has above) or in `allOf` with
further conditions, or deploy refuses the app. See [Sharing and keys](/docs/e2ee/sharing-and-keys).

`generate` refuses, naming the table, what deploy would refuse: a `space` that is not `"id"` or a
relation over one `uuid` column, an encrypted column without a space, and a merge strategy on an
encrypted column (the server can't merge ciphertext, so its writes are last-writer-wins). A space's
`id` and its relation's column stay plain, because the server routes rows by them.

Members are rows of `app.__e2ee_members`. Use `db.encryption.members.row` to add an account with an insert,
`where` to list members and `remove` to remove an account. Your permissions govern these operations.

## Give each device a private store

On Node, supply a private store for the device's keys. An encrypted app opened without one fails
and names the missing option. In the browser, Jazz provides an
[IndexedDB private store](https://github.com/garden-co/jazz/blob/94cd8e1e45/packages/jazz-tools/src/encryption/browser-host.ts#L37-L47).

```ts
import { createJazzClient } from "jazz-tools/backend";
import { app } from "./jazz.generated";
import permissions from "./jazz.permissions.json" with { type: "json" };

const session = await createJazzClient({
  serverUrl,
  app,
  permissions,
  store: accountStore,
  initial: "device",
  encryption: { store: privateStore },
});
```

[Private store](/docs/e2ee/private-store) says what the store holds and gives a starting point.

## Read and write

```ts
await session.db.insert(app.tasks, { projectId, title: "Call the venue" }).wait({ tier: "global" });
const tasks = await session.db.all(app.tasks.where({ projectId, title: "Call the venue" }));
```

An equality filter on an `equality` column works like any other. Other filters, ordering and joins on
an encrypted column fail with an error that names the pattern (for example "Reading encrypted table
`tasks` with an aggregate is not supported yet"); they are never answered by scanning everything.

A write to a space whose key this device does not hold yet waits for it (up to ten seconds, for a
member waiting on another member's delivery) before it fails with the reason `key-pending`.

### Rows this device cannot read

A row this device cannot decrypt (it holds no key for it, or the key is still on its way) is never read
as empty: the read leaves it out and says so. `unreadableRows(result)` returns the rows a read left out,
each with its `table`, `id`, the `column` that could not be opened and a `code` (`key-pending`,
`key-unavailable`, `invalid-ciphertext`, ...). When key acquisition settles, Jazz updates provisional missing-key reasons
to reflect the space’s state, such as `space-pending` when a member’s space has no valid
root yet. A live result can update that reason even if its visible rows stay the same.
See the [settled read reasons test](https://github.com/garden-co/jazz/blob/5a4121130c/crates/jazz-e2ee-client/tests/settled_reasons.rs#L57-L139).

An empty `unreadableRows(result)` list means the query left out no candidate rows at decryption.
An online equality filter can still miss matches when Jazz knows about key versions it does not
hold. Jazz reports the affected query as `type: "unreadable"` with `table` and `space`,
`id` and `column` set to `null`, and a code such as `key-pending`. It reports that condition
once while the keys are missing. See the [incomplete equality query test](https://github.com/garden-co/jazz/blob/5a4121130c/crates/jazz-e2ee-client/tests/settled_reasons.rs#L140).

```ts
import { unreadableRows } from "jazz-tools/backend";

const page = await session.db.all(app.tasks.where({ projectId }).limit(20));
const missing = unreadableRows(page);
if (missing.length > 0) {
  // This page is incomplete: `page.length + missing.length` rows matched.
}
```

`limit` and `offset` count the rows left out, because they are applied before rows are decrypted. A page
can come back shorter than its limit, or empty, and still not be the last one: the rows
`unreadableRows` names make up the difference, and the next page starts after them. (For a query that
filters on an encrypted column, they may include rows that would not have matched.) A `key-pending` row
comes back once its key arrives; read again, or use a subscription, which updates by itself.

A subscription's results say the same. Each result it delivers carries the rows it leaves out, and
`unreadableRows` works on it as on a read's:

```ts
const stop = session.db.subscribe(app.tasks.where({ projectId }), (tasks) => {
  render(tasks);
  showIncomplete(unreadableRows(tasks));
});
```

The list stays current: a new row this device cannot open is named in the next result (even when the
visible rows did not change), a row whose key arrives joins the result and leaves the list in the same
update, and a row that leaves the query (deleted, or moved out of a page) is no longer named. A
subscription with `limit` counts these rows toward its page, as a read does.

The framework hooks carry the list too, as `unreadable` beside `data`, and update it with every result.
`unreadableRows` is exported from each framework's entry point (and from `jazz-tools/client`), and in
React it also works on `data` itself.

React Native's and Expo's `useAll` return the same fields as React's.

The runtime also reports unreadable rows, pending space keys and notices about rows it returned:

```ts
session.db.encryption.onReport((report) => {
  if (report.type === "unreadable") console.warn(report.code, report.table, report.id);
  if (report.type === "reports-dropped") console.warn(report.count, "reports dropped");
});
```

While no listener is registered, the runtime keeps up to 1,024 native reports and queues a
`ready-failed` report if background verification fails. When the native queue fills, it drops the
oldest report it can, giving device challenges priority. The next `onReport` listener receives a
`reports-dropped` report with the count before the other native reports. Use `onUnreadable` to
receive only reports of type `unreadable`, including space-level reports and notices about returned
rows. Use `unreadableRows(result)` for the rows a particular read omitted. See the
[report listener implementation](https://github.com/garden-co/jazz/blob/94cd8e1e45/packages/jazz-tools/src/encryption/index.ts#L348-L368) and the
[report overflow test](https://github.com/garden-co/jazz/blob/94cd8e1e45/crates/jazz-e2ee-client/src/host/runtime.rs#L1598-L1625).

### Before a device can read

A device reads its encrypted rows from its own store, offline too, once it has synced with the server
once. A device that has never synced (a new store) cannot tell yet which of its rows are encrypted, so
its live queries on encrypted columns stay loading until its first sync, however long that takes,
rather than show an empty result. `db.encryption.readable()` resolves when the device can read: after
its first sync, and in a browser that started thin, also once the encryption runtime has loaded and
checked the account (a returning device waits only for those). Loading and the check share a
30-second deadline. It rejects if the encryption runtime has not loaded by then or the Db closes; an
account check that fails or is still running at the deadline does not stop it:

```ts
let reading: "waiting" | "ready" | "failed" = "waiting";
session.db.encryption.readable().then(
  () => (reading = "ready"),
  () => (reading = "failed"),
);
// While `reading` is "waiting", say that encrypted data is still loading rather than show it as empty.
// If it is "failed", show that encrypted data could not load.
```

## The backend holds no keys

Your backend (`createJazz`) starts for an encrypted app and relays its clients as usual. It is not an
encryption participant: it has no account, no identity and no keys. Its own database reads plain tables
and the plain columns of an encrypted table as normal, never sees an encrypted column (the rows come
back without it), refuses a write that names one ("the backend holds no encryption keys; encrypted
columns are written by clients") and refuses a filter, ordering or selection of one. A server
that needs to compute on encrypted content cannot; do that on a client.

The generated types are the clients': they give an encrypted column its plaintext type. On the backend,
query through `keyless(app)` from `jazz-tools/backend`, the same app typed as the backend reads it: an
encrypted column is absent from its rows (`title?: undefined`), its inserts and its filters.

```ts
import { keyless } from "jazz-tools/backend";
import { app } from "./jazz.generated";

const backendApp = keyless(app);
// jazz = await createJazz({ app, ... }).ready()
const tasks = await jazz.db.all(backendApp.tasks); // each task.title is undefined
```

`db.encryption` exists on every `Db`; for an app that declares no encryption, using it throws
`EncryptionNotDeclaredError`.
