## For developers

A modern app's data layer is usually assembled by hand. There's a hosted database such as Supabase
or Convex for tables, auth and an API. A sync engine sits next to it so screens update live and
keep working on a flaky connection. Streams carry chat, presence or agent output, and a blob store
holds files. Each piece has its own client, its own idea of who the user is and its own permission
rules, and your team writes and maintains the glue that keeps them consistent.

Jazz is that whole data layer in one piece, running inside the backend you already have:

- **One database inside your backend.** Tables, relations and a typed client for backend and
  frontend, with no API layer to write. Jazz plugs into whatever auth your backend uses. Backend
  code can act with full trusted access or as a specific user, and clients sync with your backend
  over a same-origin endpoint (`/jazz` by default) using your app's existing session.
- **Sync built in.** Subscribe to any query and your UI stays current on its own: a feed, a
  dashboard or a shared list updates the moment someone adds, edits or removes a row, including
  rows that start or stop matching a filter. When a screen needs instant writes or offline support,
  switch that client to local-first, with the same schema, queries and policies.
- **Streams and files in the same model.** Files, streams and mergeable text are columns in your
  tables, so they sync, version and follow permissions like every other value. Edit metadata
  (`$createdBy`, `$updatedAt`, …), history, drafts and branches come with every row.
- **One set of permissions.** Policies live next to your schema in TypeScript and apply the same way
  to backend code, thin clients, local-first clients, files and streams. They're verbose, but agents
  are good at writing and checking them.

**When to use Jazz.** You want live queries, typed policies and collaboration features without
running a database platform, and you want the option of offline-capable local-first clients later.

**When to use Supabase.** You need full Postgres and its extension ecosystem, or you want a mature
hosted dashboard with auth, storage and functions included.

**When to use Jazz.** Your app needs users to see each other's changes live, with access rules
enforced in one place, and you'd rather not build the API and sync layer on top of a database.

**When to use Postgres.** You need arbitrary SQL, heavy analytics or a specific extension, or your
data already lives there and many systems read it.

## For engineering leaders

- Custom code as a liability: less backend code to own
- Fewer systems and moving parts
- Your backend owns auth; Jazz Cloud or your own Jazz server stores and syncs
- Licensing: MIT for unsharded Jazz, a license for sharded Jazz
