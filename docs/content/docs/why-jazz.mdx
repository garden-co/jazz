## For developers

Think of Jazz as a modern Supabase that sits right next to your app. You get a relational database, auth integration, permissions and a typed client for backend and frontend, with no API layer of your own to write and maintain. Then it goes further:

- **Your backend in front.** Jazz runs inside your backend, which handles auth and talks to Jazz Cloud or your own Jazz server. Browsers never hold a Jazz credential. Unsharded Jazz is MIT and free.
- **Live queries, not change feeds.** Every query can be a subscription. The server keeps results up to date as rows change, including rows that start or stop matching.
- **Permissions as code.** Policies live next to your schema in TypeScript and apply the same way to backend, thin-client and local-first reads and writes. They're verbose, but agents are good at writing and checking them.
- **Built-in collaboration.** Edit metadata (`$createdBy`, `$updatedAt`, …), history, drafts and branches, mergeable text, and files and streams, without bolting on extra services.
- **Local-first when it pays off.** Start with server-first reads and writes. Switch a client to local-first for instant UI and offline support, with the same schema, queries and policies.

## Compared to

Rough plan: each comparison answers the questions developers actually ask (lock-in, SQL access, migrations, scaling, cost, offline), carries a "last checked" date and only makes claims we can link to. The bullets below are what we'd emphasize; claims about other products still need checking and links.

### Supabase

- Same promise of a database, auth hooks, permissions and a client SDK in one, but you run Jazz next to your app instead of a hosted platform or a multi-service self-host stack
- Live queries return updated results, not a stream of row changes you re-apply yourself
- Policies are typed TypeScript next to the schema instead of SQL row-level security
- Built-in collaboration: history, branches, mergeable text, edit metadata
- Optional local-first clients for offline and instant UI
- Scales from zero to shards without picking an instance size
- Where Supabase is stronger: full Postgres and its extension ecosystem, a mature hosted dashboard

### Postgres

- Jazz is relational too, but adds live queries, permissions and sync on top, so there's no API layer to write
- No connection pooling or long-lived server to size and keep warm
- Schema migrations are typed and generated, not hand-written SQL
- Where Postgres is stronger: decades of tooling, arbitrary SQL, analytics workloads, extensions

### Plain SQLite

- Jazz runs on SQLite underneath, so you keep its speed and simple storage
- Adds what you'd otherwise build yourself: sync between clients and server, permissions, live queries, conflict handling
- Same schema runs on the server, in the browser and on mobile
- Where plain SQLite is stronger: zero dependencies, full control, no sync model to learn

### Plain Durable Objects

- Jazz shards across DO-sized units, but you work with tables and queries instead of hand-rolled per-object state and storage
- Sharding across objects is handled for you, including cross-shard transactions
- Permissions and live queries come built in rather than as custom code in every DO
- Where plain DOs are stronger: full control over the actor model, no abstraction overhead

### Convex

- Both give reactive queries and a typed schema; Jazz runs inside your own backend and is MIT when unsharded
- Jazz queries are declarative relational queries, not server functions you write and deploy
- Declarative permission policies instead of checks written inside each function
  - When a rule is too complex for a policy, write it as ordinary code in a backend route that uses the backend client, and close that data off to clients entirely
- Local-first clients with offline writes
- Where Convex is stronger: a polished hosted product, server functions co-located with data

### Zero

- Both sync query results to clients; Jazz is the database itself, not a sync layer in front of Postgres
- Permissions apply to backend, thin-client and local-first access alike
- Collaboration features (history, branches, mergeable text) are built in
- Thin client option when you don't want a client-side cache at all
- Where Zero is stronger: keeps your existing Postgres as the source of truth

### Neon (sync)

- Neon is serverless Postgres; Jazz is a serverless relational database with sync, permissions and live queries built in
- No separate sync product or replication setup to wire up
- Where Neon is stronger: real Postgres, branching for dev databases, a managed service

### TanStack DB

- TanStack DB is a client-side reactive store over your own APIs; Jazz also provides the server, storage and permissions
- No API layer to write to feed the client collections
- Same live queries on the backend and frontend
- Where TanStack DB is stronger: plugs into an existing backend with no new database

## For engineering leaders

- Custom code as a liability: less backend code to own
- Fewer systems and moving parts
- Your backend owns auth; Jazz Cloud or your own Jazz server stores and syncs
- Licensing: MIT for unsharded Jazz, a license for sharded Jazz
