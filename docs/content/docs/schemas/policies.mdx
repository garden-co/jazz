Declarative permissions control who can read, insert, update, and delete rows. You declare them as policies in `jazz.permissions.json`, and Jazz enforces them server-side. Clients that fail a policy check have their writes rejected and their reads filtered.

If you know Postgres row-level security (RLS), declarative permissions are similar: rules over rows and the signed-in user. In Jazz they are short SQL-like expressions in a file next to your schema, checked against it, every operation is denied until a policy grants it, and you test them like the rest of your app.

Jazz decides permissions per table:

- every read, insert, update, and delete requires an explicit grant
- every omitted operation is denied, including on tables with no policy declarations

For example, declaring `read` without `insert`, `update`, or `delete` makes that table
read-only. A table without any grants returns no
rows to permission-scoped reads and rejects writes on the server. Optimistic
local writes can still appear before the server accepts or rejects them.

## Authoring workflow

Permissions live in `jazz.permissions.json`, next to `jazz.app.json`. Each table has `read`,
`insert`, `update` and `delete`, and each is a policy: an expression over the row and the session.

If we have the following schema:

```json title="jazz.app.json"
{
  "format": 1,
  "tables": {
    "projects": {
      "columns": {
        "name": "string",
        "owner_id": "uuid"
      },
      "relations": {
        "todos": { "reverse": "todos", "relation": "project" }
      }
    },
    "todos": {
      "columns": {
        "title": "string",
        "done": "boolean",
        "parentId": "uuid?",
        "projectId": "uuid?",
        "owner_id": "uuid"
      },
      "relations": {
        "parent": { "rel": "todos", "column": "parentId" },
        "children": { "reverse": "todos", "relation": "parent" },
        "project": { "rel": "projects", "column": "projectId" },
        "shares": { "reverse": "todoShares", "relation": "todo" }
      }
    },
    "todoShares": {
      "columns": {
        "todoId": "uuid",
        "user_id": "uuid",
        "can_read": "boolean"
      },
      "relations": {
        "todo": { "rel": "todos", "column": "todoId" }
      }
    }
  }
}
```

We can define permissions in `jazz.permissions.json`:

```json title="jazz.permissions.json"
{
  "$schema": "https://jazz.tools/schemas/jazz.permissions.schema.json",
  "format": 1,
  "tables": {
    "projects": {
      "read": "true",
      "insert": "true"
    },
    "todos": {
      "read": "owner_id = session.user",
      "insert": "owner_id = session.user",
      "update": "owner_id = session.user",
      "delete": "owner_id = session.user"
    }
  }
}
```

Expressions read like SQL: a bare name is a column of the row being checked, string literals use
single quotes, and `and`, `or`, `not` and parentheses combine conditions. The full grammar is in
[App files](/docs/reference/app-files#expressions).

<Callout type="info">
  Keep `jazz.permissions.json` next to `jazz.app.json`. By default Jazz looks for both files at your project root — except in SvelteKit projects, where they should live in `src/lib/` (the standard location for shared app code).

Run `npx jazz-tools generate` before publishing: it compiles every policy against your schema, points at the exact spot of a mistake, and warns about missing table or operation grants that will deny access. You do not need to write a schema migration to update permissions policies. Updated policies go live when your main backend restarts or deploys with them.

Only backends read `jazz.permissions.json`: `createJazz({ app, permissions })` takes it, imported as JSON (`import permissions from "./jazz.permissions.json" with { type: "json" }`). Client bundles never include it.

</Callout>

Apps that do not need user-scoped filtering must still declare every required operation explicitly, using grants such as `"read": "true"` and `"insert": "true"`.

## Basic policies

### Simple conditions

Compare columns with values and with the session to restrict access based on column values:
`=`, `!=`, `<`, `<=`, `>`, `>=`, `in [...]`, `contains`, and `= null` / `!= null`.

Policies decide which rows a user may read or write, not which columns. To keep a column from some
users, move it to its own table with a one-to-one relation to the row, and give that table its own
policies.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "read": "owner_id = session.user",
      "insert": {
        "$comment": "Users cannot create todos with different owners",
        "where": "owner_id = session.user"
      },
      "update": {
        "$comment": "Users can update their own todos, but only if not already done",
        "old": "owner_id = session.user and done = false",
        "new": "owner_id = session.user"
      },
      "delete": {
        "$comment": "Users can only delete their own todos",
        "where": "owner_id = session.user"
      }
    }
  }
}
```

JSON has no comments: a `$comment` key, allowed in any object, says what a policy is for.
`{ "$comment": "…", "where": … }` is a commented policy.

### `true`

Use `"true"` when an operation should always be permitted.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "read": "true",
      "insert": "true",
      "update": "true",
      "delete": "true"
    }
  }
}
```

### `false`

Use `"false"` when an operation should be impossible. Leaving the operation out denies it too;
`"false"` says it's on purpose.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "read": "false",
      "insert": "false",
      "update": "false",
      "delete": "false"
    }
  }
}
```

#### Tables only your backend writes

A table your users read but only your backend writes (an audit log, imported data, counters a job
keeps) needs no write grants: your backend isn't checked when it acts as the system (see
[System-authored rows](/docs/setup/auth/backend#system-authored-rows)). `npx jazz-tools generate`
warns about each operation without a policy, so say it's on purpose with `"false"` rather than
adding an allow rule to silence the warning:

{/* check-app: {"format":1,"tables":{"auditLog":{"columns":{"ownerId":"uuid","action":"string"}}}} */}

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "auditLog": {
      "read": "ownerId = session.user",
      "insert": "false",
      "update": "false",
      "delete": "false"
    }
  }
}
```

## Composing policies

### Combining conditions (`allOf` / `anyOf`)

Combine conditions with `and` and `or` inside an expression, or list whole policies with
`{ "allOf": [...] }` (all must match) or `{ "anyOf": [...] }` (any can match), which keeps long
rules readable:

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "projects": {
      "read": "owner_id = session.user"
    },
    "todos": {
      "read": {
        "$comment": "Users can read a todo if they own it, or if it's not done and they can read its project.",
        "anyOf": ["owner_id = session.user", "done = false and allowedTo.read(project)"]
      }
    }
  }
}
```

`and` binds tighter than `or`, and `not` tighter than both; add parentheses when you mean
otherwise.

### Named conditions (`defs`)

When several policies repeat a condition, name it under `defs`, with `$`-parameters, and call it
like a function. Definitions may call each other, but never recursively:

```json title="jazz.permissions.json"
{
  "format": 1,
  "defs": {
    "isOwner($owner)": "$owner = session.user"
  },
  "tables": {
    "projects": {
      "read": "isOwner(owner_id)"
    },
    "todos": {
      "read": "isOwner(owner_id)",
      "update": "isOwner(owner_id) and done = false",
      "delete": "isOwner(owner_id)"
    }
  }
}
```

### Session claims

When your backend's `authenticate` returns claims, `session.claims.<path>` lets you check them directly in permissions without mapping them onto row columns first.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "read": { "anyOf": ["owner_id = session.user", "session.claims.role = 'manager'"] }
    }
  }
}
```

A claim can also be the value a row is compared with, for example rows of the user's organization
(`orgId = session.claims.org`), or a list to test membership in (`teamId in session.claims.teams`).

Claims are JSON, so a claim is compared as the type of the column it meets, the same way in every
policy form: a `uuid` column (or `id`) reads a string claim as the UUID it spells, a text column
compares the claim's text exactly, and an integer column accepts a JSON number or a string such as
`"42"`. A claim the column can't hold matches no rows.

### Inherited access (`allowedTo.*`)

A row can inherit its access from a related row. Use
`allowedTo.read/insert/update/delete(relationName)` to express that inheritance.
The argument is a relation name declared on the protected table, the same names relation hops
use. For `"writer": { "rel": "users", "column": "authorId" }`, write
`allowedTo.update(writer)`; the stored column `authorId` is not accepted here.

Reverse names work the same way. Given
`"authored": { "reverse": "posts", "relation": "writer" }` on `users`,
`allowedTo.delete(authored)` grants deletion only when at least one referencing
post permits deletion for the current identity. Readability or mere existence
of a referencing post does not grant deletion. No matching reference means no
grant; nullable references contribute no match, and UUID arrays use membership.
For a link no relation names, `allowedTo.delete(via posts.writer)` names the rows of `posts`
whose `writer` column points here, and `allowedTo.read(via authorId)` a forward column itself.

Inheritance keeps each operation's own policy, and each update rule's old/new row checks.
`jazz-tools generate` checks that the relation exists on the rule's table, and its direction and
target.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "projects": {
      "read": "owner_id = session.user",
      "update": "owner_id = session.user"
    },
    "todos": {
      "read": {
        "$comment": "Users can read a todo if it's not done, or if they can read its project.",
        "anyOf": ["done = false", "allowedTo.read(project)"]
      },
      "update": {
        "$comment": "Users can update a todo if they can update its project and it's not done.",
        "old": "allowedTo.update(project) and done = false",
        "new": "allowedTo.update(project)"
      }
    }
  }
}
```

### Share-based access

Sometimes access isn't determined by ownership or a parent relationship, but by a separate "shares" table. Use `exists <table>(…)` to check whether a matching row exists in another table.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "read": {
        "$comment": "Users can read a todo if they own it, or if someone shared it with them.",
        "anyOf": [
          "owner_id = session.user",
          "exists todoShares(todoId = this.id, user_id = session.user, can_read = true)"
        ]
      }
    }
  }
}
```

Inside `exists todoShares(…)`, a bare name is a column of `todoShares`, and `this.col` is the
current row, so you can correlate it with rows in other tables. The conditions are separated by
commas and must all hold.

An `exists` can also follow a relation from the row it finds:
`exists docs(id = this.id).author(uid = session.identity.subject)` reads `uid` on the row
`author` leads to.

One correlation links the two rows: the one on the other table's `id`, if there is one. It must
follow a relation, either `id` against a column declared with a `rel` to that table, or two columns
that are relations to the same table; otherwise validation fails with `JoinNotRefCompatible`.
Further correlations, such as `authUserId: row.authUserId`, only need comparable column types.

To match the `userId` your `authenticate` returned (for example an `assignee` text column holding
your auth's user ids), compare with `session.identity.subject`: `session.user` is the Jazz account,
not your user id.

Inside a transaction, `exists` also sees the transaction's own writes, so a row can be written in
the same transaction as the row that grants it access, such as a task inserted together with its
project. A row that already existed still counts if the same transaction deletes it, so you can,
for example, admit a member and remove their join request together. A row the transaction both
creates and deletes never counts, and neither do writes from other transactions that the server
has not accepted yet. Rows a transaction writes cannot grant each other access in a cycle:
each one has to be allowed by rows that already exist or that the transaction writes and are
themselves allowed. Every write must also still be allowed by the state the whole transaction
leaves behind, so demoting your own membership from admin in the same transaction as creating a
document that requires admin is rejected. The order in which you make the writes doesn't matter.

Importing many rows whose permissions rest on rows that already exist (for example, thousands of
folders under existing parents) is checked once per row. A transaction whose rows mostly depend on
each other (for example, thousands of folders nested inside one another in the same transaction)
is rejected with the `write_rejected` code and a reason ending in "is not supported yet" once its
checks would have to read more than 262,144 of its own rows. Split such an import into smaller
transactions.

### Access through related rows

When access depends on rows in another table, check that a matching path exists with `exists`
and a relation hop: start from a table, filter it, follow a relation with `.relation(…)`, and
filter again. For example, a doctor may read the patients they have an appointment with:

```json title="jazz.app.json"
{
  "format": 1,
  "tables": {
    "doctors": {
      "columns": {
        "userId": "string",
        "name": "string"
      }
    },
    "patients": {
      "columns": {
        "name": "string"
      }
    },
    "appointments": {
      "columns": {
        "doctorId": "uuid",
        "patientId": "uuid",
        "at": "timestamp"
      },
      "relations": {
        "doctor": { "rel": "doctors", "column": "doctorId" },
        "patient": { "rel": "patients", "column": "patientId" }
      }
    }
  }
}
```

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "doctors": {
      "read": {
        "$comment": "A doctor reads their own record.",
        "where": "userId = session.identity.subject"
      }
    },
    "patients": {
      "read": {
        "$comment": "Patients with an appointment whose doctor is the signed-in user.",
        "where": "exists appointments(patientId = this.id).doctor(userId = session.identity.subject)"
      }
    },
    "appointments": {
      "read": {
        "$comment": "A doctor's own appointments.",
        "where": "exists doctors(id = this.doctorId, userId = session.identity.subject)"
      }
    }
  }
}
```

These are read rules only: who may book or change appointments needs insert and update policies
too. A hop takes a relation name declared with `rel` or `reverse`, and the conditions after it
filter the rows it reaches. An `exists` takes one hop: chaining a second one is not supported yet.

<Accordions type="single">
<Accordion title="Recursive inheritance">

If a table references itself (e.g. a comment that can have sub-comments), you can inherit access recursively up to a fixed depth.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "read": {
        "$comment": "Users can read a todo if they can read its parent (follows the chain upward).",
        "where": "allowedTo.read(parent)"
      },
      "update": {
        "$comment": "Users can update a todo if they can update its parent, up to 5 levels deep.",
        "where": "allowedTo.update(parent, maxDepth: 5)"
      }
    }
  }
}
```

`maxDepth` must be a non-negative integer. A value of `0` performs no inheritance
hop, so the inheritance condition cannot grant access; `1` checks only the
directly referenced row. These bounds apply to forward relationships. Reverse
inheritance currently rejects `maxDepth` rather than ignoring it; cyclic reverse
policy expansion is rejected during schema validation.

</Accordion>
</Accordions>

### Update policies: old row vs new row

An update policy can check both the row **before** the update (`old`) and the row **after** the
update (`new`). This is useful when you need to verify that the user had permission to modify the
original row and that the result is also valid.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "update": {
        "$comment": "Users can only update their own rows, and the result must still be owned by them.",
        "old": "owner_id = session.user",
        "new": "owner_id = session.user"
      }
    }
  }
}
```

A single policy, `"update": "owner_id = session.user"`, applies the same condition to both the old
and new row. Use `old` and `new` when the checks differ.

`exists` runs before a write is applied, so it can be used to prevent some columns from being updated.
The row being written is always seen as it was before the write, even inside a transaction.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "update": {
        "$comment": "parentId and projectId cannot be updated.",
        "old": "owner_id = session.user",
        "new": "owner_id = session.user and exists todos(id = this.id, parentId = this.parentId, projectId = this.projectId)"
      }
    }
  }
}
```

## Check permissions before an action

Use `db.canInsert()`, `db.canRead()`, `db.canUpdate()`, or `db.canDelete()` when your app needs to
check an action before showing it to the user. Each method returns `"allowed"`, `"denied"`, or
`"unknown"`.

These results are advice, not permission enforcement. A result can become stale, and `"unknown"`
means Jazz could not give a definite answer. The authority still makes the final decision when the
read or write reaches it.

## Magic columns

Jazz exposes a small set of system-provided magic columns at query time. They do not exist in your
schema, and they are omitted from `select("*")`, so opt in explicitly when you want them.

### Edit metadata columns

Jazz also tracks row authorship and timestamps automatically:

- `$createdBy`&hairsp;—&hairsp;the Jazz principal that created the row
- `$createdAt`&hairsp;—&hairsp;when the row was first created
- `$updatedBy`&hairsp;—&hairsp;the Jazz principal that last updated the row
- `$updatedAt`&hairsp;—&hairsp;when the row was last updated

Jazz always tracks this metadata; select the columns explicitly to include them in query results. Backend writes that are not attributed to a user use the reserved system account and an internal system identity. See [System-authored rows](/docs/setup/auth/backend#system-authored-rows) for their account, issuer, and originating-node subject.

### Authorship-based policies

You can use these edit metadata magic columns directly in `jazz.permissions.json`. This is useful for simple
"creator can read/edit/delete their own rows" policies without adding explicit `owner_id` columns.

Compare `$createdBy.account` with `session.user` to scope a rule to the row's creator. `session.user` is
the account, so the rule matches rows written through any identity linked to it, including
alpha.59 rows whose author was imported with an account. To match only the exact login that wrote
the row, compare `$createdBy.identity = session.identity` (its issuer and subject). `session.claims`
holds the claims your `authenticate` returned, not a raw JWT payload; with
[`fromJWT()`](/docs/setup/auth/custom#tokens-from-your-identity-provider), `session.identity` is
`{ issuer: "jazz:backend", subject }`, not your provider's `iss`. Claims never replace the
canonical author identity.

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "$comment": "Only the row's creator can read, create, update, or delete it.",
      "read": "$createdBy.account = session.user",
      "insert": "$createdBy.account = session.user",
      "update": "$createdBy.account = session.user",
      "delete": "$createdBy.account = session.user"
    }
  }
}
```

The creator condition is a plain comparison, so it composes inside larger rules:

```json title="jazz.permissions.json"
{
  "format": 1,
  "tables": {
    "todos": {
      "read": "$createdBy.account = session.user or done = true"
    }
  }
}
```

For more dynamic sharing or ownership models, prefer explicit tables and relations rather than
encoding extra meaning into authorship alone.

## Changing permissions in production

Each deployment of your backend serves the permissions it was built with, and every client is checked by the permissions of the deployment it connected through. When a deployment with new permissions starts, every connected client reconnects, including clients of your other deployments (previews too), and each is checked again by the permissions of the deployment it now reaches. Deploying permissions that have been deployed before, such as a rollback, reconnects no one.

To retire permissions that grant too much, deploy fixed ones and delete every deployment that still serves the old ones, including older production and preview deployments that are still reachable. Until it is gone, any client that connects through such a deployment is checked by its permissions.

## Troubleshooting denied access

If a write appears locally but does not persist, wait for
[server durability](/docs/writing/writing-data#write-durability-tiers) and handle the rejection.
The local-first client rejects with `PersistedWriteRejectedError`, code `permission_denied`. The
thin client rejects with a `ThinRemoteError` whose `code` is `WriteRejected` and whose message
starts with the reason, such as `authorization_denied: …`. Use
`db.onMutationError(...)` as a fallback for rejections without an active wait;
see [Handling mutation errors](/docs/writing/writing-data#handling-mutation-errors).
A backend connected to Jazz Cloud (deprecated) doesn't refuse a session's write up front either: the cloud
decides it, and a denial arrives through `wait(...)` with the same `permission_denied` code. A store
with no authority above it, such as a client with `serverUrl: null` or a backend on its own
storage, refuses some denied writes at once (the write call throws), and accepts others, such as a
denied update of a row it holds, then rejects them through `wait(...)`. So in backend code, await every write
and handle both:

```ts
try {
  await db.update(app.deals, dealId, { stage: "won" }).wait({ tier: "global" });
} catch (error) {
  // permission_denied, thrown by update() or by wait()
}
```

In Node, a write's rejected `wait()` that nothing awaits or catches is an unhandled rejection, which
ends the process.

An empty query result can also mean that read permissions filtered out rows.

As the app developer, check your own configuration:

1. Run `npx jazz-tools generate` and check that every required table
   and operation has an explicit grant. For updates and upserts that update an
   existing row, also check the required read permission.
2. Check that the grants match the authenticated session and the relevant row
   values, including both old and new values for updates. Test these cases with
   [permission tests](/docs/tooling/testing#testing-permissions).
3. Deploy your main backend with the intended policies
   and verify the app ID and deployed configuration. Editing `jazz.permissions.json`
   locally does not update the server's policies.

Treat `permission_denied` as a generic rejection: it does not tell the caller
whether a policy is missing, a predicate failed, or a protected row exists.
Keep these configuration checks in developer tooling and tests; do not expose
protected policies, row values, or row-existence details in client-facing errors.
