Declarative permissions control who can read, insert, update, and delete rows. You declare them as policies in `permissions.ts`, and Jazz enforces them server-side. Clients that fail a policy check have their writes rejected and their reads filtered.

If you know Postgres row-level security (RLS), declarative permissions are similar: rules over rows and the signed-in user. In Jazz they are typed TypeScript next to your schema, every operation is denied until a policy grants it, and you test them like the rest of your app.

Jazz decides permissions per table:

- every read, insert, update, and delete requires an explicit grant
- every omitted operation is denied, including on tables with no policy declarations

For example, declaring `allowRead` without `allowInsert`, `allowUpdate`, or
`allowDelete` makes that table read-only. A table without any grants returns no
rows to permission-scoped reads and rejects writes on the server. Optimistic
local writes can still appear before the server accepts or rejects them.

<Callout type="info">
  Write your permissions policies in `permissions.ts` next to `schema.ts`. By default Jazz looks for both files at your project root — except in SvelteKit projects, where they should live in `src/lib/` (the standard location for shared app code).

After you edit `permissions.ts`, run `npx jazz-tools validate`: it writes the new policies into `jazz.permissions.json`, which your backend passes to `createJazz` and publishes, and surfaces missing table or operation grants that will deny access. Commit the file with your change: until you do, the backend keeps serving the old permissions, and `validate --check` in CI fails. You do not need to write a schema migration to update permissions policies. Updated policies go live when your main backend restarts or deploys with them. Clients never import `jazz.permissions.json`, so your policies stay out of client bundles.

</Callout>

Apps that do not need user-scoped filtering must still declare every required operation explicitly, using grants such as `policy.todos.allowRead.always()` and `policy.todos.allowInsert.always()`.

## Basic policies

### Simple conditions

Use the policy helpers `allowRead`, `allowInsert`, `allowUpdate`, and `allowDelete` with [`.where(...)`](/docs/reference/where-operators) to restrict access based on column values.

Policies decide which rows a user may read or write, not which columns. To keep a column from some
users, move it to its own table with a one-to-one relation to the row, and give that table its own
policies.

<include cwd lang="ts" meta='title="permissions.ts"'>
  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-simple-ts
</include>

### `.always()`

Use `.always()` when an operation should always be permitted. It is equivalent to `.where({})`.

<include cwd lang="ts" meta='title="permissions.ts"'>
  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-always-ts
</include>

### `.never()`

Use `.never()` when an operation should be impossible. It is equivalent to
`.where(anyOf([]))`.

<include cwd lang="ts" meta='title="permissions.ts"'>
  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-never-ts
</include>

#### Tables only your backend writes

A table your users read but only your backend writes (an audit log, imported data, counters a job
keeps) needs no write grants: your backend isn't checked when it acts as the system (see
[System-authored rows](/docs/setup/auth/backend#system-authored-rows)). `npx jazz-tools validate`
warns about each operation without a policy, so say it's on purpose with `.never()` rather than
adding an allow rule to silence the warning:

```ts title="permissions.ts"
policy.auditLog.allowRead.where({ ownerId: session.user });
policy.auditLog.allowInsert.never();
policy.auditLog.allowUpdate.never();
policy.auditLog.allowDelete.never();
```

## Composing policies

### Combining conditions (`allOf` / `anyOf`)

Combine conditions with `allOf` (all must match) or `anyOf` (any can match).

<include cwd lang="ts" meta='title="permissions.ts"'>
  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-combinators-ts
</include>

Plain objects in a condition are row predicates. This includes tables with columns such as `type`,
`column`, or `operation` that also appear in Jazz's policy representation. Results from helpers such
as `allowedTo.*`, `allOf`, and `anyOf` remain directly composable with those row
predicates.

An object such as `{ type: "True" }` is row data only when the table schema declares a `type` column.
On a table without that column, Jazz rejects the unbranded policy-shaped value rather than silently
interpreting it as either row data or policy IR. For advanced cases that need manually-authored
policy IR, use `raw(...)` to opt in explicitly:

```ts
definePermissions(app, ({ policy, raw }) => {
  policy.documents.allowRead.where(raw({ type: "True" }));
});
```

### Session claims

When your backend's `authenticate` returns claims, `session.where(...)` lets you check them directly in permissions without mapping them onto row columns first.

<include cwd lang="ts" meta='title="permissions.ts"'>
  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-session-claims-ts
</include>

A claim can also be the value a row is compared with, for example rows of the user's organization:

```ts
policy.projects.allowRead.where({ orgId: session.claims["org"] });
```

### Inherited access (`allowedTo.*`)

A row can inherit its access from a related row. Use
`allowedTo.read/insert/update/delete(relationName)` to express that inheritance.
The argument is an explicit relationship name declared on the protected table,
using the same names as `hopTo`. For `writer: s.rel("users", "authorId")`, use
`allowedTo.update("writer")`; the stored column `authorId` is not accepted here.

Reverse names work with the same helpers. Given
`authored: s.reverse("posts", "writer")` on `users`,
`allowedTo.delete("authored")` grants deletion only when at least one referencing
post permits deletion for the current identity. Readability or mere existence
of a referencing post does not grant deletion. No matching reference means no
grant; nullable references contribute no match, and UUID arrays use membership.
The explicit source form `allowedTo.deleteReferencing(policy.posts, "writer")`
uses the named forward relationship on `posts` that targets the protected table.

Relationship-name resolution preserves existing operation-policy semantics and
each update rule's old/new row checks. The global helper's TypeScript name check covers the app's declared
relationships; permission compilation also checks the particular rule's table,
and the source direction and target for `*Referencing`.

  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-allowed-to-ts
</include>

### Share-based access

Sometimes access isn't determined by ownership or a parent relationship, but by a separate "shares" table. Use `policy.<table>.exists.where(...)` to check whether a matching row exists in another table.

<include cwd lang="ts" meta='title="permissions.ts"'>
  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-shares-ts
</include>

The callback form `(todo) => ...` gives you access to the current row, so you can correlate it with rows in other tables.

A `where(...)` key can also reach one hop through a relation, qualified with the relation's name:
`policy.docs.allowRead.where({ "author.uid": session.identity.subject })` reads `uid` on the
row `author` leads to (from alpha.62). The name of the table a relation leads to works too, when
only one of the table's relations leads there, also before alpha.62.

One correlation links the two rows: the one on the other table's `id`, if there is one. It must
follow a relation, either `id` against a column declared with `s.rel` to that table, or two columns
that are relations to the same table; otherwise validation fails with `JoinNotRefCompatible`.
Further correlations, such as `authUserId: row.authUserId`, only need comparable column types.

To match the `userId` your `authenticate` returned (for example an `assignee` text column holding
your auth's user ids), compare with `session.identity.subject`: `session.user` is the Jazz account,
not your user id.

Inside a transaction, `exists` also sees the transaction's own writes, so a row can be written in
the same transaction as the row that grants it access, such as a task inserted together with its
project. A row that already existed still counts if the same transaction deletes it, so you can,
for example, admit a member and remove their join request together. A row the transaction both
creates and deletes never counts, and neither do writes from other transactions that the server
has not accepted yet. Rows a transaction writes cannot grant each other access in a cycle:
each one has to be allowed by rows that already exist or that the transaction writes and are
themselves allowed. Every write must also still be allowed by the state the whole transaction
leaves behind, so demoting your own membership from admin in the same transaction as creating a
document that requires admin is rejected. The order in which you make the writes doesn't matter.

Importing many rows whose permissions rest on rows that already exist (for example, thousands of
folders under existing parents) is checked once per row. A transaction whose rows mostly depend on
each other (for example, thousands of folders nested inside one another in the same transaction)
is rejected with the `write_rejected` code and a reason ending in "is not supported yet" once its
checks would have to read more than 262,144 of its own rows. Split such an import into smaller
transactions.

### Access through related rows

When access depends on rows in another table, check that a matching path exists with
`policy.exists(...)` around a relation: start from a table, filter it, follow a relation with
`hopTo`, and filter again. For example, a doctor may read the patients they have an appointment
with:

```ts title="schema.ts"
const schema = {
  doctors: s.table({ userId: s.string(), name: s.string() }, {}),
  patients: s.table({ name: s.string() }, {}),
  appointments: s.table(
    { doctorId: s.uuid(), patientId: s.uuid(), at: s.timestamp() },
    { doctor: s.rel("doctors", "doctorId"), patient: s.rel("patients", "patientId") },
  ),
};
```

```ts title="permissions.ts"
// Read rules only: who may book or change appointments needs insert and update policies too.
s.definePermissions(app, ({ policy, session }) => [
  // A doctor reads their own record.
  policy.doctors.allowRead.where({ userId: session.identity.subject }),
  // Patients with an appointment whose doctor is the signed-in user.
  policy.patients.allowRead.where((patient) =>
    policy.exists(
      policy.appointments
        .where({ patientId: patient.id })
        .hopTo("doctor")
        .where({ userId: session.identity.subject }),
    ),
  ),
  // A doctor's own appointments: "doctors.userId" filters the related doctor.
  policy.appointments.allowRead.where({ "doctors.userId": session.identity.subject }),
]);
```

`hopTo` takes a relation name declared with `s.rel` or `s.reverse`, and the `where` after it
filters the rows it reaches. A relation takes one `hopTo`: chaining a second one is not supported
yet. A qualified key filters a related table directly: `"doctors.userId"` is qualified with the
table's name, which works because only one relation leads from `appointments` to `doctors`. From
alpha.62 the relation's name, `"doctor.userId"`, works as well (see
[Share-based access](#share-based-access)).

<Accordions type="single">
<Accordion title="Recursive inheritance">

If a table references itself (e.g. a comment that can have sub-comments), you can inherit access recursively up to a fixed depth.

<include cwd lang="ts" meta='title="permissions.ts"'>
  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-recursive-inherits-ts
</include>

`maxDepth` must be a non-negative integer. A value of `0` performs no inheritance
hop, so the inheritance condition cannot grant access; `1` checks only the
directly referenced row. These bounds apply to forward relationships. Reverse
inheritance currently rejects `maxDepth` rather than ignoring it; cyclic reverse
policy expansion is rejected during schema validation.

</Accordion>
</Accordions>

### Update policies: old row vs new row

Update policies can check both the row **before** the update (`.whereOld(...)`) and the row
**after** the update (`.whereNew(...)`). This is useful when you need to verify that the user had
permission to modify the original row and that the result is also valid.

<include cwd lang="ts" meta='title="permissions.ts"'>
  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-whereold-wherenew-ts
</include>

If you only use `.whereOld(...)`, the same condition is applied to both the old and new row. The
same applies if you only use `.whereNew(...)`. Use both when the old-row and new-row checks differ.

`exists` runs before a write is applied, so it can be used to prevent some columns from being updated.
The row being written is always seen as it was before the write, even inside a transaction.

<include cwd lang="ts" meta='title="permissions.ts"'>
  ../examples/docs/todo-server-ts/src/permissions-snippets.ts#permissions-update-protected-columns
</include>

## Check permissions before an action

Use `db.canInsert()`, `db.canRead()`, `db.canUpdate()`, or `db.canDelete()` when your app needs to
check an action before showing it to the user. Each method returns `"allowed"`, `"denied"`, or
`"unknown"`.

These results are advice, not permission enforcement. A result can become stale, and `"unknown"`
means Jazz could not give a definite answer. The authority still makes the final decision when the
read or write reaches it.

## Magic columns

Jazz exposes a small set of system-provided magic columns at query time. They do not exist in your
schema, and they are omitted from `select("*")`, so opt in explicitly when you want them.

### Edit metadata columns

Jazz also tracks row authorship and timestamps automatically:

- `$createdBy`&hairsp;—&hairsp;the Jazz principal that created the row
- `$createdAt`&hairsp;—&hairsp;when the row was first created
- `$updatedBy`&hairsp;—&hairsp;the Jazz principal that last updated the row
- `$updatedAt`&hairsp;—&hairsp;when the row was last updated

Jazz always tracks this metadata; select the columns explicitly to include them in query results. Backend writes that are not attributed to a user use the reserved system account and an internal system identity. See [System-authored rows](/docs/setup/auth/backend#system-authored-rows) for their account, issuer, and originating-node subject.

### Authorship-based policies

You can use these edit metadata magic columns directly in `permissions.ts`. This is useful for simple
"creator can read/edit/delete their own rows" policies without adding explicit `owner_id` columns.

Compare `$createdBy` with `session.user` to scope a rule to the row's creator. `session.user` is
the account, so the rule matches rows written through any identity linked to it, including
alpha.59 rows whose author was imported with an account. To match only the exact login that wrote the row, compare
`$createdBy.identity` with `session.identity` (its `{ issuer, subject }`). `session.claims`
holds the claims your `authenticate` returned, not a raw JWT payload; with
[`fromJWT()`](/docs/setup/auth/custom#tokens-from-your-identity-provider), `session.identity` is
`{ issuer: "jazz:backend", subject }`, not your provider's `iss`. Claims never replace the
canonical author identity.

## Changing permissions in production

Each deployment of your backend serves the permissions it was built with, and every client is checked by the permissions of the deployment it connected through. When a deployment with new permissions starts, every connected client reconnects, including clients of your other deployments (previews too), and each is checked again by the permissions of the deployment it now reaches. Deploying permissions that have been deployed before, such as a rollback, reconnects no one.

To retire permissions that grant too much, deploy fixed ones and delete every deployment that still serves the old ones, including older production and preview deployments that are still reachable. Until it is gone, any client that connects through such a deployment is checked by its permissions.

## Troubleshooting denied access

If a write appears locally but does not persist, wait for
[server durability](/docs/writing/writing-data#write-durability-tiers) and handle the rejection.
The local-first client rejects with `PersistedWriteRejectedError`, code `permission_denied`. The
thin client rejects with a `ThinRemoteError` whose `code` is `WriteRejected` and whose message
starts with the reason, such as `authorization_denied: …`. Use
`db.onMutationError(...)` as a fallback for rejections without an active wait;
see [Handling mutation errors](/docs/writing/writing-data#handling-mutation-errors).
A backend connected to Jazz Cloud doesn't refuse a session's write up front either: the cloud
decides it, and a denial arrives through `wait(...)` with the same `permission_denied` code. A store
with no authority above it, such as a client with `serverUrl: null` or a backend on its own
storage, refuses some denied writes at once (the write call throws), and accepts others, such as a
denied update of a row it holds, then rejects them through `wait(...)`. So in backend code, await every write
and handle both:

```ts
try {
  await db.update(app.deals, dealId, { stage: "won" }).wait({ tier: "global" });
} catch (error) {
  // permission_denied, thrown by update() or by wait()
}
```

In Node, a write's rejected `wait()` that nothing awaits or catches is an unhandled rejection, which
ends the process.

An empty query result can also mean that read permissions filtered out rows.

As the app developer, check your own configuration:

1. Run `npx jazz-tools validate` and check that every required table
   and operation has an explicit grant. For updates and upserts that update an
   existing row, also check the required read permission.
2. Check that the grants match the authenticated session and the relevant row
   values, including both old and new values for updates. Test these cases with
   [permission tests](/docs/tooling/testing#testing-permissions).
3. Deploy your main backend with the intended policies
   and verify the app ID and deployed configuration. Editing `permissions.ts`
   locally does not update the server's policies.

Treat `permission_denied` as a generic rejection: it does not tell the caller
whether a policy is missing, a predicate failed, or a protected row exists.
Keep these configuration checks in developer tooling and tests; do not expose
protected policies, row values, or row-existence details in client-facing errors.
