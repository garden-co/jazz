## Why Jazz migrations are different

Most migration systems are one-way: rewrite every row to the new shape, then cut over. That assumes you can stop the world long enough to upgrade&hairsp;—&hairsp;which doesn't hold when your clients are local-first, frequently offline, and updating their app on their own schedule.

Jazz keeps every schema version usable and translates rows between them on read and write. Clients on different versions stay interoperable, and nothing on disk is rewritten when you ship a new schema.

## Schemas and lenses

Every unique version of your `schema.ts` has a hash which can be used to refer to it. When creating migrations, you describe the changes required to move between two schema versions. This is known as a 'lens'. Fetching all intermediate lenses allows clients with any published schema version to read data created with any other published schema version.

<LensDiagram />

Rows retain the physical schema identity under which they were written. A read in another compatible
schema uses lenses to project those rows into the requested shape. Non-adjacent reads compose lenses in sequence to bridge multiple schema
versions.

In practice, this lets you:

- Ship a schema change without waiting for every user to update their app.
- Roll out platform-by-platform (mobile, desktop, web) on independent cadences.
- Accept writes from clients that have been offline since before the new schema landed.

## Workflow

1. If this is the first migration you are creating, run:

   ```bash
   pnpm dlx jazz-tools@alpha migrations create
   ```

   This creates an initial snapshot of your schema in `migrations/snapshots/`. No migration file is created yet because there is no previous schema to diff against.

2. **Edit `schema.ts`**&hairsp;—&hairsp;change the data shape as needed.
3. **Validate locally**&hairsp;—&hairsp;optionally run `pnpm dlx jazz-tools@alpha validate` to surface
   any policy diagnostics without publishing. Your main backend runs the same checks when it starts;
   `validate` is most useful as a fast check before you deploy, or in CI.
4. **Create a migration stub for the updated schema**&hairsp;—&hairsp;run:

   ```bash
   pnpm dlx jazz-tools@alpha migrations create --name <your-migration-name>
   ```

   By default, Jazz diffs the latest committed snapshot in `migrations/snapshots/` against the
   current schema and writes a stub migration file into `migrations/`. It also saves a snapshot of the generated schema.

5. **Review and customise**&hairsp;—&hairsp;the migration, if needed (see below).
6. **Deploy your main backend**&hairsp;—&hairsp;restart it locally, or deploy it as usual. When it
   starts, `createJazz` sends the schema, permissions and migrations your code imports to its store
   as one bundle. There is no separate deploy or push command. If the bundle has no migration path
   from the schema already in the store, the backend refuses to start with an error naming the
   missing migration. First deployments and permission-only changes need no migration.

   Each deployment's sessions run under that deployment's own bundle, so two deployments can run
   side by side, and rolling back your backend rolls back its permissions too.

The `jazz-tools` CLI only scaffolds and checks migrations (`migrations create`, `validate`,
`migrations graph`). It never publishes anything: only your main backend does.

### Shipping migrations with your app

`validate` and `migrations create` also regenerate `migrations/index.ts`. It bundles every schema version and
every lens, and your app passes it to `defineApp`:

```ts title="schema.ts"
import { migrations } from "./migrations";

export const app = s.defineApp(schema, { migrations });
```

Commit it with your schema. Clients use it to read and write data from any version, including
before they first sync, so a client never has to rename or reshape stored data later. A client
whose schema version is missing from the bundle refuses to open with an error telling you to
regenerate it.

Permission-only changes in `permissions.ts` don't need a migration; they go live when your main
backend restarts with them. See [Permissions](/docs/schemas/policies) for details.

## The migration file

The generated stub describes the diff as declarative operations which carry enough information to run in either direction. That
is how older clients can still read data written under a newer schema: the same operations replay
in reverse.

<Callout type="warn">
  If the diff contains ambiguities (e.g. a column was removed and a same-typed column was added,
  which could be a rename), the generated lens is marked as a **draft**. Draft lenses will fail at
  startup if they are in the path to a live schema. You need to review the draft lens and resolve
  the ambiguity before publishing.
</Callout>

## Adding relations to existing UUID columns

To add a relationship using an existing `ownerId` UUID column, declare `owner: s.rel("users", "ownerId")` in the table's relationships and follow the migration workflow above. Existing UUID values stay unchanged; Jazz emits an explicit identity table lens, which preserves row values while making the relation available under the new schema.

## Handling concurrent migrations

When working on real apps, it's normal for multiple devs (or agents) to create migrations starting from the same schema but branching off in different directions.

For example, suppose your task app has a `tasks` table with a `title` column. Alice adds a `dueDate` column while Bob independently adds `priority`, both starting from the original schema:

```text
Original tasks
├──add dueDate───→ Tasks with due dates (Alice's backend)
└──add priority──→ Tasks with priorities (Bob's backend)
```

Each deployment publishes its own bundle and its sessions run under it, so Alice's and Bob's
backends (two preview deployments, say) can both serve the same data side by side. Nothing on the
server becomes "current", and neither deployment blocks the other. A bundle's migration history
must have a single root, which both branches share here.

Reading across the branches has a cost, though. Jazz reads a row written under another schema by
applying lenses backwards to the common ancestor and forwards again, and that route can discard
values. A task written with a due date loses that field when read from the priorities schema, and
adding `dueDate` again later along that route supplies a default instead of the task's original due
date.

So while both branches run, each side sees the other's rows without the other's new column. When
you're ready to ship, pick one branch or converge both into a merged schema.

### Picking one branch

To leave Alice's due-date change behind, deploy Bob's backend and stop deploying Alice's. Rolling
back works the same way: redeploy older code, and its sessions run under its own bundle again. No
reverse migration is needed, and you shouldn't write one: it would create a cycle, which your main
backend rejects on start.

<Callout type="warn" title="Leaving a branch behind doesn't delete its data">
  Rows keep their stored values and column identities. Reads using the original or priorities schema
  don't expose due dates, but a backend that still runs the due-dates schema can keep writing them,
  and returning to that schema exposes the retained values again.
</Callout>

### Converging into a merged schema

To preserve both changes, edit `schema.ts` so `tasks` contains both `dueDate` and `priority`. Create a migration into this merged schema from each branch:

```text
               ┌──→ Due dates ──add priority──┐
Original tasks ┤                             ├──→ Due dates + priorities
               └──→ Priorities ──add dueDate──┘
```

Use the hashes shown by `migrations graph`:

```bash
pnpm dlx jazz-tools@alpha migrations create <appId> --fromHash <due-dates-hash> --name add-priority-to-due-dates
pnpm dlx jazz-tools@alpha migrations create <appId> --fromHash <priorities-hash> --name add-due-date-to-priorities
```

Both commands use the current `schema.ts` as their destination. Review the generated migrations:

- The migration from Alice's schema should preserve `dueDate` and introduce `priority`.
- The migration from Bob's schema should preserve `priority` and introduce `dueDate`.

And then deploy your main backend.

Rows written under either branch now read with both columns intact. Jazz validates that alternative forward paths agree on the values and column identities they
preserve or introduce.

## Visualizing the migration graph

Run `jazz-tools migrations graph` to see the schemas and migrations:

```sh
pnpm dlx jazz-tools@alpha migrations graph <appId> --server-url <url> --admin-secret <secret>
```

The graph includes all schemas and migrations present in the server and locally. Schemas and migrations that exist only on the server or locally are labelled accordingly.
The graph also marks the local `schema.ts` and, with "(latest bundle)", the schema of the bundle your
backends published most recently.

## Choosing migration endpoints

By default, `migrations create` compares the latest local snapshot with the current `schema.ts`. With
no local snapshot, it starts from the latest bundle's schema.
Use explicit schema hashes to choose different endpoints, for example when connecting schemas developed on separate branches:

```bash
pnpm dlx jazz-tools@alpha migrations create <appId> --fromHash <fromHash>
pnpm dlx jazz-tools@alpha migrations create <appId> --fromHash <fromHash> --toHash <toHash>
```

`--toHash` defaults to the current local schema. When a requested hash is not already saved locally, Jazz resolves it from the
server and saves a snapshot in `migrations/snapshots/`. Remote lookup requires the app ID, server URL, and admin secret;
provide the server URL and secret through `--server-url` and `--admin-secret` or their environment variables.

## Compiling the schema

Use `schema compile` when working on a non-TypeScript Jazz application that needs to consume the schema written in TypeScript.

You don't need to run it as part of the normal migration workflow: `migrations create` saves
the required snapshots, and your main backend compiles the schema when it starts.

`pnpm dlx jazz-tools@alpha schema compile` prints the compiled schema as JSON to stdout. It
also saves a snapshot of the schema in the local snapshot directory.

```bash
pnpm dlx jazz-tools@alpha schema compile
pnpm dlx jazz-tools@alpha schema compile --schema-dir ./packages/app
```

The command compiles the current local `schema.ts`. To create migrations against a historical
schema, use `migrations create --fromHash <hash>`; it fetches and saves missing snapshots as needed.

| Flag                   | Default           | Description                                      |
| ---------------------- | ----------------- | ------------------------------------------------ |
| `--schema-dir <path>`  | current directory | Path to app root containing `schema.ts`          |
| `--migrations-dir <p>` | `./migrations`    | Path to migrations directory and snapshot folder |

## Migration flags

`migrations create` uses flags rather than positional hashes. When it needs to resolve missing
schema hashes from a server, pass `<appId>` as the leading positional argument.

| Flag                   | Default                                                | Description                                      |
| ---------------------- | ------------------------------------------------------ | ------------------------------------------------ |
| `--schema-dir <path>`  | current directory                                      | Path to app root containing `schema.ts`          |
| `--migrations-dir <p>` | `./migrations`                                         | Path to migrations directory and snapshot folder |
| `--server-url <url>`   | `JAZZ_SERVER_URL`                                      | Server URL used when resolving missing schema    |
| `--admin-secret <sec>` | `JAZZ_ADMIN_SECRET`                                    | Admin secret used when resolving missing schema  |
| `--fromHash <hash>`    | latest local snapshot, else the latest bundle's schema | Optional source schema hash                      |
| `--toHash <hash>`      | current schema                                         | Optional target schema hash                      |
| `--name <name>`        | `unnamed`                                              | Optional migration filename label                |
