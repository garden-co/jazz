---
title: Upgrading from alpha.55
description: Rewrite an alpha.55 schema for explicit relations, and what happens to alpha.55 clients once the server is upgraded.
---

Apps on `jazz-tools@2.0.0-alpha.55` need two things when they move to alpha.57 or later: a schema
file rewritten for explicit relations, and a plan for end users who still run an alpha.55 build of
the app for a while. Stored data needs nothing: server data directories and browser storage from
alpha.55 open in place, with no reset or conversion step.

Apps on alpha.56 or later can skip this page.

## Rewrite the schema

Newer versions don't load an alpha.55 `schema.ts`. Running the CLI on an unchanged alpha.55 schema
fails with:

```
s.table(columns, relations) requires a relationship map; use {} for no relationships.
```

alpha.55 declared a reference as a column, `projectId: s.ref("projects")`, and derived relation
names from it: the forward relation `project` and the reverse relation `tasksViaProject`. Now
references are plain UUID columns and every relation is named in a second argument to `s.table`
(see [Explicit relations](/docs/schemas/defining-tables#explicit-relations)):

1. Change each `s.ref("table")` column to `s.uuid()` (`s.uuid().optional()` if it was optional).
2. Declare the forward relation with `s.rel("table", "column")`.
3. Declare each reverse relation you use with `s.reverse("table", "forwardRelation")`, under
   whatever name you like.
4. Pass `{}` for tables without relations.

Before (alpha.55):

```ts title="schema.ts"
const schema = {
  projects: s.table({
    name: s.string(),
  }),
  tasks: s.table({
    title: s.string(),
    done: s.boolean(),
    projectId: s.ref("projects"),
  }),
  notes: s.table({ text: s.string() }),
};
```

After:

```ts title="schema.ts"
const schema = {
  projects: s.table(
    {
      name: s.string(),
    },
    { tasks: s.reverse("tasks", "project") },
  ),
  tasks: s.table(
    {
      title: s.string(),
      done: s.boolean(),
      projectId: s.uuid(),
    },
    { project: s.rel("projects", "projectId") },
  ),
  notes: s.table({ text: s.string() }, {}),
};
```

Then update the relation names your queries and permissions use. Forward names can stay the same
(`project` above), but the generated reverse names are gone, so an include such as
`app.projects.include({ tasksViaProject: true })` becomes `app.projects.include({ tasks: true })`,
or whatever name you gave the `s.reverse`.

### No migration needed

The rewritten schema has the same structural hash as the alpha.55 one, so
`deploy` reports that the schema is already stored and skips publishing it. There's no migration to
write, and stored rows are untouched. Schema changes you make after the rewrite go through the
normal [migrations](/docs/schemas/migrations) flow.

## alpha.55 clients against an upgraded server

alpha.55 clients speak an older sync protocol than alpha.57 and later servers, so once your server
(or Jazz Cloud app) is upgraded, end users still running an alpha.55 build of your app work
local-only until they load a newer build:

- Local reads and writes keep working.
- Reads and waits that need the server fail straight away rather than hanging: `global` waits
  reject and `remote` reads error with
  `unsupported wire protocol advertisement: remote 2..=2, expected 3..=3`.
- Local writes are kept. When the page loads a newer build of your app, the same account comes
  back and every write made in the meantime syncs.

alpha.56 clients use the current protocol and keep syncing with upgraded servers.

To keep the local-only window short, ship the upgraded app build at the same time as the server
upgrade, and make sure your HTML isn't cached: a cached `index.html` keeps loading the old client.
