## Write tiers

Mutations such as `insert`, `upsert`, `update`, `delete`, and `restore` apply locally with no
durability guarantee and return a `MutationResult`. Transaction helpers resolve to the same kind of
result. Call `.wait({ tier: ... })` when you need confirmation that the mutation reached a specific
durability tier.

See [Writing Data](/docs/writing/writing-data#write-durability-tiers) for detailed guidance on which tier to use and code examples.

### Mutation errors

Jazz throws errors it can detect locally as soon as you call the mutation. The server may reject the
change later, e.g. if the user does not have permissions. The change can appear locally before that
rejection arrives. If this happens, `.wait(...)` rejects and Jazz removes the local change.

If you are not waiting with `.wait(...)`, use `db.onMutationError(listener)` to handle a rejection.
Transactions use `.wait(...)` and report errors in the same way as individual mutations.

## Read tiers

Read choices control which data a query uses and when its **first result** is delivered.
They are intentionally separate from write durability.

New applications should use the two product read choices `"local-first"` and `"remote"`:

- `"local-first"` uses cached local knowledge and shows pending local writes immediately, while still syncing.
- `"remote"` uses the server's current query scope, without pending local writes. It waits while offline.

Without a `tier`, browser clients read `"local-first"`. Other clients read `"remote"` when they have a
server, and `"local-first"` when they don't. A remote read shows your own writes once the server has
confirmed them, so wait for a write (`.wait({ tier: "global" })`) before reading it back.

### Waiting for the server (`firstLoadRemoteWaitMs`)

A local-first read accepts an optional `firstLoadRemoteWaitMs` that bounds how long
its first result may wait for the server. The default, `0`, is plain `"local-first"`. It applies to
`"local-first"` and the browser default; TypeScript rejects it with `"remote"` (JavaScript callers have it ignored). In Rust, use
`client.query_local_first(query, timeout)` and `client.subscribe_local_first(query, timeout)`.

Only the initial load waits: a one-shot read, or a subscription's first callback. While the client
looks online (its connection is live, or its connection attempt started less than five seconds
ago), the first result waits up to `firstLoadRemoteWaitMs` for the server's answer and then shows that
server-confirmed result, together with the client's own pending writes. If the server has not
answered by then, the local result is shown. The read waits even when local data exists, but never
longer than the timeout.

It never waits on a server it cannot reach. The first result is local, and immediate, when no
server is configured, after `db.disconnect()`, while the connection is down or retrying, or when the
connection attempt fails. If the connection drops during the wait, the local result is delivered at
that moment. After the first result, a subscription behaves exactly like `"local-first"`: local
writes show immediately and remote rows appear as they sync.

Queries with an `offset` are the exception. A partly synced local cache would apply the offset to
the wrong rows, so while waiting an offset window reads the server's page. If the timeout passes
first, it shows the cached page; a subscription then switches to the server's page when it
arrives, so rows can shift at that moment.

### Removed read tiers

Reads accept only `"local-first"` and `"remote"`; any other name throws.

- `"local-first-unless-empty"` (`ReadTier.LocalFirstUnlessEmpty`) was removed. It showed a
  non-empty cache at once and made only an **empty** local result wait for the server, without a
  time limit once connected. Use `"local-first"` plus a `firstLoadRemoteWaitMs` of, for example, a
  few seconds. The new option also waits when the cache has data, but is always bounded by the
  timeout.
- The read names `"local"` and `"global"` (and the `"core"` alias) were removed. Use
  `"local-first"` for `"local"` and `"remote"` for `"global"`. A `"remote"` read shows your own
  pending writes once the server confirms them, where the old `"global"` read showed them at once.
- `"remote-if-possible"` and `"edge"` were removed in alpha.57.

Losing remote access does not erase cached data: local-first reads may still show it. An actual
synced deletion, however, hides the row from local reads too.

Write durability is separate and unchanged: it uses `wait({ tier: "local" | "global" })`.

These options apply to:

- `db.all(query, options?)`
- `db.one(query, options?)`
- `db.subscribe(query, callback, options?)`
- `useAll(query, options?)` / `useAllSuspense(query, options?)` (React/Expo)
- `new QuerySubscription(query, options?)` (Svelte)
- `useAll(query, options?)` (Vue)
- `useAll(() => ({ query, options }))` (Solid)

The React Native/Expo alpha uses these same read and write durability tiers
after opening its account-handle client with `createJazzClient`. Its native
relay owns persistence and upstream connectivity; do not substitute a browser
storage driver or a JavaScript-side SQLite path.

For most queries and subscriptions, omitting a tier is the right choice: Jazz delivers results from local storage immediately and streams in remote updates as they arrive. Reserve explicit tiers for cases where eventual consistency is not acceptable.

<Callout type="info" title="Reads and write confirmation are different">
  Strict remote subscriptions use Core-authorized state for later updates as well as their initial
  result. Local-first subscriptions may display pending changes before Core accepts them. Waiting
  for a write does not change the read choice of a separate subscription.
</Callout>
