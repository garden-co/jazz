title: App files
description: jazz.app.json and jazz.permissions.json, the readable description of an app's schema, history and permissions.
---

`jazz-tools validate` writes two readable JSON files beside your `schema.ts`:

- **`jazz.app.json`**: your tables, the relations between them, and the schema history your app
  ships. Clients, and apps in every language, read it.
- **`jazz.permissions.json`**: your current permissions. Only backends read it, so no client
  bundle carries your policies.

Commit both. `jazz-tools validate --check` fails in CI when either one is missing or no longer
matches `schema.ts`, `permissions.ts` and your migrations. `createJazz` refuses to start when the
committed files are out of date, and says which one to regenerate. A project that has never run
`validate` has no files and starts as before.

Today the files are generated from your TypeScript: keep writing `schema.ts`, `permissions.ts`
and migrations as you do now, and run `npx jazz-tools validate` after changing them. Other
languages, such as Rust (`jazz::tools::deployment::artifact::load`), read the files. Keep
formatters off them: they are written byte for byte (add both names to `.prettierignore` or your
formatter's ignore file).

## `jazz.app.json`

```json
{
  "format": 1,
  "tables": {
    "chats": {
      "columns": { "name": "string?", "isPublic": "boolean", "joinCode": "string?" },
      "relations": { "chatMembersViaChat": { "reverse": "chatMembers", "relation": "chat" } }
    },
    "chatMembers": {
      "columns": { "chatId": "uuid", "userId": "uuid" },
      "relations": { "chat": { "rel": "chats", "column": "chatId" } },
      "indexes": [["chatId", "$createdAt"]]
    }
  }
}
```

- **Columns** are written as in the DSL: `string`, `int`, `bigint`, `float`, `boolean`,
  `timestamp`, `uuid`, `bytes`, with `?` for optional. Columns with options are objects:
  `{ "enum": ["todo", "done"] }`, `{ "json": { …JSON Schema… } }`, `{ "array": "string" }`,
  `{ "type": "int", "default": 0, "merge": "counter" }`.
- **Relations** are separate from columns: `{ "rel": "chats", "column": "chatId" }` is
  `s.rel("chats", "chatId")`; `{ "reverse": "chatMembers", "relation": "chat" }` is
  `s.reverse("chatMembers", "chat")`.
- **Table options**: `indexes` (a name is `indexOnly`, an array a `compositeIndex`),
  `branchBy`, and `"history": "latest"`.
- **History**: earlier versions your app ships, and the migrations between them, under
  `history` and `migrations`. `jazz-tools migrations create` adds them.

## `jazz.permissions.json`

```json
{
  "format": 1,
  "tables": {
    "chats": {
      "read": {
        "anyOf": ["isPublic = true", "exists chatMembers(chatId = this.id, userId = session.user)"]
      },
      "insert": "$createdBy.account = session.user",
      "update": {
        "old": "exists chatMembers(chatId = this.id, userId = session.user)",
        "new": "exists chats(id = this.id, isPublic = this.isPublic)"
      }
    },
    "reactions": { "read": "allowedTo.read(message)" }
  }
}
```

Each table has `read`, `insert`, `update` and `delete`; a missing one is denied. `update` is one
policy, or `{ "old": …, "new": … }` for `whereOld` / `whereNew`. A policy is an expression
string, `{ "anyOf": [...] }`, `{ "allOf": [...] }`, or `{ "$comment": "…", "where": … }`.
`defs` holds named expressions, `"isChatMember($chat)": "exists chatMembers(chatId = $chat, userId = session.user)"`,
which policies call as `isChatMember(this.id)`. Files generated from TypeScript inline your
helpers, so they have no `defs`.

## Expressions

Expressions read like SQL. String literals use single quotes.

| You want                   | Write                                                                                    |
| -------------------------- | ---------------------------------------------------------------------------------------- |
| Compare a column           | `userId = session.user`, `status != 'archived'`, `count >= 3`                            |
| Null checks                | `joinCode = null`, `joinCode != null`                                                    |
| Membership                 | `role in ['admin', 'owner']`, `teamId in session.claims.teams`, `tags contains 'urgent'` |
| A claim                    | `session.claims.role = 'admin'`                                                          |
| Who wrote the row          | `$createdBy.account = session.user`                                                      |
| Combine                    | `a and b`, `a or b`, `not a`, parentheses                                                |
| Another row exists         | `exists chatMembers(chatId = this.id, userId = session.user)`                            |
| Follow a relation          | `exists files(id = this.id).folder(ownerId = session.user)`                              |
| Inherit from a related row | `allowedTo.read(chat)`, `allowedTo.update(folder, maxDepth: 8)`                          |
| Always / never             | `true` / `false`                                                                         |

- A bare name is a column of the table the policy is about; inside `exists t(…)` it is a column
  of `t`. `this.col` always means the row being checked.
- Conditions inside `exists t(…)` are separated by commas and all must hold.
- A literal takes its column's type: `'2026-01-01T00:00:00Z'` for a timestamp, a UUID string for
  a `uuid`.

When an expression is wrong, `validate` and `createJazz` point at the exact spot, suggest the
name you probably meant, and show a correct example.
