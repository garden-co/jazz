# Current SQLite frozen replica publications

A physical authenticated durable replica can enable its initialization journal before exposing writes, open an ordinary serializable batch, prepare its insert coordinates, and seal the complete batch. Sealing spends a durable original `(node, tx)` identity and retires the mutable open handle. It publishes no rows. Publication consumes the owner-local capability and runs the existing serializable, governance, actor, read-set and candidate checks under the captured view. The actual publication position can differ from the reserved transaction number. Cancellation or dropping a seal does not recycle its identity.

An actual authenticated physical authority can use the same seal/publication checks without becoming a replica. It must already be the real authority, have no client/hybrid role, use its physical owner and preserve that actual owner in every selected session. SYSTEM owners refuse. A successful authority publication records its real validated Global fate and original history identity atomically; reserving alone does not. There is no new JS constructor that turns a replica into such an authority, no role swap and no assumption that an authority possesses E2EE keys.

The shared host wrappers expose `enableInitializationJournal`, `prepareInitializationInsert`, `sealInitializationTransaction`, `publishInitializationTransaction`, `cancelInitializationTransaction` and `initializationTransactionStatus`. A seal returns named JSON containing `token` and `reservedTxId`. The random token is usable only once in the same physical owner; reservation bytes alone grant nothing. The registry shares tokens across schema views. Closing a view preserves its root's tokens; closing the root retires them. Staged host refusal poisons the whole transaction, so sealing cannot publish only its successful prefix. At most 64 outstanding host seals are retained per physical owner; each status call admits at most 64 identities.

## Identity, pending proof and fate

`jazz-sqlite-init-v1:<canonical UUID>:<canonical positive decimal>` names a reserved identity, not accepted evidence. Optional `jazz.sqlite.initialization-allocation.v1` metadata uses raw 16-byte nodes, integer IDs and separate publication positions. It never writes a fake reservation into `_jazz_transactions`, where a null landing means refusal. Activation refuses an unqualified legacy pending prefix rather than inventing its original proof.

A pending publication stores the original current `Commit` header, ordered operations, read predicates and row manifest through the ordinary pending tables. Its new journal checksum is captured from the intended original parts and checked against the persisted parts in the same savepoint. Reopen and resend verify the whole outstanding prefix, including original IDs and the exact persisted packet. An optimistic row version is required until genuine accepted Rows record its original landing; normal reconciliation may then remove that optimistic rank without settling its still-pending Fate. A missing or incomplete unit blocks every upload in that prefix; it is not an empty proof and is not filled from a later resend. These checks detect missing or changed retained parts; they are not a signature against a hostile writer that can replace the entire SQLite file and checksum.

A journal-known incomplete publication remains outstanding for individual and whole-queue waits: neither may infer Global success from its absence in the recovered in-memory queue. Snapshot dots resolve retained pending originals to their actual publication ranks, including after a same-store node change.

Local publication and genuine Global acceptance remain distinct. A provisional relay acceptance cannot discard this role's original pending proof or become Global. The authority still validates actual policies, claims, read sets, dependency ownership and writes. Original pending proof can be retired after a real terminal decision; this adds no permanent post-settlement read-proof retention. Refusal retains the existing rejected-operation behaviour and exact current error code, reason and message. Status uses the named `jazz.sqlite.initialization-status.v1` envelope with `not-observed`, `incomplete` or `complete`; a complete result explicitly states pending/accepted/refused fate and observed Local/Global durability.

Publication and pending recording are atomic. Confirmed rollback restores the upload suffix without exposing rows or notifications. An unconfirmed release or rollback fences the owner and requires reopening; it does not advertise a guessed unseen outcome.

## Current wire and compatibility limit

Legacy `WireKind` tags 0 (Mergeable) and 1 (Serializable) keep their encodings. Current `SerializableOriginsV2` appends tag 2, named `jazz.sqlite.serializable-origins.v2`. It retains current read schema versions, queries, bindings, include-deleted flags and explicit row-writer versions. Its own prefix is a frozen list of `(local publication position, original node, original tx)`. It is emitted when legacy sender-node/local-number interpretation cannot represent the mapping. Publication never recomputes the captured prefix from a newer pending set.

Cross-node own-prefix admission uses the existing full-principal `writes_as` rule under the actual effective session. It does not claim or take over a referenced node, grant by account alone, or turn an ordinary observed foreign row into an own-prefix grant. Same-node reserved numbers are also resolved by original identity rather than publication position. Local publication order, read cuts, pending reopen, relay forwarding and terminal receipts keep these coordinates separate. The current prefix limit is 4096 distinct, valid positions and origins; invalid, duplicate, self or unauthorised dependencies refuse. An enabled replica also admits at most 4096 outstanding publications, including ordinary writes. An excess append refuses atomically before a visible local commit; genuinely settling the existing prefix releases capacity.

The current wire envelope is also the stored pending-header envelope. Older decoders reject the appended case. **Opting into this journal is not downgrade-safe, even during reservation-only state:** older writers do not understand its allocation metadata. All writers of this physical root must support the journal. There is no old-writer exclusion protocol, legacy fallback, storage-format-2 migration or guarantee that an arbitrary older binary can reopen/write it safely. The existing physical-owner/writer coordination requirement remains.

The independent current fixture pins the legacy cases and an empty-read origin case using the actual current declaration order, not the retired Groove-era or OriginsV1 layout. Populated read proofs are exercised by native dependency/reopen controls; that fixture does not independently encode every query/read-field shape. A small pre-extension enum subset checks byte-level unknown-variant refusal, not execution or qualification of an older runtime.

This capability supplies no complete offline history, membership, absence of revocation, schema authority, privileged session or automatic Global receipt. Cached app catalogue metadata and private retained keys retain their separate validation and lifetime boundaries.
